# Control protocol and MCP

> **Last updated:** 2026-10-13 · **Status:** the headless JSON-lines server (`craft3d-cli serve`), the MCP server (`craft3d-cli mcp`), the desktop control server (`craft3d --control`) and the MCP bridge to a running window (`craft3d-cli mcp --bridge`) exist. The sections below describe the target; **what is implemented today is listed first and wins where they differ.**

## Implemented today (2026-10-12)

**JSON lines** (`craft3d-cli serve`): the envelope below, on stdin/stdout only (no TCP, so no auth). Methods: `engine.execute {command, params?}`, `engine.commands {filter?}` → `{"commands": [...]}`, `batch {steps: [{command, params?}], stopOnError?}` → `{completed, failed, results}`, `methods`. Everything else goes through `engine.execute` with a command id: there are no `doc.*`, `session.*` or `jobs.*` methods, no `wait`, and batch steps are commands only. Unknown keys are refused, also at the top level of a request. A batch is checked as a whole before its first step runs.

**MCP** (`craft3d-cli mcp`): `initialize`, `ping`, `tools/list`, `tools/call`; protocol versions 2025-11-25, 2025-06-18, 2025-03-26 and 2024-11-05. Tools: `command_list`, `command_run`, `command_batch`, `doc_inspect` (returns `{"document": null}` when nothing is open), `doc_render_preview` (an image block plus a text block). No resources, no `doc_new`/`doc_open`/`doc_save`/`doc_export` tools (use `command_run` with `file.new`, `file.open`, `file.save`, `file.export`). The bridge to a running window is its own paragraph below (*MCP bridge*). Tested against the specification, not yet against a real MCP client.

**Desktop control** (`craft3d --control PORT --control-token-file FILE [--automation-read-root DIR] [--automation-write-root DIR]`): the same envelope and methods as `craft3d-cli serve`, on a TCP listener bound to 127.0.0.1, executed on the document the window shows. The first request of every connection must be `auth {token}`; a failed attempt closes the connection, a connection silent for 30 seconds is closed, 16 connections at most. The token file is created (mode 0600 on Unix) when it does not exist. Added methods: `ui.get`, `ui.set {view?, camera?, panels?, selectedFeature?, notice?, quality?, highlight?, highlightEdge?, highlightVertex?, transparency?, section?, show?}`, `ui.pick {x, y, width?, height?, radius?, select?}` and `ui.highlight {face | edge | between | vertex | corner, feature?}` (see *Pointing* below), `ui.fit {view?}`, `ui.screenshot {path?, width?, height?, scale?}` (a PNG of the viewport as framed: the CPU reference render plus the overlay of body edges, sketches and axes, without the panels), `ui.notice {text}`, `ui.quit`, and `mcp.message {line}` (below). Not there: `ui.inspect` (it is `ui.get`), `ui.focus`, display modes, themes. Requests are answered on the thread that owns the document whenever the window's event loop is woken for them, which does not take a frame (since 2026-10-13; `apps/craft3d/src/app.rs`, `Desk::turn` and `Driver`): a window the compositor does not show (another workspace, minimised, fully covered, a locked screen: a Wayland compositor then sends no frame callbacks and winit delivers no redraw) answers like any other, and `ui.quit` ends the process without the window having to be drawn once more. Before, such a window answered nothing until the request timed out after 120 s, and a `ui.quit` it had answered was not acted on until the window was looked at (`apps/craft3d/tests/hidden_window.rs` runs the application under a headless `mutter` to pin this; it skips where there is none).

**The window keeps answering while a command runs** (2026-10-14; `apps/craft3d/src/worker.rs`, `Desk` in `app.rs`). Commands run on the window's engine thread, which has the session while they run: `engine.execute`, `batch` and every MCP tool call but `control_call` (`host::route`). Meanwhile the window draws what it showed before (camera, tree and picking all work on it) with the work in progress over the viewport, and nothing on the drawing thread waits for regeneration or meshing: the scene the window shows is built on the engine thread too, after the command and whenever the window asks for one it does not have. Requests are still answered one at a time, in the order they arrived, whichever connection sent them; a reply comes when its command is done, as before. Two methods are answered at once even while work runs, from what the window shows: `ui.get`, whose `work` is then `{label, phase, feature, name, step, steps, seconds}` (`label` the command or `batch of N` or `meshing`; `phase` `running`, `regenerating`, `measuring` or `meshing`; `feature`/`name` the feature being rebuilt and `step` of `steps` its place in the history, `0 of 0` for a phase without steps; `seconds` how long the work has run) and `null` when the window is idle, and `ui.quit`, which closes the window at once (work still running gets three seconds to finish, so the documents are put away cleanly; after that the application ends and its recovery files stay, as after a crash). The other `ui.*` methods wait their turn, because they read the session. A panic on the engine thread is caught there: the request gets an error, the documents with unsaved changes are autosaved, and the session comes back as it was before the command. A quick command is answered within the same turn of the event loop as before (the drawing thread waits up to 12 ms for it). Not cancellable yet. *Coarse first, then sharp:* after a change the window shows a quick first picture and builds the display-quality mesh beside the engine thread, which a command does not wait for; `ui.get` › `scene.refining` is `true` meanwhile, and `ui.screenshot` waits for the display mesh (the requests after it wait with it, in order).

The window makes its sharp image on a thread of its own and shows a quick preview until it is ready; `ui.get` says which is on screen (`render.sharp`). The viewport is drawn by the wgpu renderer on the window's own device when the machine has a graphics adapter (directly into the texture that is shown, multisampled, every frame sharp: then `render.sharp` is always true), by the wgpu renderer on a device of its own, read back, when that direct path cannot be set up, and by the CPU reference renderer otherwise, or when the window was started with `--renderer cpu` (`CRAFT3D_RENDERER=cpu`), or after the GPU failed: `ui.get` reports the renderer of the image on screen (`render.renderer`, `gpu` or `cpu`, with `render.ssaa` and `render.msaa`, the samples per pixel) and, as `renderer {backend, adapter, fallback, direct, msaa}`, which one the viewport uses, the adapter's name, why it is not the direct GPU path although that was wanted (`null` otherwise), whether it draws directly on the window's device, and with how many samples per pixel. `ui.screenshot` does not depend on any of that: it renders its own picture of the state as it is when the request is answered (camera, document, selection), at full quality and always with the CPU reference renderer (the oracle the GPU viewport is checked against, docs/architecture.md §7), so it never returns a preview or the image of an earlier state. The mesh the viewport shows is the scene at the *display quality* (`state.quality`, settable with `ui.set {"quality": {"chordal": fraction of the model's size = 2e-4, "maxTriangles": integer = 1000000, "angle": degrees = 12}}`, numbers out of range clamped): a chordal tolerance of `chordal` times the model's size, coarsened until the scene has at most `maxTriangles` triangles but never beyond the quick first picture's tolerance (1e-3 of the diagonal of the model's box), which the window shows while the display mesh is built; `ui.get` › `scene.tolerance` is the tolerance it got and `scene.coarsened` whether the budget or the tessellator's limits made it coarser than asked. `ui.screenshot` renders that same scene, so what it shows is what the window shows; `view.render`, previews and `file.export` keep the automatic tolerance (or the one given). In the overlay, the part of a body's edge behind a body is left out, and the part of a sketch behind a body is drawn dimmed.

**MCP bridge** (`craft3d-cli mcp --bridge PORT --control-token-file FILE`): an MCP server on stdin/stdout without a session of its own. Each message is passed unchanged to the window's `mcp.message`, answered there by the same MCP code as `craft3d-cli mcp` on the window's document, and the reply is passed back: same tools, same limits, and the viewport shows every change. One short connection per message. `PORT` may be `127.0.0.1:PORT`; an address that is not this machine is refused, because the token is sent as it is. The file roots are the window's. When the window is not running, every request gets a JSON-RPC error (code -32000) that says how to start it, and the bridge keeps serving. Of the bridge-only tools of the table further down, `control_call` exists (2026-10-13: it runs a `ui.*` method of the window, see *Pointing* below); `ui_inspect`, `ui_screenshot` and `ui_set` do not: use `control_call` with `ui.get`, `ui.screenshot` and `ui.set`, or `doc_render_preview`.

**Commands** (50): `craft3d-cli commands` prints the registry with parameters and summaries; it is the source of truth.

**Pointing** (2026-10-13, faces, edges and vertices): the developer and an agent say "this face", "this edge" and "this corner" to each other in the words of the document: a face by its persistent name, the one `document.inspect` lists under `faceNames`; an edge the way `document.edges` lists it, by its own persistent name (`name`) where it has one and by the names of the faces it lies between (`faces`) always. A vertex likewise: `document.edges` lists, under `vertices`, the vertices its edges end in, each with `index`, `name` (its own persistent name, where it has one), `point` and `faces` (the names of the faces that meet in it). After a boolean the edges and the vertices have no names of their own, and the faces are how they are referred to. Since 2026-10-14 every edge of `document.edges` also has `short`: the names of `faces`, in the same order, each shortened to the shortest name a blend or a face operation follows back to that face (`F1:face(0)` for `F13:copy(0)/…/F3:copy(0)/F1:face(0)`; a copy of a pattern or a shell stays in front, since without it the name means several faces). A chamfer, a fillet, an offset face, a delete face and a shell take either; a sketch, a datum and an extrusion up to a face take the full name to mean the newest form (architecture §4.1 › *References that follow a body*). `document.inspect` shows, per feature whose names were followed, `followed`: its parameters as it was built, with the full names. `view.pick` gives the full names, as before.

- *The rule for what a position points at*, the same for `view.pick`, `ui.pick` and a click (`engine/src/pick_cmds.rs`, `Scene::point_at`): (1) the face is the one the picture has under the position, whatever else is near; (2) an edge is *near* when a point of it is within the pick radius of the position in the picture and in sight, that is, no face is in front of that point (an edge is looked at every half pixel along the part of it within the radius, starting from its nearest point); the nearest such point of all edges wins, at the same distance the one nearer to the eye, then the earlier body, then the earlier edge; (3) a vertex is near when it is within the radius and in sight, the nearest wins with the same tie-breaks; (4) a vertex that is near is what the position points at, however near an edge is (an edge ends in its vertices, so beside a vertex an edge is always at least as near: without this rule a corner could not be clicked); otherwise an edge that is near, otherwise the face under it, otherwise nothing. The radius is in pixels of the picture, 4 by default (`radius`, 0 to 64; 0 looks at faces only); a click uses `theme::Tokens::pick_radius` points (4), times the window's pixels per point. So an edge is picked from 4 pixels either side, also from just outside the silhouette where no face is under the pointer, and a hidden edge is never picked through the face in front of it. The edges are the ones the viewport draws (one polyline per edge of the B-rep, the points the mesh has along it); the silhouette of a curved face is not an edge.
- *What is at a position of a picture* is the command `view.pick {x, y, width?, height?, radius?, view?, projection?, zoom?, box?, camera?, tolerance?}`, on every transport: the picture is the one `view.render` makes with the same `view`, `projection`, `zoom`, `box` and `tolerance`, or the one seen by `camera` (`{eye, target, up?, projection?, fovY? | height?}`: perspective with `fovY`, the vertical field of view in degrees, default 30; orthographic with `height`, the model units from the top of the picture to its bottom). `x` and `y` are pixels from the top-left corner, x to the right and y down, and the centre of pixel (i, j) is (i + 0.5, j + 0.5). The answer: `{hit: true, kind, feature, name, face, faceIndex, aliases?, point: [x, y, z], depth, edge? | vertex?, x, y, width, height, radius, camera}`. `kind` is `"vertex"`, `"edge"` or `"face"`: what the position points at. `feature` to `depth` describe the face under the position and are there whenever one is, also when `kind` is `"edge"`: the feature that made the body (`F3`) and its name, the face's persistent name and its place in `faceNames`, the point in space and its distance from the eye along the view. `edge` is there when `kind` is `"edge"`: `{feature, body, name, index, faces, point, depth, distance}`, the feature and the name of its body, the edge's own persistent name or `null`, its place in the list of `document.edges`, the names of the faces it lies between (two; one for a seam), the point of the edge nearest to the position, that point's distance from the eye and its distance from the position in pixels. `vertex` is there instead when `kind` is `"vertex"`, with the same fields: `name` its own persistent name or `null`, `index` its `index` under `vertices` of `document.edges`, `faces` the names of the faces that meet in it, `point` the vertex. An edge or a vertex beside the silhouette has no face under it: `kind` and `edge` or `vertex` only. Nothing there is `{hit: false, outside}`, with `outside` true when the position is not in the picture: an answer, not an error. `camera` is the camera that was used, in the shape the parameter takes. At a pixel centre the face is the one the id buffer of the CPU renderer has for that pixel (`craft3d_render::pick` is the renderer's arithmetic for one sample), so it is the face the picture shows there.
- *What the viewport shows at a pixel* is `ui.pick {x, y, width?, height?, radius?, select?}` on the desktop control channel: the same answer (without `camera` and `radius`) for the viewport's own mesh (the display quality) and camera. `x` and `y` are pixels of the viewport, the picture `ui.screenshot` makes at its default size; `width` and `height` say so when the picture was made at another size. Without `radius` it is the click's, scaled with the picture. With `select: true` it counts as a click.
- *A click in the viewport* (the left button, pressed and released without dragging) is that pick: the answer becomes `state.picked` of `ui.get` (`{serial, x, y, feature, name, face, faceIndex, point, kind, edge, vertex}`; `serial` counts the picks in this window, so a second click on the same thing is seen; `feature` to `point` are the face under the click and null without one; `kind` is `"vertex"`, `"edge"`, `"face"` or null; `edge` and `vertex` are `{feature, body, name, index, faces, point}` or null) and what it points at is highlighted: the vertex (`state.highlightVertex`), or else the edge (`state.highlightEdge`), or else the face (`state.highlight`), one of the three. A click on nothing removes them. `picked` cannot be set with `ui.set`.
- *The tabs of the open documents* (2026-10-14): `ui.get` › `tabs` is the row of tabs above the viewport, one per open document in the order of `file.list`: `{document, name, path, dirty, active, asksToClose}` (`document` the number `file.activate` takes; `name` the file's name without its extension, or `Untitled n` for a document never saved, counted from 1 in the row; `dirty` unsaved changes, marked on the tab; `asksToClose` true when closing it from its tab asks first, exactly when `file.close` refuses it without `discard`). `ui.get` › `closing` is that question while the window asks it, `{document, name, path}`, else `null`; only the person at the window answers it, and it goes away by itself when an agent closes or saves that document meanwhile. A click on a tab runs `file.activate`, its close button `file.close` (with `discard` after *Don't Save*), through the engine thread like any command; the status bar and `lastCommand` report them. Neither can be set with `ui.set`: an agent uses the commands. `file.close` over the channel is unchanged: it closes the active document.
- *Highlighting a face*: `ui.highlight {face, feature?}` shows the face in the viewport in the theme's highlight colour (`theme::Tokens::face_highlight`), shaded like the body. `face` is the persistent name or one of the face's aliases; `feature` (an id, `F3` or `3`, or a name) says which body when several have a face of that name, and without it a name that several bodies have is refused. It returns `{highlight: {feature, face}, name, faces}` (`faces`: how many faces carry the name; a boolean can cut a face into pieces that keep it), and a name no body has is an error that changes nothing. `{face: null}` removes every highlight. `ui.set {highlight: {feature?, face} | null}` does the same without the checks. The highlight is view state, it is dropped when no body has a face of that name any more, and it follows the face through every edit that keeps the name. The highlight is in `ui.screenshot` and in the viewport whichever renderer draws it: both renderers shade the same face ids from the same colour (`craft3d_render::Highlight` in `RenderParams`), compared under the parity tolerances of [`architecture.md`](architecture.md) §7.2.
- *Highlighting an edge*: `ui.highlight {edge, feature?}` (the edge's own name) or `ui.highlight {between: [face, face], feature?}` (every edge between two faces, as `document.edges {between}` finds them; the same name twice for a seam). It returns `{highlightEdge: {feature, edge, between}, name, edges}` (`edges`: how many edges are meant) and sets `state.highlightEdge`; a name no body has, or two faces with no edge between them, is an error that changes nothing. `ui.highlight` points at one thing: a face takes the edge's and the vertex's highlight away, and so on; `ui.set {highlight: ..., highlightEdge: {feature?, edge? | between?} | null, highlightVertex: {feature?, vertex? | corner?} | null}` can set all three. The edge is drawn over everything else as a line of `theme::Tokens::highlight_width` points (3) in the highlight colour, and the part of it behind a body is drawn dimmed, as a sketch there is, so that an edge an agent points at is found from the wrong side too. It is a line of the overlay like the others: the GPU's direct path draws it from the same segments with the same depth test as the CPU oracle (`crates/ui-egui/tests/pointing_edges.rs` compares the two along the line, 8 levels as for the other lines). Dropped when no body has such an edge any more.
- *Highlighting a vertex*: `ui.highlight {vertex, feature?}` (the vertex's own name) or `ui.highlight {corner: [face, ...], feature?}` (one to 16 face names: every vertex in which all of them meet; the three faces of a corner name that corner, one face names all its vertices). It returns `{highlightVertex: {feature, vertex, corner}, name, vertices}` and sets `state.highlightVertex`. The vertex is drawn as a dot of `theme::Tokens::highlight_radius` points (4) in the highlight colour, over everything else and dimmed behind a body, by the same two paths as the edge's line. Dropped when no body has such a vertex any more.
- *Over MCP*: `view.pick` is a command like any other (`command_run`). Through the bridge to a window the MCP server has one more tool, `control_call {method, params?}`, which runs a `ui.*` method of that window (`ui.get`, `ui.set`, `ui.fit`, `ui.pick`, `ui.highlight`, `ui.screenshot`, `ui.notice`; not `ui.quit`): that is how an MCP client reads what the developer clicked, asks what is at a pixel of the viewport and points at a face, an edge or a vertex. A picture comes back as an image block. `craft3d-cli mcp` without `--bridge` does not list the tool.
- Not there yet: several highlights of one kind at once, a highlight in `view.render`. A long edge of which only a stretch shorter than half a pixel is in sight within the radius can be missed (the half-pixel steps).

**See-through bodies** (2026-10-13): `ui.set {"transparency": t}` with `t` from 0 (opaque, the default) to 0.9 (nearly clear; larger is clamped, a value that is not a number is refused) makes the viewport draw the bodies see-through, so that inner faces, holes and cavities show; `ui.get` has it as `state.transparency`, and the slider under the view cube sets the same field. The definition is the CPU renderer's (`craft3d_render::render`, `RenderParams::opacity` = 1 - t): per sample, the front-most surface blended over the nearest surface strictly behind it (the background when there is none), `opacity * front + (1 - opacity) * behind`, rounded. One layer shows through and is itself drawn opaque: the two are minima over all triangles, so the picture does not depend on triangle order, and a cavity stays readable where blending every layer would turn it grey. A highlighted face in front is not seen through; behind, it shows in the highlight colour. The hidden parts of the bodies' edges are drawn dimmed (as hidden sketch lines are), highlighted edges and vertices as ever. `ui.pick`, `view.pick` and a click still give the front-most face: the id and depth buffers are the opaque picture's. At `transparency` 0 the picture is today's, bit for bit. `ui.screenshot` shows it. **The wgpu renderer draws it too** (2026-10-14: two depth layers and a blend, [`architecture.md`](architecture.md) §7.2), so the window's device keeps drawing while the bodies are see-through and `ui.get` › `render.renderer` stays `gpu`. A device that cannot (the renderer says why, `GpuError::SeeThrough`) hands those frames to the CPU renderer, on its render thread with a preview while the camera moves (`render.renderer` is then `cpu`); opaque again, the GPU draws. `view.render` has no such parameter.

**The section plane** (2026-10-14): a plane that cuts the picture open, to look inside a shell, a pocket or a cavity. It is a view: the document and its bodies do not change and nothing is regenerated. One object says it everywhere, `{plane, feature, point, normal, offset, flip}`: the plane is `plane` (`xy`, `yz` or `zx`; a datum plane by its feature's id or name; or a flat face by its persistent name from `document.inspect`, with `feature` to say which body when several have that face) or `point` and `normal` (`[x, y, z]` each), moved by `offset` model units along its normal. What lies on the side the normal points to is not drawn; a face's normal points out of its body, so on a face a negative offset cuts into the body and offset 0 cuts nothing. `flip: true` keeps that half and cuts the other away. Where the plane passes through the inside of a body the cut is closed with a flat cap in a colour of its own (the theme's `section_cap`; unshaded), so a solid cut open looks solid; a face of a body that lies in the plane goes with its body.
- *In a picture without a window:* `view.render {…, "section": {…, "cap": true}}` (`cap: false` leaves the cut open) and `view.pick {…, "section": {…}}`; the result of `view.render` then has `section: {point, normal, range}`: the plane as it was used (`normal` into the half that is cut away) and the offsets between which it passes through the model, so an agent can choose an offset.
- *In the window:* `ui.set {"section": {"on": true, "plane": "zx", "offset": 12, "flip": true}}`; the fields given change and the rest stay, except that `plane` replaces `point` and `normal` and the other way round. `on` with no plane at all is `xy`. `ui.get` has it as `state.section` and says under `section` where the plane lies (`point`, `normal`, `range`), or `{"lost": reason}` when the section was switched off because its plane no longer exists (the face or the datum plane it names is gone; `state.section.on` is then false and the name is kept), or `null` when it is off. A plane that means nothing when it is set (an unknown name, a face that is not flat, a normal without direction, a number that is not finite) is an error of `ui.set` and changes nothing. The controls beside the view cube set the same field: *Section*, the axis the plane is across (X, Y, Z), a slider across the model's extent, and *Flip*.
- *What follows the section:* the viewport (both renderers), `ui.screenshot`, `ui.pick` and a click. The edges of the bodies end at the plane and the outline of the cut is drawn as edges; sketches and the world axes are not cut. A pick answers what is seen, never a face that is cut away; where the cap is in front, `kind` is `section` and the result has `section: {feature, body, point, depth}` (the body that is cut there, `null` where two bodies overlap in the plane, and the point of the plane) and no face; as a click that is `state.picked` with `kind: "section"`, and nothing is highlighted. Edges and vertices in the half that is cut away are near nothing. A highlighted face shows where it is not cut away. With `transparency` the cap is seen through like any face.
- *Limits:* one plane; no hatching; the cap is found by counting the surfaces a ray crosses, over all bodies together, so where two bodies overlap in space the plane through both shows no cap.

**Datums** (2026-10-14): the viewport draws the datum planes, axes and points that are placed (not suppressed, rolled back or failed): a plane as a translucent square a little larger than the model with its outline, an axis as a line through the model's extent, a point as a dot, in a colour of their own, dimmed behind a body like a sketch, with their names beside them in the window (not in `ui.screenshot`). `ui.set {"show": {"datums": false}}` hides them and `ui.get` › `state.show.datums` says whether they are shown (default `true`); with none shown the picture is the one without datums, bit for bit. Likewise `ui.set {"show": {"sketches": false}}` hides the sketches, their lines and their points, on both drawing paths and in `ui.screenshot` (`state.show.sketches`, default `true`; with the sketches shown the picture is the one from before the field existed, bit for bit; 2026-10-14). In the window two toggles in the row above the section's controls, *Sketches* and *Datums*, set the same two fields. `ui.screenshot` shows them as the window does. A click, `ui.pick` and `view.pick` pass through a datum to the face behind it. `view.render` does not draw them (nor edges or sketches: it renders the bodies).

**The feature tree** (2026-10-14): `ui.get` › `features` lists the tree's rows in history order as `{id, name, kind, state, status, error, causedBy, selected}`: `state` is `ok`, `failed`, `suppressed` or `rolledBack`; `error` is the reason a failed feature gives (as `document.inspect` has it); `causedBy` is `{id, name}` of the feature at the start of the chain when the feature failed because something it is made from failed (the one to fix), and `null` otherwise. In the window a row starts with a mark in the state's colour (✔ built, ⚠ failed, ⏸ suppressed, ○ rolled back), a failed name is in the failed colour, a suppressed one struck through and a rolled-back one in italics; the reason is shown under the row and on hover; a row with a cause has a *caused by* link under it, and a click on it selects that feature (`state.selectedFeature`), as a click on its row would, but without toggling.

**Autosave and crash recovery** (2026-10-13): a session with a recovery directory (`craft3d --recovery-dir DIR|none --autosave-interval SECONDS`, on by default in the app; the same flags on `craft3d-cli serve` and `mcp`, off by default) autosaves documents with unsaved changes, and after a crash the next start offers them. Three commands, the same for an agent as for the window's recovery bar: `recovery.list` (looks in the directory; returns `enabled`, `directory`, `interval`, `autosaved`, `write_ms`, `writes`, `pending`, `problem`, `running` and `documents`: `id`, `name`, `path`, `time`, `size`, `revision`, `features`, `pid`, `openable`, `problem`), `recovery.open {id}` (opens it as an unsaved document that remembers its original path; `file.list` marks it `recovered: true` until it is saved) and `recovery.discard {id}` or `{all: true}`. Nothing is opened or removed without being asked. `file.save` of a recovered document refuses to replace an original that changed since the autosave unless `overwrite: true` is given. `ui.get` carries the same overview as `recovery` (without looking at the disk), and `ui.set {"panels": {"recovery": false}}` hides the bar. The directory's layout is in [`file-formats.md`](file-formats.md) › *The recovery directory*.

**A profile from coordinates alone** (`sketch.path`, 2026-10-13): one command draws a chain of lines and arcs through shared corners in one undo step, so a driver that does not read responses can still close a loop of lines and arcs. A slot, 30 between centres and 10 wide, tangent in all four corners:

```json
{"command": "sketch.path", "params": {"sketch": "Profile", "start": [0, -5], "segments": [
  {"line": [30, -5], "tangent": true},
  {"arc": [30, 5], "tangent": true},
  {"line": [0, 5], "tangent": true},
  {"arc": "start", "tangent": true}]}}
```

Each segment runs from the end of the one before it to its own end: a point id, coordinates, or `"start"`, the path's start point (which closes the loop with that segment; `"closed": true` adds a straight line back instead). An arc is given by `center` (counter-clockwise unless `"clockwise": true`), by a point it passes `through`, by `radius` (the shorter way round unless `"large": true`, counter-clockwise unless `"clockwise": true`), or by `"tangent": true` alone, which leaves in the direction the segment before it arrives. Arcs are stored as `sketch.arc` stores them, counter-clockwise from start to end about a centre point, so a segment walked clockwise is stored with its ends swapped. `"tangent": true` on any segment also adds a tangent constraint with the segment before it (on the first segment: with the last one, in a path that ends at its start), so the corner stays smooth when a dimension changes; without it the arc is only drawn where the numbers put it. Ids are handed out in the order of the path: the start point, then per segment its end point and its centre (each only when new) and the segment itself, then the closing line; the reply lists them as `points`, `entities`, `centers` and `constraints`. A segment that cannot be drawn (no length, a `through` point on the chord, a radius under half the chord, a tangent arc to a point straight ahead) is refused as `segments[i]: ...` and nothing is added.

**Limits enforced:** 1 MiB per request line, 8 MiB per reply, 256 steps per batch, previews at most 2048 px on the long side, renders 16 to 4096 px per side. Not enforced yet: the triangle budget for tessellation.

**`document.inspect`** returns the shape shown further down with these differences: feature parameters are under `"params"` with a `"type"` field; a failed feature carries `"error"` (the reason: it starts with the parameter and names the feature and the name it lost) and, when the reason is that something it is made from failed, `"causedBy"` (the id of the feature at the start of that chain, the one to fix; `document.check` and the result of a feature command carry it too); bodies are listed per feature with `"feature"` and `"name"`, and carry a `"bbox"` taken from a tessellation (exact for flat-faced bodies, inside the true box by at most `"bboxTolerance"` for curved ones); `"history"` holds the undo and redo labels as arrays; `"path"`, `"dirty"`, `"ok"` and `"document"` (its index) are added.

Three transports, one command registry:

| Transport | Process | Use |
|---|---|---|
| **Headless server** | `craft3d-cli serve` | Fastest way for a script or agent to make many edits; no window, no GPU |
| **Desktop control** | `craft3d --control <port>` | Drive and screenshot the running app while the developer watches |
| **MCP** | `craft3d-cli mcp [--bridge host:port]` | Agent clients; wraps either of the above |

## Envelope

Each request is one JSON line; each reply is one JSON line with the same `id`:

```json
{"id": 1, "method": "engine.execute", "params": {"command": "document.measure", "params": {}}}
{"id": 1, "ok": true, "result": { "volume": 8000.0, "unit": "mm^3" }}
{"id": 2, "ok": false, "error": "unknown command `feature.extrud`; did you mean `feature.extrude`?"}
```

Errors are sentences an agent can act on: they name the command, the parameter and the entity involved. `params` of a command must be a JSON object (or omitted); anything else is an error in every transport.

## Authentication (TCP only)

Both TCP listeners bind `127.0.0.1` only. Start with a token file so the credential is not on the command line:

```sh
craft3d --control 7878 --control-token-file /private/path/craft3d-control.token \
  --automation-read-root /work/project --automation-write-root /work/project
```

If the file does not exist it is created with a fresh 256-bit token (mode `0600` on Unix). The first request on every connection must authenticate; nothing else is dispatched before it succeeds:

```json
{"id": "auth", "method": "auth", "params": {"token": "<64 hexadecimal characters>"}}
```

Stdio transports need no handshake: access is inherited from the process pipe.

## File access

Automation never gets ambient filesystem access. Paths in requests are relative to, or absolute beneath, an explicit **read root** and **write root** given at launch (`--automation-read-root`, `--automation-write-root`); the two are independent, and omitting one denies that direction. Parent traversal, paths outside the root and link escapes are rejected before any file effect. Interactive file pickers in the desktop app keep normal user-selected access.

How the window's own File menu fits in (`apps/craft3d/src/files.rs`): New, Open, Save and Save As are the commands `file.new`, `file.open` and `file.save`, run by the application for the person at the window. For a file chosen in the system's dialog the application grants that one command access to the directory of the chosen file, in one direction (reading to open, writing to save), and restores the automation roots before anything else runs. Requests are answered on the same thread, one at a time, so no request ever runs under the grant, and there is no method, parameter or tool that asks for it. What follows for a client: a document the person opened from outside the roots is the active document like any other and can be inspected and edited over the channel, but `file.save` without a `path` is refused for it (its own path is outside the write root); save a copy with a `path` beneath the write root. When pointer and key replay arrive (`ui.pointer`, `ui.key`), they must not be able to reach the File menu's dialogs.

## Methods

### Engine (all transports)

| Method | Params |
|---|---|
| `engine.execute` | `{command, params?, wait?}`: run any command by id. `wait: false` starts a long one (regeneration, export) as a background job: `{job, pending}` |
| `engine.commands` | `{filter?}`: the registry with params docs and enablement (`enabled`, `disabledReason`, `needsDocument`) |
| `jobs.list` / `jobs.cancel` | `{}` / `{job?}` |
| `session.list` | open documents and the active index |
| `doc.new` / `doc.open` / `doc.close` / `doc.select` | `{units?, tolerance?}` / `{path}` / `{index?}` / `{index}` |
| `doc.save` | `{path?, index?}`: native `.3dcraft`, atomic |
| `doc.export` | `{path, format?, tolerance?, bodies?, index?}`: by extension: `.step`/`.stp`, `.stl`, `.3mf`, `.obj` |
| `doc.inspect` | `{index?, detail?}`: same JSON as the command `document.inspect` |
| `doc.render` | `{index?, view?, size?, mode?, path?}`: PNG to `path`, else `{mime, base64}`; CPU renderer in headless mode. Today this is the command `view.render` `{path?, width?, height?, view?, projection?, zoom?, box?, mode?, tolerance?}`: `projection` is `perspective` (default) or `orthographic` (lengths across the view to scale); `box` is two opposite corners `[[x, y, z], [x, y, z]]` in document units, framed instead of the whole model and seen from outside the model; `zoom` (0.01 to 1000) magnifies about the centre of the picture. The result repeats `projection`, `zoom` and the `box` that was framed |
| `batch` | `{steps: [{command, params?} \| {method, params?}], stopOnError? (true), terse? (false)}` → `{completed, failed, results}`, or with `terse` `{completed, failed, errors: [{step, error}], last: {step, result}}`. Not a transaction: earlier steps stay applied |
| `methods` | this list |

```sh
printf '%s\n' \
  '{"id":1,"method":"doc.new","params":{"units":"mm"}}' \
  '{"id":2,"method":"batch","params":{"steps":[
      {"command":"feature.primitive.box","params":{"size":["40 mm","20 mm","10 mm"]}},
      {"command":"document.measure"}]}}' \
  '{"id":3,"method":"doc.export","params":{"path":"box.step"}}' | \
  craft3d-cli serve --automation-write-root /work/project
```

## What `document.inspect` returns

The contract that lets an agent verify its work without a picture:

```json
{
  "units": {"length": "mm", "angle": "deg"},
  "tolerance": {"linear": 1e-6, "angular": 1e-9},
  "variables": [{"name": "width", "expr": "40 mm", "value": 40.0, "dimension": "length"}],
  "features": [
    {"id": "F1", "name": "Sketch1", "kind": "sketch", "status": "ok", "dof": 0, "entities": 4, "constraints": 6},
    {"id": "F2", "name": "Extrude1", "kind": "extrude", "status": "ok", "inputs": ["F1"], "params": {"distance": "10 mm"}},
    {"id": "F3", "name": "Fillet1", "kind": "fillet", "status": "failed",
     "error": "edge reference `F2/side(e3)∩side(e4)` no longer exists after Sketch1 changed"}
  ],
  "rollback": null,
  "bodies": [
    {"id": "B1", "kind": "solid", "valid": true, "faces": 6, "edges": 12, "vertices": 8,
     "volume": 8000.0, "area": 2800.0, "centroid": [20.0, 10.0, 5.0],
     "bbox": [[0, 0, 0], [40, 20, 10]]}
  ],
  "history": {"undo": 3, "redo": 0}
}
```

`detail: "topology"` adds every face, edge and vertex with its persistent name, geometry kind and tolerance. Field names are part of the protocol: changing one is a breaking change recorded in this document.

## MCP

`craft3d-cli mcp` serves MCP on stdio. Tool names use underscores (the dotted names belong to the JSON protocol above).

| Tool | Notes |
|---|---|
| `session_list`, `doc_new`, `doc_open`, `doc_save`, `doc_export`, `doc_select`, `doc_close` | File paths resolve beneath the roots |
| `doc_inspect` | The JSON above; an empty session returns `document: null` |
| `doc_render_preview` | PNG image content; `view`, `max_side` (default 1024, maximum 2048), `mode` (`shaded`, `shadedEdges`, `wireframe`, `ids`) |
| `command_list` | `filter`, `enabled_only` |
| `command_run` | `id`, `params`, `wait` |
| `command_batch` | ordered `steps`, `stop_on_error` (default true), `terse` (default false: only the failures and the last result come back); not atomic |
| `jobs_list`, `jobs_cancel` | Background jobs |
| bridge only: `ui_inspect`, `ui_screenshot`, `ui_set`, `control_call` | Need a running desktop app |

Resources `craft3d://document` and `craft3d://commands` return the same JSON as `doc_inspect` and `command_list`.

Conventions (from PhotoCraft's MCP server): unknown tool arguments return JSON-RPC `-32602` naming the key, before execution; tool failures return `isError: true`; a worker panic becomes a tool error and the session keeps serving; invalid JSON lines get `-32700` with `id: null` and the next line is still processed. Before experiments, duplicate the document (`file.duplicate`) and work on the copy. Recover from a failed batch by inspecting, then `edit.undo` once per applied step.

## Limits

Enforced before dispatch, so a hostile or mistaken request cannot exhaust the process:

- 1 MiB maximum request line; 8 MiB maximum reply
- at most 16 simultaneous connections per listener; 30-second socket timeouts
- at most 256 steps per batch
- previews: longest edge ≤ 2048 px; PNG ≤ 5 MiB
- tessellation for export or preview refuses a tolerance that would exceed a triangle budget (default 20 million), with an error naming the tolerance that would fit

A request over a limit gets an error reply; the session and its documents keep serving.
