# Control protocol and MCP

> **Last updated:** 2026-11-02 · **Status:** the headless JSON-lines server (`craft3d-cli serve`), the MCP server (`craft3d-cli mcp`), the desktop control server (`craft3d --control`) and the MCP bridge to a running window (`craft3d-cli mcp --bridge`) exist and are described below as built. The browser build (`craft3d-web`) has none of them: no control channel and no MCP, so an agent cannot drive it yet. What is not built is marked *(planned)*.

## Implemented today

**JSON lines** (`craft3d-cli serve`): the envelope below, on stdin/stdout only (no TCP, so no auth). Methods: `engine.execute {command, params?}`, `engine.commands {filter?, id?, brief?}` → `{"commands": [...]}`, `batch {steps: [{command, params?}], stopOnError?}` → `{completed, failed, results}`, `methods`. Everything else goes through `engine.execute` with a command id: there are no `doc.*`, `session.*` or `jobs.*` methods, no `wait`, and batch steps are commands only. Unknown keys are refused, also at the top level of a request. A batch is checked as a whole before its first step runs.

**MCP** (`craft3d-cli mcp [--automation-read-root DIR] [--automation-write-root DIR] [--recovery-dir DIR] [--autosave-interval SECONDS]`): `initialize` (with `instructions` that tell the client how to start), `ping`, `tools/list`, `tools/call`, `resources/list`, `resources/templates/list` and `resources/read`; protocol versions 2025-11-25, 2025-06-18, 2025-03-26 and 2024-11-05. Tools: `command_list`, `command_run`, `command_batch`, `doc_inspect` (returns `{"document": null}` when nothing is open), `doc_render_preview` (an image block plus a text block) and `selection_get`; one resource, `craft3d://selection`. There are no `doc_new`/`doc_open`/`doc_save`/`doc_export` tools: use `command_run` with `file.new`, `file.open`, `file.save`, `file.export`. The bridge to a running window is its own paragraph below (*MCP bridge*), with one more tool, `control_call`. The tools and their arguments are in the table under *MCP* further down. Used by real MCP clients (Claude Code) in the field tests of 2026-10-12 and 2026-10-22 ([`field-test/`](field-test/2026-10-22/README.md)) and the R1 acceptance (22 tasks built by an agent over MCP; [`testing.md`](testing.md) › *The task set*).

**Desktop control** (the switch **Allow AI agents**, or `craft3d --control PORT [--control-token-file FILE] [--automation-read-root DIR] [--automation-write-root DIR]`; *Connecting an agent*, below): the same envelope and methods as `craft3d-cli serve`, on a TCP listener bound to 127.0.0.1, executed on the document the window shows. The first request of every connection must be `auth {token}`; a failed attempt closes the connection, a connection silent for 30 seconds is closed, 16 connections at most. The token file is created (mode 0600 on Unix) when it does not exist. The window's other options: `--recovery-dir DIR|none`, `--autosave-interval SECONDS`, `--recent-file FILE|none`, `--renderer auto|gpu|cpu`, `--window-size WxH`, and files to open. Added methods: `auth {token, client?}`, `bye {}` (*Connecting an agent*), `mcp.message {line}` (the bridge's), `ui.get`, `ui.set {view?, camera?, panels?, selectedFeature?, notice?, quality?, highlight?, highlightEdge?, highlightVertex?, transparency?, section?, show?, dialogs?, timeline?, parameters?, export?, look?, analysis?, appearance?, sidePanel?}`, `ui.param {name, value} | {lastGood: true}` (*The Parameters tab*, below), `ui.pick {x, y, width?, height?, radius?, select?, all?, shift?, alt?}` and `ui.highlight {face | edge | between | vertex | corner, feature?}` (see *Pointing* below), `ui.select {items? | names?, mode?}` (see *Selection* below), `ui.fit {view?, feature? | selection?}` (*Flying to a feature*, below), `ui.screenshot {path?, width?, height?, scale?}` (a PNG of the viewport as framed: the CPU reference render plus the overlay of body edges, sketches and axes, without the panels; with `window: true` and at most `path` instead a frame of the window, panels and the controls over the viewport included, at the window's size in pixels: painted by the window's own renderer into a texture of that size and read back (*Recording the window*, below), so it is taken also when the window is covered, minimised or on another workspace, after three passes and once the viewport has averaged the frames of its still picture, the studio look's environment is prepared and no popover or drawer is still fading or sliding in (2026-11-02) (the studio look's `accumulate`, 16 by default) and shows the display scene (2026-10-30); a window without a wgpu device instead waits for a frame of the compositor, asked again every 30 frames that bring none, and when none came within 8 seconds it is an error that says so; the requests after it wait meanwhile, except `ui.get`, `ui.quit {save?}` (*Closing the window*, below) and what a dialog of the File menu answered, and the picture is answered only once a command running on the engine thread has finished; 2026-10-18), `ui.record {path, fps?, step?, includeUi?} | {stop: true} | {}` and `ui.advance {frames?, dt?}` (*Recording the window*, below), `ui.notice {text}` (a one-line caption over the viewport, for narrated demos; empty removes it) and `ui.quit {save?}`; `methods` lists them with their params and summaries. Not there: `ui.inspect` (it is `ui.get`), `ui.focus`, display modes. The panels' appearance is `ui.set {"appearance": "system|light|dark"}` (2026-11-02; `ui.get` › `appearance` says which is in force; the viewport and its pictures are the same in both). Requests are answered on the thread that owns the document whenever the window's event loop is woken for them, which does not take a frame (since 2026-10-13; `apps/craft3d/src/app.rs`, `Desk::turn` and `Driver`): a window the compositor does not show (another workspace, minimised, fully covered, a locked screen: a Wayland compositor then sends no frame callbacks and winit delivers no redraw) answers like any other, and `ui.quit` ends the process without the window having to be drawn once more. Before, such a window answered nothing until the request timed out after 120 s, and a `ui.quit` it had answered was not acted on until the window was looked at (`apps/craft3d/tests/hidden_window.rs` runs the application under a headless `mutter` to pin this; it skips where there is none).

**The window keeps answering while a command runs** (2026-10-14; `apps/craft3d/src/worker.rs`, `Desk` in `app.rs`). Commands run on the window's engine thread, which has the session while they run: `engine.execute`, `batch` and every MCP tool call but `control_call` (`host::route`). Meanwhile the window draws what it showed before (camera, tree and picking all work on it) with the work in progress in its status bar, and nothing on the drawing thread waits for regeneration or meshing: the scene the window shows is built on the engine thread too, after the command and whenever the window asks for one it does not have. Requests are still answered one at a time, in the order they arrived, whichever connection sent them; a reply comes when its command is done, as before. Two methods are answered at once even while work runs, from what the window shows: `ui.get` (also through MCP's `control_call`, since 2026-11-05: before, that one waited for the command to finish), whose `work` is then `{label, phase, feature, name, step, steps, seconds, subject}` (`label` the command or `batch of N` or `meshing`; `phase` `running`, `regenerating`, `measuring` or `meshing`; `feature`/`name` the feature being rebuilt and `step` of `steps` its place in the history, `0 of 0` for a phase without steps; `seconds` how long the work has run; `subject` the name of the file being opened, without folder and extension, when the work opens one) and `null` when the window is idle, and `workShown`, what the work indicator in the status bar says while it shows (`null` otherwise: it shows only for work that has run 0.35 s and stays 0.3 s after, so a moment of a motion or a quick edit never shows it, though `work` says it runs; 2026-10-30), and `ui.quit`, which closes the window at once (work still running gets three seconds to finish, so the documents are put away cleanly; after that the application ends and its recovery files stay, as after a crash). The other `ui.*` methods wait their turn, because they read the session. A panic on the engine thread is caught there: the request gets an error, the documents with unsaved changes are autosaved, and the session comes back as it was before the command. A quick command is answered within the same turn of the event loop as before (the drawing thread waits up to 12 ms for it). Not cancellable yet. *Coarse first, then sharp:* after a change the window shows a quick first picture and builds the display-quality mesh beside the engine thread, which a command does not wait for; `ui.get` › `scene.refining` is `true` meanwhile, and `ui.screenshot` waits for the display mesh (the requests after it wait with it, in order).

The window makes its sharp image on a thread of its own and shows a quick preview until it is ready; `ui.get` says which is on screen (`render.sharp`). The viewport is drawn by the wgpu renderer on the window's own device when the machine has a graphics adapter (directly into the texture that is shown, multisampled, every frame sharp: then `render.sharp` is always true), by the wgpu renderer on a device of its own, read back, when that direct path cannot be set up, and by the CPU reference renderer otherwise, or when the window was started with `--renderer cpu` (`CRAFT3D_RENDERER=cpu`), or after the GPU failed: `ui.get` reports the renderer of the image on screen (`render.renderer`, `gpu` or `cpu`, with `render.ssaa` and `render.msaa`, the samples per pixel) and, as `renderer {backend, adapter, fallback, direct, msaa}`, which one the viewport uses, the adapter's name, why it is not the direct GPU path although that was wanted (`null` otherwise), whether it draws directly on the window's device, and with how many samples per pixel. `ui.screenshot` does not depend on any of that: it renders its own picture of the state as it is when the request is answered (camera, document, selection), at full quality and always with the CPU reference renderer (the oracle the GPU viewport is checked against, [`design/rendering.md`](design/rendering.md)), so it never returns a preview or the image of an earlier state. The mesh the viewport shows is the scene at the *display quality* (`state.quality`, settable with `ui.set {"quality": {"chordal": fraction of the model's size = 2e-4, "maxTriangles": integer = 1000000, "angle": degrees = 12}}`, numbers out of range clamped): a chordal tolerance of `chordal` times the model's size, coarsened until the scene has at most `maxTriangles` triangles but never beyond the quick first picture's tolerance (1e-3 of the diagonal of the model's box), which the window shows while the display mesh is built; `ui.get` › `scene.tolerance` is the tolerance it got and `scene.coarsened` whether the budget or the tessellator's limits made it coarser than asked. `ui.screenshot` renders that same scene, so what it shows is what the window shows. `view.render`, `view.pick`, `view.replay` and MCP's `doc_render_preview` mesh for their own picture (2026-10-15; the rule is under `view.render` below); previews and `file.export` keep the automatic tolerance (or the one given). In the overlay, the part of a body's edge behind a body is left out, and the part of a sketch behind a body is drawn dimmed.

**MCP bridge** (`craft3d-cli mcp --bridge [PORT] [--state-dir DIR]`, or `--bridge PORT --control-token-file FILE`): an MCP server on stdin/stdout without a session of its own. Each message is passed unchanged to the window's `mcp.message`, answered there by the same MCP code as `craft3d-cli mcp` on the window's document, and the reply is passed back: same tools, same limits, and the viewport shows every change. One short connection per message. `PORT` may be `127.0.0.1:PORT`; an address that is not this machine is refused, because the token is sent as it is. The file roots are the window's. Without `--control-token-file` the window and its token are found through discovery (*Connecting an agent*, below). When the window is not running, the bridge answers `initialize`, `ping` and `tools/list` itself (the same answers, the tool list static; `control_call`'s description then names the usual `ui.*` methods instead of listing the window's), so an MCP client that starts it before the window keeps the server instead of marking it failed (2026-11-04), and every other request (a tool call) gets a JSON-RPC error (code -32000) that says how to start the window (or to turn on Allow AI agents); the bridge keeps serving. The same holds for a program at the port that drops the connection, or does not answer the bridge's `challenge` within 5 seconds, before it has proved it is the window (2026-11-04; a window answers it at once on the connection's own thread, whatever its engine is doing). A window that already has its 16 connections answers the challenge with `too many connections`, closes the connection after reading what was sent (so the line is not lost to a reset), and the bridge passes that on as such. It has one tool more than `craft3d-cli mcp`: `control_call {method, params?}`, which runs a `ui.*` method of the window (2026-10-13; see *Pointing* below); there are no separate `ui_*` tools.

**Commands** (111 at 2026-10-23, in 20 families: `assert`, `body`, `datum`, `document`, `edit`, `face`, `feature`, `file`, `history`, `jig`, `measure`, `param`, `recovery`, `select`, `session`, `set`, `sketch`, `table`, `variable`, `view`): `craft3d-cli commands` (or `engine.commands`, MCP `command_list`) prints the registry with parameters and summaries; it is the source of truth.

**Playing a motion: lighter drawing and the bake hint** (2026-11-02; [`design/motion.md`](design/motion.md) › *The player*). `ui.set {"timeline": {"motion": true, "playing": true}}` plays the motion over `t`. While it plays the viewport draws lighter, unless `timeline.playQuality` is `full` (`auto` is the default): the studio look in one frame a moment, without its accumulated frames, its depth of field, its ambient occlusion and its screen-space reflections and contact shadows (the key light's shadows stay); once it stops or pauses the full look comes back at once and settles. Pictures of the window (`ui.screenshot`, also with `window: true`), recordings (`ui.record`, frame by frame or in real time), `view.render` and `view.replay` are always drawn at the full quality. `ui.get` › `timeline` has `playQuality`, `playingLight` (true while it draws lighter) and `heavy {msPerMoment, moments, provisional, heavy, suggestBake, baking, dismissed}`: the median time the `view.motion` of a moment took in the window, not the frame around it, over the last 15 moments played (null before 8 are weighed; the browser has the clock too), the share of them shown provisionally while their configurations were built in the background, and whether the player offers *This motion is heavy — bake first?* (heavy: a median of 100 ms or more, light again only below 70 ms; not when the motion is baked or the offer was dismissed for the document in this session). Its Bake button runs `motion.bake {frames: 120, background: true, limit: 1}` (in the background builder for an assembly on the desktop, else a piece between frames), and `baking {progress, auto}` follows what is left (the motion's `building` counted by grid points and frames, or the pieces' `remaining`; it never goes back) until it is done. A motion that is not heavy but shown provisionally (half of the moments weighed) is baked so by itself, once (`auto: true`). An agent bakes with `engine.execute {command: "motion.bake"}` itself.

**Holding a joint by hand** (2026-11-06; [`design/assemblies.md`](design/assemblies.md) › *Driving a joint by hand*). `view.drive {mate, value, which?}` shows the active assembly with one mate's joint held at `value` (a number: degrees for an angle, the document's length unit for a distance; or an expression, `"30 deg"`), as view state: the document, its undo history and its dirty state do not change. Any mate with a free motion: one a formula of `t` drives (its driver gives way), one that follows another through a coupling or a closure (the first other driver whose release frees it is let go of, listed in `released`), or a free one. The others follow; the pose is solved along a fixed grid of the held value from the document's pose, so it is a function of the value alone, and where the mechanism cannot go on (a dead point, a limit) the view stops at the last value reached and `stopped` says why (a later value past it costs no solve). At most 10 turns (720 steps of 5°) from the document's value; further is refused. With collisions on (`collisions: true`, one switch with `view.motion`'s and the player's) the held pose is checked as a moment is: the overlapping bodies drawn red, the answer's `collisions` and `volumeUnit` as `view.motion`'s; `later: true` holds the pose alone (a slider being dragged, `checkLater: true`: not checked yet, never "free") and the next `view.drive` without it (`view.drive {}` when the drag ends) checks it; `checksCollisions` is the switch, which the player's chip follows. A refused call changes neither. `view.drive {mate: null}` lets go; a `view.motion` with a `t`, an edit or another document lets go too; `view.drive {}` says what is held. The viewport, `view.render`, `view.pick`, screenshots and the Assembly tab's values show the held pose; measures, checks and exports see the document. In the browser the pose is made in the worker: the answer says `pending: true` and `elsewhere: true` until it came; a joint the worker refuses is let go of, the next `view.drive {}` says why (`error`, not after an edit) and the window's status bar says it once.

**Traces in the window** (2026-11-02): with the window's engine thread, `view.trace` is worked out in the background unless `background: false` is given, so a motion that plays does not stop for it. The point is checked at once (a wrong vertex or instance is an error as before); the answer then has `pending: true` and no points. `view.trace {name, wait?}` returns the trace's full answer once it is there (points, length, closed, box, plane), the error that stopped it (also `let go of: …` when the background work was cancelled or the document changed), or `pending: true`; with `wait: true` it waits for it, in the window at most 2 s (the wait holds the engine thread, so the play and every other client wait with it: ask again, or follow `ui.get` › `traces`), in `craft3d-cli serve` at most 600 s. `ui.get` › `traces` lists every trace of the active document as `{name, pending, error, length, closed}`, and a failed one is said in `timeline.problem`. `file.export {trace}` needs the trace to be there.

**Bug reports** (2026-10-23): the command `session.report` returns a plain-text report to paste into an issue (`text`: the 3DCraft version and the commit it was built from, the platform, what the frontend runs on, and the last command that failed in the session with its params and its whole error), and the same as fields (`version`, `commit`, `platform`, `host`, `lastFailure`). In the window `host` names the renderer and its graphics adapter, and `ui.get` › `report` is the text the status bar's *Copy details* button puts on the clipboard after a command failed and shows in a window of its own (a status-bar failure that no command made, such as a file chooser that could not open, gets lines of its own, and the engine's last failed command is then marked as an earlier one; which one the status bar shows is told by the engine's failure serial). The code is `engine/src/report.rs` and `ui-egui/src/shell/report.rs`; the commit is embedded at build time by the programs' build scripts (`crates/buildinfo`; the environment variable `CRAFT3D_GIT_COMMIT` overrides it; `unknown` without either, and for a library used without one of 3DCraft's programs).

**Pointing** (2026-10-13, faces, edges and vertices): the developer and an agent say "this face", "this edge" and "this corner" to each other in the words of the document: a face by its persistent name, the one `document.inspect` lists under `faceNames`; an edge the way `document.edges` lists it, by its own persistent name (`name`) where it has one and by the names of the faces it lies between (`faces`) always. A vertex likewise: `document.edges` lists, under `vertices`, the vertices its edges end in, each with `index`, `name` (its own persistent name, where it has one), `point` and `faces` (the names of the faces that meet in it). After a boolean the edges and the vertices have no names of their own, and the faces are how they are referred to. Since 2026-10-14 every edge of `document.edges` also has `short`: the names of `faces`, in the same order, each shortened to the shortest name a blend or a face operation follows back to that face (`F1:face(0)` for `F13:copy(0)/…/F3:copy(0)/F1:face(0)`; a copy of a pattern or a shell stays in front, since without it the name means several faces). A chamfer, a fillet, an offset face, a delete face and a shell take either; a sketch, a datum and an extrusion up to a face take the full name to mean the newest form ([`design/names.md`](design/names.md) › *References that follow a body*). `document.inspect` shows, per feature whose names were followed, `followed`: its parameters as it was built, with the full names. `view.pick` gives the full names, as before.

- *The rule for what a position points at*, the same for `view.pick`, `ui.pick` and a click (`engine/src/pick_cmds.rs`, `Scene::point_at`): (1) the face is the one the picture has under the position, whatever else is near; (2) an edge is *near* when a point of it is within the pick radius of the position in the picture and in sight, that is, no face is in front of that point (an edge is looked at every half pixel along the part of it within the radius, starting from its nearest point); the nearest such point of all edges wins, at the same distance the one nearer to the eye, then the earlier body, then the earlier edge; (3) a vertex is near when it is within the radius and in sight, the nearest wins with the same tie-breaks; (4) a vertex that is near is what the position points at, however near an edge is (an edge ends in its vertices, so beside a vertex an edge is always at least as near: without this rule a corner could not be clicked); otherwise an edge that is near, otherwise the face under it, otherwise nothing. The radius is in pixels of the picture, 4 by default (`radius`, 0 to 64; 0 looks at faces only); a click uses `theme::Tokens::pick_radius` points (4), times the window's pixels per point. So an edge is picked from 4 pixels either side, also from just outside the silhouette where no face is under the pointer, and a hidden edge is never picked through the face in front of it. The edges are the ones the viewport draws (one polyline per edge of the B-rep, the points the mesh has along it); the silhouette of a curved face is not an edge.
- *What is at a position of a picture* is the command `view.pick {x, y, width?, height?, radius?, view?, projection?, zoom?, box?, camera?, tolerance?}`, on every transport: the picture is the one `view.render` makes with the same `view`, `projection`, `zoom`, `box` and `tolerance` (the same default: the picture's own tolerance, with `camera` for that camera; a pick with the camera it passed back has the same tolerance), or the one seen by `camera` (`{eye, target, up?, projection?, fovY? | height?}`: perspective with `fovY`, the vertical field of view in degrees, default 30; orthographic with `height`, the model units from the top of the picture to its bottom). `x` and `y` are pixels from the top-left corner, x to the right and y down, and the centre of pixel (i, j) is (i + 0.5, j + 0.5). The answer: `{hit: true, kind, feature, name, face, faceIndex, aliases?, point: [x, y, z], depth, edge? | vertex?, x, y, width, height, radius, camera}`. `kind` is `"vertex"`, `"edge"` or `"face"`: what the position points at. `feature` to `depth` describe the face under the position and are there whenever one is, also when `kind` is `"edge"`: the feature that made the body (`F3`) and its name, the face's persistent name and its place in `faceNames`, the point in space and its distance from the eye along the view. `edge` is there when `kind` is `"edge"`: `{feature, body, name, index, faces, point, depth, distance}`, the feature and the name of its body, the edge's own persistent name or `null`, its place in the list of `document.edges`, the names of the faces it lies between (two; one for a seam), the point of the edge nearest to the position, that point's distance from the eye and its distance from the position in pixels. `vertex` is there instead when `kind` is `"vertex"`, with the same fields: `name` its own persistent name or `null`, `index` its `index` under `vertices` of `document.edges`, `faces` the names of the faces that meet in it, `point` the vertex. An edge or a vertex beside the silhouette has no face under it: `kind` and `edge` or `vertex` only. Nothing there is `{hit: false, outside}`, with `outside` true when the position is not in the picture: an answer, not an error. `camera` is the camera that was used, in the shape the parameter takes, and `tolerance` the chordal tolerance of the mesh it looked at. At a pixel centre the face is the one the id buffer of the CPU renderer has for that pixel (`craft3d_render::pick` is the renderer's arithmetic for one sample), so it is the face the picture shows there.
- *What the viewport shows at a pixel* is `ui.pick {x, y, width?, height?, radius?, select?}` on the desktop control channel: the same answer (without `camera` and `radius`) for the viewport's own mesh (the display quality) and camera. `x` and `y` are pixels of the viewport, the picture `ui.screenshot` makes at its default size; `width` and `height` say so when the picture was made at another size. Without `radius` it is the click's, scaled with the picture. With `select: true` it counts as a click.
- *A click in the viewport* (the left button, pressed and released without dragging) is that pick: the answer becomes `state.picked` of `ui.get` (`{serial, x, y, feature, name, face, faceIndex, point, kind, edge, vertex}`; `serial` counts the picks in this window, so a second click on the same thing is seen; `feature` to `point` are the face under the click and null without one; `kind` is `"vertex"`, `"edge"`, `"face"` or null; `edge` and `vertex` are `{feature, body, name, index, faces, point}` or null) and what it points at is highlighted: the vertex (`state.highlightVertex`), or else the edge (`state.highlightEdge`), or else the face (`state.highlight`), one of the three. A click on nothing removes them. `picked` cannot be set with `ui.set`.
- *The tabs of the open documents* (2026-10-14): `ui.get` › `tabs` is the row of tabs above the viewport, one per open document in the order of `file.list`: `{document, name, path, dirty, active, asksToClose, jigInUse, assembly}` (`document` the number `file.activate` takes; `name` the file's name without its extension; for a document without a file the title of an example the start screen opened (since 2026-11-10, also once it is recovered after a crash), else `Untitled n`, counted from 1 in the row; `dirty` unsaved changes, marked on the tab; `asksToClose` true when closing it from its tab asks first, exactly when `file.close` refuses it without `discard`; `jigInUse` a published Jig opened to be used, whose tab says **Jig**; `assembly` an assembly, a `.3dcraftasm` or one seen to be while it was active (2026-11-02): the tab's line icon is a part's, an assembly's or a Jig's). `ui.get` › `closing` is that question while the window asks it, `{document, name, path}`, else `null`; only the person at the window answers it, and it goes away by itself when an agent closes or saves that document meanwhile. A click on a tab runs `file.activate`, its close button `file.close` (with `discard` after *Don't Save*), through the engine thread like any command; the status bar and `lastCommand` report them. Neither can be set with `ui.set`: an agent uses the commands. `file.close` over the channel closes the active document, or since 2026-10-22 the document of the number given (`{document, discard?}`, as `file.list` numbers them; the active one stays active). `file.new` and `file.open` make their document the active one, so the next request of any connection works on it and the window shows its tab (pinned by `a_new_document_is_the_one_the_next_request_works_on`, 2026-11-04). The active document is shared with the person, though: a click on a tab, the documents in the File menu or Ctrl+Tab make another one active between two requests, and the requests after it work on that one. A script that builds in one document for a while, with pauses, says which with `file.activate {document}` again, or checks `file.list` › `active`.
- *The menus* (2026-11-02, UI overhaul 2b): File · Edit · View · Help, the kit's dark plates. The **View** menu toggles fields of the state, so an agent reaches them with `ui.set` and reads them with `ui.get`: *Side panel* (Ctrl+B) is `panels.tree`, *Status bar* `panels.status`, *System*, *Light* and *Dark* are `appearance` (`ui.get` › `appearance` says what it resolves to); *Full screen* (F11, the desktop app) is the window's own and not in the state. File › *New Part* (Ctrl+N) runs `file.new`, *New Assembly* (Ctrl+Shift+N) `assembly.new`.
- *Highlighting a face*: `ui.highlight {face, feature?}` shows the face in the viewport in the theme's highlight colour (`theme::Tokens::face_highlight`), shaded like the body. `face` is the persistent name or one of the face's aliases; `feature` (an id, `F3` or `3`, or a name) says which body when several have a face of that name, and without it a name that several bodies have is refused. It returns `{highlight: {feature, face}, name, faces}` (`faces`: how many faces carry the name; a boolean can cut a face into pieces that keep it), and a name no body has is an error that changes nothing. `{face: null}` removes every highlight. `ui.set {highlight: {feature?, face} | null}` does the same without the checks. The highlight is view state, it is dropped when no body has a face of that name any more, and it follows the face through every edit that keeps the name. The highlight is in `ui.screenshot` and in the viewport whichever renderer draws it: both renderers shade the same face ids from the same colour (`craft3d_render::Highlight` in `RenderParams`), compared under the parity tolerances of [`design/rendering.md`](design/rendering.md).
- *Highlighting an edge*: `ui.highlight {edge, feature?}` (the edge's own name) or `ui.highlight {between: [face, face], feature?}` (every edge between two faces, as `document.edges {between}` finds them; the same name twice for a seam). It returns `{highlightEdge: {feature, edge, between}, name, edges}` (`edges`: how many edges are meant) and sets `state.highlightEdge`; a name no body has, or two faces with no edge between them, is an error that changes nothing. `ui.highlight` points at one thing: a face takes the edge's and the vertex's highlight away, and so on; `ui.set {highlight: ..., highlightEdge: {feature?, edge? | between?} | null, highlightVertex: {feature?, vertex? | corner?} | null}` can set all three. The edge is drawn over everything else as a line of `theme::Tokens::highlight_width` points (3) in the highlight colour, and the part of it behind a body is drawn dimmed, as a sketch there is, so that an edge an agent points at is found from the wrong side too. It is a line of the overlay like the others: the GPU's direct path draws it from the same segments with the same depth test as the CPU oracle (`crates/ui-egui/tests/pointing_edges.rs` compares the two along the line, 8 levels as for the other lines). Dropped when no body has such an edge any more.
- *Highlighting a vertex*: `ui.highlight {vertex, feature?}` (the vertex's own name) or `ui.highlight {corner: [face, ...], feature?}` (one to 16 face names: every vertex in which all of them meet; the three faces of a corner name that corner, one face names all its vertices). It returns `{highlightVertex: {feature, vertex, corner}, name, vertices}` and sets `state.highlightVertex`. The vertex is drawn as a dot of `theme::Tokens::highlight_radius` points (4) in the highlight colour, over everything else and dimmed behind a body, by the same two paths as the edge's line. Dropped when no body has such a vertex any more.

- *Flying to a feature* (2026-10-23, roadmap R1): a double click on a row of the feature list selects that feature and flies the camera, in 0.3 s and eased, to frame what it made: the faces whose persistent names say that feature made them, wherever they are now (the wall of a hole in the plate it was cut into, the faces of a block that later went into a union), else its body, its sketch or its datum. Since the developer's test on a large model (2026-10-23) it looks from the direction that sees it best: of the current one and the eight iso views (above and below), the one turning most of its faces' area towards the eye times the share of its most-turned triangles not hidden along the ray by the rest of the model (`Scene::best_view`; the current direction weighs 1.1, views from below 0.8), and it frames at least a fifth of the diagonal of the body the feature lies in, so it is seen with its surroundings and the eye never sits inside the part. A row under the pointer shows a ⌖ beside the eye that flies there too; a feature that failed, is suppressed or shows nothing has none, and a double click on it does nothing (`ui.get` › `features[].zoomable`). A selected feature that made faces lights those faces, not its whole body; a face of an instance a pattern, mirror or transform made (`F9:copy(2)/…`) is that feature's, the seed keeps its own faces only. The context is capped at eight times the target's own diagonal, so a small hole on a big part is still seen as a hole. F without Ctrl, Alt or Shift (over the viewport or the list, while no field takes the keys) flies to what is selected; with nothing selected it frames everything at once, as before. What it flies to is made visible: a hidden sketch or datum is shown again, and a section that cuts away every point of it (each triangle corner, edge point, sketch or datum point, beyond the cut's snap) is switched off (one that leaves some of it in view stays). A vertex, a short edge or a tiny face is framed with at least 2 % of the model's diagonal around it. A turn or flight under way when the tab is switched is kept as where it was going. A single click on a row is as before (select, no camera move). The other way round, selecting in the viewport marks the row of the feature that made what was selected (for a face, edge or vertex the feature its persistent name ends in: `F4:copy(0)/F2:face(2)` was made by `F2`; an edge named by its faces by the latest of their features) and scrolls the list to it when it is out of view; `ui.get` › `features[].madeSelection` is that mark. For an agent, `ui.fit {feature}` (an id or a name) and `ui.fit {selection: true}` frame the same at once (`autoFit` false afterwards); nothing of the feature shown, or nothing selected, is an error that changes nothing.
- *The Parameters tab* (2026-10-23, roadmap R1, Jigs): a document with public parameters (`param.list` › `jig`, a Jig) has two tabs over the side panel, **Parameters** and **Features**, and opens on Parameters; a document without them shows the feature list alone. The form is `param.list`, read again whenever the active document's revision changes; what it changes goes through `param.set`, run where the window runs commands (the engine thread on the desktop; in the browser, in the frame after one that says *Regenerating…*). It clamps a value to the parameter's range and snaps it to its step before it sends it, and says so under the field for four seconds (`clamped to 120 mm`, `rounded to 3.5 mm`); `param.set` itself refuses what is out of range. Every commit of the form, and `ui.param`, sends `clamp: true`: a value that would put another parameter outside a range that depends on it (the GT2 pulley's bore when its teeth go down) moves that one to the nearest value of its new range in the same edit, and the note says so (`bore clamped to 3.1 mm`, after the field's own note; 2026-10-23, R1 finishing). The result lists such a parameter under `clamped` and, with its new value, under `set`; the undo step is named for the parameters given, so a drag stays one step when it starts or stops clamping another. A drag on a number commits as it goes on the desktop, at most every 0.15 s, every commit after the first with `merge: true` (one undo step for the drag), and on the web only when the drag ends. A commit that makes a feature fail or an assertion break that did not in the last good state (compared as sets: failing features by id, broken assertions by name; assertions still being measured are judged once they are) marks the field in the failure colour with the reason, and a banner over the viewport says *This value breaks the model: …* with a *Back to last good* button (a `param.set` of the last good values; `ui.param {lastGood: true}` is that button for an agent, an error while nothing breaks the model). An undo, a redo or an agent's edit that brings back a value that breaks the model is said the same way, at the parameter that moved off the last good values (2026-11-04). The viewport always shows the document as it is, so picks, screenshots, saves and exports agree with it. A refused value is said at the field, without a banner. `ui.get` › `parameters`: `{jig, tab: "parameters"|"features", count, inUse (a published Jig opened to be used, `.3dcraftjig`: only its parameters change; the tab shows *Open for editing*, which runs `jig.edit`, and the feature list has no eyes), busy, live: {name, value, dragging} or null, note: {name, text} or null, trouble: {name, message, broke, elsewhere} or null}` (`elsewhere`: broken by an undo, a redo or an agent's edit rather than the form's own commit; `message` led by the check's name); `ui.set {parameters: {open, collapsed}}` switches the tab (each document keeps its own) and folds groups; `ui.param {name, value}` sets one value as the form does (a number in the parameter's unit, `true`/`false`, or a choice's label) and returns `{sent, note, result, parameters}`: it is settled on the window's thread, joined to a commit of the form that waits, and run on the engine thread like every command; the reply comes once the window has synced. Through MCP's `control_call` (whose reply cannot wait for the engine thread) it is queued as a commit of the form instead and answers `{sent, note, queued: true, parameters}`; `ui.get` › `parameters` and `param.list` tell the outcome. The values themselves are `param.list`'s.

- *Closing the window* (2026-10-21, roadmap R1): the window's close button asks before it drops anything. When no document has unsaved changes worth keeping (those `file.close` refuses without `discard`) the window closes at once; otherwise it stays and asks the question of a tab's close button, *Save*, *Don't Save* or *Cancel*, for one document after the other, each made the active one first (`ui.get` › `closing` with `"quitting": true`, and `ui.get` › `quitting` true while it asks). *Save* writes the document to its own file (one never saved is named in the save dialog first) and closes it, *Don't Save* closes it and drops its autosave, and once none is left the application ends and removes its recovery files. *Cancel*, a save that fails or a save dialog that is cancelled keeps the window with what is still open. A window killed or crashed meanwhile keeps its recovery files as before. The same over the channel: `ui.quit {save: "discard" | "ask" | "save"}`. `"discard"`, the default, is `ui.quit` as it was: the application ends at once, dropping the unsaved changes and their autosaves (answered even while a command runs). `"ask"` is the close button (pressed while a command runs, the window waits for it and decides on what it left): `{"quitting": true}` when it closes at once, else `{"quitting": false, "asking": {document, name, path, quitting}}` (`asking` is `null` while the window first makes that document the active one, so the person sees what the question is about; `ui.get` › `closing` has it then); only the person answers the questions. `"save"` saves every document with unsaved changes to its own file on the engine thread, through the automation write root as `file.save` does (never with the person's own access), shows the document that was shown, answers `{"quitting": true, "saved": [paths]}` and ends; it is refused, with nothing saved, while a document with unsaved changes was never saved (save it with `file.save {path}` first) or its file lies outside the write root (a file the person opened from the dialog is the person's to save), and a save that fails is an error that leaves the application running. An application that ends with a document still unsaved that was not dropped on purpose (changed by work that finished while the window closed) writes its autosave and leaves it, as after a crash.

**Selection** (2026-10-21, decisions B1 and B4 of [`decisions.md`](decisions.md); how it is built: [`design/selection.md`](design/selection.md)): one selection per open document, shared by the developer in the window and every agent. It is an ordered list of items `{kind, name, feature}`: `kind` is `body`, `face`, `edge`, `vertex`, `feature`, `sketch` or `datum`; a body, feature, sketch or datum has its feature's name as `name` and its id as `feature`; a face, edge or vertex its persistent name as `name` and the feature of its body as `feature`. It is window state (B1): not saved in the `.3dcraft`, not part of the history, not undone. Names stay selected through every regeneration that keeps what they name (a body by its feature id, a face by its persistent name); since 2026-10-22 a face, an edge or a body that a later feature takes (a boolean, a fillet, a pattern: its first copy) is followed to its image there, and what a suppressed, rolled-back or failed feature hides stays selected, listed under `hidden` (`{kind, name, feature, why}`), and comes back in its place when the feature does; what no longer exists drops out at the next look, and `dropped` says what dropped out at the last change of the document, one line each (an undo clears it). Items are found again by their feature's id only; since 2026-10-21 a new feature name may not be written like an id (`F` and digits), and `F3` always means the feature with id 3.

- *Reading and setting it, on every transport*: the commands `select.get {context?}` → `{items, count, summary, dropped, hidden}` (`summary`: "3 bodies, 2 faces"; each item with its context unless `context: false`, below), `select.set {items? | names? | set?, mode?}` (`set`: what a named set holds now, added to the items given) (`mode`: `replace` (default), `add`, `remove`, `toggle`, `clear`; `names` is the short form, a feature's name or id or a persistent name, the kind read from it; a name that means nothing is an error and nothing changes; at most 10000 items) and `select.query` (below). In the window: `ui.get` › `selection` (the same object) and `ui.select {items? | names?, mode?}` (`select.set` on the window's document). Over MCP: the tool `selection_get` and the resource `craft3d://selection` (`resources/list`, `resources/read`), both the same JSON, also through the bridge, so an agent can always ask what the developer selected. `ui.set {selectedFeature: id}` selects that feature (and `null` takes the features out): `selectedFeature` is now the first body, feature, sketch or datum of the selection, kept for the controls that used it.
- *In the window*: a click replaces the selection with what it points at (the vertex, else the edge, else the face, by the rule of *Pointing*), a click on nothing clears it, Shift+click toggles it, a double click selects the whole body, Esc over the viewport clears it, and a click on a row of the feature list selects that feature (Shift: toggles; the selected row again: clears; a double click selects it and flies to it, *Flying to a feature* above), F flies to the selection. Ctrl (Cmd) and a drag draws a box: the bodies whose whole mesh lies inside it are selected, and of the other bodies the faces wholly inside it, seen or hidden (Shift too: added). Selected bodies and faces are lit in the selection colour (`theme::Tokens::face_highlight`, the copper of the Mission theme), their outlines, the selected edges and vertices are drawn over the picture like a highlighted edge, dimmed where something is in front, so a selected face behind another body is still seen; the status bar says "3 bodies, 2 faces selected" and how many dropped out. `ui.screenshot` shows it.
- *Picking through*: `view.pick` and `ui.pick` with `all: true` add `hits`: every face along the ray through the position, front to back, one entry per face `{feature, name, face, faceIndex, point, depth}` (the first is the face the pick gives; faces a section cuts away are left out). Clicking again on the same spot (within 3 pixels, the camera and the model unchanged), or Alt+click, selects the next face behind the last one, round to the front after the last; `ui.pick {select: true, alt: true}` and `{select: true, shift: true}` do what a click with those keys does. A right click opens a small *Select other* list of the faces under the cursor (at most 24), front to back by name and body; hovering an entry lights its face up, clicking it selects it (Shift held when it opened: toggles).
- *Context for agents* (2026-10-22): the items of `select.get` and `select.set`, and of `select.query` with `context: true`, also have `body`, `origin {feature, name, type}`, for a face `surface` (`type` and its key measure: a plane's outward `normal`, a cylinder's `radius`, `axis`, `center` and `hole`, …), for an edge `curve`, for a vertex `point`, `drivers` (the parameters that set the measure: a primitive's `radius` or `size`, a fillet's `radius`, the `diameter` constraint of the sketch circle an extrusion swept, also through `equal` constraints as `via`; each with `edit: {command, params}`, the edit to make with the new value) and `copyOf` (`[{feature, name, type, instance}]`, the patterns and mirrors it is a copy made by). A driver says what its edit changes: `affects` (faces of the current bodies that feature or constraint makes), `alike` and `shared` (copies of this face that change with it); a formula is marked (`formula`, and `variable` with a `variable.set` edit when it is one variable). "Make this hole 6.5 mm" is one `edit`, after a look at `shared`. `select.get` › `followed` lists the items followed from what was selected (`from`, `copies`, `pieces`): into every piece of a split, into the first copy of a pattern. Details: [`design/selection.md`](design/selection.md) › *Context*.
- *Named sets* (2026-10-22, decision B2): `set.define {name, kind?, where?}`, `set.edit {set, kind?, where?, name?}`, `set.remove {set}`, `set.list {}` keep a query of `select.query` in the document under a name (saved, undoable; format 27), computed again whenever it is used, so a set grows with the design: the filter `{set: name}`, `select.set {set: name}`, and `set.list`, which gives each set's `count` now (or its `error`, when a feature it names was deleted). Features in `in`, `madeBy` and `copyOf` are kept by id; a set that uses itself is refused; renaming a set renames it in the sets that use it, and a set in use is not removed.
- *Selecting by description*: `select.query {kind?, where?, then?, limit?, context?}` finds what fits JSON filters (B4) and returns `{items, count, truncated, summary}` in document order; each face, edge and vertex also has `body` (its body's name) and `origin {feature, name}`, the feature that first made it (the end of its persistent name's way, such as the cylinder that drilled a hole: the feature to edit to change it). With `then` (`replace`, `add`, `remove`) the result also becomes the selection, and the window lights it. Filters: `all`, `any`, `not`; `set` (a named set); `kind`; `name` and `type` (globs); `in` (a body), `madeBy` (a feature, anywhere along the name's way), `copyOf` (a pattern or mirror, with `instance`); `color` (with `within`) and `material`; `volume`, `area`, `radius`, `length` (a value, `{eq, tol}` or `{min, max}`, expressions with units); `surface` (plane, cylinder, cone, sphere, torus, freeform); `hole` (a cylindrical face whose outward normal points at its axis and that goes all the way round it: not a concave fillet; a face split into pieces that keep its name is one item); `normal {along | perpendicular, tol}`; `axis {along, tol}`; `inside` (a box), `above` and `below` (`{x | y | z: value}`). `limit` (default 1000, at most 10000) caps the result, and `summary` says how many fit. Semantics and examples: [`design/selection.md`](design/selection.md). Example, "the 6 mm holes of the plate": `{"kind": "face", "where": {"hole": true, "radius": "3 mm", "in": "Plate"}, "then": "replace"}`.

**Verification** (2026-10-22, roadmap V1; how it is built: [`design/verification.md`](design/verification.md)): questions about the design's geometry, read-only, and assertions the document keeps. A *subject* is a body by its feature's name or id, a list of them, a query `{"kind", "where"}` as `select.query` takes, or a bare filter (which selects faces for `distance` and `through`, bodies or faces for `thickness`, bodies otherwise). Lengths are in the document's unit (`lengthUnit` in every result); points and planes take expressions.

- *Queries*: `measure.distance {from, to}` → `{distance, atLeast, from: {point, body, feature, face}, to: {…}}`, the least distance between two sets of faces, settled on the exact surfaces and edges (`distance` is between two real points; `atLeast` is proven). `measure.clearance {from, to}` (bodies) → `{clearance, atLeast, least, pairs: [{a, b, status: clear|touch|overlap, distance, from, to}]}`; `clearance` is null when a pair overlaps. `measure.thickness {of}` → `{thickness, atLeast, at: {point, face, …}, to: {…}, samples}`: the thinnest wall by lines into the material along the inward normal; `thickness` is the least found (at a real place), `atLeast` what is proven no place is below. `measure.ray {from: [x, y, z], direction: axis or [x, y, z], of?, limit? = 100}` → `{hits: [{distance, point, body, feature, face, enters, edge, tangent}], count, truncated}`, nearest first. `measure.through {of}` (cylindrical and conical faces) → `{through, throughCount, faces: [{face, body, through, axis: {point, direction}, radius, why?, blocked?: [{point, faces}]}]}`: whether the whole bore (the face's narrowest circle, along its axis, exactly) is clear of the body; `blocked` is where material lies in it. `measure.symmetry {of? = all bodies, plane: "xy"|"yz"|"zx" or datum plane or {point, normal}, tol? = 10 × tolerance}` → `{symmetric, deviation, worst: {point, face, …}, samples}`.
- *Assertions*: `assert.add {name, measure, …the measure's parameters, eq + tol? | min? + max? | is?}` keeps an assertion in the document (one undo step, saved, format 28) and returns it checked: `{name, measure, expect, status: passed|failed|notProven|error, measured, unit, expected, message}`; `notProven` (a warning, never passed) when a searched-for least lies within the bound but what is proven does not. A bound written `N unit^k` (`"50 cm^3"`, which is (50 cm)³) is refused with the form meant (`50 * (1 cm)^3`), except for N 0 and 1, where both readings agree (`"tol": "0 mm^3"`). Measures: `volume`, `area`, `mass` (`of`), `count` (`of`: a query; the number it finds), `extent`, `boxMin` and `boxMax` (`of`, `axis`: the size of the bodies' box, where it begins, where it ends), `centerOfMass` (`of`, `axis`; every body needs a material), `distance` and `clearance` (`from`, `to`), `thickness` (`of`), `through` (`of`), `overlap` (`of`, `to?`: true when a pair overlaps; the message names the pairs and their common volume, *Bolt overlaps Plate by 12 mm^3*, or says *no overlap*), `symmetric` (`of`, `plane`, `tol`). `through` and `symmetric` take `is` (default true), `overlap` takes `is` without a default (`false`: none overlap). The old name `interference` (true when none overlap) is still accepted and written as `overlap` with the opposite `is`; files are migrated on load (format 36). The others take `eq` (with `tol`, which may be 0) or `min` and/or `max`, expressions in the document's variables (`"eq": "t"`). Features named in a subject are stored by id. `assert.edit {name, rename?, …}` replaces what is given, `assert.delete {name}`, `assert.list {details?, wait? = true}` → `{assertions, count, passed, failed, errors, notProven, pending, ok}` (`ok`: all passed). Assertions are measured off the caller's thread, only when what they depend on changed, and never block regeneration; one still being measured is `pending` (the window does not wait, an edit's result waits two seconds, `assert.list` and `document.check` wait for all). A broken one (failed, or error: its measure could not be taken) shows like a failed feature: under `assertions: {count, passed, broken: [{name, status, measured, unit, expected, message}], unproven, pending}` in the result of every feature command and `variable.set` while the document has assertions, as a problem in `document.check` (`ok` false; one not proven is under `warnings`), under `assertions` in `document.inspect` (each `{name, measure, status, measured, unit, expected, message, when}`, `measured` and `unit` as `assert.list` gives them), in the window's tree (a section *Checks* under the features) and in `ui.get` (`assertions: [{name, measure, status, measured, expected, message}]`). Example, the housing's bolt holes: `{"name": "the bolt holes go through", "measure": "through", "of": {"hole": true, "madeBy": "Hole"}}`.

**Cut lists** (2026-11-03; how it is built: [`design/cutting.md`](design/cutting.md)): `cut.list {bodies?, format: json|csv, geometry?}` returns the plates (prisms of constant thickness, recognised from their faces) and sheet-metal parts (by their flat patterns) of the document, grouped by thickness and material, with per part `name`, `kind`, `count` (identical parts up to a rigid motion, turned over included), `bodies`, `features`, `thickness`, `material`, `length`, `width`, `area`, `cutLength`, `holes`, `frame {origin, xAxis, yAxis, normal}`, `top` and `notes`, and under `notPlates` every other body with its `reason` and `faces`; with `format: "csv"` `{format, csv, parts, distinct, notPlates}`, the CSV text in the document's unit. `cut.export {path, format?, bodies?, layout: sheet|each, copies?, kerf?, gap?, width?, stroke?}` writes their outlines to DXF or SVG beneath the write root (one file, or one per part: `files`), each part on a layer named after it, and returns `parts [{name, layer, count, file, at, bbox, thickness, material}]`, `rows`, `kerf`, `notPlates`, `length`, `bytes`. Neither changes the document; an assembly is refused.

**See-through bodies** (2026-10-13): `ui.set {"transparency": t}` with `t` from 0 (opaque, the default) to 0.9 (nearly clear; larger is clamped, a value that is not a number is refused) makes the viewport draw the bodies see-through, so that inner faces, holes and cavities show; `ui.get` has it as `state.transparency`, and the See-through field on the window's display bar (at the bottom of the viewport) sets the same field. The definition is the CPU renderer's (`craft3d_render::render`, `RenderParams::opacity` = 1 - t): per sample, the front-most surface blended over the nearest surface strictly behind it (the background when there is none), `opacity * front + (1 - opacity) * behind`, rounded. One layer shows through and is itself drawn opaque: the two are minima over all triangles, so the picture does not depend on triangle order, and a cavity stays readable where blending every layer would turn it grey. A highlighted face in front is not seen through; behind, it shows in the highlight colour. The hidden parts of the bodies' edges are drawn dimmed (as hidden sketch lines are), highlighted edges and vertices as ever. `ui.pick`, `view.pick` and a click still give the front-most face: the id and depth buffers are the opaque picture's. At `transparency` 0 the picture is today's, bit for bit. `ui.screenshot` shows it. **The wgpu renderer draws it too** (2026-10-14: two depth layers and a blend, [`design/rendering.md`](design/rendering.md)), so the window's device keeps drawing while the bodies are see-through and `ui.get` › `render.renderer` stays `gpu`. A device that cannot (the renderer says why, `GpuError::SeeThrough`) hands those frames to the CPU renderer, on its render thread with a preview while the camera moves (`render.renderer` is then `cpu`); opaque again, the GPU draws. `view.render` has no such parameter.

**The side panel** (2026-11-02): its tab is `state.panels.sideTab`, one of `features`, `variables`, `bodies`, `parameters`, `assembly` and `agent` (2026-11-02: what agents did to the document, newest first, from `agent.log`; offered on the desktop while agents are allowed or the document has a log; a feature an agent made carries ✦ in the Features tab, from its `madeBy`); a tab the document does not offer shows the nearest one it does (`assembly` for `features` in an assembly and the other way round, else the first: Parameters first for a document with public parameters, which follows `parameters.open` both ways). What the panel shows besides is `state.sidePanel`: `filter`, `variableFilter`, `bodyFilter` (the search fields, at most 200 characters), `unfolded` (the rows opened: a feature with a sketch nested under it by its id, a group of datums as `datums:` and its first datum's id, `units`), `folded` (groups of variables folded shut, by name), `checksOpen` (true by default; the checks fold to their heading while something is selected or the panel is short, whatever it says), `showConsumed` (the Bodies tab lists the bodies later features used up), `body` (the body whose card shows, by its feature's id), `hover` (a feature whose dependencies are marked, as the pointer on its row marks them: `ui.set {"sidePanel": {"hover": "F3"}}`), `menu` (a feature whose context menu is open), and for an assembly `mate` (the mate chosen on the Assembly tab or by a click on its marker: its row marked, its marker highlighted) and `mateHover` (the mate pointed at: its marker highlighted and its two parts tinted, as the pointer on its row or marker does; 2026-11-05). Under a mate's row on the Assembly tab is its joint's slider: `joint.set` (one undo step per drag) for a joint that can be set by hand, else `view.drive` (2026-11-06: a joint a formula of `t` drives, or one that follows through a coupling or a closure, held by hand for the view only; Esc lets go). Each is view state: nothing of the document changes. What the panel changes it changes by commands (`feature.edit`, `feature.rename`, `feature.move`, `feature.suppress`, `feature.visible`, `feature.delete`, `history.rollback`, `variable.set`, `material.preset`, `body.material`), each one undo step. `select.get {measures: true}` (with context) also gives each face its `area`, integrated from its exact surface, which the panel's card of a selected face shows.

**The Studio and Analysis popovers** (2026-10-31): whether the options of the studio look and of the analysis are open is state, `state.panels.lookOptions` and `state.panels.analysisOptions` (booleans, true by default), so an agent can show or hide them before a screenshot: `ui.set {"panels": {"lookOptions": false}}` closes the studio look's popover and keeps the look on, `true` opens it again (it shows while the look is on and no analysis is). Switching the look on with `ui.set {"look": {"mode": "studio"}}` opens its options as the Studio chip does, unless the same patch sets `panels.lookOptions`; the same holds for `analysis.mode` and `analysisOptions`. In the window the ▾ caret of each split button opens and closes them, Escape closes the open one.

**The section plane** (2026-10-14): a plane that cuts the picture open, to look inside a shell, a pocket or a cavity. It is a view: the document and its bodies do not change and nothing is regenerated. One object says it everywhere, `{plane, feature, point, normal, offset, flip}`: the plane is `plane` (`xy`, `yz` or `zx`; a datum plane by its feature's id or name; or a flat face by its persistent name from `document.inspect`, with `feature` to say which body when several have that face) or `point` and `normal` (`[x, y, z]` each), moved by `offset` model units along its normal. What lies on the side the normal points to is not drawn; a face's normal points out of its body, so on a face a negative offset cuts into the body and offset 0 cuts nothing. `flip: true` keeps that half and cuts the other away. Where the plane passes through the inside of a body the cut is closed with a flat cap in a colour of its own (the theme's `section_cap`; unshaded), so a solid cut open looks solid; a face of a body that lies in the plane goes with its body.
- *In a picture without a window:* `view.render {…, "section": {…, "cap": true}}` (`cap: false` leaves the cut open) and `view.pick {…, "section": {…}}`; the result of `view.render` then has `section: {point, normal, range}`: the plane as it was used (`normal` into the half that is cut away) and the offsets between which it passes through the model, so an agent can choose an offset.
- *In the window:* `ui.set {"section": {"on": true, "plane": "zx", "offset": 12, "flip": true}}`; the first section switched on without a place cuts across Z (or the base plane given) through the middle of the model's box, as the Section chip does (2026-10-30; the box of the scene shown, so before the window has drawn its first scene the offset is 0); the fields given change and the rest stay, except that `plane` replaces `point` and `normal` and the other way round. `on` with no plane at all is `xy`. `ui.get` has it as `state.section` and says under `section` where the plane lies (`point`, `normal`, `range`), or `{"lost": reason}` when the section was switched off because its plane no longer exists (the face or the datum plane it names is gone; `state.section.on` is then false and the name is kept), or `null` when it is off. A plane that means nothing when it is set (an unknown name, a face that is not flat, a normal without direction, a number that is not finite) is an error of `ui.set` and changes nothing. The controls on the display bar set the same field: *Section* and, while it is on, the axis the plane is across (X, Y, Z), the Offset field across the model's extent, and *Flip side*.
- *What follows the section:* the viewport (both renderers), `ui.screenshot`, `ui.pick` and a click. The edges of the bodies end at the plane and the outline of the cut is drawn as edges; sketches and the world axes are not cut. A pick answers what is seen, never a face that is cut away; where the cap is in front, `kind` is `section` and the result has `section: {feature, body, point, depth}` (the body that is cut there, `null` where two bodies overlap in the plane, and the point of the plane) and no face; as a click that is `state.picked` with `kind: "section"`, and nothing is highlighted. Edges and vertices in the half that is cut away are near nothing. A highlighted face shows where it is not cut away. With `transparency` the cap is seen through like any face.
- *Limits:* one plane; no hatching; the cap is found by counting the surfaces a ray crosses, over all bodies together, so where two bodies overlap in space the plane through both shows no cap.

**Datums** (2026-10-14): the viewport draws the datum planes, axes and points that are placed (not suppressed, rolled back or failed): a plane as a translucent square a little larger than the model with its outline, an axis as a line through the model's extent, a point as a dot, in a colour of their own, dimmed behind a body like a sketch, with their names beside them in the window (not in `ui.screenshot`). They are hidden by default (`state.show.datums`, default `false` since 2026-11-11, so that a document opens on its bodies, not on its planes): `ui.set {"show": {"datums": true}}` shows them, `{"datums": false}` hides them again, and `ui.get` › `state.show.datums` says whether they are shown; with none shown the picture is the one without datums, bit for bit. A flight to a datum (`ui.fit` with its feature, or with a selection that holds it; a double click on its row, F) shows them. Likewise `ui.set {"show": {"sketches": false}}` hides the sketches, their lines and their points, on both drawing paths and in `ui.screenshot` (`state.show.sketches`, default `true`; with the sketches shown the picture is the one from before the field existed, bit for bit; 2026-10-14). Likewise `ui.set {"show": {"edges": false}}` hides the bodies' edges, the outline of a section's cap with them, on both drawing paths and in `ui.screenshot` (`state.show.edges`, default `true`; with the edges shown the picture is the one from before the field existed, bit for bit; 2026-10-30); a highlighted or selected edge or vertex is drawn either way, since it points at something. Likewise `ui.set {"show": {"mates": false}}` hides an assembly's mate markers (`state.show.mates`, default `true`; a part has none; 2026-11-05): per mate a small glyph at its frame (its axis an arrow, an arc about it for a revolute, a double arrow along it for a slider, both for a cylindrical, a square for a planar, a crossed box for a fixed mate, three circles for a ball; docs/design/assemblies.md › *Mate markers*), the same size on screen at any zoom, dimmed behind a body, on both drawing paths and in `ui.screenshot`. In the window three toggles on the display bar, *Sketches* (*Mates* in an assembly, in its place), *Datums* and *Edges*, set the same fields (in a viewport too narrow for their names, the three by their icons). The studio look has its own `look.edges` (window only: `view.render` draws no edges): `soft` (the default) fades each pixel of an edge where the look's depth of field blurs the model, to `w / (w + π c / 2)` of its ink for a line `w` pixels wide and a blur radius of `c` pixels at its distance (crisp in focus, and without a lens the picture of `sharp`, bit for bit), `sharp` draws them as the plain look does, `off` leaves them out of the studio look; anything else is refused. The plain look ignores it. `ui.screenshot` shows them as the window does. A click, `ui.pick` and `view.pick` pass through a datum to the face behind it. `view.render` does not draw them (nor edges or sketches: it renders the bodies).

**The feature tree** (2026-10-14): `ui.get` › `features` lists the tree's rows in history order as `{id, name, kind, state, status, error, causedBy, selected, hidden, madeSelection, zoomable, when}` (`hidden`: `feature.visible`; `madeSelection` and `zoomable`: *Flying to a feature*): `state` is `ok`, `failed`, `suppressed`, `inactive` (switched off by its condition, `feature.when`; 2026-10-23) or `rolledBack`; `when` is the condition as written, or `null`; `error` is the reason a failed feature gives (as `document.inspect` has it); `causedBy` is `{id, name}` of the feature at the start of the chain when the feature failed because something it is made from failed (the one to fix), and `null` otherwise. In the window a row starts with a mark in the state's colour (✔ built, ⚠ failed, ⏸ suppressed, ○ rolled back), a failed name is in the failed colour, a suppressed one struck through, an inactive one greyed with a small *when* beside it (the condition on hover) and a rolled-back one in italics; the reason is shown under the row and on hover; a row with a cause has a *caused by* link under it, and a click on it selects that feature (`state.selectedFeature`), as a click on its row would, but without toggling. *An assembly's rows* (2026-11-06) are its instances; `held` is why an instance does not show what its source file holds now (pinned, or the file changed and could not be read again, when it keeps the last version read), and `null` otherwise: the row's status then ends in ⚠ and its tooltip gives the reason; `featureFailed` (2026-11-10) is the feature of the instance's part (or of a part in it) that failed in its configuration, with the part's own message, marked and explained the same way (the instance is placed with the bodies from before that feature; `assembly.inspect` has it too, and the assembly's `document.check` lists it as a problem). *Following the sources*: an open assembly reads again what changed of its source files by itself, after a `file.save` in the session (whose answer lists them under `followed`, and a source that could not be read again under `warnings`), on `file.activate` of its tab (`followed` too) and on `assembly.follow`, which the window runs when it gets the focus back (its status bar then says which file changed). A file whose size and modification time did not change is not read; nothing is regenerated when no bytes changed; a pinned instance never follows (`docs/design/assemblies.md` › *Derived state*).

**Autosave and crash recovery** (2026-10-13): a session with a recovery directory (`craft3d --recovery-dir DIR|none --autosave-interval SECONDS`, on by default in the app; the same flags on `craft3d-cli serve` and `mcp`, off by default) autosaves documents with unsaved changes, and after a crash the next start offers them. Three commands, the same for an agent as for the window's recovery bar: `recovery.list` (looks in the directory; returns `enabled`, `directory`, `interval`, `autosaved`, `write_ms`, `writes`, `pending`, `problem`, `running` and `documents`: `id`, `name`, `path`, `time`, `size`, `revision`, `features`, `pid`, `openable`, `problem`), `recovery.open {id}` (opens it as an unsaved document that remembers its original path; `file.list` marks it `recovered: true` until it is saved) and `recovery.discard {id}` or `{all: true}`. Nothing is opened or removed without being asked. `file.save` of a recovered document refuses to replace an original that changed since the autosave unless `overwrite: true` is given. `ui.get` carries the same overview as `recovery` (without looking at the disk), and `ui.set {"panels": {"recovery": false}}` hides the bar. The directory's layout is in [`file-formats.md`](file-formats.md) › *The recovery directory*.

**A profile from coordinates alone** (`sketch.path`, 2026-10-13): one command draws a chain of lines and arcs through shared corners in one undo step, so a driver that does not read responses can still close a loop of lines and arcs. A slot, 30 between centres and 10 wide, tangent in all four corners:

```json
{"command": "sketch.path", "params": {"sketch": "Profile", "start": [0, -5], "segments": [
  {"line": [30, -5], "tangent": true},
  {"arc": [30, 5], "tangent": true},
  {"line": [0, 5], "tangent": true},
  {"arc": "start", "tangent": true}]}}
```

Each segment runs from the end of the one before it to its own end: a point id, coordinates, or `"start"`, the path's start point (which closes the loop with that segment; `"closed": true` adds a straight line back instead). An arc is given by `center` (counter-clockwise unless `"clockwise": true`), by a point it passes `through`, by `radius` (the shorter way round unless `"large": true`, counter-clockwise unless `"clockwise": true`), or by `"tangent": true` alone, which leaves in the direction the segment before it arrives. Arcs are stored as `sketch.arc` stores them, counter-clockwise from start to end about a centre point, so a segment walked clockwise is stored with its ends swapped. `"tangent": true` on any segment also adds a tangent constraint with the segment before it (on the first segment: with the last one, in a path that ends at its start), so the corner stays smooth when a dimension changes; without it the arc is only drawn where the numbers put it. Ids are handed out in the order of the path: the start point, then per segment its end point and its centre (each only when new) and the segment itself, then the closing line; the reply lists them as `points`, `entities`, `centers` and `constraints`. A segment that cannot be drawn (no length, a `through` point on the chord, a radius under half the chord, a tangent arc to a point straight ahead) is refused as `segments[i]: ...` and nothing is added. An arc given by `center` whose end is farther than the document's tolerance from the circle about that centre through its start (an end rounded to a few decimals is the usual cause) is handled in one of two ways (2026-10-15). An end given as coordinates that is off by at most 1 % of the radius is put on the circle, in its direction from the centre (the arc keeps its angles, its start and everything before it stay where they are, and the solver has nothing to move), and the reply carries `snapped`: one entry per such segment, `{"segment": i, "given": [x, y], "end": [x, y], "moved": distance}`. An end that is a point id or `"start"` (another segment may share it), or one farther off (more likely a mistake than rounding, which moving it would hide), is drawn as given, and the reply carries `warnings`: one line per such segment, `segments[i]: ...`, with the distance, what the solver does about it (it moves the start, the end and the centre as little as it can until both ends are on one circle, and with them the segments that share those points, so a line before the arc tilts) and the point on the circle where the end would keep the start in place. Both are absent when there is nothing to say. A saved document holds the sketch, not the command, so this changes no saved file.

**A colour and a material per body** (2026-10-15): `body.appearance {body, color, metallic?, roughness?, clear?}` gives the body of a feature (id or name; not a sketch or a datum) a colour, `"#rrggbb"`, `"#rgb"` or `[r, g, b]` (sRGB, 0 to 255), with `metallic` and `roughness` from 0 to 1 (both renderers shade with them, and an OBJ export's material library carries them as `Pm` and `Pr`); `clear: true` takes it away. `body.material {body, name, density, clear?}` gives it a material: a name and a density, a number in kg/m³ or a string with a unit (`"7.85 g/cm3"`; kg/m3, g/cm3, g/mm3, lb/in3, lb/ft3). Both are one undo step each and are saved with the document (format 16); neither changes the history or regenerates anything. A body made from a coloured body keeps its colour (a boolean's result its target's), unless the later feature has a colour of its own. A face has its body's colour, unless it came into the body as part of another body with a colour of its own: walking back the way its persistent name records (`F7:copy(1)/F3:side(e2)` came through instance 1 of F7, the tool, from F3), the first feature with a colour of its own gives the face its colour, and a step through the tool of a subtraction ends the walk at the body there (since 2026-10-15, as SolidWorks, Fusion and Onshape colour a cut). So a red boss united with a grey block keeps its red faces (an intersection likewise), and the wall of a hole a red tool cut into a grey plate is grey ([`design/document.md`](design/document.md)). `body.appearance` returns `{body, appearance, bodies: [{feature, appearance}]}` (every body that has a colour now), `body.material` `{body, material, bodies: [{feature, appearance?, material, mass, massUnit, inertia, inertiaUnit}]}`. `document.inspect` and `document.measure` give each body its `appearance` (`{color: "#rrggbb", metallic?, roughness?}`) and, with a material, `material` (`{name, density, from?, off?}`; `from` is the feature it came from when that is another; `off: true` when that feature is switched off, so its material weighs the body only because nothing that is on gives one), `mass` (kg) and `inertia`, the inertia tensor about the centroid along the model's axes as three rows (`inertiaUnit`: `"kg mm^2"` in a document in millimetres), computed exactly from the B-rep like the volume; `massError` or `inertiaError` when the body cannot be measured. `document.measure` also has the total `mass` when every body has one. The colours show in `view.render`, `view.replay`, `ui.screenshot`, the viewport (both renderers) and 3MF and STEP exports.

**A colour per face** (2026-10-21): `face.appearance {faces: [name], body?, selection?, color, metallic?, roughness?, clear?}` gives faces a colour of their own, by their persistent names (`body`, the feature whose body has them, when the name alone does not say: else the first body in history order that has a face of that name; an alias is read as the face's own name) or, with `selection: true`, the faces of the selection (`select.get`; other kinds are skipped and listed under `skipped`), so the developer's flow is: select a face in the window, then ask for its colour. One undo step for all the faces; saved with the document (format 26). The colour follows the face by the rule of body colours (above, and [`design/document.md`](design/document.md) › 4.2): through edits that keep its name, to its pieces and copies; it goes before the body's colour. A face an edit took away keeps its entry and colours nothing: it is listed under `lostFaces` (`{feature, face, notice}`) in the reply and in `document.inspect`, as a warning of kind `lostFace` in `document.check`, and the window shows it as a notice (it never stops `view.render` or an export; one whose face only a feature that is off would make waits and is not listed); `clear: true` takes it away by name. Replies `{faces: [{feature, face, shown}], appearance, faceAppearances, lostFaces?, skipped?}` (`shown`: what the face is drawn in now). `document.inspect` lists every entry under `faceAppearances` (`{feature, face, color}`), when there is one. *Clearing a body's face colours* (2026-11-10): `face.appearance {body, clear: true}` without `faces` takes away every face colour the body's faces carry, wherever along its history it was given, as one undo step, so that the body's colour shows on every face; colours given at a feature that is off now go too. Replies `{body, cleared: [{feature, face, color}], count, kept: [{feature, face, color, for, why, clear}], message, faceAppearances}`. A pattern's instances are one body, so the seed's colour goes from every instance. A colour that also colours another body's face (a copy kept by a mirror or a transform, the other pieces of a `body.split`) is kept, `for` naming those bodies; `clear` is the params of the `face.appearance` that clears it from all of them (its own name at the feature it was given on), and `why` says so in words. `document.inspect` gives a body `faceColors` for the colours of its own (what the body form clears) and `sharedFaceColors` with `sharedWith` for the shared ones. A sketch, a datum, a body switched off now and a body that went into a later feature are refused, by name.

**Sheets** (2026-10-18): `feature.fill {sketch, name?}` adds a sheet, the flat faces a sketch's closed profiles (or an offset of them) bound, one per profile with its holes, facing along the sketch's normal; `document.inspect` lists it with `"kind": "sheet"`, its area and volume 0 (no centroid). `feature.boolean` takes a sheet: as the target it is trimmed by a solid tool (`intersect` keeps the part inside, `subtract` the part outside; the result is a sheet), as the tool it cuts a solid target it reaches across (`subtract` keeps the part in front of the sheet, where its normal points (decided 2026-10-18); `intersect` the part behind; with `keepTool` one sheet cuts several bodies). A union with a sheet, two sheets, a sheet that ends inside the solid or misses it, a piece of a sheet on a face of the solid and a part of the solid the sheet does not cross fail the feature with the reason. Names: the fill's face `F5:startCap(e1,e2,e3,e4)`, the cut face `F7:copy(1)/F5:startCap(e1,e2,e3,e4)`. STEP writes a sheet as a `SHELL_BASED_SURFACE_MODEL` of `OPEN_SHELL`s.

**Hiding and the timeline** (2026-10-23): `feature.visible {feature: id or name or [id or name], visible}` hides the body, sketch or datum of features in the view (`false`) or shows them again (`true`): they leave the viewport, `ui.screenshot`, `ui.pick`, `view.render`, `view.pick` and `view.replay`, and nothing else changes (unlike `feature.suppress`: still built, measured by `document.inspect`, and written by `file.export`, which exports every body unless `bodies` names some). Kept in the document (`hidden`, format 30) and one undo step, like a colour. Replies `{features: [{id, name, visible}], hidden: [id]}`; `document.inspect` marks a hidden feature `"hidden": true`, `ui.get` › `features[].hidden` too. `view.scrub {feature: id or name or null | step: integer}` shows the model as it was after that feature (step 1 is the first), as if the rollback marker stood there, without changing the document (not its marker, undo history, revision or dirty state): the viewport, `ui.screenshot`, `ui.pick`, `view.render` and `view.pick` show that state, while `document.inspect`, measures and exports see the document. `null` shows the document as it is again; without parameters it only reports. Replies `{feature, step, steps, rollback}`. It is view state of the open document (not saved, not undone), let go of when the features of the history change (one added, deleted or moved, also several in one batch). While scrubbed, a click in the window's viewport does not select (the status bar says to go To end first: a selection names the document as it is, where the face clicked may be another one) and `view.pick` adds `"scrubbed": true`; a section on a datum plane is placed where the document has the plane, and `view.replay` replays the document's own history. A flight to a feature (a double click on its row, F with it selected, `ui.fit {feature}`) shows it again when it is hidden (`feature.visible`) and lets go of a scrub before it (the view goes to the end), then frames it. Each step is regenerated once from a copy of the document's regeneration cache and kept with its scenes, so scrubbing back over steps seen before is immediate; every step is meshed at the tolerances of the document as it is (not of its own, smaller model), so the bodies a step shares with others keep their meshes and the picture does not grow finer as the model grows; when the document's cache has let go of bodies to stay within its budget, a step takes the bodies the step before it derived again, so a step forward derives one body at most, and the regenerations kept hold at most 1 GiB of bodies beyond the document's own (the least recently shown let go first). Timings in [`design/engine.md`](design/engine.md) › *Scrubbing*. The window's timeline (under *Features*) runs `view.scrub` while dragged, "Roll back here" runs `history.rollback` on the step shown, "To end" `history.rollback` with null; `ui.get` › `timeline {steps, shown, scrub: {feature, step} or null, rollback, problem, playing, speed, loop, orbit, caption, playQuality, playingLight, heavy}` says where it is.

**Recording the window** (2026-10-30; `crates/ui-egui/src/record.rs`, `apps/craft3d/src/recording.rs`): `ui.record {path, fps = 30, step = false, includeUi = true, accumulate = 1, quality = "screen"}` records the desktop window's own frames, panels and controls included (`includeUi: false`: the viewport alone, at the place and size it had when the recording started). The window runs its frame itself, outside the toolkit's loop: a pass of the shell on its own egui context, tessellated and painted by its own wgpu renderer (the GPU viewport's texture is one it holds) into a texture of the window's size, read back. Nothing is taken from the compositor, so a covered, minimised or hidden window records like one on screen (a Wayland compositor draws no frame for a window it does not show). `path` is under the write root: a directory, which gets `frame-000001.png`, `frame-000002.png`, …, or a video file (`.mp4`, `.mkv`, `.mov`, `.webm`, `.gif`, `.avi`, `.m4v`) written through a pipe by an external `ffmpeg` (`CRAFT3D_FFMPEG`, else the one on `PATH`; none is an error). The encoder is the best one this ffmpeg has and can run, chosen once per ffmpeg (2026-10-31; `crates/ui-egui/src/encoder.rs`): what `ffmpeg -hide_banner -encoders` lists, then a trial of each candidate on two small frames, since a listed encoder may not work (Fedora's `ffmpeg-free` has no x264 at all, and lists VAAPI H.264 on machines whose driver has no H.264 profile). The choice runs on the window's thread when `ui.record` starts, so it is capped: the listing 5 s, a trial 10 s, all of it 20 s, the window frozen meanwhile; only what ffmpeg answered by ending is remembered (a trial that timed out is tried again next time), keyed by the ffmpeg's path, size and modification time, so an upgraded ffmpeg is asked again. In practice it takes well under a second, once. In order, for `.mp4`, `.m4v`, `.mov` and `.mkv`: `libx264`, `libopenh264`, `h264_vaapi`, `h264_qsv`, `h264_nvenc`, then `mpeg4` (MPEG-4 part 2, in every ffmpeg, not played by browsers); for `.webm`: `libvpx-vp9`, `libsvtav1`, `libaom-av1`, `libvpx` (VP8); `.gif` uses `gif`, `.avi` `mpeg4`. When none works, `ui.record` itself fails before a frame is drawn, naming what it looked for and why each it tried failed. `quality` is how the video is encoded: `screen` (the default) keeps text and edges crisp where the encoder can, with colour at full resolution (x264 4:4:4 at CRF 12, VP9 4:4:4 at CRF 16, AOM AV1 4:4:4 at CRF 20), which some players (browsers, QuickTime) do not play; `web` is 4:2:0 (x264 CRF 18, VP9 CRF 30), playable everywhere. The other encoders always subsample colour (4:2:0); OpenH264 gets a keyframe every second, since through ffmpeg its background detection and rate control cannot be set and it leaves blocks it took for background stale (faint remnants after a change, blocky gradients in the environment) until the next keyframe: on an ffmpeg without x264, `.webm` (VP9 4:4:4) or PNG frames give the crisp video. A 4:2:0 encoder needs even sides: a window of odd width or height is padded to even by repeating its last column or row (never cut, never black), and the status says `encoder` and the `encoded` size. When ffmpeg stops taking frames, the error carries the last lines it said. A `.gif` gets a palette made from its frames. The PNG frames are the lossless way. The frames keep the size the window had at the start (a window resized meanwhile is cut or padded with black). They are written on a thread of their own, at most four behind. One recording at a time; `{stop: true}` ends it once everything is written (and ffmpeg has finished the file) and replies with its status; `{}` replies `{recording, path, format, fps, step, includeUi, accumulate, quality, width, height, encoder, encoded, frames, skipped, time}`. While it records, the window shows the frames recorded instead of drawing the shell itself, so there is one clock.
- *Real time* (`step: false`): a frame every `1/fps` seconds of the wall clock, woken by a timer, whether the window is shown or not; what the person does in the window goes into the next frame; frames that cannot be drawn in time are skipped (counted in `skipped`), not drawn late.
- *Frame-exact* (`step: true`): nothing is drawn until `ui.advance {frames = 1, dt = 1/fps, timeout = 30}` (frames 1 to 100000, dt above 0 and at most 60 seconds, which `timeout` = 30, above 0 and at most 110 seconds) draws its frames each `dt` seconds of the window's clock after the last (egui's own animations, a panel fading in, step by `dt` too), so the history player, a flight, the orbit and a motion advance by exactly that, and draws each one only once the window has settled: no command running on the engine thread, the scene built and refined, the CPU renderer's sharp image made, and the studio look's still averaged over `accumulate` frames (1 by default: a model that moves starts its average again every frame; `accumulate: 16` waits for the still, about 16 passes a frame). Between frames it runs what the last one asked for (the player's next step is a `view.scrub`, its scene built on the engine thread). It replies when the last frame is drawn, or after `timeout` seconds with the frames drawn so far (then `complete` is false and the client asks again for `left`, so a client never waits past its own timeout), `{frames, left, complete, unsettled, recorded, time, seconds, timing: {passesPerFrame, readPassMs, settlePassMs, pushMs, waitMs}}`; the requests after it wait for it, but `ui.get`, `ui.quit` and `ui.record {stop: true}`, which ends the advance at once (its reply an error saying how many frames it drew) and then the recording. Nothing waits without end: a frame whose picture has not settled within 4 s is drawn as it is and counted in `unsettled`, a window that does not settle for the next frame within 60 s (a command or a scene still running) ends the advance with an error, a writer that takes no frame for 20 s (a stuck disk or ffmpeg) ends the recording with an error, and an ffmpeg that does not finish within 20 s of the stop is killed. What ffmpeg says is read as it says it (its last 4 KiB kept), and its last six lines go into the error when it fails or stops taking frames. The person's input is ignored meanwhile, so the same requests give the same frames. `ui.advance` without a frame-exact recording is an error. A host without a window (`craft3d-cli serve`, MCP without the bridge, the web build) refuses both methods.

**The history player** (2026-10-23): under the timeline's slider the window has a player like a video player's (first step, a step back, play or pause, a step forward, To end, speed 0.5×/1×/2×, loop, orbit), with Space, ← / →, Home and End over the viewport or the feature list while no text field has the keyboard and no dialog is open. The keys only change the view: End shows the end (`view.scrub` with null) and leaves the rollback marker, which the To end button removes. Playing is view state, `state.timeline {playing, speed, loop, orbit}`, which `ui.set` changes, so an agent can start a replay for the person watching: `ui.set {"timeline": {"playing": true, "speed": 2, "loop": true}}`. Each step is a `view.scrub` as the slider runs it; the next step is asked for only once the scene of the step shown is built (on the window's engine thread, as every scene) and it has been drawn for 0.8 s divided by `speed`, so a heavy model is played step by step without skipping (a `view.scrub` of an agent's that lands meanwhile is where it goes on from). `playing: true` without a document or without features is refused. Play at the end starts from the first step; at the last step it stops (or starts again with `loop`); an edit of the document, another tab, To end, Roll back here and a scrub that fails stop it (`playing` becomes false). `orbit` turns the active tab's camera about the vertical (12° a second at 1×, at most 30 frames a second) while it plays, and waits while a view-cube turn, a flight or a drag moves the camera. While the view is scrubbed or playing the viewport shows the step's caption at the top, `Step 3/6 · Join · boolean`, the same text `view.replay` writes into `captions.srt`; `ui.get` › `timeline.caption` has it (null otherwise). A speed other than 0.5, 1 or 2 is an error and changes nothing.

**Limits enforced:** 1 MiB per request line, 8 MiB per reply, 256 steps per batch, previews at most 2048 px on the long side, renders 16 to 4096 px per side; a mesh export of more than 20 million triangles is refused, and a picture is meshed within a budget of a million triangles (coarsened, `coarsened: true`).

**`document.inspect {measures?, inertia?}`** returns the shape shown further down with these differences: feature parameters are under `"params"` with a `"type"` field, in the document's own words (`keep_tool`, a feature by its number: `"target": 1`), and, with `{"named": true}`, where those differ, also under `"named"` in the commands' words (`keepTool`, a feature by its name: `"target": "Plate"`; since 2026-10-23, `params` unchanged for the agents that read it); a failed feature carries `"error"` (the reason: it starts with the parameter and names the feature and the name it lost) and, when the reason is that something it is made from failed, `"causedBy"` (the id of the feature at the start of that chain, the one to fix; `document.check` and the result of a feature command carry it too); bodies are listed per feature with `"feature"` and `"name"`, and carry a `"bbox"` taken from a tessellation (exact for flat-faced bodies, inside the true box by at most `"bboxTolerance"` for curved ones); `"history"` holds the undo and redo labels as arrays; `"path"`, `"dirty"`, `"ok"` and `"document"` (its index) are added. With `"measures": false` (2026-10-21; default `true`, the full answer as before) a body's entry leaves out everything that takes measuring the body: `volume`, `area`, `centroid`, `mass`, `massUnit`, `inertia`, `inertiaUnit`, `bbox` and `bboxTolerance`; the rest is the same, to the byte. The first measure of a body with a large spline face takes seconds (the Garabit valley's cut terrain: 8 s on 14 threads, 32 s before 2026-10-21); a measure is remembered per body, so asking again costs nothing until the body changes. That is the quick way for an agent to read the features, their status and the face names of a large model.

Three transports, one command registry:

| Transport | Process | Use |
|---|---|---|
| **Headless server** | `craft3d-cli serve` | Fastest way for a script or agent to make many edits; no window, no GPU |
| **Desktop control** | Allow AI agents, or `craft3d --control PORT [--control-token-file FILE]` | Drive and screenshot the running window while the person watches |
| **MCP** | `craft3d-cli mcp [--bridge [PORT] [--control-token-file FILE]]` | Agent clients: a session of its own, or bridged to the window |

## Envelope

Each request is one JSON line; each reply is one JSON line with the same `id`:

```json
{"id": 1, "method": "engine.execute", "params": {"command": "document.measure", "params": {}}}
{"id": 1, "ok": true, "result": { "volume": 8000.0, "unit": "mm^3" }, "ms": 0.4}
{"id": 2, "ok": false, "error": "unknown command `feature.extrud`; did you mean `feature.extrude`?", "ms": 0.0}
```

`ms` (an `engine.execute` reply only, ok or not) is the wall-clock milliseconds the command took (*Timings*, under *Engine*).

Errors are sentences an agent can act on: they name the command, the parameter and the entity involved. `params` of a command must be a JSON object (or omitted); anything else is an error in every transport.

## Authentication (TCP only)

The window's control port, the only TCP listener, binds `127.0.0.1` only, and is behind a token that is never on a command line. Without `--control-token-file` the window uses the default token file, `control.token` in 3DCraft's state folder (*Connecting an agent*); a script names its own:

```sh
craft3d --control 7878 --control-token-file /private/path/craft3d-control.token \
  --automation-read-root /work/project --automation-write-root /work/project
```

If the file does not exist it is created with a fresh 256-bit token (mode `0600` on Unix), whole: written to a temporary file and linked in under its name, so no reader sees half a token and two windows starting at once agree on the first one's. The first request on every connection must authenticate; nothing else is dispatched before it succeeds, and the token is compared in constant time (no early exit on the first wrong character):

```json
{"id": "auth", "method": "auth", "params": {"token": "<64 hexadecimal characters>", "client": "my script"}}
```

**The challenge** (2026-11-02; `crates/automation/src/proof.rs`). A client may open with `{"method": "challenge", "params": {"nonce": hex}}` (32 to 128 hexadecimal characters); the window answers `{nonce, pid, proof}` with a nonce of its own, its process id and `HMAC-SHA256(token, "3dcraft window\nport " + port + "\npid " + pid + "\n" + client nonce + "\n" + window nonce)`, the port being the one it listens on and the nonces in lower case; the client checks it with the port it connected to (and, when discovery named the window, its process), and then authenticates with `{"method": "auth", "params": {"proof": HMAC-SHA256(token, "3dcraft client\nport " + port + "\npid " + pid + "\n" + window nonce + "\n" + client nonce)}}` instead of the token. The port and the process in the proofs stop a relay: a program on another port that passes the client's challenge on to the real window gets a proof for the window's port, which does not pass where the client connected. The bridge always does this, checks the window's proof before it sends anything else, and never sends the token: a program that took the port learns nothing it can use. `auth {token}` still works, but **scripts should use the challenge too**: it never sends the token, and it tells a script that it reached the window and not something else on the port. A token file another user could read or change (Unix mode with group or other bits) or that belongs to another user (the process's own user on Linux, the owner of the home folder on macOS) is refused, by the window and by the bridge.

`client` (optional, at most 80 characters, none of them a control, direction or invisible character) names the client for the window's count of connected agents. A first line that fails to authenticate gets an error reply and the connection is closed; a first line that is an HTTP request line (`GET `, `POST `, `OPTIONS `, …, any case) is closed **without a reply and without reading further**, so a request body is never parsed, whatever it holds.

**Why the token, on a port that only this machine can reach.** The protocol is plain JSON lines. Without a token, any web page open in the person's browser could send a request to `http://127.0.0.1:7878` whose body is a JSON line (a cross-protocol request: a "simple" `POST` with `text/plain` needs no CORS preflight, and the browser sends it before it knows the answer is not HTTP) and drive 3DCraft, including writing files beneath the roots. With the token, such a request has nothing to authenticate with: a page cannot read the token file, the token is never in a URL, a log or what the start screen copies, and the HTTP request line is refused before its body. Programs of the same user can read the file; the guard is against the browser and other users, not against the person's own programs.

Stdio transports need no handshake: access is inherited from the process pipe.

## Connecting an agent

How a person connects an agent, with no flags and nothing secret to copy (2026-11-02; [`guide/install.md`](guide/install.md) › *Connect an AI agent over MCP*):

- **The switch and the pill.** *Allow AI agents* is in one panel, the same everywhere: the start screen's *Connect an AI agent* block, and the popover over the **agents pill**, which is at the right end of the status bar on the desktop (decision of 2026-11-02, board s3 of the UI overhaul; the kit's pill, `kit::PillState`). Its colour is its state: off, an outlined grey pill *Agents off*; on with nobody connected, an outlined indigo pill with a ring, *Waiting for an agent*; connected, filled indigo with the client's name (*Claude Code connected*, the `clientInfo.name` its MCP client gives in `initialize`, which the window reads from the `mcp.message` the bridge passes on), or *2 agents connected*; a question waiting, amber (*Claude Code asks for a folder*, *asks to write a file*, *asks to open a file*). While an agent runs a command its mark turns and the pill names it (*Claude Code · feature.edit*) for 1.5 s after the last one (a still mark where animations are off), so no agent acts unnoticed. A click on the pill opens the popover (`state.dialogs.agents`, also `ui.set {"dialogs": {"agents": true}}` and Help › *Connect an AI agent…*), a dark plate whose pointer points down at the pill; Escape or a click elsewhere closes it. Under *Connect* the panel offers *Copy command* (`claude mcp add 3dcraft -- … mcp --bridge`), *Copy MCP configuration* (the `mcpServers` JSON) and *Other clients*, a menu that copies a ready configuration for Claude Desktop or Cursor (`mcpServers`), VS Code (`servers` with `"type": "stdio"`) or any stdio client (`command` and `args`). In the browser there is no pill and no popover (agents drive the desktop app only); the start screen says so. **Off by default.** On, the window starts the listener in the running process (no restart); off, the listener stops, every connection is closed, the port is released, the discovery entry removed and the agents' roots taken back. The choices are remembered per user (`agents.json` in the state folder: `{"allowAgents": bool, "folder": path|null, "documentFolder": bool}`; anything unreadable reads as off, the default folder, the document's folder on) and honoured at the next start. `--control PORT` turns it on from the start for scripts, on that port only (an error when it is taken); the switch still turns it off for that run. `ui.get` reports it under `agents` (`{available, allowed, forced, port, connected, clients: [{name, sinceMs, lastCommand, lastMs}], workFolder, commandLine, documentFolder, roots: [{path, from, read, write}], error}`), **read-only**: `ui.set` refuses `agents`. Over the channel it would mean nothing or too much: off, there is no channel to set it on with; a request turning off the channel it came over, or widening its own roots, is the person's decision, not an agent's.
- **The state folder.** `3dcraft` in the per-user state directory, beside `recovery/` and `recent-files.json` (Linux `$XDG_STATE_HOME` or `~/.local/state`, macOS `~/Library/Application Support`, Windows `%LOCALAPPDATA%`); `--state-dir DIR` or `CRAFT3D_STATE_DIR` name another (for the window: also the default recovery directory and recent files). It holds `control.token` (the default token, 0600), `agents.json` and `windows/`.
- **Ports.** The switch listens on 7878, or the first free port of 7878 to 7897; when all are taken it says so (in the block and in `agents.error`) and stays off.
- **Discovery.** Each listening window that uses the default token file writes `windows/<pid>.json` (mode 0600, folder 0700, written whole): `{pid, port, tokenFile, focusedAt, startedAt}`, times in milliseconds since the Unix epoch. No secret: the token stays in its own file. It is rewritten when the window gets the focus and removed when it stops listening or closes. A window given a token file of its own (`--control-token-file`: a script's, a test's) writes none; it is reached with that file and its port, and the command its start screen and agents panel copy says so (`craft3d-cli mcp --bridge PORT --control-token-file FILE`, the file's absolute path, never the token; 2026-11-04: it named neither, and the bridge then said to turn on Allow AI agents although they were on). An entry whose process is gone (on Linux, checked in `/proc`) or whose port no longer accepts a connection is stale and removed by the next window that starts listening and by the bridge.
- **Which window the bridge takes** (`craft3d-cli mcp --bridge` without a token file): of the live entries (on the port given, when one is), the only one, else the one focused most recently. When none was focused later than the others it is an error that names them (`3DCraft (process 4242) on port 7878, …`) and says to click into the one to use, or to give its port; with none, the error says to turn on Allow AI agents. The window is chosen at the first message and kept while it answers; when it stops answering, the next message looks again. A port given without an entry for it is an error (since 2026-11-02: no token is offered to whatever listens on a port no window announced). An entry is live when its process runs, its port answers and, on Linux, the listening socket is that process's (`/proc/net/tcp` and the process's open files).
- **Files: the agents' roots** (2026-11-02). An agent the switch lets in may read and write files beneath, in this order (`ui.get` › `agents.roots`, each with `from`): the folder the person chose, `chosen` (*Change…* opens the system's folder picker; remembered; by default `Documents/3DCraft`, made when missing; *Open folder* shows it), or instead the roots the command line gave, `command line` (`--automation-read-root`, `--automation-write-root`: they win, and *Change…* is off); the folders the person allowed when asked, `allowed` (remembered, for all agents) or `session`; and the open document's folder, `document`, while *Also the open document's folder* is on (the default, remembered), **only for a document the person opened or saved themselves and made active themselves** (`Session::person_document_file`; a file an agent opened or wrote is also left out of the recent files, so opening it from there later grants nothing): never one an agent opened, saved elsewhere or made active (`file.open`, `file.save {path}`, `file.activate`, `recovery.open` while an agent acts), nor a recovered or unsaved one; it follows the active tab. Every one of these but the command line's passes the protected check below; one that fails it is left out (the panel says why for *Change…*). A relative path is beneath the first root; an absolute one beneath whichever holds it. Off takes them back. A command refused a path says the way out of the host it runs in (`craft3d_engine::FileHelp`, 2026-11-05): in the window, that the person gives agents a folder under Help › Connect an AI agent… › Work folder (*Change…*, *Also the open document's folder*), or, where the command line set the roots, that `--automation-read-root`/`--automation-write-root` set them; in `craft3d-cli serve`, `mcp` and `run`, "start it with a write root". A window `--control` opened gets the same roots when its command line gives none, and only the command line's when it does (2026-11-05: before, it got none, and *Change…* there did nothing). In the engine this is `Access::Roots` (several roots, `Access::from_roots`); containment stays strict in every root: no `..`, no absolute part, and since 2026-11-02 no symbolic link beneath a root that leads outside it (the deepest existing part of the path is resolved and must lie beneath the root's resolved spelling; a dangling link is refused too). A folder that cannot be made or used is said in the panel (`agents.error`), never a panic.
- **Asking the person** (2026-11-02; `apps/craft3d/src/consent.rs`). While the person's switch lets agents in (not in a window `--control` opened for a script), the window asks before an agent reaches a folder outside its roots, and only the person's click answers:
  - *When a client connects.* The bridge sends the folder its MCP client started it in (`auth`'s `cwd`: absolute, links resolved; Claude Code starts it in the project folder). Once per client and run, unless that folder is reachable already, protected, or spelled with a control, direction or invisible character, the window asks "*Claude Code wants to connect. It is working in this folder. 3DCraft can let it read and write files there, besides the work folder:*", the folder on a line of its own, with **Refuse** at the left, **Only the work folder** and **Allow this folder** (amber), and the box **Remember for this folder** (board s3, decision of 2026-11-02). **Only the work folder** refuses the folder (the answer `deny`): the agent stays connected with the work folder (and the document's) alone. **Refuse** (the answer `refuse`, decision of 2026-11-04) refuses the folder and disconnects that agent: its connection is closed and it is refused for the rest of the window's run, as *Disconnect all* does for every agent, and the questions it still had go with it. Allow this folder allows it for this run (`session`) or, with the box ticked, for every agent from now on (`folder`: remembered in `agents.json` › `folders`, listed in the panel as *Always* with *Remove*). Unanswered, the question goes after 10 minutes.
  - *When a command names a path outside every root* (`path` or `dir` of `file.open`, `file.save`, `file.export`, `file.import`, `view.render`, `view.replay`, `jig.export`, `ui.screenshot`, …, in `engine.execute`, `batch`, and the MCP tools `command_run`, `command_batch` and `control_call`): the request is held, the window keeps answering everything else, and the person is asked "*Claude Code asks to write a file*" (*to open a file* for a command that reads): "*file.export wants to write outside the folders it may use:*" with the path on a line of its own, escaped, and **Deny** at the left, **Allow this folder** (for all agents, remembered) and **Allow once** (amber: that one file, in that one direction, for that one request: `Access::Grant`, given to the request alone and taken back when it has run; later requests, other clients and the rest of a batch are asked again). Unanswered after 120 s, or denied, the command fails with a normal error (over MCP a tool error, `isError: true`): "*file.save: the person has not given access to `…`; ask them to confirm in the 3DCraft window*". The control channel waits 300 s for a reply and the bridge 330 s, both longer than the prompt. At most 32 questions wait at a time, 4 per client; more are refused with what to do.

A command that wants one is refused at once with the reason. A path with `..` or through a symbolic link is never offered either; the command fails with the engine's containment error.

To keep every agent out, turn the switch off.
- **What is copied.** *Copy command*: `claude mcp add 3dcraft -- <craft3d-cli> mcp --bridge`; *Copy MCP configuration*: `{"mcpServers": {"3dcraft": {"command": "<craft3d-cli>", "args": ["mcp", "--bridge"]}}}`. `<craft3d-cli>` is the absolute path of `craft3d-cli` beside the window's program when it is there, else its name; for the AppImage, the AppImage and `cli` first. No port, no token.

### Threat model

What each guard is for, and what it is not (2026-11-02):

- **Loopback only.** Nothing off the machine reaches the port.
- **The token** (256 bits, a file only its user can read). Keeps out what runs on the machine without that user's files: a web page in a browser (it cannot read the file; and an HTTP request line closes the connection before its body is read), another user's processes. It does not keep out the person's own programs: anything running as that user can read the file; that is the person's trust boundary, as for their other files.
- **The challenge.** Keeps the token itself off the socket: a program that took the port (another user's, a port reused after a window crashed) and pretends to be the window learns nothing, because the bridge sends nothing before the window proved it holds the token, for the very port the bridge connected to (a relay to a real window fails). On Linux a discovery entry is believed only when the 127.0.0.1 listener on its port is its process's own socket and nothing else listens on that port (`0.0.0.0` or IPv6); where that cannot be read the challenge still guards. A listener on `[::1]` or another address of the port is no concern, as it takes no 127.0.0.1 connection; `0.0.0.0`, dual-stack `[::]` and `::ffff:127.0.0.1` are. A window in a sandbox with its own process ids (Flatpak, a container with its own pid namespace) is refused by this check (its pid is not the host's); toolbox and distrobox share the host's and are fine. On Windows the token file's privacy rests on the access list of `%LOCALAPPDATA%` (its user alone); there is no mode to check. Off Linux the token file's owner is held to the owner of the home folder.
- **The switch.** Off, there is nothing to connect to at all. Its state is the person's; no request changes it.
- **The roots.** What an agent that is in can touch: its folders, nothing else; no `..`, no link out, the protected places never, the document's folder only when the person put it there.
- **The questions.** Let the person widen the roots one decision at a time, with the full path in front of them; answered only by a click in the window (no method answers them, an agent sees only its own), never in the first 0.7 s, never for a path spelled to mislead, never for a protected place.
- **Not covered:** an agent that is allowed in and misbehaves within its roots (the person sees each command it runs, in the status bar's pill and in the agent log, and can disconnect it, turn the switch off and undo); the person's own programs reading the token file.

## File access

Automation never gets ambient filesystem access. Paths in requests are relative to, or absolute beneath, an explicit **read root** and **write root** given at launch (`--automation-read-root`, `--automation-write-root`); the two are independent, and omitting one denies that direction. Parent traversal, paths outside the root and link escapes are rejected before any file effect. Interactive file pickers in the desktop app keep normal user-selected access.

How the window's own File menu fits in (`apps/craft3d/src/files.rs`): New, Open…, Save, Save As…, Import… (Ctrl+I), Export… (Ctrl+E), Export as Jig… and Open for editing are the commands `file.new`, `file.open`, `file.save`, `file.import`, `file.export`, `jig.export` and `jig.edit`, run by the application for the person at the window; under them the recent files and Close (`file.close`). For a file chosen in the system's dialog the application grants that one command access to the directory of the chosen file, in one direction (reading to open or import, writing to save or export), and restores the automation roots before anything else runs. Import… reads a STEP file into the active document (a new one when none is open, closed again when the file cannot be imported): one undo step, the file's bytes kept in the document, so a client inspects and edits the imported bodies without any access to the file. Export… opens the export dialog first (`crates/ui-egui/src/shell/dialogs.rs`; since 2026-10-27, before which the system's save dialog came first and the format was the extension typed in it): *What* goes into the file, *Format* (only those that hold it) and the options, then *Export…* opens the system's save dialog with that format's filter only, the document's name with the format's extension and the folder of the last export, and the file is written at once, its name given the format's extension when it has none or another format's (`part` → `part.stl`, `part.dxf` → `part.stl`; a corrected name that would replace a file the save dialog did not ask about is refused). *What*: **the model** (STEP and the mesh formats get every body; DXF and SVG a drawing of the model as seen, `file.export {view, projection, hidden}`: as in the viewport, the camera the window gave the session, or a named view; orthographic or perspective; hidden lines left out or dashed), **the selection** (`select.get`; offered when something is selected, chosen first when a format holds it: only bodies to STEP or a mesh, `bodies` by their features' ids; flat faces to DXF or SVG on one sheet, `faces`; one sketch, `sketch`; the body of one sheet-metal part or fold, its pattern; anything else is said with what it holds and no format is offered for it), **Sheet of set: …** (a named set's flat faces with a sheet width and a gap, `file.export {set, width, gap}`), **Flat pattern of …** (`sheetMetal`), **Crease pattern of …** (`fold`) and, with two parts or more, **Flat patterns of every part** (`sheetMetal: [..]` with width and gap); the sheet or pattern chosen last for a document is chosen first next time it still has it. Options: a mesh's quality (Coarse, Normal, Fine: `file.export {quality}`), a drawing's view, projection and hidden lines, a sheet's width and gap; the format and options chosen last are offered again, kept only once a file was written (a cancel, in the export dialog or the save dialog, or a failed export changes nothing). The selection is read when *Export…* is clicked: `file.export`'s parameters are made then, so a selection changed while the save dialog is open does not change the file, and *the selection* with nothing selected is refused. Never something else exported in its place. In the browser the same dialog makes the file and then downloads it or asks with the browser's save dialog; without file dialogs it asks the file's name itself. `ui.set {"export": {open, what, format, quality, drawing, width, gap, name}}` drives it (`state.export`; `what` is `"model"`, `"selection"`, `{"set": name}`, `{"sheetMetal": part}`, `{"fold": fold}` or `"everyPart"`; what the document does not offer, or a format that cannot hold it, is refused and nothing changes, not even the rest of the request; set while it is closed, `what`, `width`, `gap` and `name` are what the next opening chooses, `what` when the document offers it) and `ui.get` › `export` lists what it offers (`{whats: [{what, label, formats}], problem, namesFile, file}`, null while it is closed). A failed Open, Save, Save As, Import, Export, New or example the person started opens an error dialog with OK and *Copy details*; both dialogs are modal and take Enter and Escape first; an agent's failures stay in the status bar and its reply. A client draws a view with `file.export {path, view, projection, hidden}` ([`file-formats.md`](file-formats.md) › *Projected views*); `view: "current"` is the window's camera when the request reaches the window. These two have no method of their own either: a client imports and exports with `file.import` and `file.export` beneath its roots, which take the same parameters. Requests are answered on the same thread, one at a time, so no request ever runs under the grant, and there is no method, parameter or tool that asks for it. What follows for a client: a document the person opened from outside the roots is the active document like any other and can be inspected and edited over the channel, but `file.save` without a `path` is refused for it (its own path is outside the write root); save a copy with a `path` beneath the write root. A file named on the window's command line by a path relative to the working directory is kept by its absolute path (as `file.list` and the tabs show it), so when it lies beneath the write root `file.save` without a `path` writes it back (before 2026-10-15 the relative path was taken again beneath the root). When pointer and key replay arrive (`ui.pointer`, `ui.key`), they must not be able to reach the File menu's dialogs.

### Pictures without a window: `view.render` and `view.replay` (commands)

- `view.render {path?, width? = 800, height? = 600, view?, projection?, zoom?, box?, mode?, section?, tolerance?, background?, look?, analysis?, renderer?}` draws the bodies: PNG to `path` under the write root, else returned. `projection` is `perspective` (default) or `orthographic` (lengths across the view to scale); `box` is two opposite corners `[[x, y, z], [x, y, z]]` in document units, framed instead of the whole model and seen from outside the model; `zoom` (0.01 to 1000) magnifies about the centre of the picture; `mode` `ids` draws one flat colour per face with a legend; `section` cuts the picture open (*The section plane*, above). On the light viewport background since 2026-10-23 (`background: "dark"` keeps the old one). Since 2026-10-15 without `tolerance` the bodies are meshed for the picture: the chordal tolerance is `floor · 2^⌊log2(f / floor)⌋`, the coarsest of the floor times a power of two that is at most `f`, half the model units a pixel covers where the picture shows the model nearest (the point of the bodies' box nearest the eye, for the camera the picture is framed with): so between a quarter and half a pixel, and a larger picture, a `zoom` or a close-up `box` is finer. The floor is 2e-4 of the diagonal of the box around the bodies. The display's 12 degrees per chord hold, and the scene is coarsened by the display's ladder until it has at most a million triangles and every body is within what the tessellator can do (`coarsened` then). The same parameters give the same picture, whatever the window has built. With `tolerance`, at that chordal tolerance alone. The result repeats `projection`, `zoom` and the `box` given, or else the model's box: the drawn mesh's box grown by the picture's `tolerance` and kept within what the faces hold, so it holds the model and is not loose on a face on a spline (2026-11-05), and says `tolerance`, `maxAngle` (degrees, `null` with a tolerance given) and `coarsened`. Hidden features (`feature.visible`) are left out and a scrubbed view (`view.scrub`) is followed. MCP's `doc_render_preview` is the same picture. **Which renderer** (2026-10-30): `renderer` is `auto` (the default), `cpu` or `gpu`. `craft3d-cli` and `craft3d-cli serve`/`mcp` give their sessions the wgpu renderer on an offscreen device of their own (made at the first picture, no window, no surface); `auto` draws on it and falls back to the CPU renderer when there is no adapter or the device fails, `gpu` refuses then, `cpu` draws with the CPU reference renderer, the oracle the GPU is held to (parity: [`design/rendering.md`](design/rendering.md) › *Headless GPU*). The window's control port and the browser draw these pictures on the CPU (their sessions have no headless renderer: `gpu` is refused there). The result says `renderer` (`gpu` or `cpu`; for a replay `mixed` when the GPU failed part-way and the CPU drew the rest, with `pictures {gpu, cpu}` and `cpuAccumulate` when the CPU averaged fewer frames per studio still), `adapter` when the GPU drew, and `rendererFallback`, why `auto` drew on the CPU. `mode: "ids"` is always drawn on the CPU (its pixels are read by machine). On the GPU a studio still averages up to 256 frames at any size; the CPU's limit of 2^26 samples stays the CPU's.
- `view.replay {dir, width?, height?, view?, projection?, zoom?, box?, tolerance?, from?, to?, every?, framesPerStep?, hold?, orbit?, fps?}` (2026-10-14): a showcase of how the document is built. The rollback marker is stepped from nothing through the history (from `from` to `to`, default all of it up to the document's own marker), and every step that changes a body (`every: true`: every step) is drawn as `view.render` draws it, from one camera framed on the model at `to`; `orbit` turns that camera so many degrees about the vertical over the whole replay. Writes `dir/frame-00000.png`, … under the write root (frames of an earlier, longer replay there are removed) and `dir/captions.srt`, a subtitle per shown step (`Step 3/42 · Extrude2 · extrude`, the caption the window's history player shows, timed at `fps`). The start and each shown step get `framesPerStep` frames, the last one `hold` more. Without an orbit the last frame is the `view.render` picture of the document with the same parameters, to the byte. The document does not change: the steps are regenerated on a copy, from a copy of its regeneration cache, and its marker, revision, undo history and dirty flag stay as they were, also when the replay fails. At most 3600 frames and 8e9 pixels. Returns `{dir, frames, framePattern, fps, width, height, view, orbit, box, shownSteps, steps: [{feature, name, type, status, frames: [first, last] or null, caption}], captions}`. Not in the browser build (it writes files). Video: `craft3d-cli replay` ([`development.md`](development.md) › *A showcase video*).
- **`view.replay` as an animation renderer** (2026-10-30). Every replay also takes `look` and `background` (those of `view.render`; a studio frame averages `look.accumulate` frames, 16 when not given, the window's settled count), `renderer` (as `view.render`'s; on the GPU the frames are drawn one at a time and their PNGs written on every core), `camera` (`{keys: [{t, eye?, target?, up?, fov?}], orbit?, dolly?, easing?}`: the camera passes through the keys, `t` from 0 at the first frame to 1 at the last, on a Catmull-Rom spline, the fields a key leaves out the framed camera's; `orbit` degrees about the vertical, the same as the top-level `orbit`, not both; `dolly` the distance at the end over the one at the start; `easing` `linear`, `in`, `out` or `inOut`) and `video` (a path under the write root ending in `.mp4`, `.webm` or `.gif`, made of the frames by an external `ffmpeg` in a session whose host has an encoder, `craft3d-cli` and its `serve`/`mcp`; refused before a frame is drawn when ffmpeg is missing, with the PNG sequence of `dir` alone as the alternative; the result then has `video` and `captionsTrack`). `animate: [{variable, from, to} | {variable, keys: [{t, value}]}, unit?, easing?}]` renders an animation instead of the history: `frames` states (or `duration` seconds at `fps`; 2 s by default), each the document with every track's variable at its value there (written with `unit`, which must keep the variable's dimension), regenerated from the document's regeneration cache so only what the variables touch is rebuilt; a track of the timeline `t` plays the motion as `view.motion` does (an assembly's only track); `[]` animates the camera alone. Captions give each frame's values; the result has `animate: {tracks: [{variable, from, to, timeline?}], states, failed: [{frame, failed: [feature]}]}`. `from`, `to`, `every`, `framesPerStep` and `motion` do not go with `animate`, `frames` and `duration` go only with it. The document does not change. Example: `view.replay {"dir": "sweep", "width": 1920, "height": 1080, "duration": 4, "fps": 30, "look": {}, "animate": [{"variable": "width", "from": 30, "to": 60, "unit": "mm", "easing": "inOut"}], "camera": {"orbit": 40}, "video": "sweep.mp4"}`.
- **Settling** (2026-10-30): the studio look's viewport averages `look.accumulate` frames while the camera stands still (16 unless set); `ui.set {"look": {"accumulate": n}}` sets that count over the control channel, and `ui.screenshot {window: true}` waits for it (within 8 seconds).

## What `document.inspect` returns

The contract that lets an agent verify its work without a picture (`document.inspect {measures? = true, named? = false}`; MCP's `doc_inspect` is the same with the defaults):

```json
{
  "document": 0, "path": "/work/plate.3dcraft", "dirty": false, "ok": true,
  "units": {"length": "mm", "angle": "deg"},
  "tolerance": {"linear": 1e-6, "angular": 1e-9},
  "variables": [{"name": "width", "expr": "40 mm", "value": 40.0, "dimension": "length", "lengthUnit": "mm"}],
  "features": [
    {"id": "F1", "name": "Sketch1", "suppressed": false, "status": "ok", "dof": 0, "params": {"type": "sketch", "...": "..."}},
    {"id": "F2", "name": "Extrude1", "suppressed": false, "status": "ok", "params": {"type": "extrude", "sketch": 1, "distance": "10 mm"}},
    {"id": "F3", "name": "Fillet1", "suppressed": false, "status": "failed",
     "params": {"type": "fillet", "...": "..."},
     "error": "edges.0: ... no longer exists ..."}
  ],
  "rollback": null,
  "bodies": [
    {"feature": "F2", "name": "Extrude1", "kind": "solid", "valid": true, "faces": 6, "edges": 12, "vertices": 8, "shells": 1,
     "volume": 8000.0, "area": 2800.0, "centroid": [20.0, 10.0, 5.0],
     "faceNames": ["F2:startCap()", "..."], "bbox": [[0, 0, 0], [40, 20, 10]], "bboxTolerance": 0.0}
  ],
  "history": {"undo": ["Add sketch", "..."], "redo": []}
}
```

Feature parameters are under `"params"` with a `"type"` field, in the document's own words (`keep_tool`, a feature by its number: `"target": 1`), and, with `{"named": true}`, where those differ, also under `"named"` in the commands' words (`keepTool`, a feature by its name: `"target": "Plate"`; since 2026-10-23). A failed feature carries `"error"` (the reason: it starts with the parameter and names the feature and the name it lost) and, when the reason is that something it is made from failed, `"causedBy"` (the id of the feature at the start of that chain, the one to fix; `document.check` and the result of a feature command carry it too). Also per feature where they apply: `hidden` (`feature.visible`), `passesOn` and `passesNothing` (a suppressed or inactive feature: whose body it hands on, or why it hands on none), `bodyUsedBy`, `followed` (its parameters with the full names it followed), `dof` (a sketch), `datum`, `path` (a sweep), `thread`, `offset`. A variable that is a public parameter has `public`; an angle variable `angleUnit` and `degrees`; one with a doubtful expression a `warning`. Bodies are listed per feature with `"feature"` and `"name"`, and carry a `"bbox"` taken from a tessellation (exact for flat-faced bodies, inside the true box by at most `"bboxTolerance"` for curved ones), `faceAliases`, and with a colour or a material `appearance`, `material`, `mass` and `inertia` (*A colour and a material per body*, above). The document may add `info` (`document.info`), `sets`, `faceAppearances`, `lostFaces` and `assertions`. With `"inertia": false` (2026-11-05; `document.inspect` and `document.measure`) the bodies are measured but their inertia is left out and not integrated, the mass being the volume times the density (the window's Bodies tab and Properties card ask this way: on a large spline body the inertia took seconds after every undo). With `"measures": false` (2026-10-21) a body's entry leaves out everything that takes measuring the body: `volume`, `area`, `centroid`, `mass`, `massUnit`, `inertia`, `inertiaUnit`, `bbox` and `bboxTolerance`; the rest is the same, to the byte. The first measure of a body with a large spline face takes seconds (the Garabit valley's cut terrain: 8 s on 14 threads); a measure is remembered per body, so asking again costs nothing until the body changes. That is the quick way for an agent to read the features, their status and the face names of a large model. Edges and vertices are listed by `document.edges`, tables by `table.list`, public parameters as a form shows them by `param.list`. Field names are part of the protocol: changing one is a breaking change recorded in this document.

Two short forms save an agent a round trip (2026-10-22, from the R1 acceptance): wherever a face is named, `F2:startCap()` and `F2:endCap()` name the cap of that role of feature `F2` without spelling out its outline ([`design/names.md`](design/names.md) › *The short form of a cap, everywhere*); and a sketch point given as `[x, y]` with an expression in it (`["-width / 2", 0]`) is held there by `x` and `y` constraints, so a profile is drawn on variables in one command (`sketch.rect`, `sketch.polyline`, `sketch.path`; [`design/document.md`](design/document.md) › *Sketch coordinates as expressions*).

## MCP

`craft3d-cli mcp` serves MCP on stdio; with `--bridge` it passes every message to a running window instead (*MCP bridge*, above). Tool names use underscores (the dotted names belong to the JSON protocol above).

| Tool | Arguments | Notes |
|---|---|---|
| `command_list` | `brief?`, `id?`, `filter?`, `enabled_only?` | The commands with params notation, summary and `enabled`/`disabledReason`; `brief` and `id` as `engine.commands` has them (the tool's description and the server's instructions tell agents to start with `brief: true`) |
| `command_run` | `id`, `params?` | One command; a refused command is a tool error (`isError: true`) whose message starts with the command's id; the tool result's `_meta.ms` is the milliseconds it took |
| `command_batch` | `steps: [{id, params?}]` (at most 256), `stop_on_error? = true`, `stop_on_break? = false`, `terse? = false` | As the method `batch` (judged at the end: `isError` when a command failed or `featuresFailed` is not empty; `ms` per step and in all); not atomic |
| `doc_inspect` | none | `document.inspect` with its defaults; `{"document": null}` when nothing is open |
| `doc_render_preview` | `view?`, `mode?` (`shaded`, `ids`), `projection?`, `zoom?`, `box?`, `tolerance?`, `max_side?` (16 to 2048, default 1024) | A PNG (4:3, drawn as `view.render` draws it: by the GPU in a `craft3d-cli` session that has an adapter, by the CPU renderer otherwise and through a window) as an image block, and the coverage, triangle count and bodies as text |
| `selection_get` | none | The selection as `select.get` gives it, also what the person clicked in the window when bridged |
| `control_call` (bridged only) | `method`, `params?` | A `ui.*` method of the window but `ui.quit`; a picture comes back as an image block |

The resource `craft3d://selection` (`resources/list`, `resources/read`) is the same JSON as `selection_get`. *(planned)* Resources for the document and the commands, background jobs.

**A failed feature is not a tool error** (by design: the command did what was asked, the feature is in the history). The result of a feature command carries the feature's own `status`, `error` and `causedBy`; the result of an edit that can make *other* features fail (`variable.set`, `variable.delete` with `force`, `feature.edit`, `feature.suppress`, `feature.when`, `feature.move`, `feature.delete`, `history.rollback`, `param.set`, `table.set`; 2026-10-22; and every command that changes an existing sketch: `sketch.point`, `sketch.line`, `sketch.polyline`, `sketch.rect`, `sketch.circle`, `sketch.arc`, `sketch.spline`, `sketch.curve`, `sketch.path`, `sketch.pattern`, `sketch.constrain`, `sketch.edit`, `sketch.delete`, where the sketch itself carries its own status; 2026-10-22) carries `failed: [{feature, id, error, causedBy?}]`, the features that fail after the change and did not before it (other than the feature the result is about), left out when there are none. On a host that regenerates a piece at a time between its frames (the web page, `Session::set_stepwise`; 2026-10-27) the edits that do not regenerate the document themselves, `param.set`, `table.set`, `table.delete`, `variable.delete`, `feature.delete` and `history.rollback`, leave the regeneration to the frames after the command: their result leaves out `failed` and `assertions` and says `deferred: true` instead, and the window shows both once the document is regenerated. The other edits that report `failed`, `variable.set`, `feature.edit` and every other feature or sketch command, regenerate in the command (their result gives the variable's value or the feature's own status, which only a regeneration knows), so they never return `deferred` for a part; an assembly's `variable.set` there is the exception: its instances are placed by the frames after it (on the page, by its worker), so without `wait` its result says `deferred: true` (2026-11-04). They regenerate the state before the edit too when the pieces have not got to it yet, so that what failed already is not reported as made to fail. Given `wait: true` (`param.set`, `variable.set`) a command regenerates and measures every assertion there and then all the same (on such a host without the 60 s ceiling: the page has no clock to stop by): its result has `failed` and the final `assertions`, never `deferred`. `variable.delete` refuses a variable still in use, naming every user (variables, features and sketches with the parameters, assertions, named sets, conditions); `force: true` deletes it anyway and the result lists them under `usedBy`.

Conventions (from PhotoCraft's MCP server): unknown tool arguments return JSON-RPC `-32602` naming the key, before execution; tool failures return `isError: true`, with a message that starts with the command's id (`file.save: `/x.3dcraft` is outside the write root …`, also for what the file roots refuse; 2026-10-22); a worker panic becomes a tool error and the session keeps serving; invalid JSON lines get `-32700` with `id: null` and the next line is still processed. Recover from a failed batch by inspecting, then `edit.undo` once per applied step.

## Limits

Enforced before dispatch, so a hostile or mistaken request cannot exhaust the process:

- 1 MiB maximum request line; 8 MiB maximum reply
- at most 16 simultaneous connections on the window's control port; a connection silent for 30 seconds is closed
- at most 256 steps per batch
- previews: 16 to 2048 px on the long side; PNG at most 5 MiB
- a mesh export of more than 20 million triangles is refused (choose a coarser quality); pictures are meshed within a million triangles, coarsened when needed

A request over a limit gets an error reply; the session and its documents keep serving.
