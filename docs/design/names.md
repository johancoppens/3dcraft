# 3DCraft design: Persistent names

Persistent names of faces, edges and vertices: how they are made (`regen` from the kernel's origins, `regen/src/entity.rs`), stored (`doc::PersistentName`, `doc/src/name.rs`), followed (`regen/src/follow.rs`) and resolved. Rule 6 of the map ([`../architecture.md`](../architecture.md) §1).

## Method

**A name says how an entity was made, never where it sits in a body.** Every kernel operation reports an origin for every entity of its result; `regen` turns origins into names, three ways:

- *By role and source*, for what a feature makes: `F3:face(1)` for a primitive (its entities are made in a fixed order), `F2:side(e7)`, `F2:endCap(e5,e6,e7,e8)`, `F2:lateralEdge(e5,e6)` for a sweep (the sketch entities involved; `piece(k)/` for the further pieces of one source; `e7[3]` for instance 3 of a pattern of `e7` inside the sketch, `e7[2,5]` in a grid, and in a cap's name `e7[*]` for every instance at once; `e3[2][1]` for instance 2 of the inner pattern in instance 1 of the outer one, an index per level innermost first), `F9:fillet(k)`, `F9:chamfer(k,i)`, `F9:thread(0)` for what a blend or a thread adds.
- *As a copy*, for what a feature takes over from a body: `F7:copy(1)/F3:side(e2)` is the image in instance 1 (a boolean's tool, a pattern's instance) of what F3 called `side(e2)`. A name has one link per *run* of instance 0 or of other instances along the way, so it does not grow with a row of cuts (`copy(0)` through a thousand features); a run of instance 0 that ends in a name that is no copy is left out after other instances as it is at the start, so every instance names a face of its seed alike (*Every instance named alike* below).
- *By faces*, for edges and vertices of a body a boolean or a joined pattern made: `F7:between[a,b]` and `F7:corner[a,b,c]`, with faces near it after `|` when several entities lie on the same faces, and a number by position in space only when no face tells them apart. An entity an operand already had also answers to its old name as an alias; a merged face answers to the names of every face it was merged from. Stored as the ranks of the faces each lists and its number, the name itself made when asked for (`Names::edge_name`); a copy's entities are stored as the source's names and the instance (*What the names of a body cost* below).

**Resolution.** At every regeneration a reference is found again against the results so far: the feature must exist, come earlier, have succeeded and have an entity with that name or alias. The outcome is one entity, several (a face cut in pieces shares its name: accepted where the pieces lie on one surface, as for a sketch's plane), or none, which fails the referring feature with the name and the names that are there; a name never resolves to a different entity. A cap's name survives a change of its outline, since all caps of one role lie in one plane. Edges are referred to by the pair of faces they lie between wherever a feature takes them (chamfers, fillets, datums), which survives what an edge's own name does not.

**Following a body.** A feature that takes the body it works on (a blend, a face operation, a thread) may name faces as an earlier body of the same chain had them; each name is followed through the features that took that body, copy by copy, to its newest form, and the feature is built from the full names. What cannot be followed (gone, or several copies) fails the feature and says why. References that do not take the body (a sketch on a face, an extrusion up to a face, a datum) keep meaning the face of the body they name.

**Where stability cannot be had** (stated, not hidden): a numbered name follows position, so an edit that reorders tied entities moves the number; an alias follows the kernel's choice where entities of both operands coincide; a name with faces after `|` is lost when those faces change. Each is in the findings below.

## Findings and history

**Every instance named alike (2026-10-21, the Perseverance's finding; an R1 blocker).** After a pattern `F4` of a chamfered seed (`F3`, a chamfer of the fin `F2`), instance 0 was named `F4:copy(0)/F2:face(2)` (the run of instance 0, `F4:copy(0)/F3:copy(0)`, is one link) but instance 3 `F4:copy(3)/F3:copy(0)/F2:face(2)`: a chamfer put on the seed or taken off renamed every instance but the first, so a fillet on instance 3 failed (`Missing`) after an upstream edit that leaves its fin where it was. *Rule, by construction:* in `PersistentName::copy` a link of other instances followed by a run of instance 0 that ends in a name that is no copy (or one listing faces) takes that run in, as a run of instance 0 at the start does: `F4:copy(3)/F2:face(2)` whatever took the seed's body between `F2` and `F4`, and `F5:copy(1,3)/F2:face(2)` through a union's tool. Before a copy of another instance the run stays a link (`F9:copy(1)/F8:copy(0)/F7:copy(2)/…`), since taking it in there would read two different ways through a pattern of a pattern as one (`F9:copy(1,2)/…` is instance 2 of `F8`, not of `F7`). *Reading:* `follow::steps` and the colour's walk (`appearance`) go on through instance 0 after the instances listed until they reach the feature of the name after `/`; a name in the old form (a file, a steps file) is read in the new one by `canonical`, so it resolves to the same entity (the action matrix's ratchet, which compares names as text, was rewritten into the new form entity for entity); no format version (the meaning of no stored name changes). *Unique:* the body a copy is made from names its entities with its own feature first, so taking in the run never makes two of its names one. *Stated limit:* the run between two links of other instances (a pattern of a chamfered pattern) still names the features in it, so a chamfer put between two patterns renames the instances of the outer one beyond its first. Held to by `crates/doc/src/name.rs` › `every_instance_names_a_face_of_its_seed_alike` and `crates/engine/tests/pattern_seed_names.rs` (a fillet on instance 0, 3 and 6 of eight fins round a rod, located by the angle of the material it adds, through a chamfer put on the seed, its size changed and the chamfer deleted again, at three scales; every instance's faces named alike, no link for the chamfer).


**Splits (2026-10-20, format 24).** `body.split` turns a body of several lumps into one body per lump: one split feature per lump (`doc::Split`, `regen/src/split.rs`), added together as one undo step, which take the source's body together (a body taken by a split is open to every split of it: `derive::source_body_shared`). *Which lump a split is* is said by a face, never by the order of the shells (which the kernel's sewing sets and an upstream edit may change): the lump that holds a piece of the face `face`, resolved by name or alias at every regeneration. The command picks, per lump, the least name (in the order names compare in) among the faces whose every piece lies in that lump: the bottom of a block for the piece below a cut, the top for the piece above, the slab's two faces for the two caps of a ball. When no face is a lump's own (a ring cut in two crescents by a tube that swallows it twice: the ring's one wall and the tube's one wall each have a piece in both) the least name among its faces is taken with a *number* among the lumps that hold that face, by where they lie in space (`entity::sort_in_space` of the centre of each lump's volume: by x, then y, then z, coordinates within the tolerance as one), the one rule entities that no face tells apart are numbered by, with the same stated limit: an edit that moves the lumps past each other moves the number. A split fails, never lands on another lump, when its face is gone, when a face without a number has pieces in several lumps now (the cut turned so it crosses the face), when a numbered face lies in one lump, or in fewer than the number counts to, and when the lump it names is the body of an earlier split of the same source already (the pieces grew together, or the body is one lump now): the first split of a merged lump is that lump, grown, as a face cut in pieces is still the face, and every later one fails with "split it again". *Every lump is some split's* (reviewed 2026-10-20): a lump no split of the group names (an upstream edit made one more lump, a split was deleted or suppressed) fails the last built split of the group ("`Cut` has 3 lumps and 2 of them are split; the lump holding … is no split's: split `Cut` again to add it"), so no material goes missing in silence; `body.split` on a body its own splits took adds splits for the lumps that have none (`split_plan`), and refuses a body that is split already, naming its splits. `document.inspect` lists all the splits a body went into under `bodyUsedBy` (`"F5, F6"`). Each split's result depends on the other splits of its body (which they are, whether they are built, which lump each names): the cache keeps that as part of the split's context (`cache::Context::group`), and lists the earlier splits among what a split is made from (`cache::Lookup::inputs`). Two lumps whose volume centres lie within the tolerance of each other (one in the other's cavity, pieces symmetric about a point) are not numbered: refused with the reason, never ordered by the shells (`split::in_space`, its unit test). *Names:* the pieces of a face in one lump are copies, `F4:copy(0)/F1:face(2)` for the piece in the lump of `F4` of the top a cut left in two (the short form of `F4:copy(0)/F3:copy(0)/F1:face(2)`), the cut face `F4:copy(0)/F3:copy(1)/F2:face(0)`; edges and vertices are copies too, kept as the source has them and made when asked for (`entity::Entities::Picked`: some of another body's entities, each the copy of the one it is). Nothing is new in the grammar of names. *Following:* a name of the source is followed through the splits of it as through the instances of one taker: to the one split that has the face (`F1:face(1)`, the top, to the upper piece), or it fails listing the splits that do (`F1:face(2)`, a side with a piece in each: "more than one face after the splits Lower, Upper … give one of these names"); the blend and face-operation commands check that faces are of one body by where each name follows to. *Not had:* a lump identified without any face (a split of a body that does not name its faces fails), and the number's stated limit above. Held to by `crates/engine/tests/body_split.rs` (a cut that fell apart, a cavity that stays with its lump, the caps of a ball turned off-axis, the crescents of a ring, a fillet on a piece through the slab moving and the block turned upside down, a pattern's instances with the step reversed, the refusals, save and reopen, undo) at 1e-3, 1 and 1e6, and `crates/format/tests/format.rs` (format 24).

**Sheets (2026-10-18, format 22).** A fill's entities are named as the start cap of an extrusion of the same profiles: the face `F5:startCap(e1,e2,e3,e4)` (the curves of its outer loop, runs of a sketch pattern collapsed to `e7[*]`), its edges `F5:startEdge(e2)`, its vertices `F5:startVertex(e1,e2)`; an offset's curves name them as they name an extrusion's cap. No role is new. Through a boolean the pieces of a sheet's face are copies like any tool's (`F7:copy(1)/F5:startCap(…)` for the face where a solid is cut, `F7:copy(0)/F5:startCap(…)` for what a trim keeps); where one face of the sheet leaves several pieces (the cut faces in two lumps of a solid the sheet crosses, the pieces a trim leaves of one face), they share one name, by the rule for a face cut in pieces.

**Curves of nested sketch patterns (2026-10-17, format 21).** A curve made by nested sketch patterns has an index per level, the innermost first, and a trailing level at instance 0 is left out: `e3[2][1]` is tab 2 of cell 1, `e3[2]` the same tab in cell 0, `e3[0][1]` the seed's image in cell 1, `e5[1][2,4]` slot 1 of cell (2,4). So wrapping a pattern in a new outer one renames nothing (cell 0 is the old pattern), unwrapping keeps the names of cell 0 and makes the others fail (`Missing`), and a count change on either level keeps every name on the instance of the same origin (`k` 2 -> 3 adds `e3[2][i]` in every cell; 3 -> 2 removes exactly those, and a reference to one fails naming it). An outer-first form would rename every curve of a pattern at the moment it is wrapped. *Caps* collapse one level at a time, the innermost first: a loop that holds every instance of `e3` on every level names it `e3[*]` (the rib edge, whatever `k` and `n`); one that holds every inner instance of one cell (a profile per cell) `e3[*][1]` (in cell 0 `e3[*]`); "every" is every instance there is, so skipped instances change no cap name. The cap of cell 0 of separate cells and the cap of a whole run are both `e3[*]`: when cells start to touch and join into one loop, the one name moves from cell 0's cap to the joined cap (the class of a row at count 1, whose seed's cap and whole run share `e7[*]` for a chained run). *Data* (`doc::CurvePath`): the first number is the curve as before (its index in the innermost level; `At(0)` when there are outer levels and it is 0), followed by one continuation word per outer level: bits 32 to 47 zero, the tag 5 (one direction) or 6 (a grid) from bit 48 (the tags of `OffsetHead` are 1 to 4, so no number is read as two things), and `i + 1` (`0xFFFF` for `*`), or `i + 1` and `j + 1` from bit 16, in the low 32 bits. Every reader of a name's sources reads a curve with its continuation words (`doc::curve_groups`: the text, the offset groups, `check`, which refuses a continuation word that follows no curve and a path not in the one form names keep); curves of a cap are kept word by word in order (`doc::sort_curves`), which for curves without nesting is the order of their numbers, so a name without nesting has the numbers and the text it always had (`craft3d-cli info` of the 24 showcase files and the working files is byte for byte what it was). *The kernel's numbers:* the kernel takes a curve id as one number; a curve whose name takes more than one word gets a sketch-local number with bit 63 set, dense in the order of the names (`regen::CurveIds`, kept in the sketch's result), and the namers of extrusions, revolutions, sweeps and offsets turn it into its words (faces, edges and vertices alike), as error messages do (`e3[2][1] and e5[2][1] cross`). *Not had:* a level inserted between two (an un-wrap and re-wrap makes `e3[k][i]` mean the middle level's `i`: the known limit of names by origin when a seed moves between patterns), a persistent "last cell".

**Curves of an offset (2026-10-16, format 19).** What a sweep makes of an offset of a sketch's profiles (`feature.offsetProfile`, [`document.md`](document.md)) is named after the offset's curves, which are named after the feature that made them and the sketch curves they come from: `F10:side(F9:offset(e7))` the face swept by the offset of `e7` (`e7[3]` for an instance of a pattern, so a face keeps its name when the count changes, as the instance's own does), `F10:side(F9:offsetCorner(e7,e8))` the face swept by the arc or mitre the offset put at the corner where `e7` runs into `e8` (in the direction the loop runs), `F10:side(F9:offsetExtension(e7,e8))` the straight piece a sharp corner carries the arc `e7` on by to its mitre with `e8`, `F10:side(F9:loop(e1,e2,e7)/F9:offset(e7))` one of the pieces one curve left in several loops (a region split), named by the curves of the loop it closes (never by an order along the curve, which moves to another region as the distance changes; pieces in loops of the same curves have the same name, and a reference to it resolves to all of them, by the rule for a face cut in pieces), and edges and vertices likewise (`F10:lateralEdge(F9:offset(e7),F9:offsetCorner(e7,e8))`). A cap is named after the sketch curves whose offset its loop is, one offset, runs collapsed as for a sketch: `F10:endCap(F9:offset(e1,e2,e7[*]))`, so it keeps its name when a corner comes or goes (round or sharp, a distance through zero), when an arc of the outline vanishes, and when a pattern's count changes. *Data:* no new field. In `sources` an offset curve is a head number followed by the curves it names (`doc::OffsetHead`): the feature in the low 32 bits, 0 in bits 32 to 47 and the kind from bit 48 (offset, corner, extension, or loop, which qualifies the group after it), a number no `CurveRef` encodes to, so a name without offsets has the numbers and the text it always had, and a head is never read as a curve. The sources of a name are all curves of a sketch or all offset curves (a head before each), never mixed; an offset and a loop name at least one curve, a corner and an extension two, and a loop is followed by the curve it qualifies (`doc::offset_groups`, in `check` and when reading text). The kernel numbers the offset's curves from 0; `regen::offset_profile::rename` turns them into these names for extrusions, revolutions and sweeps. *Not had:* the corner's name says which two curves meet, so a corner that comes or goes with the distance's sign (a convex corner of the material gets a joint outward, a concave one inward) makes or removes a face of that name, never renames another.

**Instances of a pattern inside a sketch (2026-10-16, format 18).** A curve a sketch pattern makes is named by its seed entity and its instance index from the seed: `e7[3]`, `e7[2,5]` in a grid; the seed keeps `e7`, so patterning an existing outline renames nothing, and every name a sweep gives follows (`F2:side(e7[3])`, `F2:lateralEdge(e7[3],e8[3])`). The index is the instance's origin, never its place in a loop: a count from 5 to 7 keeps `e7[0..4]` on the same instances and adds `e7[5]` and `e7[6]`; from 7 to 5 exactly those two go, and a reference to one fails with the names there are (it is the existing `Missing` path), never landing on another instance; the count back repairs it. *Caps:* a cap is named after the curves of its outer loop, which would change with every count; where the loop holds every instance of a seed curve (a chained run, a ring of teeth; a chained run of one instance too) the curve is named once, `e7[*]`, so the cap keeps its name whatever the count (`regen::collapse_runs`, for extrusions, revolutions, sweeps and the first and last section of a loft). Separate instances (discs, each its own profile) are never collapsed, not even at one instance: the seed's cap is `endCap(e2)` at every count, the others `endCap(e2[1])` and so on. *Data:* the source stays one `u64` (`doc::CurveRef`): the entity id in the low 32 bits (a sketch gives out ids below 2^32 now), the first index plus one from bit 32, the second plus one from bit 48, `0xFFFF` from bit 32 for `[*]`. A name without instances therefore has the numbers and the text it always had (the turbofan, the bike, the engine block and the laser box give byte-identical `craft3d-cli info`, `document.edges` and `datum.references` output before and after), the kernel carries instances without knowing about them, and the order of sources is by instance, then entity. A plain `e` number from 2^32 on is refused when a name is read (it was accepted before and named nothing). A list of faces in `between[...]` may hold names with brackets now: the reader finds the closing `]` by depth. *Not had:* a persistent "last instance" for faces (only image points have `last`), and an index counts from the seed, so moving the seed to the other end of a run renumbers.

### 4.1 Persistent names

A `PersistentName` identifies a topological entity by its origin, for example "the face made by extruding sketch entity `e12` of feature `F3`", "the cap face at the end of `F3`", "the edge between faces *A* and *B*", "the part of face *A* that survived boolean `F7`, on the side of operand 2". Names are produced by `kernel` operations (each operation reports, for every entity of its result, where it came from) and resolved by `regen` against the body at that point in the history.

Resolution outcomes are explicit: `One(entity)`, `Many(entities)` (the entity was split; the feature's policy decides whether that is acceptable) or `Missing`. A `Missing` or unexpected `Many` marks the feature as failed with a message naming the reference; the features before it remain valid.

The naming scheme is the hardest design problem in this plan and is prototyped in M6 before anything depends on it. Its rules and known limits get their own section in this document when that prototype lands.

**As built so far (M6, first slice).** An extrusion names what it makes by role and by the sketch entities involved, written `F2:side(e7)`: the caps are `startCap` and `endCap` with the entity ids of the profile's outer loop; a side face is `side(curve)`; the cap edges are `startEdge(curve)` and `endEdge(curve)`; the upright edge swept by a corner is `lateralEdge(incoming, outgoing)` in the direction the loop runs through that corner, and the corners are `startVertex` and `endVertex` with the same pair. The names do not depend on the order of the curves or on what else is in the sketch: drawing a hole afterwards adds names and changes none. Known limits: drawing a loop *around* an existing one turns it into a hole and reverses it, so its corner and upright-edge names get their pair the other way round (the old names go missing rather than land elsewhere), and the caps are renamed after the new outer loop. **Resolution (M6).** `doc::PersistentName` is the name as data (feature, role, sources; `F2:side(e7)` as text). `regen` resolves it against the features regenerated so far: the feature must exist, come earlier in the history, have succeeded, and have a face whose origin is exactly that name. Anything else fails the referring feature with a reason that says which of those it was and lists the names that do exist; a name never resolves to a different face. One looser match exists, for the *plane* of a sketch only: all caps of one role of one extrusion lie in one plane and share one frame, so a cap name whose outline is no longer there (`F2:endCap(e5,e6,e7,e8)` after the corners were rounded, or simply `F2:endCap()`) still gives the sketch its plane, that of any cap of that role of that feature. The stored name is not rewritten. A side face has no such fallback. The first consumer is a sketch on a face (`SketchPlane::Face`), and the suite in `crates/engine/tests/naming.rs` holds the scenarios.

**Bodies made from bodies (M6).** A transform, a mirror and a pattern make their body out of the body of an earlier feature. That feature's result stays in the regeneration (names are resolved against it) and is marked as taken by the later feature, so its body is no longer one of the document's bodies; `keep` leaves it its body. A body can be taken once. Every entity of the new body is named after the entity it is the image of, as a *copy*: `F5:copy(2)/F2:side(e7)` is the image, in instance 2 of F5, of the face F2 calls `side(e7)` (instance 0 for a transform or a mirror). The part after `/` is a name of its own, so copies of copies chain (`F9:copy(0)/F5:copy(2)/F2:side(e7)`), in the short form of *Copies of copies* below. A copy resolves by walking the chain down to the face as it was first made, with the rules above (the looser match for caps included), and carrying its frame back up through the motion of each copy; a name whose instance no longer exists, or whose inner name is not of the body the feature was made from, points at nothing. After a mirror the frame is still seen from outside and right-handed: x is the image of x, and y points the other way than the image of y. Instances of a pattern that touch or overlap (their boxes come within the tolerance of each other) are joined by the kernel's union; the faces keep their copy names (a face merged from the faces of several instances is named after the first and answers to the others as aliases, see *Merged faces carry aliases* below), and edges are then referred to by the faces they lie between, as after any boolean.

**Booleans (M7).** A boolean feature combines the bodies of two earlier features (target and tool) and takes both, unless the tool is kept. Every face of the result is a face of one operand, or a piece of one, and is named as a copy of it: instance 0 is the target, 1 the tool (`F7:copy(0)/F2:endCap(e5,e6,e7,e8)`, `F7:copy(1)/F3:face(0)`). A face cut into pieces gives several faces with one name. That is resolution outcome `Many`; for the plane of a sketch it is accepted, because the pieces lie on one surface. A face the boolean removed is not among the result's names, and a reference to it fails and lists the faces that are there. **Edges are referred to by the faces they lie between** (`regen::edges_between`, `document.edges`): an edge of a solid is where two faces meet, and faces have names through every feature kind. "The edges between `F4:copy(0)/F2:endCap(...)` and `F4:copy(1)/F3:face(0)`" is the rim of a drilled hole, whatever the body's edge numbering is, and it is a list: two faces can meet in several edges, and pieces of one face share a name. Since 2026-10-14 an edge of a boolean also has a name of its own, made of exactly that pair (`F7:between[a,b]`, below); sweeps and primitives name their edges and vertices by where they came from. **Merged faces carry aliases (2026-10-13).** Faces that a boolean split needlessly, or that continue across both operands on one surface (the tops of two flush blocks united), are merged again by the kernel, so a union of flush bodies has no seam. The kernel lists every contributing face of such a face (`BooleanResult::merged`, the target's faces first, in order). `regen` names the face after the first contributor (`F3:copy(0)/F1:face(1)`) and gives it the names of the others as *aliases* (`F3:copy(1)/F2:face(1)`; `Names::aliases`, listed by `document.inspect` as `faceAliases`, per face, only when a body has any). A reference resolves by any of a face's names: a sketch on the merged top by the tool's cap name lands on it, with the frame of the tool's cap (the one plane), and `document.edges` finds the rim by either name. The stored name is not rewritten, and nothing is stored in the file: aliases are derived at regeneration, so a document written before this change resolves as it did, and a name that resolved without merging (a face of the tool that kept its own name) still does. Edits upstream: while the faces stay flush the alias follows the merged face; when they are no longer flush the name means the tool's own face, which is there, and the sketch goes with it (not a retarget: the same origin); when the tool's face is gone (sunk into the target) the name is `Missing`, listed or not. The pattern feature's union of touching instances does the same (`F2:copy(0)/F1:face(1)` with aliases `F2:copy(1)/…` and `F2:copy(2)/…`, in instance order). Edge references are consumed since 2026-10-14 by chamfers, fillets and datums.

**Edges and vertices by their faces (2026-10-14).** Every edge and every vertex of every body has a name of its own: within one body no two edges share a name and no two vertices do (`regen::Names::edges`, `vertices`; pinned by `crates/engine/tests/naming_entities.rs`). Where the name comes from depends on what made the body, and there is one rule per kind, not two schemes side by side:

- *A primitive and a sweep* name an edge and a vertex by where it came from, as before: `F1:vertex(6)`, `F2:lateralEdge(e5,e6)`, `F2:endVertex(e5,e6)`. Those names are complete and unique on every primitive and on every sweep the suite builds (profiles with holes, arcs, two arcs or two splines that share both ends, revolutions whole and partial and on the axis, an extrusion up to a face).
- *A transform, a mirror and a pattern whose instances stay apart* name an entity as the copy of the one it is the image of (`F5:copy(2)/F2:endVertex(e5,e6)`), as they do faces. What the source's entities answered to besides their own names (aliases, also those of faces) the copies answer to as copies; before 2026-10-14 the aliases of a merged face were lost in a copy and in a second boolean, which was a hole.
- *A boolean and a pattern whose instances are joined* name an edge by the faces it lies between and a vertex by the faces that meet in it, the faces by their names in that body, in the order names are compared in (by feature, role, sources, then what a copy is a copy of; a name typed or stored with its faces in another order is read as the same name): `F7:between[F7:copy(0)/F1:face(1),F7:copy(1)/F2:face(0)]` is the rim where the hole (the tool's wall) leaves the top of the target, `F7:corner[F7:copy(0)/F1:face(1),F7:copy(0)/F1:face(2),F7:copy(1)/F2:face(4)]` the corner where a slot's wall meets the top and the front. A seam, and the cut between two pieces of one face, has its face twice (`F7:between[a,a]`), the same pair `document.edges` takes. This is the decision that an edge is referred to by the faces it lies between ([`decisions.md`](../decisions.md)), made into a name: it needs nothing from the kernel but the body and the names of its faces, so it is the same for a boolean and for the row of unions that joins a pattern, it does not depend on the order in which the kernel emitted the entities (`regen/src/entity.rs`, tested by naming a body and the same body with every list in another order), and it survives every edit that leaves the faces round the entity what they were.

*When several entities lie on the same faces* (the two halves of an edge a slot cut through, the two points where an edge enters and leaves a round notch, the edges on the two pieces a face was cut into, which share the face's name) none of them gets the bare name. Each then also lists, after `|`, the other faces near it: the faces at the vertices of the edge, or at the vertices one edge away from the vertex, and when that does not tell all of them apart the faces up to four edges further away, all of the group equally far, at the nearest distance that tells them all apart (`F7:between[top,front|left,slotWall]`). Why faces near it and not the vertices at its ends or its place along a loop: a vertex is itself named by faces, so that is the same information, and the order along a loop changes with every edge an edit adds. Why not always: the bare name stays valid through edits elsewhere on the body, and a name with more faces in it is lost by more edits. *When no face tells them apart* (the two circles in which a torus half sunk into a plate cuts its top; the two straight edges of a cylinder cut in half lengthwise, and the corners at their ends) they get a number after the list, `F7:between[a,b|c](0)` and `(1)`, in the order of where they lie in space: by x, then y, then z, of the vertex or of the middle of the edge, coordinates within the document's tolerance of each other (or joined by a row of such steps) counting as one, so rounding in the last digits cannot change the order and the scale does not.

**Copies of copies (2026-10-14, format 15).** Until then every feature that made its body from another put a link in front of every name (`F11:copy(0)/F10:copy(0)/F9:copy(0)/…`), so names grew with the history and a row of more than 32 such features failed (`MAX_NAME_DEPTH`; a plate with 70 holes cut one after another hit it). Now a name has one link per *run* of steps along the way, not per feature (`PersistentName::copy`, `doc/src/name.rs`):
- *A run of instance 0* (the target of every cut, the body every blend or face operation took) is one link with the one number 0, named after the first feature of the run: `F2001:copy(0)/F1:face(1)` is the top of a plate a thousand cuts went through. Its meaning: instance 0 of F2001, of the body that was made from, and so on through instance 0 until the way reaches the feature of the link after it (here F1).
- *A run of other instances* (the tool of each union, an instance of a pattern of a pattern) is one link listing them, each step direct: `F9:copy(1,3)/F2:side(e7)` is in instance 1 of F9, in instance 3 of the body F9's tool was made from, and that body was made from F2's.
- So the wall of the first of a thousand holes is `F2001:copy(0)/F4:copy(1)/F3:side(e2)`, three links: the tool of the first cut, then the target ever after. A name grows only where the way changes between instance 0 and others, which a row of cuts, blends, booleans on the target, transforms or patterns never does; a union that takes the grown body as its tool every time lists one number per union (forty unions: `copy(1,1,…,1)`, still one link). What still has a cap is a way that switches back and forth between target and tool more than about 30 times (32 links, a guard for hostile input as well; every other cap is the sources' 4096 numbers).
- *The features in between* are the history's: each step goes to the feature the instance was made from (for a boolean instance 0 is the target, 1 the tool; for every other feature the one body it takes), as the feature was built (`follow::source_of`, `follow::steps`). They are the same every regeneration, so the name means one entity, and a feature inserted into a run of instance 0 is walked through like the others (as *References that follow a body* do on purpose).
- *Unique both ways.* In a short name two links in a row never go the same way (never 0 after 0, never two runs of other instances), and the numbers of a link are the one 0 or numbers none of which is 0 (`check` refuses `copy(1,0)`). The long form a file or a typed name may still have (one link and one number per feature) is read into the short form without the history (`PersistentName::canonical`: links that go the same way are merged), which is the name regeneration gives the same entity; a name in the short form reads as itself. Edges and vertices named by their faces list the faces in the short form, in the order names compare in, re-sorted after merging.
- *Where the way is walked.* A sketch on a face (`sketch::resolve_face`) expands the name into its steps and carries the frame up through each feature's map, moved faces and turned tools as before; following a short reference (`follow::face`) looks for `T:copy(k)/<name>` built by `PersistentName::copy`, and `short_face_name` tries the names the face had in each body on the way.
- *Files.* Format 15 writes the short form; `convert::name_to_doc` makes every name read short, so a file of any earlier version opens to the same bodies (the 24 showcase files and 25 working files: `craft3d-cli info` is byte for byte the output of before with every name rewritten to its short form by an independent script). The step from 14 to 15 changes nothing in the JSON; the version was raised so an older build, which takes a copy to have one number, says a newer 3DCraft is needed.
- *Measured* (release, one core, `crates/engine/tests/long_chains.rs`, ignored test): a plate with 70, 250, 500 and 1000 holes cut one after another regenerates in full in 0.11, 1.6, 4.6 and 18.4 s, the longest face name 39 to 42 characters at every size. A cut costs time in proportion to the faces of the plate it cuts (1.5 ms at 70 holes, 18 ms at 1000), so a full regeneration grows with the square of the row, as the bodies do; the names add nothing that grows. Adding the holes one command at a time took 593 s for 1000: each command regenerates through the cache, which compared, per feature, every feature it is made from (`regen::cache`, looked up once per regeneration instead of once per feature and input, which was the cube of the row: 268 ms per command at 400 holes before, 87 ms after), and each cut formatted its operands for the boolean's memo. Since 2026-10-15 (§5.5, *Long rows*) a feature whose inputs did not change is not compared input by input and the memo keys bodies by their bits: 1000 holes one command at a time take 29 s (`crates/engine/examples/regen_rows.rs`, release; 19 s of it the cuts themselves, a sketch or a circle 5 ms at 3000 features), 250 holes by `craft3d-cli run` 7.4 s before and 1.6 s after.

*An entity an operand already had* (the kernel's `EdgeSource::Kept` and `VertexSource::Kept`) also answers to the name the primitive or sweep that first made it gave it, as a copy and as an *alias*: `F7:copy(0)/F1:vertex(6)`, and through three booleans `F9:copy(0)/F1:vertex(6)` (`Names::edge_aliases`, `vertex_aliases`; `aliases` in `datum.references` and `document.edges`). It is given only when exactly one entity of the result came from there: the two pieces of an edge a slot cut through are neither of them "the" edge, and both lose the alias. The name an entity had by its faces in a body in between is not carried along (it says nothing the faces here do not say, and the lists would grow with every boolean). A reference resolves by the own name or by an alias (`Names::edge_named`, `vertex_named`; a datum point at a vertex of a boolean or of a joined pattern, which failed before, is the first consumer).

*What an edit does to such a name* (each case is a test in the suite):

- Sizes change and the topology does not (a variable, a radius, a tool moved so that it cuts the same faces; three booleans in a row, at scales 1e-3, 1 and 1e6): every name stays on the same entity, checked by the faces on its sides, the names of the vertices at its ends and the edges that end in it, and for ten corners by the closed form of where the corner must be.
- An entity is removed (the slot no longer reaches the front): exactly the references to it fail, with the name (``at: `Part` no longer has a vertex F7:corner[…]; its vertices are: …``), the others stay where they were, and putting the entity back repairs them.
- A second entity appears on the same faces (the slot now cuts the top front edge in two): the bare name and the alias are gone and two longer names are there. A reference to "the edge between the top and the front" fails; it does not land on one of the halves. The reverse edit brings the name back.
- **Where stability cannot be had.** (1) *A numbered name.* The number is a place in space, not an origin. While the tied entities are all there and keep their order it stays; when one of them goes the others lose the number (the reference fails, which is right); but an edit that keeps them all and changes their order in space moves the number to another entity without any failure. The minimal example is in the suite: a cylinder cut in half lengthwise, both operands turned half a turn about the axis by one variable; the solid is the same solid turned, every name is still there, and `…(0)` and `…(1)` are each on the image of the other. Use the alias instead when there is one (the two edges where the walls of a lens meet are numbered as edges of a boolean, and answer to `…/F2:lateralEdge(e6,e4)` and `(e4,e6)`, which do not move). A feature that takes such a name should say so to the user; none does yet. (2) *An alias follows the kernel's choice where entities of both operands coincide.* The kernel reports one source per edge and vertex (where a vertex of the target lies on one of the tool, the target's; for an edge merged from two collinear ones, the least), so the other operand's name for it is not an alias, unlike the faces, which carry every contributor. (3) *A name with faces after `|` is lost by an edit to those faces*, also when the entity itself did not change: louder than needed, never wrong. (4) *Pieces of one face share its name* (unchanged), so "the corner where the top, the front and the slot meet" is two corners when the slot is cut by one face (a cylinder): that is the tie the faces near it, or the number, break.

Not built: a consumer of an edge's own name (datums, chamfers and `document.edges` take the pair of faces, which gives the list of edges between them; a chamfer takes them all, see *Chamfers* below), the names in `document.inspect` (it has `faceNames`; edges and vertices are listed by `document.edges` and `datum.references`), and a way for a feature to ask for "every piece of what was this edge".

**Primitives (M6).** A primitive is built in a fixed order, so the number of an entity says where it came from: its faces, edges and vertices are named `F3:face(1)`, `F3:edge(4)`, `F3:vertex(0)`. For a block the faces are 0 bottom, 1 top, 2 front (-y), 3 back (+y), 4 left (-x), 5 right (+x) in its own axes; for a cylinder 0 the wall, 1 the bottom, 2 the top; for a cone 0 the side, 1 the base. A sketch on such a face has the frame the kernel gave the face, seen from outside (on the top of a block: the block's own x and y at its height). The order is part of the kernel's contract and is pinned by `crates/engine/tests/naming.rs`.

**The frame of a sketch on a face** is the face's own, seen from outside the body (z is the outward normal, moved by the sketch's offset): on the end cap of an extrusion, the axes and origin of the extruded sketch, moved to the end; on the start cap the same origin and x axis with y reversed; on a side face made from a line, x runs along the line (in the direction the profile's loop runs) and y along the extruded sketch's normal, and the origin is the origin of the extruded sketch dropped straight onto the face. That point moves only when the face moves along its own normal: not with the line's end points (a corner radius), and not with the depth or direction of the extrusion. "Start" is the cap in the sketch plane and "end" the far one, whichever way the extrusion goes. Known limits: turning an extrusion round (a negative distance) puts its end cap on the other side facing the other way, so a sketch on it is mirrored in y, and a sketch on a side face stays on its side of the sketch plane rather than following the body; a curved face cannot carry a sketch.

**References that follow a body (2026-10-14, M9).** A feature that takes faces or edges of a body and makes its body out of it (a chamfer, a fillet, an offset face, a delete face, a shell, a thread) may name them as an *earlier* body of the same chain had them: `["F1:face(0)", "F1:face(2)"]` for the top rim of a screw's head after the head went into a union, a cut and two blends, where until then only `F11:copy(0)/F10:copy(0)/F9:copy(0)/F6:copy(0)/F3:copy(0)/F1:face(0)` would do (since format 15 written `F11:copy(0)/F1:face(0)`, *Copies of copies*) and a name of the consumed body failed with "already went into". `regen/src/follow.rs`:
- *The rule.* At the feature's place in the history the body a name is of is followed through the features that took it (`FeatureResult::consumed_by`, which only an `Ok` feature sets: a failed, suppressed or rolled-back feature took no body and is not followed through, as everywhere else) up to the body that is its own still. Each step finds the copy the taker made of the face: the instance `k` for which a face of the taker answers to `T:copy(k)/<name>` by its name or an alias (a cap also when only its outline changed, as every cap reference). The feature is then built from the full names, exactly as if it had been given them: a short name is an abbreviation of one long name and means what that name means, no more. Each name is followed on its own, so a pair may mix a face of the head (`F1`) with one of the shank (`F2`) or of an earlier blend (`F10:fillet(0)`); whether they end up in one body is checked by the feature as before (the commands refuse at once names of bodies that never came together: `regen::newest_body`). A shell's `source` is followed the same way, since the shell takes that body. The source of the feature (the body it takes, the body it is made from for `sketch::resolve_face` walking copies, and what the cache counts it as made from) is the one the followed names are of.
- *Stored as given.* The document keeps the names the user gave; they are followed again at every regeneration, and the full names are derived (`FeatureResult::followed`, shown by `document.inspect` per feature as `followed`, the parameters as built). So a feature inserted between that takes the body is followed through (a chamfer inserted before a later fillet: the fillet rounds the chamfered body), one moved after or suppressed is no longer, and an upstream edit is followed like any other. Rule 4 forbids silently retargeting a fillet to *another* edge; following the same face through the copies of the features that took its body keeps the same entity, and where it cannot be kept the feature fails. A name given in full (as every document before this change has it) is followed only where it would have failed with "already went into" before: every body that regenerated before regenerates bit for bit the same (the showcase's `craft3d-cli info` is identical).
- *What cannot be followed fails the feature* with the parameter and the feature on the way, never resolving to something else: a face that taker has no copy of (a delete face took it away, a boolean cut it off): ``edges.0: the face F2:fillet(0) is gone: the body of `Round` went into `Sharp`, a deleteFace, which left no face of it; its faces are: …``; a face it has several copies of (the instances of a pattern, the skin and the hollow of a shell): ``edges.0: the face F1:face(1) is more than one face after `Row`, a pattern the body of `Base` went into: F2:copy(0)/F1:face(1), F2:copy(1)/F1:face(1); give one of these names``; a name the body never had: ``edges.0: `Base` has no face F1:face(9); its faces are: …``. Everything else is as for any failed feature (*A feature that fails*; `crates/engine/tests/failed_features.rs`).
- *A face a boolean cut in two* is one copy (`F3:copy(0)/F1:face(1)`) that names both pieces, so the short name means both pieces as the long name does: a fillet between "the" top and the front rounds the edges between each piece and the front (`F4:fillet(0,0)`, `F4:fillet(0,1)`), an offset or a deletion takes every piece. Refusing would make the short name mean less than the long one, and a top a slot crosses is still the top the user meant.
- *Not followed:* references that do not take the body, a sketch on a face, an extrusion up to a face, a datum on a face, an edge or a vertex. They keep meaning the face of the body they name, which they could always do (a consumed body keeps its result and names), so documents that use them keep their meaning; to sketch on the newest form of a face, give its full name (`faceNames`, `view.pick`, `document.edges`). A transform, a mirror, a pattern and a boolean take a feature's body by the feature's id, not by a face, and still fail with "already went into".
- *Readers follow too (2026-10-17).* `file.export` of a flat face (and of a sheet of them) is no reference stored in the history but a reader of the finished regeneration; it follows a name by the same rule at the end of the history (`regen::follow_face`), so a blank's `F1:face(1)` exports the panel it became, and a face that became several fails and lists them, as for a feature ([`files.md`](files.md)).
- *Short names.* `document.edges` lists, beside `faces` (the full names, unchanged), `short`: the same faces by the shortest name that is followed back to them (`regen::short_face_name`: the full name without as many leading copies as can be left out; the copies of a pattern or a shell stay, since without them the name means several faces). `view.pick` and `document.inspect` give the full names as before.
- *Tests:* `crates/engine/tests/follow_refs.rs` (the screw blended by the names its head and shank were made with is, body for body and name for name, the screw of full names; every kind against its full-name twin, before and after an upstream edit; a chamfer inserted at the rollback marker, then moved after the fillet, then suppressed; a face a slot cut in two; a face a delete face took; the copies of a pattern and a shell; save, reopen, undo and redo; the short names of `document.edges`, which build what the full ones build).

### What the names of a body cost (2026-10-19)

The names of a body were six times the body: 4.6 to 6.6 KB per face against 0.72 KB for the B-rep, measured on the Garabit pier's lattice bars ([`regeneration.md`](regeneration.md) › *A chain of unions costs memory quadratically*). A name by faces written out (`F7:between[a,b]`, `F7:corner[a,b,c|d]`) held its own copies of two to four face names, each a chain of `copy` links with a heap allocation per link; a body of 838 faces has 3,922 edges and vertices, most of them with such a name and an alias (the name kept from the body it came from, another chain); and a transform or a pattern copied all of them once more per instance. Since 2026-10-19:

- `PersistentName::of` is an `Arc`: a copy of a copy shares the chain it is a copy of. A body's face names cost one link each (about 90 bytes) over the names of the body they came from. Nothing changes in what a name is, says, parses to or compares as; `canonical` takes a shared link out by cloning it.
- `Names` keeps its faces' names and aliases as they were and its edges and vertices in the form that takes the least room (`entity::Entities`): named by faces, as the ranks of the faces each lists among the distinct face names, with its number (`entity::ByFaces`, 24 bytes an entity plus the ranks), and the aliases as one list with an end per entity; named by a primitive or a sweep, listed as they are; a copy's (a transform, a mirror, a pattern whose instances stay apart, an offset face, a move face, a draft) as the instances and the names of their source, shared with that source's result (`Entities::Copied`). A name is made when asked for (`Names::edge_name`, `vertex_name`, `edge_names`, `edge_aliases_of`, `edge_named`, …; the fields are gone); `edge_named` compares a name by faces list against list without making one, and on a body of copies looks only in the instance the name's first number says; an index into a body of copies is found by where each instance starts. A copy's edge and vertex names are still held to the caps of a name when the copy is made (`PersistentName::check`, as when every copy was written out), so a feature that could not write its names fails as before; a body with more entities than a name's parts can count fails with `the body has too many entities to name` rather than naming them wrong. What a boolean's entities keep (`Names::edge_kept_names`: the names a primitive or a sweep gave, never one by faces) is asked of the operand's names the same way. Let go of with a body the cache evicts (`Entities::Dropped`, only the counts), and derived again with it.
- Measured (838-face bar, 3,922 edges and vertices): names 3.85 MB → 321 KB (0.38 KB per face); the transform of it 4.14 MB → 54 KB; the union of eight bars (6,704 faces) 44.4 MB → 2.6 MB. Every name regeneration gives is the same as before: `crates/regen/src/entity.rs` holds what is stored to what is written out (the names of a body and of the same body with its entities in another order, each found by its name), `merged_names.rs` and the naming suites of the engine are unchanged in what they expect.
