# 3DCraft design: The engine and its clients

The engine (`craft3d-engine`): `Session`, the command registry, undo, scenes, autosave and recovery; and its clients: the window's engine thread, the CLI, the control server and MCP (`craft3d-automation`). §7 of the map ([`../architecture.md`](../architecture.md)).

## Method

**Session.** A `Session` holds the open documents (one active), each with its undo history (`ops::History`: `Arc<Document>` snapshots), its regeneration cache and its scenes, plus the read and write roots that every file path must lie beneath. It runs commands synchronously: `Session::execute(id, params)` → JSON result or `CommandError`. An edit applies to a copy of the document; it becomes one labelled undo step only if it succeeds and changes something, and a failed command changes nothing. A panic inside a command is caught, reported as an error, and the document is kept (autosaved at once).

**Commands.** A `CommandSpec` is an id, a label, a parameter string in the notation agents read, a summary, whether it needs a document, and `run`. Specs live in `commands.rs` and in one `<area>_cmds.rs` module per area, listed in `Session::commands`; there are 111 at 0.1.0 (2026-10-23), in twenty families: `file`, `recovery`, `edit`, `variable`, `table`, `sketch`, `datum`, `feature`, `body`, `face`, `history`, `document`, `measure`, `assert`, `select`, `set`, `param`, `jig`, `view` and `session` (`craft3d-cli commands` lists them). `document.inspect`, `document.edges`, `document.check`, `document.measure`, `document.interference`, `document.sample`, the `measure.*` queries and the `assert.*` assertions let an agent verify from JSON what it did; `view.render`, `view.pick`, `view.replay` and `view.scrub` let it look; `session.report` gives the bug report of the last failed command. `panic_hunt` runs every command with adversarial parameters in four document states.

**Scenes.** `Session::scene_with(SceneQuality)` gives meshes, edge polylines, sketches, datums, names and colours per document revision ([`tessellator.md`](tessellator.md) for the qualities); scenes of every open document and of the states its undo history holds are kept within a memory budget, so an undo or a switch of document shows one again without meshing. The mesh of a body is kept by the body (`meshes.rs`: regeneration hands on the same `Arc<Body>` for what an edit did not touch) within a second budget of the same size, which the kept scenes' meshes overlap (the memory is at most the two budgets together), so a scene built after an edit meshes only the bodies the edit changed, and the scenes of several states share the meshes of their common bodies ([`tessellator.md`](tessellator.md) › *A scene rebuild meshes only what changed*). A host that draws while the display scene is built gets a quick first picture and builds the display scene elsewhere (`refinement`, `accept_refined`). Mass and inertia are measured once per body, when asked.

**Recovery.** A session given a recovery directory notes after every command which documents changed and writes them with the `.3dcraft` writer on one thread of its own, at most once per interval; a clean end removes them, and the next session offers what a killed one left (`recovery.*`).

**Clients.** The window (`apps/craft3d`) hands the session to its engine thread with one task at a time (a request, a file from a dialog, or only the scene to show) and draws the last scene meanwhile with the progress reported; its control listener (loopback TCP, a token) answers the `serve` protocol plus `ui.*`. The page (`apps/craft3d-web`) runs the same `ui-egui` shell on one thread, commands between frames, with the session's files in memory and no control channel ([`../development.md`](../development.md) › *Web build*). `craft3d-cli` runs commands headless (`run`, `info`, `render`, `convert`, `replay`, `score`, `check-range`, `commands`) and serves them (`serve`, `mcp`, and `mcp --bridge` to a running window). The protocol is in [`../control-protocol.md`](../control-protocol.md). No client adds behaviour of its own: the CLI and the automation server can do everything the window does.

**A piece at a time** (`stepwise.rs`, since 2026-10-26). The page has one thread, and a browser draws nothing while it works: a Jig that took ten seconds to open showed an empty page for ten seconds. A session told so (`Session::set_stepwise`) leaves the long work to its host, which asks for a piece of it per frame with `Session::prepare_some(quality, stop)`: the active document's regeneration (stopped between features, `craft3d_regen::progress::with_stop`), the quick first picture (stopped between bodies: the build is cancelled from the progress sink, the bodies meshed so far stay in the store of meshes, and the next call is asked to stop only past the bodies the last one reached, so every call meshes at least one more), the display scene (the refinement, the same way) and the assertions (one at a time, from the job the window's thread would have run; a clearance or an overlap over many pairs of bodies a pair at a time since 2026-10-27, `measure_pieces.rs`: the measure asks for its pairs in order, the pairs measured so far wait in the job between calls, and the answer is the one-go answer bit for bit). Each call does at least one feature, body, assertion or pair of bodies and says what is left (`regenerating` with the features built of all, `meshing`, `refining`, `checking` with the assertions measured of all); the scene and the answers are those of doing it all at once (`crates/engine/tests/stepwise.rs`, bit for bit at three scales). In such a session a command that waits for every assertion (`assert.list`, `document.check`) measures the rest in line, and an edit's result does not wait (what is not measured yet is pending). The page (`apps/craft3d-web`, `WebHost::prepare`) gives each frame 40 ms of work and draws the window as it was (`Shell::ui_away`) until the first picture is there. An edit leaves its regeneration to the pieces too (since 2026-10-27, `Session::regeneration_deferred`): in such a session `failing`, `add_failed` and an edit's assertions' summary do not regenerate the document's new state, the result says `deferred: true` instead of `failed` and `assertions`, and the window shows both once the pieces have regenerated it (the Parameters form judges a commit against the feature list and the assertion rows it reads then). Given `wait: true` (`param.set`, `variable.set`) an edit regenerates and waits in the command all the same, and its result has `failed` and the final summary, never `deferred` (2026-10-27). What still holds the page up: one feature, one body, one pair of bodies or one assertion of another kind that alone takes long. Since 2026-10-28 the page has the assertions and outputs measured in a Web Worker instead (`Session::set_checks_elsewhere`; *Checks in a Web Worker* below), and the regeneration and the meshing in another (`Session::set_regen_elsewhere`; *Regeneration in a Web Worker* below), so none of these holds it up there; the pieces are what a page without the workers does.

**The view made elsewhere** (`view_elsewhere.rs`, since 2026-11-03). A host whose regeneration is elsewhere (the page's worker, *Regeneration in a Web Worker* below) has its views made there too: an assembly, placed from its sources, and a moment of the motion (`view.motion`). The host keeps the view state (the `t` shown, collisions asked for, a bake wanted) and, per view, a stand-in: a document state of its own under which the scenes answered for that view are kept. The job of scenes carries the state below the view (the document or the state it is scrubbed to; an assembly with the source files this session read for it) and the view; the other side shows that view in its own session, as a session that shows it itself does, and answers its facts (what `view.motion` says of the moment, an assembly's outline, the joints a drag moves, the placed part's features), then its scenes, then a bake's pieces when one is wanted. What the shell reads of a moment or an assembly (`Session::motion`, `assembly_outline`, `assembly_joint_of`) comes from the facts; a command tried without the bodies that asks for the view runs where it is made, the moment shown there first (*Motion and assemblies in the worker* below). Since 2026-11-04 the commands that sample the motion (`view.trace`, `motion.check`) and an assembly's solving reads and edits run there too (*Sweeps and assembly edits in the worker* below).

**Saying what is being done** (2026-10-26, the developer's design; calmer since 2026-10-30, below). No plate over the middle of the viewport (it changed width with its text) and no bar across its top (it flickered, below): a small spinner `Tokens::work_spinner` (9 points) in the info accent before the words in the status bar, in an item of its own at the right before the renderer's numbers, always `Tokens::status_work_width` wide (elided within), `Opening welding-table… 41/82`, `Opening welding-table… meshing`, `Regenerating… 3/12`, `Checking 14 assertions… 5/14` (`Shell::busy`, `Work::status_text`), shown only for work that has run 0.35 s and then for at least 0.3 s (`Shell::work_shown`); and only while the viewport has drawn nothing yet, a small note of fixed width in its middle, `Opening welding-table…`, gone with the first body. The window's tasks carry the name of the file they open (`Task::subject`, `Work::subject`, in `ui.get` › `work`). Assertions measured are shown as each answer comes in, also while the rest of their job runs.

## Findings and history

**A calm work indicator and status bar (2026-10-30).** The developer watched the Jansen linkage walker (four legs on a crankshaft) played by a script calling `view.motion` ten times a second: the bar across the top of the viewport flickered (each moment is work on the engine thread, so it came and went ten times a second) and was not pretty, and the status bar flickered because its texts changed with every answer and every frame's render time. *Method* (`ui-egui/src/shell/calm.rs`, `Shell::settle_work`, the status bar in `shell.rs`): the bar is gone; the work indicator is a small spinner and the words, at the fixed place of the work item in the status bar, shown only for work that has run `Tokens::work_after_seconds` (0.35 s) and, once shown, kept `Tokens::work_hold_seconds` (0.3 s) after the work ended (`WorkIndicator`), with the egui frame time as the clock, so short jobs such as a motion's moments never show it and a long one never blinks; the note in the middle of an empty viewport waits the same. The texts of the status bar that change while work or a motion runs (the last command and its answer, the work, the renderer's numbers) change at most once every `Tokens::status_hold_seconds` (0.25 s), the one wanted shown once that time is up (`Held`; a repaint is asked for then), an error at once; and each keeps the widest width it had for text of the same shape, its digits counted as one (`Steady`), so numbers that count up and down never make the items after it jump. While the player plays a motion the command and answer are one steady line, *Playing* and `t = 0.420`; the answer of a `view.motion` (the script's case) is its `t` the same way. These are rules of time and width, the same for any work and any text, on the desktop and in the browser (one `Shell`). `ui.get` › `work` still says what the engine is doing whenever it is (the truth, for agents), and `workShown` what the indicator shows. Held by `crates/ui-egui/tests/status_bar.rs` (40 motion jobs of 50 ms ten times a second never show it and change the texts at most 4 times a second; a long job shows after 0.35 s and stays 0.3 s; an error shows in the next frame) and the unit tests of `calm.rs`.

**Authoring papercuts (2026-10-25, R1).** What testers writing generated scripts kept hitting, each fixed in one place: *feature names in face and edge names* resolved before a command runs ([`names.md`](names.md)); *a condition with the feature*: a command that adds features declares `"when": expr = always on` in its params (`when_cmds::WHEN_PARAM`), the dispatch takes `when` out of the parameters (`when_cmds::take_when`, so the command never sees it) and `edit_merging` gives it to every feature the command's edit adds (ids from the document's `next_feature_id` before the change on), in the same undo step, so the first regeneration already honours it; *assertions pending after an edit*: the summary every edit returns has `whenPending` when assertions are still being measured, and `param.set` and `variable.set` take `wait: true` to wait for all of them, 60 s at most (`assert_cmds::add_summary_waiting`, `WAIT_CEILING`); *reserved variable names*: `variable.set` and `variable.rename` check the name first, and the error says what it clashes with (`m` the unit metre, `mod` the function) and suggests another (`craft3d_expr::reserved_meaning`, `instead_of_reserved`). A direction (a primitive's `axis`, a transform's, mirror's, pattern's or face move's) is read as a position is, plain numbers or lengths, and normalised (`regen::derive::direction`); one of no length fails the feature, and so does one that mixes lengths with plain numbers other than 0 (a plain number would be read in the document's unit, so the direction would depend on it). `when` is not taken by `sketch.create`, `body.split` (several split features switched off together would each pass the whole body on) and `file.import`; their features get a condition with `feature.when`.

### From *Current state (2026-10-12)*

- **Undo:** `ops::History` keeps snapshots (`Arc<Document>`) rather than reversible ops: an edit is applied to a copy and becomes one labelled step only if it succeeds and changes something.

- **Engine:** `engine::Session` holds open documents and runs 72 commands (64 when this was written) (`file.*`, `recovery.*`, `edit.*`, `variable.*`, `feature.*`, `sketch.*`, `datum.*`, `history.rollback`, `document.inspect`, `document.check`, `document.measure`, `view.render`, `view.pick`, `view.replay`) by id with JSON parameters. Edits are atomic undo steps; a failed command changes nothing; a panic inside a command is caught and reported. File access goes through explicit read and write roots. `tests/panic_hunt.rs` runs every command with adversarial parameters in four document states. Deviations from the plan: synchronous (no job pool, no events, no `arc-swap` snapshots), no parameter schemas beyond the documented params string, no `enabled` predicate beyond "needs a document". **Autosave and crash recovery** (2026-10-13, `engine/src/recovery.rs`, `recovery_store.rs`, `recovery_cmds.rs`; not in a browser): a session that its host gave a recovery directory notes after every command which documents changed (an `Arc` clone of the document, under a microsecond) and writes them with the `.3dcraft` writer on the one thread the engine starts, at most once per interval per document (30 s) and at once after a caught panic; a 300-feature document of 1.8 MB takes 40 to 90 ms there and nothing on the command's thread. The host ends it on a clean quit (`Session::end_recovery`), which removes the files; a killed process leaves them, and the next session's scan offers them through `recovery.list`, `recovery.open` and `recovery.discard`. The layout is in [`file-formats.md`](../file-formats.md).

### 8. Engine (`craft3d-engine`)

#### 8.1 `Session`: commands in, events out

*(Planned, not built: `dispatch` with a `JobHandle`, `snapshot`, `events`, `DocId`, `CommandInvocation` with a schema. As built: `Session::execute(id, params)`, synchronous; see Method.)*

```rust
pub struct Session { /* docs, registry, job pool, prefs, services */ }

impl Session {
    pub fn new(services: Services) -> Self;                         // platform functions injected
    pub fn dispatch(&self, doc: Option<DocId>, cmd: CommandInvocation) -> Result<JobHandle, CommandError>;
    pub fn registry(&self) -> &CommandRegistry;
    pub fn snapshot(&self, doc: DocId) -> Arc<DocSnapshot>;         // lock-free read: document + regeneration result
    pub fn events(&self) -> EventReceiver;                          // DocChanged, RegenProgress, FeatureFailed, …
}

pub struct CommandInvocation { pub id: CommandId, pub params: serde_json::Value /* validated against the schema */ }
```

#### 8.2 `CommandRegistry`

Each command registers `id` (`"feature.extrude"`), `label`, an optional `menu_path` and shortcut (unused in phase 1), a parameter schema with a one-line params doc agents can read, `enabled(&DocSnapshot) -> bool` with a reason when disabled, and `run`. *(As built: `id`, `label`, `params` (the one-line doc), `summary`, `needs_document` and `run`; menu paths, schemas and an `enabled` predicate are planned.)* `run` returns a JSON result and records exactly **one** history step.

Command families (ids are settled when each is implemented, and are stable afterwards):

An agent must be able to verify what it did from JSON alone, and use `view.render` when it needs to look.

#### 8.3 Operations and history (`ops`)

*(Planned; as built `ops::History` keeps a snapshot, `Arc<Document>`, per labelled step, and there are no `Op`s.)* Every mutation of a document is an `Op` (`SetVariable`, `AddFeature`, `EditFeature`, `ReorderFeature`, `AddConstraint`, …). A command produces a labelled `Transaction` of ops. Undo history stores transactions; because documents are persistent data, a "before" state costs only what changed. Undo history (session-only, what the user did) is distinct from the **design history** (the feature list, saved in the file).

#### 8.4 Runtime model

```text
 Client (UI / CLI / control / MCP) ──dispatch()──► Engine thread (owns mutable docs, applies ops, publishes snapshots)
        ▲                                               │ spawns
        │ events (changed, progress, failed)            ▼
        │                                   Job pool (planned): regeneration, tessellation, export, autosave
        │                                   read snapshots, return results
 Viewport: render(snapshot) on GPU or CPU
```

*(Planned, not built:)* Every job takes a `CancelToken`. Services injected into `Session`: file system (native fs / in-memory for tests / browser later), clock, notifier.

*As built (2026-10-14):* the desktop app has the engine thread of the picture, without the snapshots: `apps/craft3d/src/worker.rs` takes the `Session` itself with one task at a time (a request line, a file chosen in a dialog, or only the scene the window shows), runs it, builds the scene at the shell's display quality, and hands the session back; the window draws the scene of the last sync meanwhile and the progress the task reports. One task at a time keeps requests in order. A panic in a task is caught there, autosaved and reported. On wasm (no app yet) the shell keeps its synchronous path: `Shell::ui` with the session, as tests and examples use it. The scenes of every open document are kept, and of the earlier states its undo history holds, within a memory budget (1.5 GiB by default, the least recently shown first out, the active document's never), so `file.activate` or an undo shows one again without meshing it, in well under a millisecond (a scene's meshes are shared by `Arc`); the display scene is built beside the engine thread while the window shows a quick first picture (`apps/craft3d/src/refine.rs`, §6 › *Coarse first, then sharp*), so a command is never queued behind it; a body's area, volume and centroid are measured once per body (`engine/src/mass.rs`, by the body's `Arc`), and its faces are measured on several threads and summed in face order (`topo::mass_properties`), which is what made opening a model with spline faces slow (the display tolerance is a fraction of the model's size, and the size is the square root of its area). *2026-10-19:* the meshes and the facts of a body are kept by its `Arc` the same way (`engine/src/meshes.rs`), and the display rule's and the first picture's tolerances stand on a ladder of rungs 9 % apart, so a rollback step on the developer's pier (307 bodies) went from 2.6–3.5 s to 75–128 ms ([`tessellator.md`](tessellator.md) › *A scene rebuild meshes only what changed*, with why an empty window held 1.9 GB after the pier: glibc keeps what the engine freed).

#### 8.5 The UI-swap seam

A frontend needs four things from the core: `Session` (commands in; events *(planned)*), the `CommandRegistry` (metadata), *(planned)* snapshots with view-models (feature tree, variable table, inspector as plain structs), and a renderer it can host (`gpu::Onscreen` on the host's own device into a texture it shows, or `render` into an RGBA buffer; the egui shell today hosts the first as `ui_egui::direct::Direct` when the window lends it the device, and otherwise `ui_egui::backend::BodyRenderer`, which gives it a `Frame` from the GPU read back or from the CPU). Interactive tools (sketching with the mouse, dragging a face) come after phase 1 and follow PhotoCraft's pattern: pointer events in, ops and overlay primitives out, so the control channel can replay them.

**Litmus test:** `craft3d-cli` and the automation server can do everything the GUI does.

### 10. Automation

Detail in [`control-protocol.md`](../control-protocol.md).

- **CLI** (`craft3d-cli`): `convert`, `info`, `run` (a list of commands against a document), `commands` (the registry), `render`, `serve` (JSON lines on stdio or loopback TCP) and `mcp`.
- **Control channel:** the desktop app listens on loopback with a token; agents send `engine.execute`, `ui.inspect`, `ui.screenshot`. This is also how the developer watches an agent work in a live window.
- **MCP** (`automation`): `doc_*`, `command_list`, `command_run`, `command_batch`, `doc_render_preview`, generated from the registry; file access limited to explicit read and write roots.
- **Scripts:** a recorded session is `Vec<CommandInvocation>`; replaying it rebuilds the model. This is the natural format for agent-written test scenarios.

### Inspecting a model of hundreds of bodies, and closing the window (2026-10-21)

*Measures remembered for every body.* The measure of a body is remembered by the body (`engine::mass`), but the store held 256 bodies and forgot the oldest first: the Garabit pier (307 bodies, 57,000 faces) measured every body again for each `document.inspect` (5.4 s after a `document.measure`, and 5.2 s again; now 1.1 s, of which the boxes' meshes most, then 0.1 s). It now holds 16,384 (`MAX_REMEMBERED`), keyed by the address of the body's `Arc` in a sorted map (a `Weak` keeps the address from being reused while it is remembered), and forgets bodies that are gone every 64 bodies it takes, and the oldest quarter at once when full (1,024 in a browser). The box `document.inspect` lists per body (`bbox`, from a mesh at the automatic tolerance) is remembered the same way, per body and tolerance (`mesh_box_of`). `document.inspect` measures the bodies with a material first, together with their inertia, and only then the others for the automatic tolerance, so no body is integrated twice. *`document.inspect {measures: false}`* lists everything but what takes measuring (volume, area, centroid, mass, inertia, bbox): it measures nothing, which a test counts (`inspect_without_measures_measures_nothing`), and its rest is the full answer's to the byte. On the valley just regenerated: 0.09 s, against 12.1 s for the full first inspect. The slowest single face is faster too ([`topology.md`](topology.md) › *One slow face on every thread*).

*The window stays responsive.* Commands, `ui.get` while one runs, and the scene a document needs already run on the window's engine thread (2026-10-14, [`control-protocol.md`](../control-protocol.md) › *The window keeps answering*); a long `document.measure` shows its work over the viewport while the camera, the tree and picking go on. Checked on a window of its own (release, the valley opened over the channel, `document.measure` on one connection and `ui.get` every quarter second on another): 37 answers while it ran for 11.9 s, the slowest in 0.15 s. What the 50 to 120 s were is the measure itself, on one thread, and measured again for each inspect of a model over 256 bodies.

*Closing the window asks first* (roadmap R1). Before, the close button ended the application and removed the recovery files of documents it had never saved. Now the shell turns the close (`Shell::request_window_close`, from `ViewportCommand::CancelClose` in the window) into the question a tab's close button asks, one document with unsaved changes after the other, each answer done as the tab's (`file.save` then `file.close`, the save dialog first for a document without a file, or `file.close {discard}`), and the desk takes the next step whenever the session is home and nothing is pending (`Shell::advance_quit`). Pressed while a command runs, nothing is decided on the tabs from before it: the window waits for the command and then asks about what it left unsaved (review, 2026-10-21). `ui.quit {save: "save"}` saves through the automation write root like a request's `file.save` and refuses, with nothing saved, a document whose file lies outside it: only the person's own Save writes with the person's access (review, 2026-10-21). When an answer closed nothing (a failed save, a cancelled save dialog) or the person pressed Cancel, the window stays. The application ends once no document asks; recovery files are then removed only when nothing unsaved is left, or when `ui.quit` dropped it on purpose: a document changed by work that finished while the window closed keeps its autosave, as after a crash. Over the channel `ui.quit {save}`: `discard` (the default, as before), `ask` (as the close button), `save` (every document saved to its file on the engine thread, refused while one was never saved). ### What an agent reads back (2026-10-22, before the R1 field test)

The user guide's writer, driving 3DCraft as an agent would, found where a result left it guessing. *Every error names its command:* `Session::execute` puts `id: ` in front of an error that does not start with the id already, so what a shared part says (the file roots: `file.save: `/x.3dcraft` is outside the write root …`) reads like every other refusal. *An edit says what it broke:* a failed feature is not an error of the command, so `variable.set`, `variable.delete`, `feature.edit`, `feature.suppress`, `feature.move`, `feature.delete` and `history.rollback` compare the failed features of the revision the edit starts from (regenerated first when an undo or a redo left it unregenerated; the cache keeps that to what changed: a regeneration of another revision missed failures and blamed edits for what an undo did, review 2026-10-22) with those after the change and list the new ones under `failed` (`commands::add_failed`). *A variable in use stays:* `variable.delete` names its users (`commands::variable_users`: variables, feature and sketch parameters by name, assertion bounds and what they measure, the measures in named sets) and refuses, unless `force`. *A refusal says its numbers:* the spindle refusal of a fillet along a rim (`KernelError::FilletSpindle`) gives the radius asked, the radius below which the ball's centre stays clear of the axis and the radius that puts it on the axis, worked out from how far the centre comes nearer per unit of radius. `file.export`'s `gap` and `width` are expressions like every other length. `craft3d-cli mcp --help` lists the tools from `automation::mcp::tool_names`, the list `tools/list` serves.

### Hiding features and scrubbing the history (2026-10-23)

*Hiding* (`feature.visible`, `visibility_cmds.rs`) is `Document::hidden`, a sorted list of feature ids beside the history like the body colours (`craft3d_doc::visibility`, format 30): regeneration does not read it, so the cache reuses every result and a toggle costs a scene join (the meshes come from the session's mesh store). `scene::build` keeps a hidden feature's row (`SceneFeature::hidden`) and leaves out its body, sketch, helix or datum; the box pictures are framed on (`bodies_box`) and `view.replay`'s bodies leave it out too. Exports ignore it (decided: most modellers export what the model is, a view setting is not a choice of bodies; `file.export {bodies}` is). It is one undo step, as every change of the document is (decided like colours; the document's dirty state moves, its geometry does not).

*Scrubbing* (`view.scrub`, `scrub.rs`) is view state of an open document (`OpenDocument::scrub`, like the selection): the feature the view shows the model after, and how many features the document had then (a feature added or deleted lets go of it). `OpenDocument::shown` is the state every scene is built from: the document itself, or a copy with its rollback marker on that feature, kept per step (at most `max_states`, 100 000 copies of features over the states, 16 to 512) for as long as the document state it copies is current. Its regeneration (`shown_regen`) runs on a copy of the document's own cache, so the features up to the step are reused and the document's cache keeps the later ones. `Session::scene_revision` observes the shown state, so the scene cache, the display refinement beside the window and `scene_ready` work on it unchanged; the document as it is stays pinned in the scene cache (`SceneCache::pinned`) so "To end" is immediate after a long scrub. Measured on the turbofan (148 features, release, `tests/scrub_speed.rs`): a step met for the first time shows its quick picture in 2.4 ms (median; 97 ms at most) and its display scene in 4 ms (2 s at most, on the refinement thread); a step seen before 0.1 ms; the scene budget let the display scenes of 65 older steps go, rebuilt from kept meshes in under a millisecond each. The window's timeline (`ui-egui/src/shell/timeline.rs`) queues `view.scrub` while dragged, only the latest, and lets the host build the scene where it builds every scene (the engine thread), so a fast drag shows the latest step that is done.

Review of the first version (2026-10-23): the states of an older document are let go of before anything else in `shown` (they held the old document after To end); a state does not keep a regeneration that derived bodies again which the document's cache had let go of (they would live outside every budget); the scrub holds while a hash of the feature ids in order (`features_key`) is the same, so a delete and an add in one batch, or a move, let go of it; while scrubbed the viewport does not select (`refused_while_scrubbed`) and `view.pick` says `scrubbed`; the eye toggles from the last value queued for its feature, so a double click comes back where it started; a flight to a hidden feature or one after the scrub queues `feature.visible` and `view.scrub` with null first and waits for the scene that shows it (`Shell::prepare_fly`; `ui.fit` runs them at once). A tab switch drops what the timeline queued for the other document; the scrub itself is the engine's, per document, so each tab shows its own timeline.

*The history player* (2026-10-23, `crates/ui-egui/src/shell/player.rs`) is the window's, not the engine's: playing is view state (`UiState::timeline`, a `Playback`), and each step is the `view.scrub` the slider runs. A small state machine (`Player::tick`) asks for the next step only when the view has settled (a sync with the session found no scrub waiting: with the engine thread that is the first frame after the scene task came back, so frames drawn while the session is away never count; whichever step it settled on, the player's or one an agent's `view.scrub` or a flight put there, the player goes on from it, so it never waits for a step that will not come) and the step has been drawn for 0.8 s / speed of egui's input time (the browser has it too). The dwell starts at the frame after the one that drew the step, whose input time is after that frame however long it took (in the browser the scene is built inside the frame). It stops at the end (or loops), on another document revision (an edit), on a tab switch, To end, Roll back here, the End key and a failed scrub. The keys only change the view: End is `view.scrub` with null, while the To end button also removes the rollback marker (no bare key edits the document; decided 2026-10-23); they are not read under the closing question or a Help window. The orbit leaves the camera alone while a turn, a flight or a drag has it, asks for at most 30 frames a second, and is drawn sharp unless a frame turns more than a degree. `ui.set` refuses `playing: true` without a document or features. The caption over the viewport is `craft3d_engine::step_caption`, which `view.replay` writes into its subtitles too (its text changed from `3/10  Plate (block)` to `Step 3/10 · Plate · block` with it).

### Scrubbing at the document's tolerances, and the window recording itself (2026-10-30)

*Why a step of the player took seconds.* Not regeneration: a step met for the first time regenerates in about a millisecond from the copy of the document's cache (the turbofan, 148 features, release, `crates/engine/tests/scrub_steps.rs`: 0.6 ms median, 1 ms at most, against 1 to 2.3 s for the same state regenerated from nothing; the engine block 0.9 ms against 2.7 s), and a step seen before is a lookup. The seconds were meshing: every scene's tolerance is a fraction of the model's size, and the size of a step's model grows with the steps, so the display tolerance moved at almost every step (18 values over the turbofan's forward pass, 10 over the rotor's 14 steps, from 0.0005 to 4 mm) and every body, also one the step shares with the steps around it, was meshed again at the new tolerance (the turbofan's display scenes 3.3 s over the pass, 1.07 s at most; the rotor's 3.5 s, 1.65 s at most). Now a scrubbed state is meshed at the tolerances of the document as it is (`Session::scrubbed_sizes`: the quick first picture's size is the diagonal of the document's bodies' box, the display scene's the side of a square with the area of the document's own first picture, which is built for it when there is none; `Refinement::size`), so the store of meshes finds every body a step shares, and the picture keeps one fineness while the player plays: the turbofan's display scenes 0.56 s over the pass, 48 ms at most; the rotor's 56 ms, 36 ms at most. A rule for any document: the states shown are states of one history, and the document as it is fixes the sampling for all of them, as it fixes the camera's framing.

*A model whose bodies take more than the budget.* The document's cache lets go of the bodies that went into later features beyond its budget (1 GiB), oldest first, and a state that needs one derives it again, and before 2026-10-30 did not keep that regeneration (its bodies would have lived outside every budget), so each step and each revisit derived the chain again. Now a state's regeneration starts from a copy of the document's cache and takes the bodies the cache of the state shown last built or derived again, where that cache's entry is the same (definition, context and stamp: `RegenCache::take_bodies_from`), so a step forward derives at most its own body; the regenerations kept are held to `STATE_BODY_BUDGET` (1 GiB, 256 MiB in the browser) of bodies beyond the document's own, the least recently shown let go first (their scenes stay in the scene cache, so showing them again costs nothing). This was the seconds per step on a big model: the engine block (196 features) under an 8 MB body budget, a forward pass then a backward one, before: 8823 bodies derived again, regeneration 223 s forward (1.0 s median per step, 4.2 s at most) and 206 s back; after: 120 derived again, one per step at most, 5.0 s forward (2.7 ms median, 0.29 s at most) and 0.12 s back. On the engine block within its budget the tolerance rule changes nothing measurable (its new body per step is what is meshed: about 10 ms a step either way). Every state shown is the one a regeneration from nothing gives, bit for bit, but for a body that went into a later feature and that a cache let go of (`Session::scrubbed_matches_a_full_one`, sampled over every bench model in `scrub_steps` and at every step in `scrub.rs`'s tests).

*The window recording itself* (`crates/ui-egui/src/record.rs`, `apps/craft3d/src/recording.rs`, the `Desk` in `app.rs`). A Wayland compositor draws no frame for a window it does not show, so pictures and recordings no longer come from it: the desk runs a pass of the shell itself on the window's egui context with the input of the window's last frame (`Rec::window_frame`), and `Offscreen::paint` applies the pass's textures to the window's own `egui_wgpu::Renderer` (shared with eframe's painter, so the window's later frames see them), tessellates, paints into a texture of the window's size in its surface format and reads it back (BGRA swapped). The passes run where the event loop is woken (`Driver::serve`, then `Desk::drive`), never inside eframe's frame. While a recording runs the window's own frames show the last frame recorded instead of the shell, so the shell is drawn on one clock; in real time a ticker thread wakes the loop every `1/fps` and the window's events go into the next pass; frame-exact, `ui.advance` advances the clock by `dt` per frame and draws a frame only once the desk is settled (session home, scene built and refined) and, at that moment of the clock, again until the viewport no longer averages its still or waits for its sharp CPU image (`Shell::sharp_pending`, `SETTLE_PASSES`). A frame goes to a writer thread through a channel of four (PNGs, or `ffmpeg`'s standard input as raw RGB), so a slow disk holds the recording up rather than filling memory. Not here: audio, a cursor drawn into the frames, a window resized while recording (its frames are cut or padded to the first size), `ui.screenshot {window: true}` through MCP's `control_call` (the shell refuses it there; `ui.record` and `ui.advance` are routed to the desk).

### A clearance or an overlap a pair at a time (2026-10-27)

On the page an assertion was one piece of work, so one over many pairs of bodies held a frame for as long as all its pairs took (the gear reducer: the bearings seated in the housing, 12 pairs; the moving parts clear of the housing, 30 booleans). Now `measure_pieces.rs` takes such a measure a pair at a time on a stepwise host: `clearance` and `overlap` ask `measure_pieces::pair` for each pair in their order; outside a piece that measures it there and then (an overlap's pairs still on several threads), inside one it hands back a pair measured in an earlier piece, measures the next, or says the piece is used up, and the measure gives up (its answer is thrown away) while the pairs so far wait in the job for the next frame. Every pair is measured by the same code from the same bodies and merged in the pairs' order, so the answer, details included, is the one-go answer bit for bit (`tests/stepwise.rs`, 12 + 21 pairs a piece each, three scales). A clearance resumed in a later piece makes the parts (mesh and probe) of only the two bodies of its next pair; the first piece made and checked all of them, so an error is the one-go error. ### Checks in a Web Worker (2026-10-28)

The roadmap asked for the web build on more than one thread, a Web Worker or a threaded build. *The choice: a Web Worker.* A threaded build needs the standard library rebuilt with atomics (`-Z build-std`, a nightly toolchain, where `rust-toolchain.toml` pins stable) and `SharedArrayBuffer`, which a browser gives only to a cross-origin isolated page: COOP and COEP headers on every host, which a web host, plain static hosts and every page that embeds 3DCraft in a cross-origin iframe would have to send (COEP `require-corp` on the embedding page too). A module Web Worker works on any static host, shares no memory and needs no header.

*What can cross.* A worker has a WebAssembly instance and memory of its own, so whatever crosses is serialised. The shell reads the session every frame (23 of its methods: the scene, the document's status, the selection, the timeline, …) and runs commands in the frame of a click, so moving the whole session into the worker needs the shell over a session it reaches only by messages, with the scene's meshes crossing as data; and the page cannot keep a session of its own beside one in the worker without the bodies, for which no serialised form exists below the format (geometry and topology have no serde). The checks are the part that crosses cleanly: regeneration stays one way (geometry, then the measures, then the outputs and the assertions; `output_cmds.rs`), a check is a function of the document, its regeneration, the assertion and the outputs it uses (`assert_cmds::check_one`), regeneration a function of the document alone, and a document's `.3dcraft` manifest regenerates to the bodies it was saved from. They were also the page's longest wait: on the gear reducer 20–30 s of assertions after a parameter, single frames of up to 10 s, against some 2 s of regeneration drawn a feature at a time (*A parameter set on the page, computed twice?* above).

*As built.* A session told to (`Session::set_checks_elsewhere`, only with `set_stepwise`) no longer measures in `prepare_some`; the job of checks it makes as before (`assert_check.rs`: stages, keys, memo, all unchanged) is handed out under a number (`Session::checks_job`, none while the state is still being regenerated), written out (`Session::checks_request`: the job's document as the bytes of its `.3dcraft` file, with the files it holds such as an imported STEP file (the manifest alone left them out, and every check of a document with an import was an error; review, 2026-10-28), its assertions with their serde form and the outputs known so far, a quantity's value as the bits of its `f64`), measured by `craft3d_engine::measure_checks` (the file read, regenerated with a regeneration cache kept between requests, `check_one` per assertion in order) and handed back (`Session::checks_answered`), after which the job is done as if the session had measured it. Numbers in the answer's JSON read back as the same `f64` (`serde_json`'s `float_roundtrip`), so the answers are the session's own bit for bit: `crates/engine/tests/checks_elsewhere.rs` compares `assert.list` with details and `output.list` against a session that measures them itself, at three scales, through two stages of outputs and an edit and back, and checks that `prepare_some` never reports `checking`. On the page (`apps/craft3d-web/src/checks.rs`, its logic tested natively with a worker that answers through `measure_checks`; `worker.rs`, the `web_sys::Worker`): `index.html` names the worker (`<meta name="craft3d-worker">`, `craft3d-worker-<hash>.js` from `packaging/web/worker.js`, a dozen lines in the style of the page's own loader); the page posts `{token, document, work, module}` with its own compiled `WebAssembly.Module`, so the worker compiles nothing, and the worker answers `{token, reply}`. One job at a time; a job replaced while it is measured (an edit, another tab) is cancelled by ending the worker, which the next job starts again. A worker whose module aborts while measuring (a panic: a bug) answers `{token, fatal}`, and every check of that job is an error that says so; never pending for ever, and never measured on the page instead, where it would end the page. A worker that cannot be had at all before it ever answered (no meta, a 404, a `Content-Security-Policy` without the worker, a browser without module workers, an instance that cannot start: `{token, unavailable}` or the worker's `error` event) sends the checks home: the page measures them a piece per frame as before. A worker that takes longer than 10 minutes over one job (`checks::DEADLINE_MS`, far beyond the 30 s of the gear reducer; the page asks for a frame every 30 s while a job runs, so the deadline is seen without input) is ended and that job's checks are errors that say so (`Session::checks_failed`, a message without the bug label); so is a job whose document cannot be written out (it breaks its own rules, or its manifest is larger than a file may be), with the reason, rather than measured on the page, where a document that large would hold the page up for as long as it takes. A load failure of the worker's script arrives as a plain `Event`, not an `ErrorEvent`, and is read as such (review, 2026-10-28). A command that waits for every answer (`assert.list`, `document.check`) still measures in line on the page.

*Rules added, and why they hold for any document.* Checks are handed out only for the active document's state once it is regenerated (its checks come after its regeneration, by the one-way rule). An answer is taken only for the job it was asked for (its number, while it waits), so a late answer for an earlier state is dropped whatever the edit was. An answer that does not fit (unreadable, another count of checks) is an error of every check of the job, as a crash is.

*In a browser.* The site the Release workflow's web job built (run 40668161902, `gh workflow run Release -f only=web`: the module 18,565,954 bytes, 7,155,117 with gzip -9, 21.5 kB of gzip more than main 536bfbc9's) served locally and opened in headless Chrome (WebGL2 on SwiftShader) on the gear reducer Jig (242 features, 22 assertions), the page's thread probed over the DevTools protocol every 100 ms (`Runtime.evaluate` of `1`, which waits for the thread): with the worker, between 6 s (the first picture there) and 45 s, the longest answer took 77–214 ms in two runs and none other over 100 ms; the 22 assertions were measured in the worker, all passed as on the desktop, done between 29 and 39 s. The same site without the worker's meta (the page measuring them itself): 20 answers over 200 ms in that span, the longest 1.65 s. The first 6 s (the regeneration and the first picture, on the page's thread either way) answered within 0.6–0.8 s at worst in every run. Evidence: `target/evidence/web-worker-checks/` (screenshots, the probes' latencies). The memory of the worker's instance comes on top of the page's (its own regeneration of the document, within the same 256 MiB body budget per regeneration cache).

*Still on the page's thread, and the general method owed:* regeneration and meshing (a feature, a body at a time between frames). Taken off the same day: *Regeneration in a Web Worker* below.

### Regeneration in a Web Worker (2026-10-28)

The R1 item after the checks: a long regeneration (a heavy Jig, a boolean of minutes) must never freeze the page; it keeps repainting, the camera turns, and an edit or an undo cancels it.

*The choice: the regeneration and the meshing cross, the session stays.* Two ways were open: (a) regenerate and mesh in a worker and send the scene to the page, which keeps the document and the commands; (b) move the session into the worker and give the shell a mirrored read model reached by messages. The code decides for (a): what the shell reads every frame is the `Scene` (meshes, edge polylines, the names and facts of every body, the feature rows with their states and errors, sketches, datums, boxes) plus the session's own document, history, selection and assertion rows. The scene is plain data, so it crosses as bytes; the bodies (no serialised form) never have to. (b) would put every command of a click behind a message round trip and the 23 methods behind a mirror, for no gain in what the page shows.

*As built.* A session told to (`Session::set_regen_elsewhere`; in effect only with `set_stepwise` and `set_checks_elsewhere`, since a page without its own regeneration cannot key the checks) does not regenerate or mesh in `prepare_some`. The scene the window shows (the shown state, scrubbed or not, at the window's quality) is handed out as a job under a number while it or its quick first picture is missing (`Session::scene_job`), written out (`Session::scene_request`: the state as the bytes of its `.3dcraft` file with the files it holds, the quality with its numbers as their bits, the page's scene budget) and built by `craft3d_engine::scene_begin` / `scene_next` on the other side: a session of its own that holds the one document and takes each request as a new state of it (`load_state`), so its regeneration cache and its store of meshes carry over and an edit rebuilds only what it changed. It answers part by part: the quick first picture, then the scene at the quality asked for, each the scene's bytes or the error building it gave. The page keeps each part as a scene built there would be (`Session::scene_answered`, the scene cache under the job's document state), draws the first picture while the display scene is built, and ends the job when the answer is complete (`Session::scene_done`: a scene that did not come is an error, so nothing is asked for again every frame). The scene's form (`scene_wire.rs`) is little-endian, every `f64` as its eight bytes, every list with its count; the scene's own mesh is left out when it is the bodies' meshes one after the other bit for bit (as `scene::build` joins them) and joined again on reading; a feature's kind is taken from the page's document by its id, so the scene of another document does not read. Reading checks every count against the bytes left before it allocates, and never panics (`scene_wire` tests: every prefix of a scene, a count of 2³²−1, another document; and see *Reading a scene that crosses* below).

The assertions and outputs of such a document are measured a whole state at a time (the page has no regeneration to key them by): `Session::checks_job` hands out the current state when it has assertions or outputs and no answer, `checks_request` writes it with `{"state": true}`, `measure_checks` measures it in a session of its own with every check in line (`checks_and_outputs(Wait::All)`, its memo kept between states) and answers the checks and the outputs, which the page keeps for that state (`OpenDocument::state_checks`). A caller that does not wait (`assertion_states`, `output_states`, `param.list`, an edit's summary) gets that answer, pending until it is there; one that waits for every answer (`assert.list`, `document.check`, `param.set` with `wait: true`) regenerates and measures on the page, as a command always did.

On the page (`apps/craft3d-web/src/scenes.rs`, its logic tested natively with a worker that answers through `scene_begin`/`scene_next`; `worker.rs`, one `web_sys::Worker` per kind of job; `packaging/web/worker.js` dispatches on `kind`, `scene` or `check`, and hands each part over as a transferable `Uint8Array`): the parts are taken before the page decides what to draw, so a part is drawn in the frame it arrives in; while the scene of the state shown is missing the window is drawn as it was (`Shell::ui_away`: the last picture, the camera turning, the Parameters form, undo) with *Regenerating…* in the status bar. A job replaced while the worker builds it (an edit, an undo, another tab, another quality) was cancelled by ending that worker until 2026-10-30, so the next state regenerated from nothing; since then the worker is kept and leaves the job for the newer one (*A worker that can be stopped, with its caches* below). A worker that is done is kept with its caches. `?pageregen` in the address regenerates on the page as before (to compare, or for a worker that misbehaves).

*Rules added, and why they hold for any document.* A part is taken only for the job that waits, by its number and the document state it was asked for (an `Arc` of the state), so a late answer never lands on a newer state whatever the edit was. A scene job is wanted while the shown state lacks its first picture or its scene at the window's quality, so a state is built once and an error is kept like a scene (no job is posted twice for one state). A worker that cannot be had before it ever answered (no meta, a 404, a `Content-Security-Policy` without the worker, a browser without module workers, an instance that cannot start) sends the work home: the page regenerates and meshes a piece per frame, as before; so does a checking worker that cannot be had (the regeneration comes home with the checks, by the rule above). A worker whose module aborts while building (a panic: a bug) leaves that state's missing scenes errors that say so, and the next state goes to a new worker: never built on the page instead, where the same bug would abort the page's module. One that takes longer than 30 minutes over a state (`scenes::DEADLINE_MS`; far beyond any model, the page asks for a frame every 30 s while a job runs) is ended and the state's scenes say so without the bug label (`Session::scene_failed`); so is a state whose document cannot be written out. While the shown state is not regenerated on the page, nothing a frame reads regenerates it: the selection is checked against it once it is (`selection_serial` and `selection`, what the shell reads every frame, give the selection as last checked; `checked_selection`, what the commands read, checks it whatever it takes), and a section on a datum plane takes the plane from the scene, which carries each datum plane as regeneration placed it (`SceneDatumShape::Plane`'s `origin` and `normal`, the datum's own numbers bit for bit), so it lies where a page that regenerates finds it. Before 2026-10-28 a frame did regenerate: the shell copies the selection when its serial differs from the one it holds, so a face selected in one tab and another tab opened (or a Jig) made the first frame that showed it check the new document's selection, a whole regeneration on the page's thread that nothing could stop; and the section on a datum plane, resolved once per scene, regenerated the state to find its plane (`crates/engine/tests/regen_elsewhere.rs` › `what_a_frame_reads_never_regenerates_on_the_host`, `crates/ui-egui/tests/regen_elsewhere.rs`). While the view is scrubbed the section still lies on the plane of the document as it is (`view.scrub`), which the scene of the scrubbed state does not hold: that one regenerates the document on the page once.

*Reading a scene that crosses.* The bytes come from another instance of the module, but are read as hostile all the same (a bug there must not become an allocation or a panic here). Every count is checked against the bytes left at its entry's least size (a body 60 bytes, a feature row 21, a sketch 112, a face colour 9, a point 24), no list gets more room up front than the bytes left would fill, and what reads is a scene the page can draw: every mesh a normal per position, a face id per triangle and only corners it has; the bodies numbered as `scene::build` numbers them (the first face id 0, each next one past the highest face id of the body before) with each body's face ids within its faces (its face names, or without names no more than its triangles: every face the tessellator meshed has a triangle at least); and a face colour of a face of those bodies, since the colours are kept by face id and one at 2²⁴ − 1 would take 16 million entries from 60 bytes. A scene that breaks any of these is one that "cannot be read", an error for that state (`scene_wire` tests). The form's version is 2 (the datum planes' own numbers).

*Bit for bit.* `crates/engine/tests/regen_elsewhere.rs` builds a document of blocks, a boolean, a sphere with a colour, a datum plane, a sketch, outputs in two stages and assertions at 1e-2, 1 and 1e3 mm, hands every job over and compares the page's first picture and display scene byte for byte (`scene_bytes`) with those of a session that builds them itself, and its assertion and output rows, through an edit and back, without the page regenerating the state it shows (`Session::regenerated_here`); and checks that an edit supersedes a job and its checks (a late answer is dropped part by part), that a worker that stops leaves errors and the next state goes on, and that without checks elsewhere the page regenerates itself.

*Still on the page's thread, and the general method owed.* Until 2026-10-30 a command that needed the bodies regenerated the state on the page when it ran: a click that selects, `measure.*`, `file.export`, a section on a datum plane while the view is scrubbed (`view.scrub` itself needs none); since then they run in the worker (*Commands where the bodies are* below). The page asks for no frame of its own while a worker builds (`WebHost::prepare` returns false: the answer's message asks for the frame that takes it, and the page looks at the deadlines every 30 s on `performance.now()`, a clock that does not go back); the bar that sweeps in the status bar asks for frames while it is drawn, as it does for any work.

### A worker that can be stopped, with its caches (2026-10-30)

Before, a job replaced while the worker built it was cancelled by ending the worker (`terminate`): a worker runs one message at a time, and the job was one call that built the whole answer, so it could not look at the newer job before it was done. The next state then regenerated from nothing, and a slider dragged over a model that takes longer to regenerate than the time between two values showed no new state until the drag stopped.

*As built.* The worker builds a job a piece at a time: `craft3d_scene_step` (the engine's `scene_step`) regenerates and meshes until about 30 ms have gone (`PIECE_MS` in `packaging/web/worker.js`; at least one feature or body, asked between features through `craft3d_regen::progress::with_stop` and between bodies through the progress sink, as `Session::prepare_some` does on a page without the worker) and returns a part when one is there; between pieces `worker.js` yields to its own event loop (a message to itself on a `MessageChannel`, which a timeout's 4 ms clamp would slow), so the messages that came are taken: a newer job of scenes replaces the one in hand (`scene_begin` loads its state into the same session, whose regeneration cache and store of meshes keep what was built, also of a regeneration stopped half way), and `{kind: "cancel"}` (`Transport::cancel`, posted when the shown state's scenes are there already, an undo) leaves it. The page (`scenes.rs`) no longer ends the worker for a superseded job; it posts the newer one, and parts of the old one on their way are dropped by their number as before. The worker's session does the long work as the page's would (`set_stepwise`, the checks left to the checking worker), so the parts are those `scene_next` builds in one go, bit for bit (`crates/engine/tests/regen_elsewhere.rs`, through the stepping path since `scene_next` is a loop over `scene_step`).

*Rules added, and why they hold for any document.* A job is stopped only between features and bodies, where `prepare_some` already stops for the page, so what is built does not depend on where it stopped. A state loaded into the worker that is byte for byte the one it holds is not loaded again (another quality of the same state keeps its scenes). A worker that aborts (a bug) is ended as before, and the job given to it since goes to a new one.

*Measured.* `apps/craft3d-web/tests/drag.rs` (ignored; `cargo test --release -p craft3d-web --test drag -- --ignored --nocapture`): the page's own `Scenes` over a session that regenerates elsewhere, a frame every 16 ms, and a thread that does what `worker.js` does, on the cutaway turbofan of the benchmark (241 steps); ten values of a variable set 250 ms apart, before (a job posted while the worker is busy ends it and starts a new one, the policy until 2026-10-30) and after. On the Strix (run 41150474442), first new state shown after the first value / values shown during the drag / the last value's display scene after it was set: `filletM` (used at step 135) before 5.3 s / 0 of 10 / 3.1 s, after 32 ms / 9 of 10 / 46 ms; `boltHeadH` (step 204) before 5.1 s / 0 / 2.9 s, after 73 ms / 9 / 69 ms; `scallopR` (step 175, whose change reaches the cutaway's heavy last booleans, about 10 s of work for any value) before 13.0 s / 0 / 10.8 s, after 12.7 s / 0 / 10.5 s. The test compares the page's last scene with a session that builds the same values one after another and with one that builds the last from nothing, and asserts all three equal: green in run 41150474442, every scenario, before and after. Its first versions found them different (runs 41145862297, 41148618955); the cause was the harness, not the product: it read the page's scene as soon as `scene_ready` held, which with the display scene refined elsewhere is as soon as the quick first picture is there, and `scene_with` then gives that picture (`preview: true`, the preview's tolerance: the field-by-field diff in the test said so). It now waits for the worker's answer to be complete and the display scene there; the timings above are to that scene `apps/craft3d-web/src/scenes.rs` › `a_superseded_job_leaves_its_caches_to_the_next` pins the reuse without a clock: after four values each replaced after one piece, the first picture of the last takes under a quarter of the pieces it takes from nothing.

### Commands where the bodies are (2026-10-30)

A command that needs the bodies (a click that selects, `select.query`, `measure.*`, `file.export`, ...) regenerated the state on the page when the page had it regenerated only in the worker: seconds to minutes on a heavy model with the page frozen. The worker has those bodies: it built the scene the page shows.

*The choice: the command crosses, the bodies stay.* Bodies have no serialised form (geometry and topology have no serde), and a resolver and measures over the scene would not give the desktop's answers (a measure over a mesh is not the exact one). The command and the selection it reads are plain data, and its answer is a function of the document state and that selection.

*Which commands.* Only a command a person or an agent dispatched is handed over (`Session::execute_deferrable`: the page's `WebHost::run` and a click that selects); the shell's own reads (what the export dialog offers, how many are selected) use `execute` and answer at once, regenerating on the page when they need the bodies (review, 2026-10-31: handed over, they answered `{deferred}` and an export after a selection wrote every body). Since 2026-11-02 the export from the menu no longer uses them on the page: the dialog's choices and the whole export are jobs of the worker (*Edits and exports where the bodies are* below). Such a command is tried on the page first (`commands_elsewhere.rs`, `Session::try_without_bodies`): the active document answers every regeneration it is asked for and does not have with an empty one and notes that (`OpenDocument::forbid_regen`; also the regeneration of a scrubbed state). A command that asked for none is done, its result stands (`view.scrub`, `param.set`, a feature added). One that asked is undone whole, the session put back from a copy made before it (the copy shares the documents, bodies, scenes and, since 2026-10-30, the files in memory, `Arc` of their bytes), so nothing it did with the empty regeneration remains, and it is handed over: its result now is `{deferred: true, job}`, and the host posts the job (`Session::command_jobs`, `command_request`: the state's `.3dcraft` bytes, the command, its parameters and the selection written out, `Selection::to_wire`) to the regenerating worker (`kind: "command"`, `craft3d_command`, the engine's `run_command`), which runs it between two pieces of a scene on its own session with that state and that selection, and answers with the result, the selection when the command changed it, and the files it wrote. The window's camera goes with it when it was given for that document (an export of `view: "current"`), and whether it follows a command still waiting on the same state and selection (then the worker runs it on the selection that one left, and only then, keyed by a digest of the state's bytes: two tabs, or a refused answer and an undo, never chain). `Session::command_answered` takes the selection (checked there against the same state, so it is kept as checked) and the files when the document is still in the state the command ran on and its selection is the one the command read; the host reports the answer (`WebHost::answered`: the result as the command's own report; an export's files offered as its dialog would have, through the system's save dialog where the page has one, which a browser may refuse so long after the click, and then as downloads). Whether a command needs the bodies is what it does on this document, found by the trial, not what it is called. Only commands that read the document were handed over until 2026-11-02 (`measure.*`, `select.*`, `file.export`, `document.inspect`, `document.edges`, `document.measure`, `document.interference`; their effects are a result, the selection and files, all an answer carries); since then an edit is too, its undo steps carried back (below).

*Rules added, and why they hold for any document.* Until 2026-11-02 a command that edited the document in its trial and asked for the bodies (`assert.add`, an edit that follows a face) ran again here at once; since then it is handed over and its edit applied from the answer (below); a read the worker finds editing (its trial took another way with the empty regeneration) is run here when its answer comes. An answer for a state the document left (an edit in between) is an error that says so, and nothing of it is taken. A worker that aborts, cannot be had or is given up at its deadline leaves every waiting command an error (`Session::commands_failed`); a page that regenerates itself again (no worker) runs commands here as before. At most 64 commands wait at once; past that a command runs here. A section on a datum plane while the view is scrubbed takes the plane from a scene of the document as it is (kept while the view is scrubbed; when none is kept the worker builds its first picture first, `Session::scene_job`), so no frame regenerates for it.

*Bit for bit.* `crates/engine/tests/commands_elsewhere.rs`: a click's `select.set`, `select.query` with `then`, `select.get`, `measure.distance`, `measure.thickness`, `measure.below` on a datum plane, `file.export` to STL and STEP and a command that fails, at 1e-2, 1 and 1e3 mm, against a session that regenerates itself: the same results, the same selection after each, the same file bytes, and the page never regenerating (`Session::regenerated_here`); `view.scrub` not handed over; the section while scrubbed with and without a kept scene; a late answer dropped, a stopped worker's commands errors, hostile requests and answers errors. `apps/craft3d-web/src/host.rs` › `an_export_beside_the_page_downloads_what_the_page_would_have`.

*Still on the page's thread.* An edit that needs the bodies; `assert.list` and `document.check`, which measure in line; motion (`view.motion`), which regenerates its states itself; and the copy of the session a command is tried with (its documents, scenes and files are shared, so it is a copy of maps and vectors of `Arc`s, but it is made for every command while the state is not regenerated here). Since 2026-11-02 all but motion run in the worker (below).

### Edits and exports where the bodies are (2026-11-02)

Two R1 items the developer decided for the field test: the export from the menu regenerated on the page when the dialog's reads needed the bodies (what is selected, the flat patterns: `select.get` checks the selection against the state, `select.query` counts the bodies and reads the features' statuses, `set.list` describes the sets), and an edit that needs the bodies (`assert.add`, `variable.measure`, a fillet on edges named by their faces), `assert.list` and `document.check` regenerated the state on the page's thread.

*The choice for exports: the whole export is a job of its own.* Reads that answer from the scene would not be the desktop's (the scene has no selection checked against the state, and the count of bodies decides whether an export names its bodies), so the host's own code runs where the bodies are: `Session::hand_over(command, params)` makes a job of the active document's state, its selection and the window's camera, as a command handed over is (`kind: "command"`), and the other side runs it with `craft3d_engine::run_on_state`, which loads that state and selection into its session and hands it to the host's function. The page's functions (`apps/craft3d-web/src/jobs.rs`): `host.exportChoices` is `export_choices` (what the dialog offers), `host.export` is `export_where_bodies_are` (`export_params` with the selection followed or the plan as the dialog was answered, then `file.export`), both the very functions a page that regenerates itself runs, so the files are its bytes. File › Export posts the choices and the dialog opens with the answer (`Shell::open_export_with`); its answer posts the export, made before any save dialog as before, and the files come back with the answer (`WebHost::answered`: the system's save dialog where the page has one, the OBJ's library waiting for its own click, downloads otherwise; a failing export shows the desktop's error and no dialog). Without the worker (none, or `?pageregen`) or with the state regenerated on the page, the page does both itself as before.

*The choice for edits: made there, applied here as undo steps.* An edit is the document's: the history stays the source of truth, so the page's history gets the step, not a result. The worker runs the command on the state it was asked on (`run_on_state`), and `edit_merging` notes each undo step it makes while a command runs for another session (`Session::edit_log`: the label, the key and whether it merges, and the document after it); the answer carries the steps and each document as the bytes of its `.3dcraft` file (`CommandAnswer::documents`). The page applies them with `History::apply_merging` as `edit_merging` would have (one step with the desktop's label, folded into a run of the same key as a slider's are), so undo and redo see an ordinary step. Which edits cross: the families whose commands change the document and nothing else (`feature.`, `sketch.`, `datum.`, `assert.`, `variable.`, `param.`, `body.`, `face.`, `set.`, `table.`, `output.`, `fold.`, `unfold.`), not the texts (their fonts are files of the page's session) and only while the view is not scrubbed; the rest runs here as before. A Jig in use goes with the job (`jigInUse`), so its refusals are the page's. `assert.list` and `document.check` are reads that cross; `assert.list` (and anything that waits for every check) is answered on the page at once from the checking worker's answer for the state once it is there (`checks_and_outputs`: that answer is measured with every check in line, `Wait::All`).

*Rules added, and why they hold for any document.* An edit's answer is taken only for the state it was made on (the same rule as a read's): an edit that came between makes it an error that says so, and nothing of it is applied. Its documents are taken only when the state it was made on crosses the format as it is here, field for field (`from_bytes(to_bytes(state)) == state`): otherwise, or for steps that do not read, the command runs here as before, so a field the format left out could never be lost by an edit. While an edit waits, the page keeps what was asked for after it (`Session::edits_waiting`; `WebHost::pump` leaves the menu's actions, Undo and the Parameters form's commit in their queues), so they run on the document the edit leaves, in the order asked, as the desktop's engine thread runs one task after another. A worker that dies mid-job leaves every waiting job an error the person sees (`commands_failed`, as before), and one that never answers is given up at the scenes' deadline (`scenes::COMMAND_TOO_LONG`, 30 minutes; the worker is ended and the next job starts a new one): no wait without end.

*Review, 2026-11-02 (on e703ad2a).* An export is a function of the state it was asked on alone: its files are taken while its document is open, whatever was done to it before the answer came (a slider moved, an eye clicked; before, such an edit threw the export away), and nothing else of its answer is (no selection). While an edit waits, nothing else edits or selects around it: the timeline's and the eyes' requests and the clicks stay queued in the shell (`Session::edits_waiting`), a file opened or dropped waits in the page's inbox, the recovery bar says to try again, and the menu's actions but Open and Import (which may ask for a file only in the frame of the click; the file then waits) stay queued; the edit's selection is taken only over the selection it read. An edit that waits longer than `EDIT_NOTE_AFTER` (0.35 s) shows *Working on <command>…* with Cancel (`WebHost::waiting_ui`, `Session::edits_failed`: not made, a late answer dropped, said in the status bar without an error dialog). The Parameters form is told the real result of a commit made in the worker (`WebHost::form_job`), so its merging, clamping and refusals hold. The worker sends an edit's steps only when each state after it crosses the file exactly, at most `ops::DEFAULT_LIMIT` steps, and also the steps that changed nothing (under a key they start a new run, as on the desktop); the page refuses more steps or labels and keys longer than 4096 bytes before it parses a document, and an edit's answer brings no files. The deadline of the commands starts again with every answer.

*Final round (2026-11-02).* Cancel also ends the worker when the edit was posted to it (it may hang on it: `Session::edit_posted`, `Scenes::restart`; what else was posted to it answers `scenes::RESTARTED`, and the next job starts a new worker), and a cancel is no failure for the bug report (`edits_failed` records none). A dialog over the page answered while an edit waits (the export dialog, Save As, Export as Jig) is kept and done once the edit is applied (`WebHost::pump`), so the export or the save is of the document the edit leaves, as on the desktop; with the system's file dialogs that comes after the click's user activation, and the page then downloads and says so (the fallback of 2026-10-30).

*The view seen, framed alike at every sampling.* A window that follows the model framed it on the scene's mesh box (`Scene::bbox`), which the quick first picture and the display scene sample differently: the camera moved when the one turned into the other, and a drawing of `view: "current"` asked in between differed from one asked after. It frames on `Scene::frame_box` now (`scene.rs` › `frame_of`, built with the scene and carried by its bytes, form 5): each body's B-rep box where that is exact (planes, cylinders, cones, spheres, tori), and for a body with a freeform face (whose B-rep box is its surfaces' control nets, far past a trimmed face or a loft) or whose box cannot be found, its mesh's box widened by the scene's chordal tolerance, so only such a body may move the camera between samplings; every sketch and helix sampled at a thousandth of the model's size whatever the scene's sampling, its curves widened by that (a circle larger than the bodies counts whole); the corners on a power-of-two grid near a billionth of its size, cosmetic (a cylinder's extremes come out round), and `Shell::sync` gives the session the camera again after it followed the scene, so the view seen is this frame's. `crates/ui-egui/tests/frame_box.rs` (a sphere, a cylinder and a block at 1e-3 to 1e6 and 1e6 from the origin: the first picture's and the display scene's mesh boxes differ, the frame, the camera and the drawing do not, and it fails with the mesh box; a sketch circle larger than a block framed whole; a loft whose control net bulges past it framed by its mesh, which fails with the B-rep box). `view.render` frames on `bodies_box` (B-rep, unsnapped, without sketches) and the drawings' perspective on their own export meshes: both are independent of the scene's sampling already, and moving them to the frame would change pictures for nothing a person sees; left as they are. `crates/engine/tests/drawing_determinism.rs`: a named view and `current` with a given camera, with the automatic and a given tolerance, the process-wide caches of the kernel and the tessellator let go before each reference drawing, give the same DXF and SVG bytes after every kind of earlier work.

*Measured.* `apps/craft3d-web/tests/page_stall.rs` (ignored; `cargo test --release -p craft3d-web --test page_stall -- --ignored --nocapture`): the page's `WebHost` and `Scenes` on this thread, a frame every 16 ms, the regenerating and the checking worker threads of their own, on the cutaway turbofan opened from its file (196,719 bytes), each action from a new state (a variable set) the page has not regenerated; with the commands run on the page (as the dialog's reads did before) and with the worker. ### Motion and assemblies in the worker (2026-11-03)

The two R1 items the developer gave after the edits: the web build's motion (`view.motion`, the player) regenerated its moments on the page's thread, and an assembly was never handed to the worker (its sources are files this session read, which a document sent elsewhere did not carry), so it was solved and placed on the page a piece per frame.

*The choice: the view crosses, the page keeps the view state.* A moment and a placement are functions of the document state, the files read for it and the view (`t`, collisions); the bodies they place have no serialised form. So the page keeps what it always kept (the document, its history, the selection, `t`, collisions asked for, a bake wanted) and hands the rest to the worker that regenerates it: the state below the view, with an assembly's sources (`view_elsewhere::state_bytes`: the `.3dcraft` file, the assembly's path and folder, and each file read or why it could not be read), and the view. The worker shows that view in its own session (`OpenDocument::set_motion_view`, `view_elsewhere::install`), as a session that shows it itself does, and answers part by part: first the view's facts (`VIEW`: what `view.motion` says of the moment, an assembly's outline, the joint a drag on each placed feature moves, the placed part as a file whose features the scenes are read against, or why the moment could not be made), then the quick first picture and the scene asked for, as for any state, then, when a bake is wanted, one part per piece of `motion.bake {limit: 1}` (`BAKE`) until it is done. The page keeps a stand-in per view (`view_elsewhere::Remote`: a copy of the state below with `t` set, a document state of its own) under which those scenes are kept, as a state regenerated elsewhere is; `shown()` is the stand-in, so a frame never makes a moment or places. `Session::motion` is the facts (`pending` until they came, `error` when the moment could not be made there), `assembly_outline` and `assembly_joint_of` the facts (the last ones of the same state while the next moment is made, so the tree does not flicker), `view.motion` answers `pending: true` (then what it answered there), `motion.bake` records the bake and answers as a bake in the background does, its `building` followed by the bake parts. The player waits for a pending moment before it asks for the next (`Timeline::motion_waiting`), weighs it for the bake hint by the time until it came (`BakeHint::made_elsewhere_from`, `came`), and says an error and stops; the page does not show a moment's job as work (the status bar says *Playing*). A job without a view shows the state as it is (the moment of an earlier job is let go of: a test found the next at-rest job of another document drawn at that `t`).

*Rules added, and why they hold for any document.* Only what the page cannot know is made there: everything the page keeps is view state, and every answer is taken only for the stand-in it was asked for (a late answer, or one for another `t`, is dropped part by part). A command tried without the bodies that asks for the moment's or the placement's regeneration (`shown_regen`, `shown_placed`, `placed` while not placed here) runs in the worker (`tried_without_view`), the moment shown there first (a read carries `t` and collisions); `regenerated_here()` is false while a moment is made elsewhere, so nothing reads a moment on the page from the state at rest. The assertions of an assembly are measured whole by the checking worker with its sources (`checks_and_outputs` no longer places the assembly on the page to find out whether it has any: that was the page's one placement after every edit). `joint.set` answers without solving there (`status: "pending"`, `deferred: true`). `assembly.new` keeps the session's shared `work` (before, the new assembly's document did not share it, so `work_here` did not see it and its view was not made elsewhere). Bounded: one view, one last facts, one bake per document; facts carry at most 4096 rows and joints; a state carries at most `MAX_SOURCE_FILES` files and is read against the bytes it has (every prefix an error, `view_elsewhere` unit tests); a bake made there stops after three pieces without progress (its budget is full) with an error that ends it.

### A recorded frame that said "refining" (2026-11-03)

`app::tests::a_step_recording_of_a_provisional_moment_records_the_exact_one` (`apps/craft3d/src/app.rs`) failed now and then in the Gate since the motion player landed, logged as a recording of the provisional moment. The recording's first frame, with the sharp scene settled, therefore still said `refining` when it came less than 0.25 s after that first pass, and not when it came later: a frame of a recording that depended on how long the window took to start it. Two conditions hid it outside the Gate: the word shows in the first pass only when egui lays that pass out twice (the interface's fonts arrive in it, `fonts.rs` asks for a discard, and the second layout has the renderer's numbers of the first), which needs the fonts (`CRAFT3D_FONTS`, set in the Gate, not in a plain checkout); and one desk had to cross 0.25 s while the other did not (under load). ### Sweeps and assembly edits in the worker (2026-11-04)

The R1 item left by *Motion and assemblies in the worker*: `view.trace` and `motion.check` made their own sweep of the motion on the page (a state regenerated, or an assembly solved and placed, per sample), and the assembly's commands that report what they solved (`instance.add`, `mate.add`, `coupling.add`, `assembly.solve`, `assembly.inspect`, a variable set and waited for) placed the assembly on the page when they ran (the trial asked for the placement, and they were in no family that crosses, so they ran here again).

*The choice: the sweep crosses as a command; its trace comes back as view state.* A trace and a check are functions of the document state, the files read for it and their parameters, as any read handed over is (*Commands where the bodies are*). Tried on the page, they stop before they sample (`OpenDocument::sweep_elsewhere`, noted as a regeneration asked for). `motion.check`'s answer is its result. *Assembly edits.* `instance.`, `mate.` and `coupling.` are families of edits that cross (made there, applied here as undo steps).
