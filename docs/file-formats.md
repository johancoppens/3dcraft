Formats live in standalone crates with their own format-level model and no workspace dependencies; the mapping to bodies and documents lives in `io` ([`architecture.md`](architecture.md) §3).

## Native format: `.3dcraft`

**Implemented today (format version 12; version 1 to 11 files open unchanged; 12 added the `deleteFace` feature kind, below; 11 added the `offsetFace` and `shell` feature kinds, below; 10 added the `sweep` feature kind, written `{"type": "sweep", "sketch": 7, "path": 9}` with the feature ids of the sketch that holds the profile and of the sketch whose curves are the path; 9 added the `fillet` feature kind and the name roles `fillet` and `filletCorner`, below; 8 added the `loft` feature kind, written `{"type": "loft", "sections": [{"sketch": 7}, {"sketch": 9, "start": 3}]}` with the feature id of each section's sketch in the order the loft passes through them, the entity id of the curve a section starts with when one was given, and `"ruled": true` and `"closed": true` only when set; 7 added the `chamfer` feature kind and the name roles `chamfer` and `chamferCorner`, below; 5 added the `transform`, `mirror` and `pattern` feature kinds and names that are copies of names; 6 added the `spline` kind of sketch entity, written `{"type": "spline", "degree": 3, "control": [1, 2, 3, 4]}` with the ids of its control points, its knots being clamped and uniform by definition):** a ZIP of stored entries with one entry, `manifest.json` (below). Unknown extra entries are ignored on load and not preserved on save. `blobs/`, `thumb.png`, the directory layout, autosave and crash recovery are the plan, not built.

A `.3dcraft` file is a ZIP of STORE (uncompressed) entries, or a directory with the same layout (useful in git and for debugging):

```text
manifest.json            the document, versioned
blobs/<blake3>.zst       content-addressed, zstd-compressed objects: imported bodies, cached regeneration results
thumb.png                preview (CPU renderer)
```

**`manifest.json`** holds `format_version` and the whole `craft3d-doc` document as JSON: readable, diffable and writable by an agent in an emergency.

- **What is stored is what the user wrote.** Expressions are stored as source text (`"width / 2 + 3 mm"`), not as evaluated numbers. Values are recomputed on load.
- **Order is stored explicitly:** the feature list in application order, the variable table in evaluation order, each sketch's constraints in the order they were added, and each sketch's last solved state (so a reopened sketch does not flip to another solution branch).
- **Ids are stable.** Feature and sketch-entity ids are never reused within a document, because persistent names are built from them.
- **Caches are optional.** A cached body is keyed by the hash of everything it was derived from. Loading verifies the key; a missing, stale or damaged cache is regenerated silently. Deleting `blobs/` of a document without imports must not change the model.
- **Imported bodies are data.** A STEP import becomes an `Import` feature whose body is a blob: it cannot be regenerated, so it is not a cache and is never garbage-collected while referenced.
- **Version history.** 1 (2026-10-12): variables; block, cylinder, sphere. 2 (2026-10-12): adds cone and torus, and an optional `orientation` (`axis`, `angle`) on block, cylinder, cone and torus. 3 (2026-10-12): adds the `sketch` feature kind. 4 (2026-10-12): adds the `extrude` feature kind (`sketch`: the id of the sketch feature, `distance`: an expression, `symmetric`) and a second kind of sketch plane, `{"type": "face", "face": {"feature": 2, "role": "endCap", "sources": [7, 8, 9]}, "offset": expr}`: a flat face of an earlier body by its persistent name. Nothing in an older file changed meaning in any step; the number was raised so that an older build reports "a newer 3DCraft is needed" instead of an unknown field or kind.
- **The ends of an extrusion (2026-10-13, no new version).** An `extrude` has two more optional fields: `end`, one of `{"type": "distance"}`, `{"type": "throughAll"}` and `{"type": "upToFace", "face": {…a persistent name…}}`, and `reversed` (against the sketch's normal). An extrusion that ends at its `distance` and is not reversed is written without them, byte for byte as before, so a file that uses neither is one an earlier build of version 6 reads; a file that does use them is refused by such a build as an unknown field, not as "a newer 3DCraft is needed" (the number was not raised because no existing data changed meaning; raising it is the developer's call, see [`decisions.md`](decisions.md)). `distance` is still written for the other ends: it is the distance the extrusion goes back to. What "through all" goes through and where an extrusion up to a face ends are not in the file: they are derived at regeneration from the features before it ([`architecture.md`](architecture.md) §4.1 › *Extrude ends*).
- **A sketch in the file** is a feature of type `sketch` with a `plane` (`{"type": "world", "plane": "xy|yz|zx", "offset": expr}`), `entities` in the order they were drawn (`{"id", "construction", "geometry"}`, where geometry is a `point` with `x` and `y`, a `line` with `start` and `end`, a `circle` with `center` and `radius`, or an `arc` with `center`, `start` and `end`, all referring to point entities by id), `constraints` in the order they were added (`{"id", "kind": {"type": …}}` with entity ids and, for dimensions, a `value` expression), and the next free entity and constraint ids. The point coordinates and circle radii are plain numbers in the document's length unit: they are the last solution, and the solver starts from them.
- **Names of pieces (2026-10-14, no new version).** A persistent name has one more role, `piece`, written like a `copy`: `{"feature": 2, "role": "piece", "sources": [1], "of": {"feature": 2, "role": "side", "sources": [7]}}` is the second of the faces that sketch entity 7 sweeps in feature 2 (as text `F2:piece(1)/F2:side(e7)`); the first keeps the plain name. Regeneration gives such names to what a spline sweeps when it is cut into pieces (a closed spline, a spline with corners) and to the second half of a full revolution of a spline. A file never held one before, so nothing changed meaning; a build from before this date refuses the role as unknown.
- **Names of edges and vertices by their faces (2026-10-14, no new version).** A persistent name has two more roles, `between` (an edge) and `corner` (a vertex), and one more optional field that only those roles have: `faces`, an object with `on`, the names of the faces of that feature's body the entity lies on, and `near`, the names of the faces next to it that tell it from others on the same faces; `sources` is then empty or holds the one number that tells it apart when the faces do not. `{"feature": 7, "role": "corner", "sources": [], "faces": {"on": [{"feature": 7, "role": "copy", "sources": [0], "of": {"feature": 1, "role": "face", "sources": [1]}}, …]}}` is what a datum point at a vertex of a boolean stores. The listed names are faces and list none themselves; a file in which they do is refused. Their order in the file does not matter: they are put in the one order on reading. As text, in commands and messages, the same name is `F7:corner[F7:copy(0)/F1:face(1),…|…](1)`. A build from before this change does not know the roles and refuses such a file as damaged.
- **Chamfers (2026-10-14, version 7).** One feature kind: `{"type": "chamfer", "edges": [[name, name], …], "size": …, "chain": false}`. Each edge is the two faces it lies between, as names (`{"feature": 1, "role": "face", "sources": [1]}`), the first distance being measured along the first; the body chamfered is that of the feature the first name starts with, and nothing else says so. `size` is `{"type": "equal", "distance": expr}`, `{"type": "twoDistances", "distance": expr, "second": expr}` or `{"type": "distanceAngle", "distance": expr, "angle": expr}`. `chain` may be left out (false). Two name roles for the faces a chamfer makes, written like every other role: `chamfer` (`sources`: the place of the edge's reference in `edges`, and when that reference gave several edges, which of them) and `chamferCorner` (`sources`: the places of the three references whose chamfers meet there); as text `F9:chamfer(0)`, `F9:chamfer(0,2)`, `F9:chamferCorner(0,1,2)`, with plain numbers. The version was raised because a build that knows version 6 could not read the new kind or the new roles: it now reports "a newer 3DCraft is needed". Nothing a version-6 file holds changed meaning (`v6_to_v7` is the identity; a version-6 fixture is pinned in `crates/format/tests/format.rs`). *For the developer to confirm:* three features of 2026-10-13/14 (datums, extrude ends, the roles `between` and `corner`) were added as optional fields and kinds without a new version, which leaves version-6 files that an earlier version-6 build cannot read; whether those should have been a version each is open, and this version 7 does not settle it.
- **Fillets (2026-10-14, version 9).** One feature kind: `{"type": "fillet", "edges": [[name, name], …], "radius": expr, "chain": false}`. Each edge is the two faces it lies between, as a chamfer's (their order says nothing here); the body filleted is that of the feature the first name starts with. `chain` may be left out (false); `radius` may not. Two name roles for the faces a fillet makes: `fillet` (`sources` as for `chamfer`) and `filletCorner` (`sources` as for `chamferCorner`); as text `F9:fillet(0)`, `F9:fillet(0,2)`, `F9:filletCorner(0,1,2)`. The version was raised for the reason versions 7 and 8 were: a build that knows version 8 could not read the new kind or the new roles, and now reports "a newer 3DCraft is needed". Nothing a version-8 file holds changed meaning (`v8_to_v9` is the identity; a version-8 fixture with a chamfer and a loft is pinned in `crates/format/tests/format.rs`). The fillet was made as version 8 beside the loft, which took 8 first; it became 9 when the two were merged. *For the developer to confirm,* with versions 7 and 8: whether a new feature kind is a version each time.
- **Reference geometry (2026-10-13, no new version).** Three feature kinds that make no body: `{"type": "datumPlane", "by": …}`, `{"type": "datumAxis", "by": …}` and `{"type": "datumPoint", "at": …}`. A plane's `by` is `{"type": "offset", "from": plane, "distance": expr}`, `{"type": "angle", "from": plane, "about": axis, "angle": expr}` or `{"type": "threePoints", "points": [point, point, point]}`; an axis's `by` is `{"type": "twoPoints", "points": [point, point]}`, `{"type": "edge", "between": [name, name]}`, `{"type": "face", "face": name}` or `{"type": "twoPlanes", "planes": [plane, plane]}`. A *plane* is `{"type": "world", "plane": "xy"}`, `{"type": "face", "face": name}` or `{"type": "datum", "feature": id}`; an *axis* is `{"type": "world", "axis": "x"}`, `{"type": "edge", "between": [name, name]}` (the two faces the edge lies between) or `{"type": "datum", "feature": id}`; a *point* is `{"type": "at", "position": [expr, expr, expr]}`, `{"type": "vertex", "vertex": name}`, `{"type": "center", "between": [name, name]}` or `{"type": "datum", "feature": id}`; a *name* is a persistent name as elsewhere in the file. Existing kinds got four optional places for a datum's feature id: a third sketch plane `{"type": "datum", "plane": id, "offset": expr}`, `plane` on a `mirror`, a fourth revolve axis `{"type": "datum", "axis": id}`, and `about` on a circular pattern layout. `plane` and `about` are written only when set, so a file that uses no datum is byte for byte what a build before datums wrote, and such a build refuses a file that does use them as an unknown kind or field (the number was not raised, for the same reason as for the ends of an extrusion: no existing data changed meaning; raising it is the developer's call). Where a datum lies is not in the file: it is derived at regeneration.
- **Face operations (2026-10-14, version 11).** Two feature kinds: `{"type": "offsetFace", "faces": [name, …], "distance": expr}` (the faces of one body, the one of the feature the first name starts with; outward positive) and `{"type": "shell", "source": 3, "thickness": expr, "open": [name, …]}` (`open` may be left out: a closed hollow; its names are faces of `source`). No name role was added: their faces are copies (`copy(0)`; the faces of a shell's hollow `copy(1)`). The version was raised for the reason versions 7 to 10 were; nothing a version-10 file holds changed meaning (`v10_to_v11` is the identity; a version-10 fixture with a fillet, a datum on its face and a sweep is pinned in `crates/format/tests/format.rs`). Made as version 10 beside the sweep, which took 10 first; it became 11 when `work` was merged into its branch.
- **Delete face (2026-10-14, version 12).** One feature kind: `{"type": "deleteFace", "faces": [name, …]}` (the faces of one body, the one of the feature the first name starts with). No name role was added: the faces that stay are copies (`copy(0)`), edges and vertices are named by their faces. `v11_to_v12` is the identity; a version-11 fixture with an offset and a shell is pinned in `crates/format/tests/format.rs`. The same build changed which way a sketch or a datum plane on a face of a subtraction's tool faces (a pocket's floor, a hole's wall: now out of the material, as on every other face). That is how regeneration reads the face, not what the file holds, and it was not migrated: a version-11 file with a sketch on such a face opens with the sketch turned over (its normal and its y axis the other way), so a pin that went down into the material now stands up into the pocket ([`decisions.md`](decisions.md), 2026-10-14).
- **Versioning.** Every change to the meaning of existing fields bumps `format_version` and adds a migration (`format/src/migrate.rs`) with a fixture of the old version in the tests. New optional fields use `#[serde(default)]`. A file from a *newer* version opens with an error that says so, never with silent data loss.
- **Completeness is enforced at compile time:** `format` destructures every `doc` struct exhaustively, so a new document field cannot be forgotten ([`AGENTS.md`](../AGENTS.md) §8).
- **Atomic saves:** write to a temporary file in the same directory, fsync, rename over the target. A crash or a full disk leaves the previous file intact.
- **Autosave and crash recovery** (2026-10-13; `crates/engine/src/recovery.rs` holds the design) reuse the writer, from a snapshot on a background thread, into a recovery directory keyed per launch. See *The recovery directory* below.

### The recovery directory

A session that was given a recovery directory (`craft3d --recovery-dir DIR`, by default `3dcraft/recovery` in the per-user state directory: `$XDG_STATE_HOME` or `~/.local/state` on Linux, `~/Library/Application Support` on macOS, `%LOCALAPPDATA%` on Windows; `craft3d-cli serve|mcp --recovery-dir DIR`, off by default) keeps there, per launch, a lock file and, per open document with unsaved changes, a document and its record. A launch is one running process with one session; its key is 16 random hexadecimal digits.

```text
<key>.lock          empty; the launch holds an operating-system lock on it while it lives
<key>-<n>.3dcraft   document n of that launch: exactly the bytes file.save would write
<key>-<n>.json      its record
.<name>.<pid>.tmp   a write in progress (removed by the next scan when its launch is gone)
```

The record is what varies between runs, so the `.3dcraft` bytes stay deterministic:

```json
{
  "recovery_version": 1,
  "launch": "9f0c2a6b41d7e835",
  "pid": 48213,
  "document": 3,
  "name": "bracket.3dcraft",
  "path": "/home/ann/parts/bracket.3dcraft",
  "original": { "size": 18234, "mtime": [1791907200, 512000000] },
  "revision": 41,
  "features": 12,
  "time": 1791907260,
  "recovered": false
}
```

`path` is the path the document was opened from or last saved to, as the request gave it (null for a document that never had one) and `name` its last part or `untitled`; `original` is the size and modification time (seconds and nanoseconds since the Unix epoch) that file had when the document was opened or last saved, null when there was none; `revision` counts the changes made to the document in that launch; `time` is when it was written, in seconds since the Unix epoch; `pid` is for a person to read and is never used to decide anything. A record of a newer `recovery_version`, one that is not JSON, or one larger than 64 KiB is not read: its document is still listed and can be opened, as `untitled`.

- **Written** when a document has unsaved changes and the autosave interval (30 s by default; `--autosave-interval SECONDS`) has passed since that document's last write, or since its first change when it was never written: a burst of commands gives one write, and at most one interval of work is lost. After a caught panic every document with unwritten changes is written at once. The document is written first and its record second, each to a temporary file that is synced and renamed over the target, so a crash in mid-write leaves the previous recovery file. An empty document that was never saved is not worth a file.
- **Removed** when the document is saved or closed, and when the launch ends on purpose (the window is closed, `ui.quit`, the server's input ends): a launch that ends cleanly leaves nothing, also of documents it did not save.
- **Dead or alive.** A launch is alive exactly while it holds the lock on its `.lock` file; the operating system lets go of it when the process ends, however it ends. A scan (at start, and by `recovery.list`) tries each other launch's lock: got it, or no lock file, means that launch is gone and its documents are offered; "held" means it is running and its files are left alone, by `recovery.open` and `recovery.discard` as well. No process id is looked up, so none can be mistaken for a reused one. Limits: on a file system without working locks (some network mounts) every other launch looks dead, so do not share one recovery directory between machines; a lock file deleted by hand under a running launch makes it look dead.
- **Recovered** by `recovery.open`: the file is loaded, opened as an unsaved document that remembers `path`, and renamed to the recovering launch's key, so it is that launch's autosave from then on and goes away when the document is saved or closed. Nothing is recovered or removed without being asked. A recovered document keeps everything a saved file keeps and regenerates to the same bodies; it loses the undo history, which no file holds.
- **Never over a newer original.** `file.save` of a recovered document to its original path is refused when the file there no longer has the recorded size and modification time (or the record had none and a file is there now), and names `"overwrite": true`. Any other path needs no confirmation.
- **Damaged files** are listed by `recovery.list` with `openable: false` and the reason (a truncated or corrupt document, a record without its document); a document without a readable record is openable and says what is unknown. Nothing in the directory can make a scan panic, and files whose names are not the ones above are never touched.
- **A directory that cannot be written** (missing and not creatable, read-only, a full disk) is a problem that `recovery.list`, `ui.get` (`recovery.problem`) and the status bar show until a write succeeds; it is retried once per interval and never fails or delays a command.

Tests: serde round trip of every feature type; save → load → regenerate gives identical bodies; cache-stripped files; migration fixtures; truncation at every offset and fuzzing never panic.

The body blob encoding (how a B-rep is serialised) is defined in M2 alongside `topo`, versioned independently inside the blob header.

## STEP

**As built (2026-10-13): export.** `file.export` with a `.step` or `.stp` name (or `"format": "step"`) writes every body of the document as an exact B-rep, with the document's length unit, its angle unit, its linear tolerance as the file's uncertainty, and each body under its feature's name. `craft3d-cli convert part.3dcraft part.step` does the same. Import is M10.

**Structure.** `craft3d-step` is the Part 21 layer and nothing else: a file is a header (records) and one data section (entity instances, simple or complex), and a record is a keyword with parameters (integer, real, string, enumeration, binary, reference, list, typed parameter, omitted `$`, derived `*`). It reads and writes that model and knows no entity. Reals are written as the shortest text that reads back as the same `f64` (`1.`, `0.25`, `1.E-7`); strings as printable ASCII with `''`, `\\` and the `\X2\`, `\X4\` directives for everything else (read: also `\X\`, `\S\`, `\P`, raw UTF-8 and raw ISO 8859-1). Unknown entities survive a read → write round trip as the instances they are; comments and white space do not. A reader gets every reference resolved (an unresolved one is an error) and can ask for a reference cycle before it follows references. Not read: a second data section, the `ANCHOR`/`REFERENCE`/`SIGNATURE` sections of edition 3, `&SCOPE` of edition 1; each is an error that says so. Hostile input is an error with byte offset, line and column; nesting (64), instances, parameters and string length are capped (`ReadLimits`). Which entities to write, and what their attributes mean, is `craft3d_io::step`: there is no typed entity layer in `craft3d-step`, the mapping builds records directly.

**Entities written.** The schema declared is `AUTOMOTIVE_DESIGN { 1 0 10303 214 1 1 1 1 }` (AP214; [`decisions.md`](decisions.md) D-open-8).

| 3DCraft | STEP |
|---|---|
| body | `PRODUCT` → `PRODUCT_DEFINITION_FORMATION` → `PRODUCT_DEFINITION` → `PRODUCT_DEFINITION_SHAPE` → `SHAPE_DEFINITION_REPRESENTATION`, and `PRODUCT_RELATED_PRODUCT_CATEGORY('part')`; one `APPLICATION_CONTEXT`, `APPLICATION_PROTOCOL_DEFINITION`, `PRODUCT_CONTEXT`, `PRODUCT_DEFINITION_CONTEXT` per file |
| solid body | `ADVANCED_BREP_SHAPE_REPRESENTATION` with one item per lump |
| lump | `MANIFOLD_SOLID_BREP` of a `CLOSED_SHELL`; with cavities `BREP_WITH_VOIDS`, each cavity an `ORIENTED_CLOSED_SHELL` (`.F.`) of a `CLOSED_SHELL` |
| sheet body | `MANIFOLD_SURFACE_SHAPE_REPRESENTATION` of a `SHELL_BASED_SURFACE_MODEL` of `OPEN_SHELL`s |
| face, loop, coedge, edge, vertex | `ADVANCED_FACE` with `FACE_OUTER_BOUND` / `FACE_BOUND`; `EDGE_LOOP`; `ORIENTED_EDGE`; `EDGE_CURVE`; `VERTEX_POINT` on a `CARTESIAN_POINT` |
| a whole sphere or torus; a cone's apex inside a face | a `FACE_BOUND` of a `VERTEX_LOOP` |
| plane, cylinder, cone, sphere, torus | `PLANE`, `CYLINDRICAL_SURFACE`, `CONICAL_SURFACE`, `SPHERICAL_SURFACE`, `TOROIDAL_SURFACE` on an `AXIS2_PLACEMENT_3D` |
| Bézier patch, NURBS surface | `B_SPLINE_SURFACE_WITH_KNOTS`; rational: the complex instance with `RATIONAL_B_SPLINE_SURFACE` |
| line, circle, ellipse, NURBS curve | `LINE` (with a `VECTOR` of magnitude 1), `CIRCLE`, `ELLIPSE`, `B_SPLINE_CURVE_WITH_KNOTS` (rational: the complex instance with `RATIONAL_B_SPLINE_CURVE`) |
| units, tolerance | one context: `GEOMETRIC_REPRESENTATION_CONTEXT(3)`, `GLOBAL_UNIT_ASSIGNED_CONTEXT` (length: `SI_UNIT` with a prefix, or `CONVERSION_BASED_UNIT` `'INCH'` 25.4 mm / `'FOOT'` 304.8 mm; plane angle: radian or `'DEGREE'`; steradian), `GLOBAL_UNCERTAINTY_ASSIGNED_CONTEXT` with one `UNCERTAINTY_MEASURE_WITH_UNIT` |

Instances are numbered from 1 in the order they are made and refer only to earlier ones; the same document gives the same bytes (`FILE_NAME.time_stamp` is empty for that reason). Geometry is not shared between entities: every placement has its own point and directions.

**Conventions.** The module documentation of `crates/io/src/step.rs` has each one with how sure it is; in short:

- Surfaces and curves are parametrised by ISO 10303-42 exactly as `craft3d-geom` does (normal `∂u × ∂v`: away from the axis or centre), so frames and radii go over unchanged. A cone gets a positive semi-angle: one that narrows along its frame's z is written on the frame seen from the other side. An ellipse gets its longer semi-axis first, on a placement turned a quarter if need be. Angles are in the document's angle unit.
- An edge runs from its start to its end vertex with the curve's parameter (`same_sense` `.T.`, always) and is the part of its curve between its vertices; an `ORIENTED_EDGE` is `.T.` unless the coedge is reversed; `ADVANCED_FACE.same_sense` is `.T.` unless the face is reversed; bounds are `.T.` (our loops already run with the face on their left seen from outside).
- `FACE_OUTER_BOUND` is written first, and only where a loop is the outer one: the one loop of a face; on a plane the loop that runs counter-clockwise; elsewhere the one loop that does not go around the surface, when none does. A cylinder wall between two circles has two plain `FACE_BOUND`s.
- The knots of a B-spline curve are written on the interval from 0 to 1, whatever they are in the body (2026-10-14). The kernel's intersection curves have knots that are lengths, so they grow with the model; a B-spline is the same point set after an affine change of its knots, and no parameter of a curve is written anywhere else (an edge is the part of its curve between its vertices), so nothing else in the file changes, and a curve whose knots run from 0 to 1 already is written bit for bit. The reason is a reader, found by experiment (below, *What a reader made of the knots*). The knots of a B-spline surface are written as they are.
- Faces on closed surfaces are written without seam edges, as they are in the kernel. Part 42 does not ask for seams; readers add their own. FreeCAD's own seam fails on a cylinder with a radius above some 4.5e8 mm (a cylinder of radius 4e8 mm is read right at any height, one of 5.4e8 mm comes back as two invalid faces), and the same file with a seam edge written by hand is read as a valid solid of our volume: a limit far outside the sizes 3DCraft is tested at, and the one thing a seam of ours would buy.
- A cavity's `CLOSED_SHELL` has its faces turned over (so its normals point away from the volume it encloses, as a closed shell's must), and `ORIENTED_CLOSED_SHELL` `.F.` turns them back. A shell is a cavity when it encloses a negative volume, and belongs to the innermost lump that contains a point of it.

**Refused**, with an error that names the body: a body that fails `topo::check` at the document's tolerance; a face without loops on anything but a sphere or a torus; a planar face without exactly one counter-clockwise loop; a solid of several shells where one cannot be measured, encloses nothing, or is a cavity outside every lump; geometry that is not finite. Not written at all: assemblies (every body is a part of its own in the world frame), colours, PMI, face and edge names, parameter-space curves.

**What a reader made of the knots (2026-10-14).** FreeCAD 1.1 (OpenCascade 7.8) called the showcase's bearing housing invalid at the scale 1e6 ("self-intersecting wire" on the sleeve's wall) and valid at 1e-3 and 1, with the same measures at every scale. What changes its answer was found by changing one thing at a time in the text of the file:

| changed in the file at 1e6 | FreeCAD's verdict |
|---|---|
| the uncertainty, from 1e-7 to 1000 | invalid, the same faces |
| the length unit declared (the same numbers as nanometres: a body of the size of the scale 1) | valid |
| the file of the scale 1 with the kilometre as its unit (a body of the same size in FreeCAD as the one at 1e6) | valid |
| the file of the scale 1 with every point and radius multiplied by 1e6 in the text | valid |
| the same, and the knots of the spline curves multiplied by 1e6 (what the kernel writes at 1e6) | invalid |
| the file at 1e6 with only the knots of its spline curves divided by 1e6 | **valid** |
| the same for the four rims of the oil holes alone | valid; for the pedestal's two edges alone, invalid |
| the knots of the spline surfaces, times or divided by 1e6 | no change |
| on the smallest body that shows it (below): parameter-space curves written by hand for the rim of the hole (`SURFACE_CURVE` with a `PCURVE` on either cylinder or on both) | invalid; FreeCAD's parameter-space curves are its own either way (311 poles where ours had 154) |

So the size of the body in the reader is not it, nor the uncertainty, nor the missing parameter-space curves: it is the knots of a closed spline edge (the rim of a hole drilled into a cylinder: one edge, one vertex), which the kernel parametrises by length. FreeCAD makes such an edge periodic, cuts it in two where it crosses the seam it adds to the hole's wall, and its check of the two halves on the *other* cylinder then depends on the knots: with knots up to some 5e3 every file tried is valid; from 1.5e4 up the verdict goes either way once the model is 1e3 or larger (the same body with its knots up to 1.6e4, 1.6e5, 1.6e6 and 1.6e7: valid, invalid, valid, invalid), which is why it looked like a matter of size; and at the scale 1 every file is valid whatever its knots (up to 1e13). The smallest body that shows it is a cylinder with one blind hole along a radius (5 faces). On 312 sleeves with an oil hole (eight directions, three radii, three depths, two places; the scales 1, 1e3 and 1e6) FreeCAD called 58 invalid as written (57 of the 144 at 1e6, 1 of the 144 at 1e3) and none with the knots from 0 to 1, with its volume and area unchanged to 2e-14; of the 144 at 1e6 enlarged to 1e7, 70 and none. What the reader does inside was not looked up (clean-room); the mechanism is inferred, the verdicts are measured.

**Specs.** The exchange structure is ISO 10303-21; the entity definitions are in ISO 10303-42 (geometry and topology) and the application protocols (ISO 10303-214, -242). ISO documents are paid publications: work from copies the project legitimately has, from the freely published EXPRESS schemas and recommended practices of the CAx Implementor Forum, and from the files other systems write. Never paste text from a standard into the repository; cite the clause. The mapping as built was written from memory of the standard and checked against what FreeCAD makes of the files; the clause numbers in the code are marked as approximate.

**Tests.** In `craft3d-step`: every real reads back bit for bit (20 000 random bit patterns); a file with one of everything reads back as the same model and its text is pinned; every string directive; hostile input (some 40 malformed files, each with the expected error and line), truncation at every offset, 20 000 random damages, limits, cycles. In `craft3d-io` (`tests/step.rs`): 26 bodies at three scales read back as the same instance graph and pass a small independent interpreter (closed loops, each edge of a closed shell used once each way, every vertex on its edge's curve and on its face's surface); each convention above (a spline edge with knots that are lengths is written from 0 to 1 at every scale, with its control points untouched); golden text for a block and a cylinder (`tests/golden/`, `CRAFT3D_UPDATE_GOLDEN=1` rewrites them); what is refused. In `craft3d-engine`: `tests/step.rs` and the acceptance scenario. And the external check ([`testing.md`](testing.md) oracle 8): FreeCAD imports the files and reports the same solids. That last test is the one that matters: a STEP file is only correct if other CAD systems accept it.

**Tolerance on export.** The document's modelling tolerance is written as the file's uncertainty measure; the body is checked with that tolerance before it is written, so no vertex is further from its edge, and no edge from its face, than the file declares. (There are no per-entity tolerances in `topo` yet to tighten or report.)

## Meshes: STL, 3MF, OBJ

All three are written from the tessellator's output at a caller-chosen chordal tolerance. `io` merges vertices at bit-identical positions (the tessellator makes shared edges exact, so no distance tolerance is involved) and marks the object a solid only when the merged mesh is closed and consistently oriented; an open mesh is exported as a surface (3MF `type="surface"`). *Planned with bodies:* a body that claims to be a solid but tessellates open is an error rather than a leaky file.

Today: one object per file, no colours or materials, OBJ without normals (`vn`) or groups per face.

| Format | Notes | Spec |
|---|---|---|
| STL | Binary by default (80-byte header, triangle count, 50 bytes per triangle, little-endian f32), ASCII on request. No units in the format: export in the document's length unit and say so in the result. Vertices are not shared in STL; closedness is checked on our indexed mesh before writing | The original 3D Systems StereoLithography interface description (1989); de facto conventions |
| 3MF | An OPC (ZIP) package with `[Content_Types].xml`, `_rels/.rels` and `3D/3dmodel.model` (XML): indexed vertices and triangles per object, explicit unit, object names, base-material colours. Preferred mesh format: it has units and guarantees an indexed mesh | 3MF Core Specification (3MF Consortium, freely available) |
| OBJ | `v`, `vn`, `f` with one `o` per body and `g` per face; optional `.mtl` for colours. No units | Wavefront OBJ format description (public) |

The ZIP and XML writing needed for 3MF is part of `meshio`: a stored (uncompressed) ZIP writer with CRC-32, no dependency. Files are larger than they need to be (the teapot at tolerance 0.002 is 11.9 MB as 3MF, 6.5 MB as STL); DEFLATE is a later improvement.

Tests (in place): exact expected text for ASCII STL, OBJ and the 3MF model part; binary STL and the ZIP container parsed back by minimal readers in the tests; FreeCAD reading a box (solid, volume 24) and the teapot in all four encodings. The FreeCAD test also covers 32-bit rounding in STL: FreeCAD merges the rounded points to exactly the vertex count of our welded mesh.

## Flat outlines: DXF and SVG

**As built (2026-10-13): export.** `file.export` with a `.dxf` or `.svg` name (or `"format": "dxf"` / `"svg"`) writes the outline of a **sketch** (`"sketch"`: id or name) or of a **flat face** of a body (`"face"`: a persistent name from `document.inspect`, `faceNames`; `"feature"` says which body when several have a face of that name), in the document's length unit at true size, for laser cutters and drawings. `craft3d-cli convert IN OUT.dxf --sketch S` (or `--face F [--feature B]`) does the same from a file. Every curve stays what it is: a line a line, a circular arc an arc with its centre and radius, a circle a circle, an ellipse (a cylinder cut on a slant) an ellipse, a NURBS edge a spline. Nothing is turned into a polyline.

Written from the DXF Reference (Autodesk publishes one per release: the group codes of `HEADER`, `TABLES`, `BLOCKS`, `OBJECTS` and of `LINE`, `ARC`, `CIRCLE`, `ELLIPSE`, `SPLINE`), the W3C recommendation *Scalable Vector Graphics (SVG) 1.1 (Second Edition)* (chapters 7 and 8, and the arc implementation notes of appendix F.6), and *The NURBS Book* (Piegl and Tiller, §5.2–5.3) for knot insertion. No DXF or SVG library is used, in the code or in the tests.

**Where the code lives.** `crates/drawing` (`craft3d-drawing`, L0, standalone like `step` and `meshio`: no workspace dependency) has its own 2D model and the two writers: a `Drawing` is a unit and layers (a name and one of seven colours) of paths; a path is a `Chain` (a start point and `Line`, `Arc`, `EllipticArc` and `Spline` segments head to tail, open or closed), a whole `Circle` or a whole `Ellipse`; a `Spline` is a B-spline of degree 1 to 15 on up to 4096 control points, polynomial or rational, which can be cut between two parameters, reversed and split into Bézier pieces. `crates/io/src/drawing.rs` maps a sketch (`sketch_outline`) and the faces of a body (`face_outline`) onto it; `crates/engine/src/drawing_cmds.rs` is the command side.

**What is drawn.**

- *A sketch:* its lines, arcs, circles and splines at their solved positions, in the sketch's own axes. Curves that meet in a point (the same point entity, or two points within the document's tolerance) are joined into one chain as long as exactly two meet there; a chain that comes back to its start is closed. Chains come in the order their first entity was drawn. Construction geometry is left out, or (`"construction": true`) drawn on a layer of its own (`construction`, blue; the rest is on `outline`, black). Lines and arcs without length are left out and listed (`skipped`). A sketch that failed to solve is refused.
- *A face:* every loop a closed chain, in the axes of the face's plane **seen from outside the body** (x is the plane's x, z the outward normal), so the outline is what one sees looking at the face and not its mirror image: the bottom of a plate comes out turned over. The result gives the origin and axes in the model (`origin`, `xAxis`, `yAxis`). A name that several faces answer to (the pieces a boolean cut one face into) draws them all, provided they lie in one plane. A face that is not flat is refused (`the face is a cylinder face: only a flat face has an outline to export`).

**DXF: decisions.**

- *AutoCAD 2000 (`AC1015`), ASCII.* The oldest release whose format has every entity needed as itself: `ELLIPSE` and `SPLINE` came with R13, and R13/R14 files are rarer than those of 2000, which every reader of the last twenty years takes. R12, the usual "safe" choice, has neither and would force ellipses and splines into polylines. The file has the sections a 2000 file is expected to have (`HEADER`, `CLASSES`, `TABLES` with all nine tables, `BLOCKS` with model and paper space, `ENTITIES`, `OBJECTS` with the root dictionary), handles on everything, and the subclass markers; it has no layout objects and no plot styles.
- *Units.* `$INSUNITS` from the document's unit (1 in, 2 ft, 4 mm, 5 cm, 6 m, 13 µm) and `$MEASUREMENT` (metric or imperial); `$EXTMIN`/`$EXTMAX` are the outline's exact box.
- *Separate entities, not `LWPOLYLINE`.* A loop is written as its own `LINE`, `ARC`, `ELLIPSE` and `SPLINE` entities head to tail. A polyline holds lines and circular arcs only (as bulges, from which a reader has to work the centre and radius back out), so a loop with an ellipse or a spline in it would fall apart anyway; entities that meet share their end points, and laser and CAM software joins them (FreeCAD does: see the tests).
- *Arcs.* An `ARC` runs counter-clockwise from its start angle to its end angle, in degrees; a clockwise piece of a loop is the same arc from its other end. An `ELLIPSE` has its centre, the end of its longer axis, the ratio and two parameters, counter-clockwise likewise. A `SPLINE` has its degree, knots, control points and, when rational, weights (flags 8, planar, and 4, rational); it is always clamped and never flagged closed or periodic.
- *Layers and colours.* Each layer of the drawing is a DXF layer with one of the colour indices 1 to 7; entities take colour and line type from their layer. Layer `0` always exists. A layer name is 1 to 31 letters, digits, `_` or `-`.

**SVG: decisions.**

- *True size.* `width` and `height` in `mm`, `cm` or `in` (micrometres and metres are written in `mm`, feet in `in`: SVG has no other units) and a `viewBox` of the same extent in document units, so one user unit is one document unit.
- *y points up.* SVG's y axis points down, so every y is written negated: the picture is the drawing, not its mirror image, and there is no `transform` for a reader to forget.
- *One `<path>` per layer*, with a subpath per loop (closed with `Z`), `fill="none"`, `fill-rule="evenodd"` and a hairline stroke (0.01 mm, the width laser software takes for a cut rather than an engraving). In one path with the even-odd rule a loop inside a loop is a hole whichever way the loops run, for a program that fills; software that only follows strokes sees the same loops either way.
- *Arcs are `A` commands* (end points, radii, flags), in parts of a quarter turn at most. An SVG arc is given by its end points and radii, from which a reader works out the centre; for a half turn that is as badly conditioned as it gets (an error of 1e-16 in a radius moves the centre by 1e-8), for a quarter turn not at all. A path has no circle of its own: a whole circle is four quarter arcs. Elliptic arcs are `A` commands with two radii and the axis angle.
- *Splines.* A polynomial B-spline of degree 1, 2 or 3 is written exactly as `L`, `Q` or `C` Bézier pieces (knot insertion). SVG has no curve of a higher degree and no rational one: those are written as cubic Béziers that lie within `tolerance` (default: the document's linear tolerance) of the curve, and the result says how many there were and how far off they are at most (`approximated`, `deviation`). DXF holds them exactly.

**Numbers and determinism.** A number is written as the shortest decimal text that reads back as the same `f64` (`0.30000000000000004`, `1E-7` outside 1e-5 to 1e17; in DXF always with a decimal point or an exponent, since some readers take a bare `10` for an integer; never `-0`), so a reader gets our coordinates bit for bit and nothing is lost to a fixed number of decimals. The same document gives the same bytes: handles count up from a fixed start, entities come in the document's order, and there is no date, time or program version in either file.

**Tests (in place).** In `crates/drawing`: hand-written expected files for a tiny drawing; every other shape (arcs of either direction, across the angle 0 and ±π, over more than a half and more than three quarters of a turn; a whole circle; a slot; a rounded rectangle with a round hole and a D hole at five scales from 1e-3 to 1e6; ellipses; splines) written and read back by two small readers that live in the tests (DXF group codes; the SVG path grammar with the recommendation's end-point-to-centre conversion) and compared to 1e-12 relative: end points bit for bit, centres, radii, angles, directions, lengths. In `crates/io`: faces with a spline edge (a piece of a longer curve, in both directions, on a face seen from either side) and a rational circle, built by hand. In `crates/engine` (`tests/drawing_export.rs`): a plate drawn with `sketch.path` and the top face of its extrusion give the same outline, whose length is the closed form to 1e-12 and whose area is the solid's volume over its height; six units; scales 1e-3 to 1e3; the cut of a cylinder on a slant is an ellipse (whole, and a quarter with two lines) of the closed-form length; the document is unchanged by an export; everything that is refused.

**FreeCAD reads both** (`cargo xtask freecad`: `crates/drawing/tests/freecad.rs` and `crates/engine/tests/drawing_freecad.rs`, one script, `crates/drawing/tests/drawing_report.py`). It imports each file, and reports the edges it got (how many, on which kind of curve, total length, bounding box), the closed wires they sort into and the area inside. Measured (FreeCAD 1.1rc2): for the plates, length, area and box agree with the closed forms to 1e-14 in DXF and SVG in millimetres, at the scales 1e-3, 1 and 1e3, and in DXF in cm and inches (which FreeCAD scales to millimetres: the proof that the unit is in the file); in SVG in cm and inches to 4e-11, because FreeCAD turns what it scales into B-splines; the bound asked is 1e-9; there are as many closed wires as we have loops; DXF lines arrive as lines and arcs as circles, a whole ellipse as an ellipse, a spline as a B-spline curve, SVG cubics as Bézier curves. Three things FreeCAD cannot tell, each pinned in the test with what was measured: (1) its DXF reader draws every `ELLIPSE` whole and ignores the start and end parameters, so an elliptic *arc* in DXF is checked by our own reader only (the same arc in SVG it reads right); (2) its area of a face with a B-spline in its boundary is rough (20.89947 where the exact area is 20.9, 1.4e-4 off for a half disc), while its length of the same edges agrees to 15 digits, so those areas are held to 1e-3; (3) its older Python DXF reader needs the "DXF Library" addon, which it would download, so only its built-in (C++) reader is used. Not checked by anything: AutoCAD itself, and laser software (LightBurn, RDWorks); the file follows the DXF Reference, but no AutoCAD has read it.

**Not built.** Import of either format. Text, dimensions, hatches. A projected view of a whole body (hidden lines): only one face, or one sketch, at a time.
