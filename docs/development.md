# Development guide

> **Last updated:** 2026-11-10 (0.1.0) · **Status:** everything in this document exists and runs, unless it is marked *(planned)*. In the workshop, heavy builds and tests run on the Strix ([Checks and the gate on the Strix](#checks-and-the-gate-on-the-strix)); the developer's laptop edits code.

**Building and testing on your own machine.** Everything you need runs on one machine with the [prerequisites](#prerequisites): `cargo build --release -p craft3d -p craft3d-cli` for the programs ([Build and run](#build-and-run)), `cargo test -p <crate>` and one test file at a time while you work ([Faster test loops](#faster-test-loops)), and `cargo xtask ci` for the whole gate, which is heavy (it builds and runs every test of the workspace). Run `cargo xtask fonts` once first: it fetches the built-in fonts (pinned, never committed), and the text tests fail without them. This guide was written in the workshop, the private repository `johancoppens/3dcraft-dev` where 3DCraft is developed with its own build server, the Strix: the parts about the Strix, watching along, the release steps, the morning health report and the dev log describe how the maintainers work, and you do not need them to build, test or contribute ([`CONTRIBUTING.md`](../CONTRIBUTING.md)).

## What works today

```sh
cargo test --workspace                          # over five thousand tests (2026-11-10), one binary after the other
cargo xtask ci                                  # fmt --check + clippy -D warnings + tests (binaries side by side) + doctests + layers + wasm: the full gate (the workshop runs it on the Strix, below)
cargo xtask layers                              # dependency layering, that every crate opts in to the never-crash lints, and no std clock where the browser gets
cargo xtask stats                               # lines and tests per crate
CRAFT3D_FREECAD=/path/to/FreeCAD.AppImage cargo xtask freecad   # FreeCAD reads our exports back
cargo xtask fonts             # fetches the built-in fonts (pinned, never committed) into assets/fonts or $CRAFT3D_FONTS; the text tests need them
CRAFT3D_FREECAD=/path/to/FreeCAD.AppImage cargo xtask boolean-corpus --check   # regenerate the boolean corpus with FreeCAD and compare with the pinned one
cargo build --release -p craft3d-cli            # the CLI: target/release/craft3d-cli
```

Model a part from the command line, look at it, export it:

```sh
craft3d-cli commands --filter feature           # what can I do? ids, params, summaries
craft3d-cli run --new '{"units":"mm"}' \
    --cmd variable.set     --params '{"name":"width","expr":"60 mm"}' \
    --cmd feature.block    --params '{"name":"Plate","size":["width","width * 2 / 3","8 mm"]}' \
    --cmd feature.cylinder --params '{"name":"Post","position":["width / 4","width / 3","8 mm"],"radius":"width / 10","height":"30 mm"}' \
    --cmd document.measure \
    --out part.3dcraft                          # one JSON line per command
craft3d-cli info part.3dcraft                   # the whole state as JSON: features with status, bodies with volume
craft3d-cli render part.3dcraft --out part.png --size 1000x700 --view iso
craft3d-cli convert part.3dcraft part.3mf       # or .stl, .obj
craft3d-cli run part.3dcraft --cmd variable.set --params '{"name":"width","expr":"80 mm"}' --out wider.3dcraft
craft3d-cli run --new '{"units":"mm"}' --script long-build.json --out build.3dcraft --keep-going
```

`run` stops at the first command that fails, saves nothing and exits with 1. A long script is better run with `--keep-going`: a failing command gets the line `{"failed": id, "step": n, "error": text}`, the next one runs (a command that fails leaves the document as it was), `--out` saves what was built, and the exit code is still 1, with the first failure on stderr. `render` (and `view.render`) meshes the model for the picture: between a quarter and half a pixel of the picture where it shows the model nearest, never finer than the floor (2e-4 of the diagonal of the box around the bodies), at most 12 degrees per chord, within a total budget of a million triangles; its JSON says the tolerance it used and whether it had to coarsen it.

Drive it as a server (see [`control-protocol.md`](control-protocol.md)):

```sh
craft3d-cli serve --automation-read-root work --automation-write-root work     # JSON lines on stdin/stdout
craft3d-cli mcp   --automation-read-root work --automation-write-root work     # MCP on stdin/stdout
claude mcp add craft3d -- "$PWD/target/release/craft3d-cli" mcp \
    --automation-read-root "$PWD/work" --automation-write-root "$PWD/work"
```

A contact sheet of every reference solid, to look at what the tessellator makes of them: `cargo run --release -p craft3d-render --example solids -- target/evidence/solids.png`.

The teapot (Bézier patches, outside the document path) still has its own examples: `cargo run --release -p craft3d-render --example teapot` and `cargo run --release -p craft3d-io --example export_teapot`.

The toolchain is pinned in `rust-toolchain.toml`; rustup installs it on first use. If `cargo` is not on `PATH`, it is in `~/.cargo/bin`.

### Checks and the gate on the Strix

**Two repositories** (2026-11-10). The same commits live in two repositories: the workshop `johancoppens/3dcraft-dev` (private; `origin`), to which the self-hosted runners of the workshop's build server, the Strix, are attached, and the public `johancoppens/3dcraft`, which has no self-hosted runner (a pull request from a fork may bring its own workflow, so none may be attached to a public repository). The Strix's workflows are not in this tree: they live in the workshop on a branch of their own, `workshop`, which is never pushed to the public repository, with `WORKSHOP.md`, which says how a run is started; they check out the commit they are given. The two workflows in this tree, `CI` and `Release`, run on GitHub's hosted runners and belong to the public repository: each job's `if` compares `github.repository` with it, so they are skipped in the workshop (CI's weekly schedule, a dispatch, a tag). `main` is pushed to both after its gate passed. Agents push their branches to the workshop; CI and Release are started in the public repository (`gh workflow run CI -R johancoppens/3dcraft`, and a release's dispatch and tag there).

Heavy builds and tests run on the Strix, not on the developer's laptop (the developer, 2026-10-23; AGENTS.md §5 and §6): an agent's quick checks of its own commit (one or a few `cargo` commands: `test`, `clippy`, `check`, `fmt`, `build`, or the xtask tasks `layers`, `wasm`, `freecad`, `web-size`, `package`, `example-thumbs`, `fuzz`); **the full gate** before `main` moves, on a runner of its own so that a merge never waits behind checks (`cargo xtask ci`, then `cargo xtask freecad`, and beside them, on another runner, the web module built as the Release workflow builds it and held to its budget, `cargo xtask web-size`, [`testing.md`](testing.md) › *Web module size*); and long runs from a fixed list (the boolean corpus, random designs for an hour, the action scripts, the benchmark, the Garabit pier, the GPU soak, a chunk of the ABC dataset), with every night a fuzz run of an hour and the boolean corpus on the head of `main`. A run starts only from the workshop (nothing else may start code on those runners), on a commit pushed there first. `main` only fast-forwards to a commit whose gate passed. From outside the workshop, the gate is `cargo xtask ci` on your own machine (after `cargo xtask fonts`), with `cargo xtask freecad` and `cargo xtask web-size` where FreeCAD and the web tools are at hand. Each runner keeps its target directories between runs, so a run builds only what changed; since the disk filled up on 2026-11-02 every job first removes a directory of its own that has grown too large, and every job compiles through one sccache cache shared by the runners.

CI on GitHub's own runners (`.github/workflows/ci.yml`) runs `cargo xtask ci` on Linux and `cargo test --workspace` on macOS and Windows, every Monday morning and on demand, in the public repository only (`gh workflow run CI -R johancoppens/3dcraft && gh run watch -R johancoppens/3dcraft`; developer's decision, 2026-10-12): run it after changes likely to differ per platform (file paths, threads, anything in `format`, `engine::workspace` or the CLI). Windows runs in three jobs (the engine, the kernel, every other crate): in one job it was cancelled at GitHub's six-hour limit. The hosted jobs build the workspace's crates at opt-level 3 (the tests run about 1.8 times faster); the Strix's gate and checks build at the workspace's own levels (1, the dependencies 2). Not green yet (2026-11-10): on Windows four tests fail, all on the software adapter the runner draws with (WARP), and are not fixed: `a_frame_exact_frame_is_one_pass_unless_it_waits_for_the_average` (`apps/craft3d/src/app.rs`: a frame takes 36 s there, so `ui.advance` runs out of time), `stripes_seen_close_on_a_gentle_surface_match_the_cpu` (`crates/gpu/tests/analysis.rs`), and `layer_three_matches_the_cpu_renderer` and `the_viewport_draws_layer_three_as_the_cpu_renderer` (`crates/gpu/tests/layers.rs`, the granite pattern); the crates after the kernel have not run there to the end yet, so more may show. On macOS `cut_open_reference_solids_match_the_cpu_renderer` (`crates/gpu/tests/section.rs`) fails on the runner's paravirtual Metal device. A full run takes hours, so while working on one platform's failure run only that: `gh workflow run CI -R johancoppens/3dcraft --ref <branch> -f os=macos -f cargo="test -p craft3d --lib consent"` runs one command (several joined by ` + `) on one system; `-f os=windows` alone is that system's full run. A narrow run needs the branch pushed to the public repository, which makes unmerged work public: delete that branch there afterwards (`git push public :refs/heads/<branch>`), and never push a branch there that should not be seen. Every job keeps what the GPU tests wrote to `target/evidence/gpu` (the summaries per device, and a failed comparison's pictures) as the run's artifact `evidence-<job>`. `Release` (`release.yml`) builds the installers and the web zip ([Packaging](#packaging)); `gh workflow run Release -R johancoppens/3dcraft -f only=web` builds only the web zip, on one Linux runner, and publishes nothing.

External oracle: FreeCAD runs as a separate program to check exported files ([`testing.md`](testing.md) oracle 8). Point `CRAFT3D_FREECAD` at a FreeCAD AppImage (run as `<AppImage> freecadcmd <script>`) or a `FreeCADCmd` executable. The tests (`crates/io/tests/freecad.rs` for meshes, `crates/drawing/tests/freecad.rs` and `crates/engine/tests/drawing_freecad.rs` for DXF and SVG, `crates/io/tests/step_freecad.rs` and `crates/engine/tests/step_freecad.rs` for STEP) are `#[ignore]`d, so plain `cargo test` and CI skip them; `cargo xtask freecad` runs them (about two minutes after the build: one launch of FreeCAD per test, and the STEP checks take nearly all of it) and fails if FreeCAD is missing. The STEP checks print a table per file (valid, volume and area against ours, centre, bounding box, counts, what FreeCAD added) and leave it with the files and FreeCAD's raw report in `target/tmp/step-io/` and `target/tmp/step-engine-files/` (`report.md`, `report.jsonl`); the booleans the kernel refused and the bodies we could not measure ourselves are in `target/tmp/step-engine/refused.md`. One of them alone: `CRAFT3D_FREECAD=… cargo test --release -p craft3d-engine --test step_freecad -- --ignored --nocapture`. After a deliberate change of the STEP mapping, `CRAFT3D_UPDATE_GOLDEN=1 cargo test -p craft3d-io --test step golden` rewrites the two golden files; read the diff. A script handed to FreeCAD must not be called `freecad.py`: that name shadows FreeCAD's own module and the script silently does nothing.

The boolean corpus ([`testing.md`](testing.md) oracle 8) is the other use of FreeCAD. The pinned file `crates/kernel/tests/fixtures/boolean_corpus.json` is read by `cargo test -p craft3d-kernel --test boolean_corpus`, which needs no FreeCAD and takes about a minute (17 s for the primitives; building a domed block measures it, 0.1 s for a Bézier roof and 0.3 s for a NURBS one). `cargo xtask boolean-corpus` regenerates the file (about a minute: it deals the cases out to one FreeCAD process per core, `--jobs N` to change that) and `--check` regenerates into `target/tmp/boolean-corpus/` and compares case by case; with the same FreeCAD build the result is byte-identical, with another one the measured numbers differ in their last digits and the corpus has to be re-pinned and the score reviewed. `--seed N` makes another corpus, `--only <part of an id>` prints the matching cases without writing anything. A pair on which FreeCAD crashes or takes more than two minutes is marked unreliable and the rest carries on. After the kernel learns something, raise `AGREEING_FLOOR` in `crates/kernel/tests/boolean_corpus.rs` to the count the test prints.

## Prerequisites

- Rust stable, pinned in `rust-toolchain.toml` (rustup installs it on first use). Add the web target with `rustup target add wasm32-unknown-unknown`.
- Linux, macOS or Windows. 3DCraft is developed on Fedora Linux; that is the Tier-1 platform. The installers are built and started on GitHub's Linux, macOS and Windows runners ([Packaging](#packaging)).
- Linux windowing, GL and GTK development packages (for the desktop app):
  - Fedora/RHEL: `sudo dnf install libxkbcommon-devel wayland-devel libX11-devel libXrandr-devel libXi-devel mesa-libGL-devel gtk3-devel`
  - Debian/Ubuntu: `sudo apt install libxkbcommon-dev libwayland-dev libx11-dev libxrandr-dev libxi-dev libgl1-mesa-dev libgtk-3-dev`
- Optional: `cargo install cargo-nextest --locked` for parallel test runs.

## Build and run

```sh
cargo test --workspace                                     # everything
cargo xtask ci                                             # fmt + clippy + tests + layers + wasm
cargo xtask stats                                          # tests and lines per crate
cargo xtask health                                         # the morning health report (below)
cargo xtask fuzz --seeds 1000                              # random multi-step designs (testing.md, oracle 11)
cargo xtask actions                                        # the action matrix over the showcase models (testing.md, oracle 12)
cargo xtask package                                        # installers for this platform; --formats web for the web zip (below)
cargo xtask web-size                                       # the web module held to its size budget (testing.md)
cargo xtask example-thumbs                                 # the pictures of the example scripts (below)
cargo xtask bundle-examples --from DIR                     # the start screen's examples, copied again from their repositories (below)
cargo run --release -p craft3d -- path/to/model.3dcraft    # the desktop app (a .3dcraftjig opens as a Jig in use)
cargo run --release -p craft3d -- --control 7878 --control-token-file .private/control.token \
  --automation-read-root work --automation-write-root work
```

Geometry code is slow at `opt-level 0`, so the workspace profile builds dependencies at `opt-level 2`. Use `--release` for anything interactive or timed.

**Autosave and crash recovery.** The app autosaves documents with unsaved changes into `3dcraft/recovery` in the per-user state directory (`~/.local/state` on Linux), 30 s after a change, and a start after a crash or a kill shows a bar with what was left there: Recover, Discard (asks twice), Later. The status bar says when the document shown was autosaved (`autosaved 2 min ago`, only while it has a recovery file: not another tab's), or why autosave failed. `--recovery-dir DIR|none` and `--autosave-interval SECONDS` (or `CRAFT3D_RECOVERY_DIR`, `CRAFT3D_AUTOSAVE_INTERVAL`) change that; closing the window is a clean end and leaves nothing: with unsaved changes it first asks, per document, Save, Don't Save or Cancel (2026-10-21); `ui.quit` ends at once and drops them (`ui.quit {save: "ask"}` asks as the window does, `{save: "save"}` saves them first). **A window started for a test or by an agent, and ended by killing it, would leave its documents in the developer's own recovery directory: start it with `--recovery-dir none` or a directory of the test's own** (`apps/craft3d/tests/hidden_window.rs` and `killed_window.rs` do). The recovery directory is described in [`file-formats.md`](file-formats.md), the three `recovery.*` commands in [`control-protocol.md`](control-protocol.md).

**Memory.** The bodies that went into later features are kept between commands within a budget, 1 GiB by default; `CRAFT3D_BODY_BUDGET_MB=256` lowers it for a small machine, and a body let go of is derived again when an edit needs it (`docs/design/regeneration.md` › *A chain of unions costs memory quadratically*).

The dev profile builds with `debug = "line-tables-only"`: backtraces keep file and line, and test binaries link faster. To inspect local variables in a debugger, build with `CARGO_PROFILE_DEV_DEBUG=true`.

### Faster test loops

```sh
cargo test -p <crate> --lib --tests        # skip examples and doctests
cargo test -p <crate> --test <file>        # one integration-test file
cargo test -p <crate> <name> -- --nocapture
cargo test --doc --workspace               # the doctests alone
```

`cargo xtask ci` builds the tests once (`cargo test --workspace --no-run`) and runs the test binaries side by side, slowest first by the durations of the previous run (`target/ci-durations.txt`), each binary's output printed in one piece when it is done; the doctests follow through cargo. `cargo test --workspace` runs the binaries one after the other and takes about twice as long. GPU tests each open their own wgpu device, so the binaries of `crates/gpu` run one after the other on one worker. The long random tests (`panic_hunt`, `boolean_random`, `meet_random`) run their cases on every core through `craft3d_testkit::parallel::map_parallel`: independent cases, each with its own seed, results in the order of the inputs. `panic_hunt` prints where its time goes per command with `--nocapture`.

## Headless CLI

`apps/craft3d-cli` builds the binary `craft3d-cli`:

```sh
craft3d-cli convert bracket.3dcraft bracket.step              # native -> STEP
craft3d-cli convert bracket.3dcraft bracket.3mf --tolerance 0.01
craft3d-cli info bracket.3dcraft                              # JSON: units, variables, feature tree with status, bodies, mass properties
craft3d-cli run --new '{"units":"mm"}' \
    --cmd feature.block --params '{"size":["40 mm","20 mm","10 mm"]}' \
    --cmd document.measure \
    --out box.3dcraft
craft3d-cli run bracket.3dcraft --cmd variable.set --params '{"name":"width","expr":"55 mm"}' --out wider.3dcraft
craft3d-cli render bracket.3dcraft --out shot.png --size 1200x800 --view iso    # CPU renderer, no GPU needed
craft3d-cli replay bracket.3dcraft --out bracket.mp4 --size 1280x720 --frames-per-step 6 --hold 60   # how it is built, as a video
craft3d-cli score plate-holes --script mine.json              # scorecard of a script for a task of docs/tasks (testing.md, The task set)
craft3d-cli check-range box.3dcraft --samples 100 --seed 7    # a Jig over its parameter range (document.sample); exit 1 on a failing point
craft3d-cli convert box.3dcraft cut.dxf --set "Cut sheet" --width "600 mm" --gap "4 mm"   # every flat face of a named set on one sheet, a layer per body, rows at most 600 mm wide
craft3d-cli convert bracket.3dcraft front.svg --view front --hidden dashed   # without --sketch, --face or --set: a drawing of the model as seen (file.export's projected view)
craft3d-cli commands --filter fillet                          # the command registry with params docs
craft3d-cli serve                                             # JSON lines on stdio (see control-protocol.md)
craft3d-cli mcp --automation-read-root work --automation-write-root work
```

`run` prints one JSON line per command result. A script file (`--script steps.json`: `[["<id>", {…}], …]`) is the same list of commands; it is the format for agent-written scenarios and demos.

### A showcase video

`craft3d-cli replay` shows how a document is built: the history is rolled forward from nothing one feature at a time, and every step that changes a body becomes a frame, drawn (on the GPU when there is one, else the CPU) from one camera framed on the finished model (the engine command `view.replay`, [`control-protocol.md`](control-protocol.md)). The document is not changed.

```sh
craft3d-cli replay part.3dcraft --out part.mp4 --size 1280x720 --frames-per-step 6 --hold 60 --orbit 60
craft3d-cli replay part.3dcraft --out part.gif --size 480x360 --frames-per-step 3 --hold 20 --fps 15
craft3d-cli replay part.3dcraft --out frames/ --from Plate --to Holes --every   # PNG frames and captions.srt only
```

- `.mp4` and `.gif` are made by `ffmpeg`, found on `PATH` or named by `CRAFT3D_FFMPEG`; the engine itself starts no program. Without ffmpeg the command fails with exit code 1 and keeps the frames in `OUT.frames/` (`frame-%05d.png` at the given fps, with `captions.srt`), which `--keep-frames` also keeps after a video is made.
- The captions (each step's place in the history, feature name and type) are a subtitle track in the MP4 (players switch it on) when the ffmpeg build has the `mov_text` encoder (the result says `captionsTrack`; Fedora's `ffmpeg-free` lacks it) and `captions.srt` beside the frames; they are not drawn into the picture, because the renderer has no text. The result JSON lists every step with the frames it got.
- `--frames-per-step` slows the build down, `--hold` lingers on the finished model, `--orbit DEG` turns the camera over the whole replay (the model is then framed so that it stays in the picture all round), `--from`/`--to` pick a range of the history, `--params` passes any other `view.replay` param (`projection`, `zoom`, `box`, `tolerance`).
- Time: opening and regenerating the document once, then about the CPU renderer's time per distinct picture, spread over the cores (each step reuses what the document's regeneration built; nothing is rebuilt). The turbofan (156 features, 113 steps that change a body) takes about 4.5 s beyond opening it on 14 cores: 3 s to tessellate the model once (as `view.render` does) and 1.5 s for the 113 frames at 800x600 (0.13 to 0.25 s of CPU each, many at once); stepping through the history costs 0.1 s.

### Video recipes

Every picture and frame without a window (`craft3d-cli render`, `replay`, `run`, `serve`, `mcp`) is drawn on the graphics card when the machine has one (`renderer: "auto"`; the result says `"renderer": "gpu"` and the adapter) and on the CPU otherwise; `--renderer cpu` / `"renderer": "cpu"` keeps to the CPU reference renderer. `WGPU_ADAPTER_NAME` and `WGPU_BACKEND` choose among several adapters. `view.replay` renders animations as well as the history ([`control-protocol.md`](control-protocol.md) › *view.replay as an animation renderer*); `--params` passes them on the command line, and `.webm` works beside `.mp4` and `.gif`:

```sh
# An exploded view: a timeline t moves the parts (formulas of t), the camera orbits and dollies in.
craft3d-cli replay box.3dcraft --out explode.mp4 --size 1920x1080 \
    --params '{"animate": [{"variable": "t", "from": 0, "to": 1, "easing": "inOut"}], "duration": 4, "hold": 30,
               "look": {}, "camera": {"orbit": 40, "dolly": 0.8, "easing": "inOut"}}'
# A parameter sweep in the studio look, settled smoother (32 frames each), as WebM.
craft3d-cli replay bracket.3dcraft --out sweep.webm --size 1920x1080 \
    --params '{"animate": [{"variable": "width", "keys": [{"t": 0, "value": 30}, {"t": 0.5, "value": 60}, {"t": 1, "value": 30}], "unit": "mm", "easing": "inOut"}],
               "duration": 6, "look": {"accumulate": 32}}'
# A mechanism's stroke with a camera path through three keys; PNG frames only.
craft3d-cli replay linkage.3dcraft --out stroke/ --size 1280x720 \
    --params '{"animate": [{"variable": "t", "from": 0, "to": 1}], "frames": 120,
               "camera": {"keys": [{"t": 0, "eye": [300, -300, 200]}, {"t": 0.5, "eye": [0, -400, 120]}, {"t": 1, "eye": [-300, -300, 200]}]}}'
```

Over MCP or `serve` the same is one `view.replay` call with `"video": "explode.mp4"`. Without ffmpeg the call is refused before anything is drawn; leave `video` out for the PNG sequence and encode it elsewhere. For a screenshot of the window in the studio look, `ui.set {"look": {"accumulate": 4}}` settles it sooner (the count `ui.screenshot {window: true}` waits for).

Measured on the Strix (2026-10-30, 1920 × 1080, the benchmark's engine block, 69k triangles): plain 22 fps on the GPU against 0.96 on the CPU, studio 20 fps against 0.14, studio settled (16 frames) 5 fps; a 199-frame replay to PNGs 26 fps plain and 5.4 fps studio-settled ([`design/rendering.md`](design/rendering.md) › *Animations*).

## Driving the app programmatically

Start the app with a private token file. It then accepts authenticated JSON lines on `127.0.0.1:7878`:

```sh
TOKEN=$(tr -d '\r\n' < .private/control.token)
printf '%s\n' "{\"id\":\"auth\",\"method\":\"auth\",\"params\":{\"token\":\"$TOKEN\"}}" \
              '{"id":1,"method":"engine.execute","params":{"command":"feature.extrude","params":{"sketch":"Sketch1","distance":"25 mm"}}}' \
              '{"id":2,"method":"ui.screenshot","params":{"path":"evidence/shot.png"}}' | nc 127.0.0.1 7878
```

See [`control-protocol.md`](control-protocol.md) for every method. `.private/` is gitignored.

**Pointing at a face.** Click a face in the viewport (the left button, without dragging): it is highlighted, and `ui.get` has what was clicked under `state.picked` (the body's feature, the face's persistent name as `document.inspect` lists it, the point), so an agent can be told "this face" by clicking it. The other way round, an agent shows which face it means with `ui.highlight` and asks what is at a pixel of a screenshot with `ui.pick`:

```sh
printf '%s\n' "{\"id\":\"auth\",\"method\":\"auth\",\"params\":{\"token\":\"$TOKEN\"}}" \
              '{"id":1,"method":"ui.pick","params":{"x":412.5,"y":300.5}}' \
              '{"id":2,"method":"ui.highlight","params":{"face":"F1:face(1)","feature":"Plate"}}' \
              '{"id":3,"method":"ui.get"}' | nc 127.0.0.1 7878
```

**Pointing at an edge.** Click within 4 points of an edge that is in sight: the edge is highlighted instead of the face, and `state.picked` has `kind: "edge"` and `edge` (its body, its own name where it has one, the faces it lies between, its place in `document.edges`, the point). An agent points at an edge with `ui.highlight {"edge": "F1:edge(7)"}` or, for an edge without a name of its own (after a boolean), `ui.highlight {"between": ["F3:copy(0)/F1:face(1)", "F3:copy(1)/F2:face(0)"]}`; `ui.pick` takes `radius` (pixels; 0 for faces only). A click within 4 points of a vertex in sight is a click on the vertex (`kind: "vertex"`, `vertex`), which then wins over the edges that end there; an agent points at one with `ui.highlight {"vertex": "F1:vertex(4)"}` or `{"corner": [face, face, face]}`, the faces that meet in it.

Without a window the command `view.pick` answers the same question about the picture `view.render` makes ([`control-protocol.md`](control-protocol.md), *Pointing*).

## The viewer today

`craft3d [FILE]` shows the active document: bodies shaded with their edges, sketches as lines (dimmed where a body is in front of them), datum planes as translucent squares with their outline and name, datum axes as lines and datum points as dots (`ui.set {"show": {"datums": false}}` hides them, `{"show": {"sketches": false}}` the sketches; the *Sketches* and *Datums* toggles over the viewport, beside the see-through slider, do the same), the feature tree and a status bar. The tree marks every feature's state with a mark and a colour (✔ built, ⚠ failed with its reason under it and on hover, ⏸ suppressed, ○ rolled back), and a feature that failed because one it is made from failed says which (*caused by Plate*; a click selects it); `ui.get` › `features` holds the same. The bodies and the lines are drawn by the wgpu renderer (`crates/gpu`) on the window's own device when the machine has a graphics adapter (multisampled, 4 samples per pixel, straight into the texture that is shown: nothing is read back and every frame is the sharp one, also while the model is turned) and by the CPU reference renderer otherwise; `--renderer cpu` (or `CRAFT3D_RENDERER=cpu`) asks for the CPU renderer, to compare the two. The status bar's `GPU 1440×900 …` or `CPU …` says which made the image on screen, `ui.get` reports it with the adapter's name, whether it draws directly on the window's device and with how many samples (`renderer.direct`, `renderer.msaa`) and, when the direct GPU path was wanted and could not be used, why (`renderer.fallback`), and the terminal prints it at start (`craft3d: viewport renderer: gpu (…; direct, 4 samples)`). `ui.screenshot` is always rendered by the CPU renderer: it is the oracle the GPU viewport is checked against. **The viewport's mesh is finer than the one `view.render`, previews and `file.export` make by default** (2026-10-13): the shell asks the engine for the *display quality* (`ui.get` › `state.quality`; `ui.set {"quality": {"chordal": fraction, "maxTriangles": integer}}`), a chordal tolerance of `chordal` times the model's size (the side of a square with the bodies' total area; 2e-4 by default, against 1e-3 for the automatic tolerance, with an angle criterion of `angle` degrees, 12 by default, that keeps small holes round), coarsened until the scene has at most `maxTriangles` (1,000,000) triangles and every body is within the tessellator's reach, but never beyond the quick first picture's tolerance (1e-3 of the diagonal of the model's box); `ui.get` › `scene.tolerance` and `scene.coarsened` say what it got. `ui.screenshot` renders that same scene, so it shows what the window shows; `--renderer cpu` follows the same rule. Measured on the flange of the demo (a disc of radius 40 mm with six bolt holes of radius 4 mm; `crates/ui-egui/tests/gpu_viewport.rs` › `the_flange_holes_are_round_at_the_display_quality`, pictures and crops of one hole in `target/evidence/ui/viewport-flange-*.png`, the window's own in `flange-8082-*.png`): before, 820 triangles and a chord error of 0.66 px in a 1020 × 754 window (1.4 px at 2560 × 1400: a visibly twelve-sided hole); after, 4328 triangles and 0.02 px (0.04 px). The scene is tessellated in about 10 ms either way (the cost is per face, not per triangle, on such a model), the GPU viewport's frame on the drawing thread takes 0.2 to 0.5 ms either way and 1.7 to 5 ms until the GPU is done, the first frame after the change (the upload) 2.2 ms; the CPU viewport's sharp image at 1020 × 754 (ssaa 2) takes 74 ms before and 92 ms after, its preview while orbiting 7 ms either way. A plate with 1024 holes (1030 faces, `crates/engine/tests/scene_bench.rs`): 24,588 triangles in 666 ms at the automatic tolerance, 122,892 in 776 ms at the display quality; the tessellator's cost beyond its cost per face is about 1.5 µs per triangle, which is what the budget of a million bounds (about 1.5 s per edit at worst). At scale (`viewport_cost`, a scene of 665,104 triangles against one of 12,796, both at 1020 × 777): the CPU viewport's sharp image takes 176 against 123 ms and its preview while moving 30 against 8 ms (0.08 and 0.03 µs per triangle: the cost is per sample), the GPU draws it in 16 to 18 ms after a one-time upload of 60 ms; the budget adds at most about 80 ms to a CPU sharp image and 30 ms to a preview. Drag to orbit, right-drag or shift-drag to pan, wheel or pinch to zoom at the pointer, F to frame everything. File menu: New (Ctrl+N), Open (Ctrl+O), Save (Ctrl+S), Save As (Ctrl+Shift+S), Import… (Ctrl+I: a STEP file into the document) and Export… (Ctrl+E: the export dialog first, since 2026-10-27: *What* (the model, the selection, a set's sheet, a part's flat pattern, a fold's crease pattern, every part's flat patterns), the *Format* (STEP, STL, 3MF, OBJ, DXF or SVG, only those that hold it) and the options; then the system's save dialog with that format's filter, the name with its extension and the last folder, and the file written at once, its extension corrected for the format; [`control-protocol.md`](control-protocol.md)), with the system's file dialog (on Linux through xdg-desktop-portal, so a portal backend has to be running, as it is on GNOME and KDE); the title shows the file's name and a `*` for unsaved changes. Everything else is done with commands over the control channel.

**The window never waits for a command (2026-10-14).** Commands (from the control channel, MCP, or a file chosen in the Open, Save As, Import and Export dialogs) run on the window's engine thread, which also regenerates and meshes; the window keeps drawing, can be moved, turned and closed, and shows what is being done: a small spinner and the words in the status bar for work that runs longer than 0.35 s (since 2026-10-30; before, a thin bar across the top of the viewport) (`Opening welding-table… 17/82`, then `Checking 14 assertions… 5/14` while the assertions are measured), and, while the viewport has nothing to show yet, `Opening welding-table…` in its middle (since 2026-10-26; before, a plate over the middle of the viewport, [`design/engine.md`](design/engine.md) › *Saying what is being done*). `ui.get` › `work` says the same and is answered at once while work runs ([`control-protocol.md`](control-protocol.md)). The window never waits for a renderer. On the GPU the frame is submitted from the drawing thread and the device finishes it on its own (the status bar's milliseconds are the drawing thread's share: uploading what changed, encoding, submitting). On the CPU, and on the GPU when the direct path is not available (then the GPU renders on a device of its own and reads the frame back, as it did before 2026-10-13), the sharp image is made on a render thread while a quick, smaller preview is on screen, and the status bar's milliseconds are the render thread's. `cargo run --release -p craft3d-ui-egui --example frame_time` times whole frames on the drawing thread for the window's path (`-- --readback` for the GPU read back, `-- --cpu` for the CPU renderer, `-- --inline` to make their sharp image on the drawing thread), and for the direct path also the time until the GPU is done with the frame; `cargo run --release -p craft3d-ui-egui --example viewport_cost` prints the parts of one image ([`design/rendering.md`](design/rendering.md) › *Desktop app and shell*). Measured on the development machine (an Intel Meteor Lake iGPU over Vulkan, 2026-10-13, other builds running; `frame_time`, the drawing thread's time per frame while orbiting, and for the direct path the time until the GPU is done with it): at 1280 × 800 with 84 triangles the direct path takes 0.2 ms on the thread and 2.1 ms until the GPU is done, against 9.6 ms for the GPU read back (a half-size preview) and 5.8 ms for the CPU (idem); with 12 796 triangles 0.4 and 2.5 ms against 12.6 and 8.9 ms; at 2560 × 1400 with 12 796 triangles 0.5 and 6.2 ms against 24.1 and 21.4 ms, and the sharp image after the camera stops, which the direct path has at once, took the readback path 142 ms (1843 × 1085, ssaa 2) and the CPU 125 ms (2048 × 1205, ssaa 1). The first frame after a scene change uploads the mesh and the lines: 0.7 ms for 12 796 triangles, about 60 ms for 665 104 triangles (80 MB of vertices), which `viewport_cost` prints; that model is then drawn in 13 ms at 1020 × 777 and 18 ms at 2560 × 1400 (GPU done).

**Zooming at the pointer (2026-10-16).** The wheel, a pinch on a touchpad and Ctrl with the wheel zoom about the point under the pointer, which stays on the same pixel, in perspective and orthographic alike: the point of the model the viewport shows there (the same answer a click gets, cut open by the section when it is on), or, where there is no model, the point of the plane through the camera's target square to the view. The whole camera (eye and target) is scaled about that point by the factor the distance changes by (`CameraState::zoom_about`), so the eye moves along the line to the point and never reaches or passes it, the distance keeps its limits (`MIN_DISTANCE`, `MAX_EXTENT`), and nothing becomes a number that is not one. The point is looked up once per gesture (again only when the pointer or the camera moved by other means). A zoom by hand switches `camera.autoFit` off, as a pan does; Fit, iso, F and a click on the cube switch it on again.

**The status bar (2026-10-18).** Units, the document's path, when it was autosaved, the last command and what it answered on the left, the renderer's numbers on the right. Too narrow for all of them, they give way in a fixed order (`shell::STATUS_YIELD`, `shell::fit_status`): first elided with an ellipsis (the whole text as the tooltip), the answer to the last command first, then the autosave and the path; then left out in that order, the renderer's numbers next to last and the units last. No two ever overlap (`tests/status_bar.rs`).

**See-through (2026-10-13).** On the display bar at the bottom of the viewport is a slider, *See-through*, from opaque to nearly clear (`state.transparency`, 0 to 0.9, also `ui.set {"transparency": 0.5}`): the bodies are drawn with the surface behind the front one showing through, and the hidden parts of their edges dimmed, so a pocket or a cavity inside a part can be looked at. The window's device draws it (since 2026-10-14: the scene twice, for the front and for what is behind it, and a blend), so turning a see-through model is as quick as turning an opaque one: measured in the window at 1020 × 754 with 16 000 triangles, 0.4 to 1.2 ms of the drawing thread per frame either way (it was 492 ms per frame on the CPU), and until the GPU is done 4.7 ms against 1.7 ms opaque for 12 800 triangles and 19 ms against 12.5 ms for 665 000 (`cargo run --release -p craft3d-ui-egui --example viewport_cost`, Intel integrated graphics). Picks and highlights work as ever. `ui.get` › `render.renderer` says which renderer drew the frame on screen: `cpu` only on a device that cannot draw the layers, or with `--renderer cpu`.

**The section plane (2026-10-14).** In the row above that slider, the Section group: *Section* cuts the picture open with a plane, so that the inside of a shell, a pocket or a cavity can be looked at; where the plane passes through material the cut is closed with a flat orange cap, so a solid looks solid. While it is on, *X*, *Y* and *Z* choose the axis the plane is across (it starts in the middle of the model), the slider moves it across the model's extent, and *Flip* keeps the other half. It is a view like the camera (`state.section`, also `ui.set {"section": {"on": true, "plane": "zx", "offset": 0, "flip": true}}`, where the plane may also be a datum plane, a flat face by its name or a point and a normal): the document does not change and nothing is regenerated. The window's device draws it (one more pass over the triangles, which counts what is cut away, and one triangle for the cap); a click on a cut-open model gives what is seen, and on the cap `state.picked.kind` is `section`. `ui.screenshot` and `view.render {"section": {…}}` cut the same way, the latter without a window.

## Watching along

The developer follows development and automated testing live. Three ways, cheapest first:

1. **Test output.** Run tests in the foreground with `-- --nocapture` when the developer is watching, and say what the run is expected to show before starting it (in the workshop, in Dutch). Geometry tests print the numbers they compare (expected, actual, tolerance), not just pass/fail.
2. **Evidence images.** Tests and scripts that render write PNGs under `target/evidence/…` ([`testing.md`](testing.md)). After a visual change, name the files to open. `craft3d-cli render` produces a picture of any document with the CPU renderer: no window, no GPU, no focus stealing.
3. **The live viewer.** `cargo build --release -p craft3d -p craft3d-cli`, then `target/release/craft3d --control 7878 --control-token-file .private/control.token --automation-write-root target/work --recovery-dir none`; launch it once and the window stays on the developer's screen. Agents then build and edit the model through the control channel or `craft3d-cli mcp --bridge PORT --control-token-file FILE` (the explicit flags: an agent's or a test's window never relies on discovery or the person's switch), and the viewport updates after every command: the developer sees the part grow feature by feature. Use `ui.set` to frame the camera on what changed, `ui.fit` to fly to a feature, and `ui.notice` to show a one-line caption of the current step. A scripted demo with a delay between steps: `cargo run --release -p craft3d --example demo -- --port 7878 --token-file .private/control.token --delay-ms 1500 --part plate`. Once a model is built, the history player under the feature list (or `ui.set {"timeline": {"playing": true}}`) replays it step by step.

**The appearance and evidence (2026-11-02).** Pictures meant as evidence are light. Headless passes (tests,
`examples/window_picture.rs`, `examples/kit_gallery.rs`, `ui_audit_evidence`) have no system preference, so
`appearance: system` resolves light there, whatever the desktop. A live window's `ui.screenshot {window: true}` and
`ui.record` show the window as it is: before taking evidence from a window, `ui.set {"appearance": "light"}` (or
`"dark"` when the dark set is what is to be shown) so it does not depend on the developer's desktop. On Linux the
desktop's setting is not seen at all today: winit 0.30 answers `None` for the system theme on both X11 and Wayland
(GNOME's `color-scheme` is not read), so `system` is light there; macOS, Windows and the browser report theirs.

Rules:

- Never launch a second window when one is already running under control; reuse it.
- Don't steal focus repeatedly: prefer offscreen renders for checks the developer did not ask to watch.
- Screenshots capture only our own window.
- Demo models are original or public-domain designs. No personal data in files, file names or requests; when fetching anything, use a generic `Craft3d-dev` User-Agent.

**A picture of the whole window**, panels and the controls over the viewport included: `ui.screenshot {"window": true, "path": "shot.png"}` on the control channel. The window paints it itself into a texture of its size and reads it back, so it works when the window is covered, minimised or on another workspace, and under a headless `mutter` (2026-10-30). `--window-size 1920x1080` (or `CRAFT3D_WINDOW_SIZE`) opens the window at a given size.

**A video of the window** (2026-10-30), for a demo of 3DCraft with an agent: `ui.record` captures the window's own frames, UI included, from its renderer (not from the compositor, so the window may be covered), into PNG frames or through `ffmpeg` (on `PATH`, or `CRAFT3D_FFMPEG`) into a video ([`control-protocol.md`](control-protocol.md) › *Recording the window*). Frame-exact is what an agent wants: the window then draws only when told, at a fixed step of its clock, each frame once what it shows has settled, so the history player, flights and parameter changes come out the same every time and no frame shows a half-built scene. Over the control channel, or through MCP as `control_call` with the same methods:

```text
ui.record  {"path": "video/demo.mp4", "fps": 30, "step": true}   # "quality": "web" for 4:2:0, "accumulate": 16 for averaged stills
ui.set     {"timeline": {"playing": true, "orbit": true}}
ui.advance {"frames": 300}                 # ten seconds of the player; after 30 s it answers with "left": ask again
engine.execute {"command": "param.set", "params": {"name": "width", "value": "80 mm"}}
ui.advance {"frames": 60}
ui.record  {"stop": true}                  # once ffmpeg has written the file
```

`"path": "video/frames"` (no video extension) writes `frame-000001.png`, … instead, for any editor; `"includeUi": false` records the viewport alone; without `step` it records in real time at `fps`, what the person does in the window included. While it records, the window shows the frames recorded. `craft3d-cli replay` (*A showcase video*, above) is the other way to film a build: headless, one fixed camera, no panels.

cargo run --release -p craft3d-ui-egui --example window_picture -- [--idle] [--first] \

## MCP (agents)

`craft3d-cli mcp` serves MCP on stdio using `crates/automation`:

- **Headless:** `craft3d-cli mcp --automation-read-root <dir> --automation-write-root <dir>`. It drives an in-process engine session and has no file authority when a root is omitted.
- **Live app:** start `craft3d --control 7878 --control-token-file <private-path> …`, then run `craft3d-cli mcp --bridge 127.0.0.1:7878 --control-token-file <private-path>`. The developer sees every step in the window. For a person, since 2026-11-02, it takes no flags: **Allow AI agents** on the start screen (or in the Help menu) makes the window listen, and `craft3d-cli mcp --bridge` finds it through the discovery entries in the state folder ([`control-protocol.md`](control-protocol.md) › *Connecting an agent*). A window started with a token file of its own (`--control-token-file`, as above) writes no discovery entry, so an agent's or a test's window never shows up for the person's bridge; one started without flags gets `--state-dir DIR` of its own (and `--recovery-dir none`), so it neither reads nor changes the person's remembered switch.

Claude Code (`.mcp.json` in the repo root, or `claude mcp add`):

```json
{
  "mcpServers": {
    "craft3d": {
      "command": "/path/to/3dcraft/target/release/craft3d-cli",
      "args": ["mcp", "--automation-read-root", "/absolute/path/to/work", "--automation-write-root", "/absolute/path/to/work"]
    },
    "craft3d-live": {
      "command": "/path/to/3dcraft/target/release/craft3d-cli",
      "args": ["mcp", "--bridge", "127.0.0.1:7878", "--control-token-file", "/private/path/craft3d-control.token"]
    }
  }
}
```

A typical agent loop:

1. `command_run {id:"file.new", params:{units:"mm"}}`
2. `command_list {filter:"sketch"}`
3. `command_run {id:"sketch.create", params:{plane:"xy"}}`, then entities and constraints
4. `command_run {id:"feature.extrude", params:{sketch:"Sketch1", distance:"25 mm"}}`
5. `doc_inspect` to verify feature status, volume and face count; `doc_render_preview` to look
6. `command_run` with `file.save {path:"bracket.3dcraft"}` and `file.export {path:"bracket.step"}` (there are no `doc_new`, `doc_save` or `doc_export` tools). The [user guide](guide/agent.md) has a full session

## Native format (.3dcraft)

See [`file-formats.md`](file-formats.md). In short: a ZIP of STORE entries holding `manifest.json` (the document: variables, tables, sketches, constraints, features in order, assertions, sets, public parameters and info; the format version is `FORMAT_VERSION` in `crates/format/src/lib.rs`, 69 on 2026-11-10), content-addressed `blobs/<sha256>.step` for the bytes of imported STEP files, and `thumb.png` (written for a Jig, ignored on load). A published Jig, `.3dcraftjig`, is the same format. Saves are atomic (write a temp file, fsync, rename). Autosave writes snapshots to a recovery directory on a background thread.

## Graphics startup and device loss

`--renderer cpu` (`CRAFT3D_RENDERER=cpu`) starts with the CPU renderer. Otherwise the viewport is drawn on the window's own wgpu device (the one eframe draws the window with); when its pipelines cannot be made there, or the graphics driver fails while that is tried, the viewport's renderer opens a wgpu device of its own on each of its two threads instead (the drawing thread for previews, the render thread for sharp images) and reads the frames back; when no adapter is found for that either, the viewport is rendered on the CPU; `ui.get` (`renderer.fallback`) and the terminal say why in both cases. A device that is lost while running, or any GPU error that is not the frame's own fault (a lost device, a failed readback, a driver that falls over inside a render), ends that path for the rest of the session: the direct path gives way to the CPU renderer on its threads, the readback path's thread renders on the CPU from then on; the status bar shows `CPU …`. A frame the device cannot take (a target or a mesh too large for it) is rendered the next way down, and the next one on the GPU again. `cargo test -p craft3d-ui-egui --test gpu_fallback` runs the no-adapter case (in a child process with `WGPU_ADAPTER_NAME` set to a name no adapter has).

The window itself is drawn by eframe on wgpu, and eframe 0.36 can only present through wgpu or OpenGL. So the window needs *some* adapter: a GPU, or a software implementation, which wgpu takes when it is the only one. With Mesa's lavapipe (`mesa-vulkan-drivers`) or llvmpipe installed the app runs without a GPU (and the viewport's renderer then runs on that software adapter too); try it with `VK_DRIVER_FILES=/usr/share/vulkan/icd.d/lvp_icd.x86_64.json WGPU_BACKEND=vulkan craft3d`. With no adapter at all the app does not start: it prints what to install and exits with code 1. A window that needs no adapter would take a presentation path of our own (a CPU rasteriser for egui's output and a software surface), which is a second windowing stack and was not built. Nothing else needs an adapter: `craft3d-cli render`, `run`, `serve` and `mcp` work on any machine.

## Debugging geometry

- `craft3d-cli run model.3dcraft --cmd document.check --params '{"deep":true}'` prints the validity report of every body (which check failed on which entity), failed features and broken assertions.
- `document.inspect` lists every body's faces by persistent name (`faceNames`); `document.edges` lists its edges and vertices with their names and the faces they lie between.
- `view.render` with `mode:"ids"` writes a false-colour image where each face has its own colour, with a legend in the JSON result: the quickest way to see which face a name refers to.
- `view.render` with `projection:"orthographic"` gives a picture to scale; `box:[[x,y,z],[x,y,z]]` frames a region instead of the whole model, and `zoom` magnifies about the centre: for looking at a detail.
- Export the smallest failing case as a test in the crate that owns the bug (`crates/<name>/tests/regressions.rs`), not as a file in the repo.

`cargo xtask package` builds `craft3d` and `craft3d-cli` in release (`--locked`) and packs both for the platform it runs on, into `target/package/` (or `--out DIR`):

**The tarball's scripts.** `install.sh` installs the files `share/craft3d/files` names, each to the same path below PREFIX and only names that are 3DCraft's, and `uninstall.sh` removes exactly what the list installed in PREFIX names (without one, what the list of the tarball beside it names) and 3DCraft's emptied folders, nothing else. Both refuse and change nothing when the tarball was unpacked into PREFIX itself, `install.sh` also away from its tarball and `uninstall.sh` when it finds no list (xtask tests run them in a prefix of their own, among other programs' files).

**Third-party notices.** Every package, and the web zip, carries `THIRD-PARTY-NOTICES.txt` beside `LICENSE`: each crate the programs are built from (`craft3d` and `craft3d-cli` for the Linux, macOS and Windows release targets, `craft3d-web` for `wasm32-unknown-unknown`, through normal and build dependencies; workspace crates left out) with its version, the licence expression of its manifest and the licence texts its published source carries, identical texts written once and referenced by number. It is made, not committed: `cargo xtask package` writes it first (`cargo xtask notices [--out FILE]` alone writes it into the target folder and prints the count per licence) from `cargo metadata` over `Cargo.lock`, reading the texts from cargo's registry (`CARGO_HOME`; `cargo metadata` may download a crate's source that is not there yet). Before its last section comes *Bundled fonts (SIL Open Font Licence 1.1)*: every font file in `fonts/` (Noto Sans, JetBrains Mono, and Inter, the interface's), each with the licence file beside it. It ends with a section *Bundled examples (MIT; Jigs and assemblies CC BY 4.0)*: the examples, Jigs and assemblies built into the programs, with their licence; the licence itself (`docs/examples/published/LICENSE.md`) travels as `EXAMPLES-LICENSE.md` in every package and beside the web page. The same review refuses the packages, and an xtask test (`every_shipped_crate_has_an_allowed_licence_and_its_text`) fails, when a crate's licence is outside the allow-list (MIT, Apache-2.0 with or without the LLVM exception, BSD-2/3-Clause, ISC, Zlib, Unicode, OFL-1.1, BSL-1.0, CC0-1.0, 0BSD; `OR` needs one allowed alternative, `AND` all; MPL-2.0 and the Ubuntu font licence pass but are named as noted) or when a crate ships no licence text and is not one of the justified exceptions in `xtask/src/notices.rs` (`NO_TEXT`; those get the standard text from `packaging/licenses/` and their authors as copyright holders).

Options: `--formats tar,appimage` (Linux), `app,dmg` (macOS), `zip,msi` (Windows) to make only some; `--target TRIPLE`; `-j N`; `--no-build` to pack what is already built; `--appimagetool PATH` (or `APPIMAGETOOL`); `--appimage-runtime PATH` (or `APPIMAGE_RUNTIME`), the [type2 runtime](https://github.com/AppImage/type2-runtime/releases) the AppImage starts with, passed to appimagetool as `--runtime-file` (without it, appimagetool downloads the newest continuous build). The tools: `tar` everywhere; [appimagetool](https://github.com/AppImage/appimagetool) on Linux (it runs without FUSE, `APPIMAGE_EXTRACT_AND_RUN=1`, and needs `file` and `desktop-file-validate` from `desktop-file-utils`, which a bare Ubuntu lacks; it writes the `.zsync` with the `zsyncmake` its AppImage carries, run in the output folder, and another appimagetool needs `zsyncmake` from the `zsync` package on `PATH`: the xtask fails when the AppImage does not carry its update information or the `.zsync` is missing); `hdiutil` and `codesign` on macOS; the WiX Toolset v5 on Windows (`dotnet tool install --global wix --version 5.0.2`). Nothing else is installed; the `.icns` and `.ico` icons are written by the xtask from the PNGs. A tool that fails has its output repeated (the last 20 lines) in the xtask's error.

The files the packages carry live in `packaging/`: `icons/` (the original SVG, "Prompt Prism", and PNGs rendered from it with `inkscape craft3d.svg --export-type=png --export-filename=craft3d-<n>.png -w <n> -h <n>` for n = 32 … 1024; the 16-pixel PNG comes from `craft3d-small.svg`, the same `>_` simplified on the pixel grid because the full drawing blurs at that size: `inkscape craft3d-small.svg --export-type=png --export-filename=craft3d-16.png -w 16 -h 16`; the Jig's file type has its own icon, `craft3d-jig.svg` with a slider, rendered the same way to `craft3d-jig-<n>.png`, its 16-pixel PNG from `craft3d-jig-small.svg`, installed as the MIME type's icon `io.github.johancoppens.craft3d-jig` (Linux), `craft3d-jig.icns` (macOS) and `craft3d-jig.ico` (Windows); render them again when an SVG changes and look at every size), `linux/`, `macos/Info.plist` (`@VERSION@` is filled in), `windows/craft3d.wxs`. The identifiers (`io.github.johancoppens.craft3d`, MIME type `application/x-craft3d`) are in [`decisions.md`](decisions.md) (2026-10-22); the xtask's tests check that the files agree on them. The window takes its app id and icon from the same place (`apps/craft3d/src/app.rs`).

**Releases** (the steps to tag and publish: [Releasing a version](#releasing-a-version)). `.github/workflows/release.yml` runs `cargo xtask package` on GitHub-hosted runners (Ubuntu 22.04, for an older glibc; macOS 15 on Apple Silicon, the oldest image there since GitHub retired the macOS 14 images on 2026-11-02, while the app's minimum stays macOS 11, Rust's deployment target for `aarch64-apple-darwin` and the `LSMinimumSystemVersion` of `packaging/macos/Info.plist`; Windows Server 2022; on Linux it installs with apt what the image lacks of `file` and `desktop-file-utils`, trying the update and install three times, and downloads appimagetool 1.9.1 and the type2 runtime of release 20251108 with curl's retries, both checked against their sha256; on Windows it installs the WiX Toolset 5.0.2 with `dotnet tool`, also tried three times), starts each packaged program with `--version` and `commands`, and keeps the packages as run artifacts: `gh workflow run Release -R johancoppens/3dcraft` (it runs only in the public repository). A tag `v<version>` matching the workspace version also makes a draft GitHub release with them, for the developer to publish; its notes are the section `## [<version>]` of `CHANGELOG.md` (from that heading to the next one), plus a line pointing at the install guide for the unsigned installers. The packaging jobs refuse a tag whose version has no such section before they build, and an xtask test holds `CHANGELOG.md` and the AppStream metainfo's newest `<release>` to the workspace version, so a version bump updates both. The binaries carry the commit they were built from (the build scripts of `apps/craft3d`, `apps/craft3d-cli` and `apps/craft3d-web` through `crates/buildinfo`, handed to the engine by their `main`, for the bug report of *Copy details* and `session.report`; only the programs embed it, so a new commit rebuilds only them; `CRAFT3D_GIT_COMMIT` sets it for a build without a checkout, and sources inside another repository's checkout report `unknown` rather than that repository's commit).

What a user meets today:

- **Not signed.** macOS: the app is ad-hoc signed and not notarised, so a downloaded copy is blocked the first time: right-click › Open (macOS 14 and earlier), System Settings › Privacy & Security › Open Anyway, or `xattr -dr com.apple.quarantine /Applications/3DCraft.app`. Windows: SmartScreen warns about an unknown publisher (More info › Run anyway). What a tester sees and does is in the user guide, [`guide/install.md`](guide/install.md). Signing needs an Apple Developer ID and a Windows code-signing certificate.
- **macOS:** Apple Silicon only (an Intel or universal build is `--target x86_64-apple-darwin` plus `lipo`, not set up). Double-clicking a `.3dcraft` file starts 3DCraft but does not open the file yet: macOS hands it over as an Apple Event, which winit does not pass on; File › Open does. `craft3d-cli` is at `/Applications/3DCraft.app/Contents/MacOS/craft3d-cli` (link it onto `PATH`).
- **Windows:** the `.exe` files carry no embedded icon (Explorer shows the generic one; the Start menu entry, the file type and the window have the icon).
- **Linux:** the binaries need the glibc they were built against or newer (Ubuntu 22.04's, 2.35, for the released ones); otherwise they link only glibc and load the window system's libraries at run time.

### Releasing a version

The steps the coordinator runs to tag and publish a release (0.1.0 first). Nothing is published until the last step; a tag only makes a draft. They are run in the public repository `johancoppens/3dcraft`, the only one where Release runs, through the remote `public` (`git remote add public git@github.com:johancoppens/3dcraft.git`), and that repository must have the commit to tag on its `main` first: after the gate passed in the workshop, `main` is pushed to both.

**Where the version is written** (the developer bumps it; agents do not). The workspace `version` in the root `Cargo.toml` (every crate and program inherits it with `version.workspace = true`), then `Cargo.lock` refreshed by any build (the packages build with `--locked`, so a stale lock fails them); `CHANGELOG.md` (the `## [<version>] - <date>` heading and the two compare links at the bottom); the newest `<release version date>` in `packaging/linux/io.github.johancoppens.craft3d.metainfo.xml` (an xtask test holds both to the workspace version). Filled in by themselves: `packaging/macos/Info.plist` (`@VERSION@`), the MSI's version (`msi_version` in `xtask/src/package.rs`), the package names, `--version` and the bug report. Held by tests and written again from the version: the STEP golden files `crates/io/tests/golden/*.step`, whose header names `craft3d-step <version>` (`CRAFT3D_UPDATE_GOLDEN=1 cargo test -p craft3d-io --test step golden` writes them again after the bump). Written out in the docs: `README.md` (the install line), `docs/guide/README.md` (*For version …*), the file names in `docs/guide/install.md`, and `docs/guide/reference.md` (*3DCraft <version> has N commands*, N held to the registry by `guide_examples`).

**Checks that only a person or a machine with a display can run**, once on the commit to tag:

- **The killed window.** `cargo test -p craft3d --test killed_window -- --nocapture` on a machine with `mutter` and a graphics adapter (the developer's laptop): the app killed with SIGKILL recovers its document. Where there is no compositor the test passes by skipping, saying so in its output: read that it ran, not only that it passed.
- **The format promise for this release.** The `FORMAT_VERSION` of the commit to tag (`crates/format/src/lib.rs`; 69 on 2026-11-10) is the first format version a released build writes, so its fixture `crates/format/tests/fixtures/versions/v<N>.3dcraft` must have been written by the build of that version and frozen with its hash (`crates/format/tests/versions.rs` and `crates/engine/tests/format_versions.rs` fail without it). Before 0.1.0 no meaning-preserving migrations were owed for unreleased versions; from the tag on, every later format version keeps this file opening as it did.
- **The web site.** The `package (web)` job's zip unpacked and served as `packaging/web/HOSTING.md` says (HTTPS for WebGPU, the MIME type `application/wasm`, the hashed files cached for ever and `index.html` not), opened in Chrome and in Firefox: an example, a Jig by `?open=`, a save and an export.

1. **Main is complete and green.** Every branch meant for the release is merged into `main`, and the gate passed on the exact commit to tag (in the workshop, on the Strix: read its exit status).
2. **The notes are final.** In `CHANGELOG.md`'s `## [<version>]` section, add a line for every branch merged since the notes were last brought up to date (each line traced to a **Done** line of `docs/roadmap.md`), and drop any line whose work did not land (with the limitation line that names one); set the date in the heading, and the `date` of the newest `<release>` in `packaging/linux/io.github.johancoppens.craft3d.metainfo.xml`, to the day of the tag. The workspace `version` in `Cargo.toml` is the version (an xtask test holds the changelog and the metainfo to it). Commit, and pass the gate on that exact commit: the commit that is tagged is always one the gate passed, whatever changed.
3. **Dry run on that commit.** `gh workflow run Release -R johancoppens/3dcraft --ref main -f only=all`, then `gh run watch <id> -R johancoppens/3dcraft --exit-status`: the four jobs `package (linux)`, `package (macos)`, `package (windows)` and `package (web)` must pass (each builds its packages and starts the programs in them); `draft release` is skipped, since it runs only for a tag `refs/tags/v*`. The artifacts of the run are the packages, to try before tagging.
4. **Tag and push the tag.** `git tag -a v<version> -m "3DCraft <version>" <sha>` and `git push public v<version>`. The Release workflow starts by itself: each package job first refuses a tag that does not match the workspace version or has no changelog section, then builds; `draft release` makes a draft GitHub release named *3DCraft <version>* with every package and `SHA256SUMS.txt`, its notes the changelog section plus a line pointing at the install guide.
5. **Check the draft.** `gh run watch <id> -R johancoppens/3dcraft --exit-status`; `gh release view v<version> -R johancoppens/3dcraft` lists eight assets: `3dcraft-<version>-x86_64-linux.tar.gz`, `3DCraft-<version>-x86_64.AppImage`, `3DCraft-<version>-x86_64.AppImage.zsync` (the AppImage's update information names it: it must be in the release), `3DCraft-<version>-aarch64.dmg`, `3dcraft-<version>-x86_64-windows.zip`, `3DCraft-<version>-x86_64.msi`, `3dcraft-web-<version>.zip` and `SHA256SUMS.txt`. Download them (`gh release download v<version> -R johancoppens/3dcraft -D <dir>`) and run `sha256sum -c SHA256SUMS.txt` in that folder. Read the notes as a user would. Try each installer once where a machine is at hand: the AppImage starts, the tarball's `install.sh` installs and the desktop entry opens a `.3dcraft`; the `.dmg` opens on Apple Silicon after *Open Anyway*; the `.msi` installs, `craft3d-cli --version` answers in a new terminal and a double-clicked `.3dcraft` opens; the web zip unpacked and served over HTTP (`packaging/web/HOSTING.md`) opens an example and a Jig. In each: open an example, save it, open it again, export STEP and STL.
6. **Publish.** The developer's step: `gh release edit v<version> -R johancoppens/3dcraft --draft=false` (or *Publish release* on GitHub). Only a published release is `releases/latest`.
7. **Afterwards.** Leave `## [Unreleased]` at the top of `CHANGELOG.md` for the next changes; record the release with its run ids under the milestone's **Done** in `docs/roadmap.md` and in the dev log.

Older builds and newer files: a build reads files up to its own format version and says a newer 3DCraft is needed for a file of a later one. A variant added to an existing kind within one version is not caught by that: an older build refuses it with serde's own message (a linear coupling, `"kind": "linear"`, read by a build before it: *unknown variant `linear`, expected one of `gear`, `rack`, `screw`*). Say so in the release notes when a release adds such a variant.

A tag build that fails: fix it on `main` (through the gate), delete the draft release if one was made (`gh release delete v<version> -R johancoppens/3dcraft`), delete the tag (`git push public :refs/tags/v<version>` and `git tag -d v<version>`), and tag the fixed commit. A tag that was published is never moved; the fix is the next patch version.

## Web build

`apps/craft3d-web` is 3DCraft in the browser: the same engine and egui shell compiled to WebAssembly, run by eframe's web runner. The only JavaScript is the glue wasm-bindgen generates and a dozen lines in `packaging/web/index.html` that load it; no Tauri, Electron, webview or JavaScript framework. It is a viewer, as the desktop app is: File, Open… (or drop a `.3dcraft` file on the page), the viewport, view cube, feature tree, tabs and selection; Save and Save As (a `.3dcraft` file, through the system's file dialog or as a download), Export… (STEP, STL, 3MF, OBJ with its `.mtl` as a second file, DXF, SVG: every body, or the selected bodies, flat faces or sketch, as on the desktop) and Import… (STEP, or drop the file). A Jig (`.3dcraftjig`) opens on its Parameters tab as on the desktop, the model following when a field is let go (the parameter's own regeneration holds up the page's one thread; opening a file, the meshes and the assertions are done a piece per frame, with the progress in the status bar, since 2026-10-26); the Jigs live in their own repository, `johancoppens/3dcraft-jigs`, and are published on the website with the examples and the assemblies (`https://3dcraft.dev/examples/`), next to the web build (`https://3dcraft.dev/app/`; [`decisions.md`](decisions.md), 2026-10-23, amended 2026-11-10). There is no control channel or MCP in the browser, so no AI agent drives it yet.

How it fits together:

- **One thread, and workers for the regeneration and the checks.** Commands and the CPU renderer run on the page's thread between frames, and so do regeneration and meshing where the workers cannot be had (or with `?pageregen`); every `std::thread::scope` in the kernel and the tessellator does its items in order on wasm32 (`craft3d_math::available_threads` is 1 there), with the same results. The assertions and outputs are measured in a Web Worker (since 2026-10-28): `craft3d-worker-<hash>.js` (from `packaging/web/worker.js`, named in `index.html`'s `<meta name="craft3d-worker">`) loads the same module, which the page posts it compiled, and answers each job with `craft3d_check`; the page's side is `apps/craft3d-web/src/checks.rs` (tested natively) and `worker.rs`, the engine's `crates/engine/src/checks_elsewhere.rs` ([`design/engine.md`](design/engine.md) › *Checks in a Web Worker*). The regeneration and meshing of the document shown run in a second worker of the same script (since 2026-10-28, `kind: "scene"`): the page posts the shown state's `.3dcraft` bytes and gets the quick first picture and the display scene back as bytes (`craft3d_scene_begin`, then `craft3d_scene_step` a piece of about 30 ms at a time, the worker taking its messages between pieces: a newer state replaces the job in hand and keeps what was regenerated, since 2026-10-30; `apps/craft3d-web/src/scenes.rs`, the engine's `regen_elsewhere.rs` and `scene_wire.rs`; [`design/engine.md`](design/engine.md) › *Regeneration in a Web Worker*). Messages only, no `SharedArrayBuffer`, so no COOP/COEP headers. A page without the workers (no meta, a policy that refuses them) regenerates and measures itself, a piece per frame. A command that needs the bodies (a click that selects, `measure.*`, `assert.list`) runs in that worker, where the bodies are (`kind: "command"`, `craft3d_command`; the engine's `commands_elsewhere.rs`, since 2026-10-30); so does an edit that needs them, whose undo steps come back as documents the page applies to its own history, and every export from the menu, the dialog's choices included (the page's own jobs, `apps/craft3d-web/src/jobs.rs`, since 2026-11-02; [`design/engine.md`](design/engine.md) › *Edits and exports where the bodies are*). An assembly is placed there too, with the source files the page read for it, and the moments of a motion (`view.motion`, the player) and its bake are made there, the page keeping the view state and drawing each moment as it comes (since 2026-11-03, [`design/engine.md`](design/engine.md) › *Motion and assemblies in the worker*). The time a slider drag takes to show a state, before and after the stoppable worker: `cargo test --release -p craft3d-web --test drag -- --ignored --nocapture`; how long the page's thread is held up by an export, an edit that needs the bodies and `assert.list` on the turbofan, with the worker and without: `cargo test --release -p craft3d-web --test page_stall -- --ignored --nocapture`.
- **Files in memory.** The session's workspace is `Access::Memory` (`crates/engine/src/memory_files.rs`): a chosen or dropped file is put into the session's memory under its name, `file.open`/`file.import` read it there, `file.save`/`file.export` write there, and the page takes the file out and writes it to the file the person chose, or offers it as a download. The host logic (`apps/craft3d-web/src/host.rs`) runs in native tests; only `page.rs` and `pickers.rs` touch the browser.
- **File dialogs.** Where the browser has the File System Access API (Chrome, Edge, ChromeOS; a secure context, not a cross-origin iframe), Open…, Import…, Save As… and Export… call `showOpenFilePicker`/`showSaveFilePicker` (`src/pickers.rs`, called by name through `js_sys::Reflect`, since web-sys has them only behind `--cfg=web_sys_unstable_apis`; the handles and writable streams are web-sys's stable bindings). A save dialog makes (or truncates) the file it names when the person confirms, so nothing that can still fail comes after it: Export… chooses what, the format and the options in the shell's export dialog (the desktop's own; without file dialogs it asks the name too) and makes the export into memory first, in the frame of the click (`WebHost::export_request`) (`Pick::Export` carries its bytes; a failing export shows no system dialog at all), and the save dialog then offers that one format without *All files* (`excludeAcceptAllOption`), refusing a name of another kind; Save As saves the document by its id (`WebHost::save_document`, so another tab shown meanwhile does not matter). A file the dialog made and nothing was written to is removed when it is empty (`pickers::remove_if_empty`), as a safety net. The handle of a document opened or saved through a dialog is kept per document id, so Save writes back without asking (`WebHost::writable`); a document's writes run one at a time, the newest waiting one replacing an older (`Page::write`). The write is asynchronous and `file.save` has already marked the document saved, so a failed write marks it unsaved again (`Session::mark_unsaved`, through `WebHost::write_failed`): the tab keeps asking, the browser keeps warning before the page is left, and Save asks where next time. A tab closed with *Save* is closed only once its file is written (`Download::close`, `WebHost::close_document`); a download closes it at once. A browser shows a dialog only with transient user activation: the page calls it in the frame that handles the click or key press (eframe hands input to the app in the next animation frame, well within the seconds the activation lasts). A closed dialog (`AbortError`) is nothing; a refused one falls back to the page's name dialog and a download, or to the file input, and says so; a refusal that is not about activation (a cross-origin iframe) switches the session to downloads (`refusal_is_about_activation`). An OBJ's `.mtl` waits for its own click (*Save…* in a small window, `WebHost::companion_ui`), since the export's dialog used the first click's activation. Elsewhere, or with `?download`, saved and exported files are downloads (a link in the page, clicked) and the status bar says *downloaded …: see the browser's downloads*. eframe leaves Ctrl+E and Ctrl+I to the browser (Chrome focuses its address bar on Ctrl+E); the page keeps them for Export and Import.
- **Renderer.** The viewport is drawn by the GPU renderer on the page's own device (`craft3d_ui_egui::direct`, the same WGSL shaders as the desktop): WebGPU when the browser has it, else WebGL2 (wgpu's GL backend, one sample per pixel there; every pass that reads the depth buffer, the lines' distances, see-through bodies and the section, samples it with the nearest filter, since OpenGL ES 3.0 reads 0 from a depth texture loaded without one: see-through and cut-open pictures are the GPU's there too since 2026-10-26, [`design/rendering.md`](design/rendering.md) › *The browser*). `?webgl` forces WebGL2, `?cpu` the CPU reference renderer. An error the device reports later goes to the page's handler (wgpu's default would end the page), and the viewport switches to the CPU renderer (`Shell::leave_gpu`). A browser with neither gets a message in place of the app.
- **Preferences** (open panels, shown sketches and datums, the last export format) are JSON in `localStorage` under `3dcraft.prefs`; every access is guarded, so a private window or a sandboxed iframe just starts with defaults (`src/prefs.rs`). **Recovery is off**: no autosave in the browser; the page warns before it is closed or reloaded with unsaved changes.
- **`?open=<url>`** opens a `.3dcraft`, `.3dcraftjig` or STEP file of the same site at the start: the decoded address must have no scheme, no backslash, no control character and not start with `//` (`flags::same_site`), and resolved by the browser against the page it must have the page's origin; the download is cut off past 256 MiB (Content-Length first, then while it streams). Dropped and chosen files are checked for kind and size before they are read.
- **Memory.** A WebAssembly module has 4 GiB at most and never gives memory back, so the page keeps less than the desktop: a scene budget of 256 MiB (`WEB_SCENE_BUDGET`, where the desktop's is 1.5 GiB; the meshes of bodies within a budget of the same size), down to which the scenes of other documents and of earlier undo states are let go, least recently shown first, while the active document's own scenes are always kept, beyond the budget when they alone are larger, and the bodies a regeneration keeps within 256 MiB per document (`craft3d_regen::DEFAULT_BODY_BUDGET` on wasm32). Older undo states are meshed again when shown. `cargo run -p craft3d-web --example memory_soak -- JIG [STEPS]` runs the page's host code natively on a Jig, one commit per step, and prints the scenes, meshes and resident memory (R1 B7, 2026-10-23: the welding table kept 3.3 MiB of scenes per commit before, without end short of 1.5 GiB; now at most 256 MiB from about 80 commits on).
- **Panics end the page.** WebAssembly in the browser aborts on a panic (no unwinding), so the never-crash rules matter even more here: the `catch_unwind` guards around commands do nothing on wasm32, and an escaped panic loses every unsaved document of the page. The graphics device's error handler is registered as soon as the page has the device (in eframe's app creator, right after eframe made it; egui-wgpu has no earlier hook); before that only eframe's own painter is set up.

**Building.** `cargo xtask package --formats web` (any platform; `--out DIR`, `-j N`, `--no-build`) builds `craft3d-web` for `wasm32-unknown-unknown` with the cargo profile `web` (release optimised for size, `opt-level = "z"`, except the modelling and meshing crates and the SIMD code of egui's text rasteriser, which keep opt-level 3: the root `Cargo.toml` says why), runs `wasm-bindgen --target web`, then binaryen's `wasm-opt -O2` when it is there (optional; without it the module is a fifth larger), names the module and its glue `craft3d-web-<hash>_bg.wasm` and `craft3d-web-<hash>.js` with the first 16 hex digits of their SHA-256, fills in `packaging/web` (`index.html`, `manifest.webmanifest`, `HOSTING.md`, `_headers`, `.htaccess`), adds `icon-256.png`, `icon-512.png`, `LICENSE`, `THIRD-PARTY-NOTICES.txt` and `EXAMPLES-LICENSE.md`, zips the folder `3dcraft-web-<version>/` into `3dcraft-web-<version>.zip` (Info-ZIP `zip`) and puts its line into `SHA256SUMS.txt` beside it. The tools, pinned: `rustup target add wasm32-unknown-unknown`; the wasm-bindgen CLI of exactly the version in `Cargo.lock` (0.2.129; `cargo install wasm-bindgen-cli --version 0.2.129 --locked`, or the release tarball, `--wasm-bindgen PATH` or `WASM_BINDGEN`; the xtask checks the version); binaryen version_133 (`--wasm-opt PATH` or `WASM_OPT`). There is no Trunk step: the xtask does what Trunk did for VectorCraft (relative URLs, hashed names) with names a cache rule can match exactly (Trunk's hash is not always 16 digits). The Release workflow builds the zip on Ubuntu 24.04 in a job of its own (`web`, the tools downloaded and checked against their sha256), checks it, and a tag's draft release carries it with `SHA256SUMS.txt` over every asset.

Sizes of 0.0.1 (2026-10-22, with wasm-opt `-O2`): the module 15.5 MB (19.0 MB before wasm-opt), 6.0 MB with gzip -9 and 4.4 MB with Brotli 11; the glue 156 kB (24 kB gzip); the zip 6.0 MB. The release build takes about 3 minutes from clean and wasm-opt about a minute (`-j 2`). The gate holds the module's gzip size to a budget (`cargo xtask web-size`: at most 12 MiB and at most 10 % over `apps/craft3d-web/size-baseline.txt`; [`testing.md`](testing.md) › *Web module size*).

**Trying it locally:**

```sh
cargo xtask package --formats web --out target/web
cd target/web && unzip -o 3dcraft-web-*.zip && cd 3dcraft-web-*/
python3 -m http.server 8765 --bind 127.0.0.1
# then open http://localhost:8765/ (add ?webgl to force WebGL2, ?open=part.3dcraft for a file put beside index.html)
```

Headless, as the build was checked: `google-chrome --headless=new --enable-unsafe-webgpu --use-angle=swiftshader --enable-features=Vulkan --window-size=1280,800 --virtual-time-budget=30000 --screenshot=shot.png 'http://127.0.0.1:8765/?open=flange.3dcraft'`.

**Hosting** is in `packaging/web/HOSTING.md` (shipped in the zip): MIME types, compression, caching by the hashed names, HTTPS for WebGPU, no isolation headers, iframes, the flags.

## Bundled examples

The start screen (`crates/ui-egui/src/shell/start.rs`) opens examples, Jigs and assemblies built into the program (docs/decisions.md, 2026-11-10): ten parts (the first two marked *Start here* for a newcomer), six Jigs and four assemblies, in three sections, and *More examples*, which opens the galleries at `https://3dcraft.dev/examples/` in the browser. They are the published files of three repositories, which are their source: [3dcraft-examples](https://github.com/johancoppens/3dcraft-examples) (MIT), [3dcraft-jigs](https://github.com/johancoppens/3dcraft-jigs) and [3dcraft-assemblies-examples](https://github.com/johancoppens/3dcraft-assemblies-examples) (CC BY 4.0). The files and their pictures are in `docs/examples/published` and are built into every program with `include_bytes!`, the web module too (6.2 MB of files and pictures: the module grew from 7.99 to 9.14 MiB with gzip, 2026-11-10), so they open offline and nothing is fetched. A card opens its file by `Session::open_bytes_titled`, without a file of its own: a part with its history, a Jig in use on its form, an assembly with its player on its motion; Save asks where (proposing the example's title), so the bytes built in are never written. Only looked at, it is no unsaved work: it counts as saved as it was opened, so it has no unsaved mark, asks nothing when it or the window closes and is not autosaved until its first edit, and its tab and the window's title name it by its title (docs/decisions.md, 2026-11-10). Over the control channel `ui.example` lists them, shows a section and opens one by its id ([`control-protocol.md`](control-protocol.md)).

`docs/examples/published/bundle.json` is the manifest: per file its `id`, `section` (`parts`, `jigs`, `assemblies`), `start`, `repository` and `folder`, which say what is bundled and in what order, and what the copy wrote: the file, the commit, the licence, the title and one-line summary of its `meta.json`, its author, size and SHA-256, and the numbers its repository recorded when it built it (`stats`). To refresh the files (when the repositories rebuilt them), or after changing the set in the manifest:

```sh
cargo xtask bundle-examples --from ..   # the folder that holds the clones 3dcraft-examples, 3dcraft-jigs and 3dcraft-assemblies-examples
```

It reads each folder at the head of `main` of the local clone with git (no network; the clone's working tree and its other branches do not matter), copies the built file unchanged, and refuses, writing nothing, a licence other than the one allowed for the repository (in `meta.json` or in the file's own document information: never a Jig shared under CC BY-SA), a file this build cannot open (a newer format version than it reads), a file of another kind than its section, a part packed in an assembly (`blobs/*.3dcraft`, in a packed subassembly too) whose own document information names another licence (named in the error), a `meta.json` without its id, title, summary or the `stats` the tests compare with, a repository without the `ATTRIBUTION.md` the licence links to, two entries whose files would have the same name, or a file larger than its cap (4 MiB for a bundled file; git is asked its size before it is read, and a preview's pixels are capped before it is decoded). Each picture is the folder's `preview.png` made 240 × 180 (an area-weighted average) and cut to 256 colours (indexed, 4 to 14 kB). Then it writes the manifest, the licence of the bundled files (`docs/examples/published/LICENSE.md`, with each file's repository, folder and commit, the MIT text, the CC BY licensor's copyright notice from the repository's `LICENSE-CC-BY-4.0.md`, and per repository a link to its `ATTRIBUTION.md` at that commit, which credits the data and designs from elsewhere its files use; the packages carry it as `EXAMPLES-LICENSE.md`), their rows in `ATTRIBUTION.md` and the start screen's list (`crates/ui-egui/src/shell/start_bundle.rs`, included by `start.rs`), and removes files the manifest no longer lists. `cargo test -p xtask` (`the_bundle_is_what_its_manifest_says`) checks the files against the manifest and that the licence, the rows and the list are what it makes; `craft3d-ui-egui`'s `bundled_examples` opens every one as the start screen does, regenerates it and holds it to its repository's numbers (features, assertions, none failed or fewer proven; for an assembly its instances, mates and freedom), and prints how long each takes to open; `cargo xtask web-size` measures the module that carries them.

## Example pictures

The command scripts of the guide's lessons (`docs/examples`) and of the models kept as tests (`crates/engine/tests/example_models`) each have a picture beside their entry in their folder's README. `cargo xtask example-thumbs` makes them again: it builds `craft3d-cli`, runs every script in a new document in millimetres and renders it with `view.render` (the CPU renderer in the studio look, environment Workshop, tone curve ACES and +0.5 EV exposure, the developer's choices of 2026-10-31, on a plain background; iso, perspective, 640 × 480: `PICTURE` in `xtask/src/thumbs.rs`), cuts it to at most 256 colours (the most common ones, each pixel to the nearest) and writes an indexed PNG. It also writes `xtask/example-pictures.txt`: per script a hash of the script, the render settings and the method. The pixels are not compared, since the renderer's last bits may differ between platforms; the stamp says what they were made from. `cargo test -p xtask` (`the_pictures_are_up_to_date`) recomputes the stamps and fails when a script or the settings changed without new pictures: run the task and commit the pictures and the stamps. Another test checks that every script of the two folders is listed. The stamp does not see the renderer, the theme or the kernel: after a change to one of them that shows in pictures, run the task again too. Scripts are hashed with CRLF line ends read as LF, and `.gitattributes` keeps the scripts and the stamps LF in every checkout. Until 2026-11-10 the task also made the start screen's thumbnails of the scripts, which the start screen no longer shows.

## Morning health report

`cargo xtask health` prints a short page of Markdown on how the project stands, for the developer in the morning. It is a tool of the workshop: it reads the workshop's gate worktree and dev log, which a clone of the repository does not have, and says `unknown` for them. It holds: the date; the last commit of `main` and of `work`; the last gate (`gate-<n>.log` with the highest number in `.claude/worktrees/gate/target/`, or `$CRAFT3D_GATE_DIR/target`): passed or failed, on which commit, when it finished, how long it took, the failed binaries; the boolean corpus of that gate (agree, refused, unscored, mismatch, invalid, digest, from `target/evidence/booleans/corpus-score.txt`); the benchmark's work counts of that gate against the baseline ([`testing.md`](testing.md) › Performance tests); the number of commands, of tests and of lines of Rust (per crate in a folded table, as `cargo xtask stats`); the refusal sites (`::Unsupported`, `Stop::of(`, `unsupported(` in non-test code); the last random-design run (`target/fuzz/summary.json` of `cargo xtask fuzz`, [`testing.md`](testing.md) › Oracle 11: seeds, groups, the refusal rate and the three most common reasons, wrong results by oracle, crashes, timeouts, out of memory); the open findings of each showcase (`== … -> FAILED` lines in `target/work/*/findings/results.txt`); and the expectation changes logged in `log/devlog.md` since the previous report (lines that say "expectation change"; the ten most recent are quoted). It only reads, and says `unknown` for whatever is missing. The page is also kept in `target/health/<date>.md`, and the dev log line it read up to in `target/health/last.txt`.

## Dev log

In the workshop, `log/devlog.md` (a local folder, gitignored and not in the repository, [`AGENTS.md`](../AGENTS.md) §7) gets a terse entry at the end of every task: date, what landed, numbers (tests, timings with machine and load), what is still open. It is how the next agent session picks up.
