# Testing: the AI loop and its oracles

> **Last updated:** 2026-10-14 · **Status:** the loop is in use. In place: oracle 1 (closed-form mass properties, `testkit::solids`), oracle 2 (validity checker with seeded defects), oracle 3 (boolean identities on seeded random pairs), oracle 4 (tessellation against the exact body, for patches), oracle 6 (constraint solver), oracle 7 (CPU side), oracle 8 (FreeCAD) and oracle 9 (no body passes through itself). The rest is design

3DCraft is written by AI agents while the developer watches. That only works if an agent can tell, without a human, whether what it built is right. This document says how.

## The loop

```text
 1. write the test      state what must be true, before or with the code
 2. run it              the narrowest command that exercises it
 3. check               read the actual output: numbers, the validity report, the picture
 4. improve             fix the code (not the test), then go to 2
 5. widen               run the crate's suite, then the gate in AGENTS.md §5
 6. record              devlog entry: what landed, numbers, what is still open
```

Rules of the loop:

- **A test that never failed proves nothing.** See it fail for the right reason first (or break the code on purpose once), then make it pass.
- **Read the output.** "exit code 0" is not a check. For geometry, look at the numbers against the expected values; for anything visual, open the PNG.
- **Never get green by weakening.** Don't loosen a tolerance, delete an assertion, mark a test `#[ignore]` or special-case the fixture. If the behaviour really is out of scope, return an `Unsupported` error, test *that*, and write the limitation in the dev log.
- **Tolerances are stated, not tuned.** Every approximate comparison names its tolerance and why (modelling tolerance, chordal tolerance, floating-point bound). A tolerance changed to make a test pass needs a justification in the commit.
- **Changing an expectation is a recorded decision, not a fix.** When a test fails there are two suspects, the code and the expectation, and the agent wrote both. An expectation may change only when all of these hold:
  1. **The reason is a fact about the mathematics, the specification or the measuring method**, stated in a comment at the assertion, and true whatever the code prints. "The lip of the spout folds inward, so outward there means towards the symmetry plane" is a reason. "The code returns 7.99" is not.
  2. **The new expectation is not weaker than it has to be.** Prefer replacing a wrong claim with a different, checkable one (normals agree across a seam) over deleting it or widening a tolerance.
  3. **Something independent of the code under test still pins the behaviour down:** a closed form, a second computation by another route, an external program, or a picture a human looked at. Where no such oracle exists (wording of an error message, a default value), say so in the test's comment: it is then a regression test, not a proof.
  4. **It is logged.** The dev log entry lists every expectation that was changed and why, under its own heading, so the developer can review them without reading the diff.

  If any of the four is missing, the code is the suspect and the test stays.
- **Shrink failures.** A failure found on a big model becomes a small synthetic regression test before it is fixed.
- **Stop and ask** when three honest attempts fail the same way, or when making a test pass would need a decision listed as open in [`decisions.md`](decisions.md).

## Why CAD is checkable

PhotoCraft's main oracle is free: every PSD contains Photoshop's own rendering. A CAD kernel has no such file. It has something better: **mathematics**. Most of what a kernel produces has properties that are known exactly or must hold by construction.

### Oracle 1: closed-form mass properties

`topo` computes volume, area, centroid and inertia from the exact B-rep. For shapes with textbook formulas the expected value is known to machine precision.

| Shape | Checks |
|---|---|
| Box a×b×c | V = abc, A = 2(ab+bc+ca), centroid at the centre |
| Cylinder r, h | V = πr²h, A = 2πr(r+h) |
| Cone, sphere, torus | V = ⅓πr²h; V = 4/3πr³, A = 4πr²; V = 2π²Rr², A = 4π²Rr |
| Extrusion of a profile | V = profile area × height (profile area from Green's theorem on the sketch) |
| Revolution of a profile | Pappus: V = angle × centroid distance × profile area; A = angle × Σ curve length × distance of the curve's own centroid, plus the two caps for a partial turn |
| Box with a through hole | V = abc − πr²h |
| Filleted box edge | V = abc − (1 − π/4) r² × edge length |

In place for revolution (`crates/kernel/tests/revolve*.rs`): the profile catalogue about axes clear of it and profiles drawn against the axis, full and partial turns, either side of the axis, at three scales on tilted planes, volume and area to 1e-10; full turns against the primitives; a seeded random run. The faces a revolution makes are checked on their own in `crates/topo/tests/mass_revolved.rs` (torus segments, sphere segments and wedges, cone wedges). That the numbers do not depend on how a surface is parametrised is checked in `crates/topo/tests/mass_frames.rs`: caps, zones, wedges and lenses of balls, each with its sphere's frame turned so that a pole lies well inside the face, well outside it, on its boundary and within 1e-12 to 0.2 of it on either side, and cone faces around, through and near the apex with the cone's frame moved along the axis and flipped; as built and inside out, at three scales, 34 000 bodies to 1e-11. Spline edges and spline surfaces have their own files, `mass_splines.rs` and `mass_surfaces.rs`: the same can with its wall as a cylinder, as one rational spline and as a spline with knot lines around it (to 1e-11 of πr²h and to 1e-12 of each other), slices and caps of a spline ball, a spline sphere and torus without loops, a lid on a plane whose parametrisation is warped between its knot lines, and the teapot's patches against a double integral.

`testkit` *(planned)* provides these as reference solids with their expected values, at several scales and after arbitrary rigid transforms (mass properties must be invariant or transform predictably).

### Oracle 2: topological invariants

Every body an operation returns must pass `topo::check`: Euler–Poincaré (V − E + F − (L − F) − 2H = 2(S − G), with H the faces that are a torus or a torus with holes in it; `crates/topo/tests/genus.rs` holds `topo::genus` to what hand-built bodies are, and `crates/kernel/tests/genus.rs` to what the booleans make of a torus), each edge of a solid used exactly twice in opposite directions, closed loops, curves on their surfaces and vertices on their curves within tolerance, consistent orientation. Expected entity counts are asserted where known (a box has 6 faces, 12 edges, 8 vertices; a box minus a through cylinder has 7 faces).

### Oracle 3: algebraic identities

Checked on generated inputs (proptest), by comparing mass properties and validity:

- `vol(A ∪ B) = vol(A) + vol(B) − vol(A ∩ B)`
- `vol(A − B) = vol(A) − vol(A ∩ B)`
- `A ∪ B` equals `B ∪ A`; `A ∩ A = A`; `A − A` is empty; `A ∪ ∅ = A`
- an operation followed by its inverse transform leaves mass properties unchanged
- pattern of *n* disjoint copies has *n* × the volume

As built for the booleans (M7, `crates/kernel/tests/boolean_random.rs`): seeded pairs (our own SplitMix64, no proptest), in two sets of shapes (blocks, cylinders, L-shaped extrusions and slots with a hole; and those with cones, balls and rings), in three placements (each turned at random; both turned alike, so axes and faces are parallel but nothing coincides; on a half-unit grid along the world axes, so faces are flush, touch and share edges), at scales 1e-3, 1 and 1e6 with the tolerance scaled along. Per pair the six booleans (both orders) must each give a body that passes the checker, an empty result, or `Unsupported`; then the volume identities above must hold to 1e-9, with the two area identities `area(A ∪ B) + area(A ∩ B) = area(A − B) + area(B − A) = area A + area B` where nothing is coincident, and `(A − B) ∪ (A ∩ B)` must have the volume of A (its pieces meet in coincident faces, which is what that union exercises). Every boolean is also run without the merge step: the same volume, area, genus and number of shells, and never fewer faces, edges or vertices.

The identities compare the booleans with each other: a kernel that missed every intersection would satisfy them. So the intersection is also checked against the operands' own definitions: exactly for two axis-aligned boxes, and by sampling 3000 points (within five standard deviations) for every pair. The test run does 120 pairs per placement, scale and set of shapes; the long runs (`cargo test --release -p craft3d-kernel --test boolean_random -- --ignored --nocapture`) do 1500 and print, per placement and scale, how many pairs were solved and how many were refused for which reason. `BOOLEAN_PAIR="seed placement scale"` with the ignored test `one_pair` reproduces one pair (`BOOLEAN_ALL_SHAPES` for the second set).

Closed forms for the booleans are in `boolean.rs` (planes and cylinders), `boolean_surfaces.rs` (the cap and the segment of a sphere, the lens of two, the frustum, the napkin ring, Pappus for cuts of a torus, a countersunk hole, a dome, a pin with a round end; also with the intersection circles handed over as splines that only approximate them, `boolean::approximate_circles`) and `boolean_contact.rs` (bodies that only touch, results that hang together by an edge, and merging: a union of flush boxes is a box in volume, area and counts; what is cut apart and put together again is the body it was). Boolean results also go through the tessellator (`crates/testkit/tests/boolean_tess.rs`, there because `kernel` and `tess` share a layer): the mesh is closed and its volume converges to the closed form, for results with conical, spherical and toroidal faces, a vertex at an apex, and spline edges. `boolean_corpus.rs` (oracle 8) compares with FreeCAD's results for 3996 pairs; where `mass_properties` of our body disagrees with the reference, the body is measured a second time by counting sampled points (`boolean::contains_points`), which tells a wrong body from a wrong measurement. Since 2026-10-14 also: a rod that goes on in a ring (`boolean_surfaces.rs` › `a_rod_that_goes_on_in_a_ring`: what they share is the integral over the height of the segment a strip cuts from a disc, by Simpson's rule in the test, held to 1e-6 and measured at 7e-9; a rod too short to pass through is held to the identities), and cones that share a ruling or an apex (`boolean_contact.rs` › `cones_that_share_a_ruling`: from outside the three rules for bodies that only touch; from inside 3000 seeded points per result against membership of the two cones by their own equations through `boolean::contains_points`, and the identities to 1e-7).

**Analytic twins for rational faces** (`crates/kernel/tests/boolean_rational.rs`, `rational_common/`). A rational NURBS patch can be a piece of a cylinder, a cone, a sphere or a torus exactly, so a solid with such faces exists twice: on the analytic surfaces, where the kernel has closed forms and the corpus has FreeCAD's answers, and on the rational patches. The analytic solid is the oracle for the rational one: the twins are held to the closed forms (volume, area, centroid, a watertight mesh), and every boolean of the rational twin to the same boolean of the analytic solid, at three scales, in the world's frame and tilted, with patches that end on the face's trims and patches that are larger. The helper refuses to make a twin whose patch would not lie under all of its face (a face that reaches more than half way around: an early version did, and what looked like a kernel fault was the fixture's). A rational face that is no quadric has no twin: it is held to a quadrature of its own (the height of the roof by Newton's iteration, integrated over the floor) and to the identities of sets.

### Oracle 4: tessellation against the exact body

- the mesh of a solid is a closed, consistently oriented 2-manifold (every edge shared by exactly two triangles, opposite directions)
- every mesh vertex lies on its face's surface within floating-point error; sampled triangle interiors lie within the chordal tolerance
- mesh volume and area converge to the B-rep values as the tolerance shrinks, at the expected rate
- identical output for 1, 2 and N threads (byte-equal)

Since 2026-10-14 the first point is also checked by the tessellator itself, on every body it returns: the mesh of each face is held against the chords of the face's edges, and a face whose mesh does not end on them (each as often, and in the direction, its loops use it) is an error ([`architecture.md`](architecture.md) §6, *Closed, and checked*). A mesh that is not closed can therefore not be a result. The suites go on welding their meshes (`Mesh::weld`, `Welded::is_closed`): that is the check of the check, by another route. What the tessellator's check takes on trust is the inside of a face (two triangles on every side that is no constraint), which is the triangulation's own invariant.

The suites, in `crates/tess/tests/` unless said otherwise: `oracle.rs` and `fixtures.rs` (the reference solids against their closed forms), `periodic.rs`, `winding_seam.rs` and `closed_surface_holes.rs` (faces that go around their surface), `closed_freeform.rs` (the same on spline surfaces that close on themselves, built by hand as a STEP file has them: a full turn with a seam edge, between two circles, a window across the seam, a NURBS torus, a surface closed to a point at both ends; and what is refused), `near_edges.rs`, `scale.rs`, `transformed.rs`, `awkward_axes.rs`, `invalid.rs`, `budget.rs`; in `crates/testkit/tests/` (bodies made by the kernel): `boolean_tess.rs`, `winding_seam_solids.rs`, `twisted_blade.rs` (a loft: every triangle runs the way its normals point and the normals are the surfaces' own); and in `crates/kernel/tests/boolean_poles.rs`, the meshes of freeform faces cut through and around a pole. **Comparing meshes before and after a change:** `crates/testkit/tests/mesh_hashes.rs` (ignored; run in release) prints a hash of every bit of 441 meshes (the reference solids straight and askew, boolean results, extruded, lofted and revolved splines, at three sizes and three tolerances, each on 1, 2, 8 and all threads, which must agree), and for the bodies with freeform faces the measured distance of the mesh from the surface over the tolerance. Two runs are compared with `diff`; a change that should leave meshes alone leaves every line alone.

### Oracle 5: determinism and round trips

- regenerate twice → byte-identical bodies
- incremental regeneration after an edit = full regeneration from scratch (built: `Session::regeneration_matches_a_full_one()`; the `run` helper of the engine suites asserts it after every command, and `crates/engine/tests/regen_cache.rs` adds a seeded random walk of edits and the counts of rebuilt features)
- save → load → regenerate → same bodies (compared by a canonical hash) and same feature statuses
- strip every cache from a `.3dcraft` → still opens to the same model
- replay a recorded command script → same document
- undo/redo returns to the exact previous snapshot
- STEP export → (our import, once it exists) → same mass properties and entity counts

### Oracle 6: constraint solver

After a solve, every constraint residual is within tolerance; the reported degrees of freedom match a hand count for known sketches (a fully constrained rectangle has 0); redundant and conflicting constraints are identified on purpose-built cases; re-solving a solved sketch moves nothing.

In place since M5, at two levels that were written independently of each other. `crates/solve/tests` has a catalogue of 26 sketches with coordinates and degrees of freedom worked out by hand in a comment at each case, solved at scales 1e-3, 1 and 1e6, plus every constraint kind alone, purpose-built redundant and conflicting cases, branch stepping and a seeded robustness run. `crates/engine/tests/sketch.rs` drives the same solver through the commands with its own hand-computed sketches (an L profile, a 3-4-5 triangle drawn on either side, a circle on a line), through a change of a variable, undo, and save and reopen.

### Oracle 7: renderers against each other

The CPU renderer has golden images for a small set of scenes (reviewed by the developer when first blessed, because a golden image is only as right as the eyes that accepted it). The GPU renderer is compared with the CPU renderer on the same scenes: id buffers equal away from silhouettes, colours within tolerance. See [`architecture.md`](architecture.md) §7.

In place since M4 for the GPU half (`crates/gpu/tests`). `parity.rs` renders 75 scenes with both renderers on every adapter the machine has and asserts the tolerances of [`architecture.md`](architecture.md) §7.2, each derived in `tests/common/mod.rs` from two facts (the GPU computes in `f32`, and its rasteriser snaps vertices to 2⁻⁸ pixel) rather than tuned: face ids equal outside a band around feature edges, distances within a bound made of the `f32` rounding and the local gradient, colours within one level of 255, and a limit on how many pixels may differ at all. The same file checks exact pixel counts that need no second renderer and that the same input gives the same frame bit for bit on the same adapter. `robustness.rs` holds the GPU renderer to the CPU renderer's errors for the CPU renderer's own bad inputs and covers what only a GPU has (no adapter, a destroyed device, a mesh of another renderer, a target format that cannot take the picture). The tests need an adapter and **fail without one**; a software rasteriser is enough (`mesa-vulkan-drivers` for lavapipe), and `WGPU_BACKEND` and `WGPU_ADAPTER_NAME` narrow the run to one. Pictures (CPU, GPU and their difference side by side) and the measured numbers go to `target/evidence/gpu/`. The renderer was checked by seeding twenty breakages one at a time (a flipped axis, a wrong tie rule, a near plane inside the model, swapped channels, an id that loses a bit, a truncated mean, ...); when a new kind of mistake becomes possible, seed it and see that a test fails.

### Oracle 8: external tools (optional, never a dependency)

For file formats the final judge is another program. Where available on the machine, test helpers may shell out to an independent tool to validate an exported file and read back its volume and bounding box (for example an open-source CAD kernel's command line for STEP, a slicer or mesh checker for 3MF/STL). These tests are opt-in (`#[ignore]`, run by `cargo xtask freecad`), fail with a clear message when opted in without the tool, and the tool is never linked, vendored or read for implementation ideas. In use since the first mesh export: on its first run FreeCAD's point count exposed near-duplicate vertices on collapsed and reversed patch edges that our own tests had not caught. FreeCAD is the approved tool ([`decisions.md`](decisions.md)); tests find it through the `CRAFT3D_FREECAD` environment variable.

**STEP (2026-10-13)** is the third use, and the one that reads our exact B-rep rather than a mesh: if FreeCAD opens a STEP file as a valid solid of our volume and area, then our faces, loops, orientations and curves mean what we think they mean. Two opt-in tests, both run by `cargo xtask freecad`, share one harness (`crates/io/tests/common/step_harness.rs`) and one script (`crates/io/tests/step_report.py`, FreeCAD's documented Python API only): FreeCAD imports each file and reports, for the shape and per solid, `isValid()`, volume, area, centre of mass, bounding box, the counts of faces, edges, vertices and shells, which shells are closed, how many seams and degenerated edges it added, and the names of the objects it made.

- `crates/io/tests/step_freecad.rs`: 100 files of bodies built on the kernel and by hand: the reference solids of `testkit` (whole and trimmed, spline roofs, an elbow, an octant), cavities of every kind, several lumps, nested lumps and cavities, rational splines, sheets, ellipses; at the scales 1e-3, 1 and 1e6; and a block and a cone in each of the six length units, with angles in radians and in degrees. A second test (2026-10-14) has 42 files of booleans of the domed block, with its roof as a Bézier patch and as a NURBS surface: a block through the roof (union, difference, intersection, each also held to the integral of the roof's own polynomial, and FreeCAD's four volumes to `vol(A ∪ B) + vol(A ∩ B) = vol A + vol B`) and a corner of one roof resting on another.
- `crates/engine/tests/step_freecad/lofts.rs` (2026-10-14): 39 documents with lofts at the scales 1e-3, 1 and 1e6 (box, frustum, pyramid, twisted prism, smooth cone, vase, square to circle to square, spline leaves, bends and rings on datum planes, a drilled leaf with a block on it), as STEP, STL and 3MF. FreeCAD calls every one a valid solid with our counts, and reads the meshes as closed; volumes agree to 6e-12 or better for 30 of them, to 1.6e-9 for the square to a circle (sides whose weights vary along the loft) and to 6.8e-8 for the drilled leaf (edges where a cylinder cuts B-spline faces), and one is beyond FreeCAD's own integration: the vase (rational faces, cubic along the loft with a knot inside: 6.0e-6 in volume and 3.3e-5 in area, alike at every scale), which is held instead to the quadrature over the geometry FreeCAD imported (2e-14), as the spline leaves are.
- `crates/engine/tests/step_freecad/sweeps.rs` (2026-10-14): 42 documents with sweeps along a path at the scales 1e-3, 1 and 1e6 (a round pipe, a tube with a bore and a bar along line, bend, line; a profile of splines; rods and bars round mitres of 60°, 90° and 120°; a gasket, a mitred frame and a ring round a circle; a hose and a rail along a spline; a bar drilled and joined). FreeCAD calls every one a valid solid with our counts; where every edge is a line in the parameter plane of its faces its volume and area agree with ours to 1e-15, and ours with the closed forms to 1e-9. Two cylinders that meet in an ellipse at a mitre come back 4e-7 (60°) and 1.2e-6 (120°) larger, alike at every scale (FreeCAD approximates such an edge on import: `APPROXIMATED`). For the faces along a spline FreeCAD's own integration is 7e-5 off, and the volume by quadrature over the geometry it imported agrees with ours to 2e-14.
- `crates/engine/tests/step_freecad.rs`: 348 documents built by commands and exported by `file.export`: every primitive upright and tilted, the bracket of the acceptance scenario, extrusions with arcs and holes, revolved bodies (ring, cone, frustum, sphere, torus; whole and part turns, through apexes and poles), moved, mirrored and patterned bodies, and the union, difference and intersection of 28 pairs like those of the kernel's boolean tests (cavities included); all at three scales, with the document's tolerance following the scale; and the bracket in six units, which must measure 40 × 30 × 8 mm in FreeCAD whatever the document's unit. A boolean the kernel refuses is listed, not failed. A second test in the same binary (`tests/step_freecad/features.rs`, 2026-10-14) has 124 documents of what was built on 2026-10-13: extrusions up to an inclined plane, a cylinder, a sphere (from outside, from inside, off its axis), a torus (on and off its lowest circle) and a freeform wall, and through all; sketches on datum planes at a distance, at an angle, about an edge and through three points; revolves about datum axes; a mirror in a datum plane, kept and joined; patterns about datum axes; spline profiles with a hole, the pillar, the impeller and the bearing housing of the showcase; bored sleeves with an oil hole along a radius (through the wall, blind, through both walls, wide), whose rims are closed spline edges; booleans that leave slivers ten tolerances thick; and bodies of 1e-5 at (2, 3, 5). There the comparison is three-way and per body: ours against a closed form or an integral written out in the test (50 bodies per scale), FreeCAD's solid against our body one by one (`harness::Part`: a peg is not measured against the ball it ends on), and FreeCAD's mesh module reading the STL and 3MF exports of the same documents (closed, our triangle count, our volume within the chordal tolerance times the area, our box).
- `crates/engine/tests/step_freecad.rs` › `freecad_reads_revolved_and_closed_splines` (2026-10-14): a hollow vase turned a full turn and a third of one, a closed spline extruded and turned, a polyline turned, at 1e-3, 1 and 1e6: FreeCAD 1.1 calls all fifteen valid with our counts of faces, edges, vertices and shells and adds no seam; the volume of the geometry it imported, by quadrature, is ours to 4e-14 (its own volume of these solids is up to 4.2e-4 off, as for every solid with spline-bounded faces; the polyline's is exact to 1e-15).

What is asked: FreeCAD calls the shape and every solid valid; it finds as many solids as we have lumps, as many faces and shells as we have, never fewer edges (beyond the seams and poles it adds) or vertices; every shell is closed; volume, area and centre of mass agree with ours (`mass_properties`, or the closed form where the test kit has one); the names arrive. Bounding boxes are compared as far as they can be: FreeCAD's box is not tight for a curved face, and for a torus it is not a bounding box at all (measured: a z extent of ±2.302 where the exact one is ±2.342), so the boxes must agree for flat-faced bodies, FreeCAD's must contain ours where ours is tight, and tori are not compared.

*The bound.* 1e-7 relative on volume and area (and ten times that, of the body's size, on the centre) wherever FreeCAD has nothing to approximate; as measured it is then within 1e-14, at every scale. Two situations are held to 1e-4 instead, each with what was measured and why it is the reader's doing and not the file's (`APPROXIMATED` in the harness, `ZONE` in the engine test): an edge that is not a line in the parameter plane of its face (an ellipse on a cylinder: FreeCAD makes its own parameter-space curve on import and comes back up to 7e-6 off, independently of scale and of the uncertainty we declare, while it measures the same solid built with its own primitives to 3e-9), and a zone of a sphere between two circles (FreeCAD adds a meridian from pole to pole as a third wire and measures the face 7.6e-6 short). A third, a rational spline with full-multiplicity interior knots (the nine-point circle), is compared at 2e-2 with the closed form: FreeCAD's area of a flat face bounded by such a curve is off by 1.8e-4, and so is `mass_properties` (2.4e-3 on the volume; a weakness of ours, reported); the rational one-span quarter cylinder is the precise check of rational splines (4e-11).

*What it found.* The mapping passed on its first run except for the test's own expectations. Bodies with a zone of a sphere do not tessellate (`document.inspect` gives them no bounding box), which the STEP check does not need and so brought to light.

*What the second set found (2026-10-14).* No defect of ours: every body agrees with its closed form to 1e-9 (to 1e-7 where an edge is a spline within the tolerance of the exact curve: 3.6e-9 measured for a peg ending on a ball off its axis), and FreeCAD reads every file as valid closed solids with our counts, and with our volume and area to 1e-11 or better where it has nothing to approximate. Where the two kernels differ, the closed forms side with ours: FreeCAD is 1.4e-5 off for the peg under the ball, 6.3e-7 for the pillar, 1.3e-6 for a post cut by an inclined plane (all edges that are no line in a parameter plane, `APPROXIMATED`). Three limits of the reader were measured and are held in the test with their evidence; a fourth thing, listed as a limit on 2026-10-13, was the making of our file and is gone (3). (1) Its own volume of a solid with plane faces bounded by a spline of several spans is rougher than was known: 1.8e-3 short for the housing's base (a cubic of four spans), 1.04e-3 for the housing, while the quadrature over the geometry it imported gives our volume to 1e-14 and its centre of mass lies 6.7e-5 mm off the housing's plane of symmetry; of a face bounded by one-span splines (the impeller's blades) its volume is ours to 1e-15. (2) It takes points closer than 1e-7 mm for one, whatever the file's uncertainty: a sliver or a body of 1e-8 mm (the scale 1e-3) comes back with 4 of its 8 vertices, or as no solid; the same numbers in a document in metres are read right. (3) *Not a limit of the reader, and fixed in the writer on 2026-10-14.* The housing was valid at the scales 1e-3 and 1 and "self-intersecting" from 1e3 up, with every edge within our tolerance of its surface and the same measures at every scale. Changing one thing at a time in the file's text showed what FreeCAD's answer follows: not the uncertainty, not the size of the body (the file of the scale 1 declared in kilometres is valid), not the absence of parameter-space curves (written by hand, they change nothing: FreeCAD makes its own), but the knots of the closed spline edges round the oil holes, which the kernel parametrises by length, so that they grow with the model. The writer now puts the knots of every spline curve on the interval from 0 to 1 ([`file-formats.md`](file-formats.md) › *What a reader made of the knots* has the table of experiments and the counts: 58 of 312 sleeves with an oil hole invalid before, none after); the housing is valid at the three scales, and four of those sleeves are in the test at the three scales, each held to its closed form (ours to 2e-10, FreeCAD's to 2e-6 of ours). (4) Its mesh module sums a volume in 32-bit floats from the corners as they are, so the volume of a body far smaller than its distance from the origin is noise (1.9e-6 for a block of 1e-15 at (2, 3, 5)); what is left to compare there is that the mesh is closed, its triangle count and its box.

*What FreeCAD can and cannot tell.* 33 breakages were seeded in the mapping and the writer (2026-10-13); every one fails a pinned test that needs no FreeCAD. Of the 26 that leave a readable file, FreeCAD notices 17: a flipped `same_sense` of a face or an edge, a flipped oriented edge or bound, swapped edge vertices (each in only 7 to 16 of the 100 files: it reorients the rest), a wrong unit factor, a cone's angle or axis, swapped torus radii, a missing uncertainty, a reference off by one, swapped placement axes, degrees written as radians, a transposed control net, dropped weights. It accepts 9 without a word, with the same numbers: an outer bound that is not typed or not first, an uncertainty a thousand times too large, a cavity's shell with orientation `.T.` or with its faces not turned over, a cavity given to the wrong lump, no vertex loop at a cone's apex, an ellipse with the shorter semi-axis first, a vertex loop off its surface. Those nine conventions are held by the pinned tests and by the reading of the standard alone.

**DXF and SVG (2026-10-13)** is the fourth use: FreeCAD imports the flat outlines `file.export` writes for a sketch or a face and reports the edges it got, the closed wires they sort into and the area inside (`crates/drawing/tests/freecad.rs` for the writers: a plate in three units and at three scales, ellipses, splines; `crates/engine/tests/drawing_freecad.rs` for documents built by commands: a plate's sketch, top and bottom in mm and inches, and the slanted cut of a cylinder; one script, `crates/drawing/tests/drawing_report.py`; both run by `cargo xtask freecad` in a few seconds). Length, area, bounding box and the number of closed wires must agree with ours and with the closed forms to 1e-9. What FreeCAD cannot tell here, and what was measured, is in [`file-formats.md`](file-formats.md) › Flat outlines: its DXF reader ignores the parameters of an elliptic arc, and its area of a face bounded by a B-spline is rough.

*Beyond 1e6 (2026-10-14, measured once, not in the suite).* With the largest scale of the three STEP tests set to 1e7 instead of 1e6 (the document's tolerance 10 mm), FreeCAD reads every kernel body and domed boolean of that scale and 142 of its 160 command documents as before, the housing and the oil holes among them; 18 fail, for two reasons that are the reader's, each shown by editing the file's text. (a) Seventeen have a cone with its apex: with an uncertainty of 10 mm declared FreeCAD loses the conical face (volume 0), with 5 mm or less in the same file it reads the cone right (and a turned cone to 1e-14 with 1 mm, 1.3e-4 off with 5 mm): it takes our uncertainty for its own tolerance at the apex. (b) The impeller's rim is a cylinder of radius 6e8 mm, and FreeCAD's own seam fails on a cylinder of a radius above some 4.5e8 mm whatever its height (4e8: valid; 5.4e8: two invalid faces where one was written), which a seam edge written by hand in the same file cures and parameter-space curves written by hand do not. At 1e9 that radius rule takes every face that goes round a cylinder, cone, sphere or torus with it (95 of the 160 command documents of that scale; the flat-faced ones and the domed booleans are read right), and the kernel bodies of `crates/io/tests/step_freecad.rs` cannot be exported at all, because that test checks them with a tolerance of 1e-6 at every scale and rounding at 1e9 is larger. Neither is asked of the suite: 3DCraft is tested from 1e-3 to 1e6.

What this oracle cannot do: FreeCAD repairs what it reads (it adds seams, poles and parameter-space curves, and reorients), so a file it accepts is not proven to follow the standard, only to be understood by one widely used reader. It says nothing about readers built on other kernels.

**The boolean corpus** is the second use: what a mature kernel answers for the same inputs. `crates/kernel/tests/fixtures/boolean_corpus.json` pins 3996 pairs of solids with FreeCAD's volume, area, centre of mass, bounding box and number of solids and shells for their common, cut and fuse: the five primitives (block, cylinder, cone, sphere, torus) and the domed block of the test kit (`trimmed::domed_block`: a block under a bicubic Bézier roof over a regular 4 × 4 net with heights between 0.7 and 1.3 of its own, without symmetry) in two representations, `dome` with the roof as a Bézier patch and `spline` with the same patch as a NURBS surface, so that every one of the 28 kind pairs is covered (2026-10-13: 1871 cases with a domed block, every one refused today, the baseline the freeform work starts from). The generator builds the dome from its definition (the Bernstein polynomials written out; the volume is the floor times the mean of the net's heights, the area a composite Gauss–Legendre quadrature that three rules agree on to 1e-14) and FreeCAD from `Part.BezierSurface` and `Part.BSplineSurface` under four planar walls that share the roof's edges. The cases are generated from a seed by `cargo xtask boolean-corpus` (`xtask/src/boolean_corpus/`, which uses no 3DCraft crate) in nine categories: `general` position, `parallel` axes, `coaxial`, `flush` (coincident faces: post on a plate, a cutter flush with a face, equal radii, the same solid twice), `tangent` (a cylinder lying on a plane, kissing spheres, a ball in a hole of its own radius), `contact` along an edge or at a vertex only, `inside`, `apart`, and `near` (a contact that is off by 10, 1 or 0.1 tolerances either way, next to the exact contact). Two cases in five are at scale 1e-3 or 1e6. FreeCAD is run at scale 1 and its numbers are scaled in the test, because its own tolerance is fixed at 1e-7. A domed block offers its floor, its walls, its straight edges and its eight corners as places like a block does (a roof corner's supporting plane leans by less than the roof climbs away from it), and a point of its roof with the roof's tangent plane; that plane is no supporting plane (the roof has no point whose tangent plane clears its other bumps), so a contact on the roof is tangent there and may overlap elsewhere: the construction expects nothing of it, and the `apart` category does not pull solids off the roof. The roof's own edges, splines, are no place.

A reference that is wrong is worse than none, and FreeCAD does get cases wrong, so an answer becomes a reference only when it survives every check that needs no kernel of ours: `isValid()` on all three results, the volume identities of oracle 3 among FreeCAD's own three results, the area identity where nothing is coincident, the common volume against 20 000 sampled points tested with the primitives' defining inequalities, and what the construction says (apart, one inside the other, the same solid). A reference is `exact` when the identities hold to 1e-9, `approximate` up to 1e-4 (FreeCAD integrates numerically and approximates most curved intersection curves by splines), and otherwise `unreliable` with the reason: 57 cases as pinned. Among the primitives (22): commons of 12.5 where the solids are apart and of 0 where they overlap, both called valid. Among the domed blocks (35): a face against the roof, quarter-turned and off by a few tolerances (`near`), where FreeCAD's three results disagree by 1e-4 to 1.3e-3 of the operands (24 cases, and 6 `tangent` ones up to 8.5e-3); three tangent contacts of a torus or a roof on a roof whose common FreeCAD gives as empty where sampled points say 0.13 to 0.72; two fuses of a cylinder's end on a roof it calls invalid.

`crates/kernel/tests/boolean_corpus.rs` needs no FreeCAD. It builds each pair with `kernel::primitives` (the domed block with the test kit's `trimmed::domed_block`), first holds our mass properties of A and B to FreeCAD's at 1e-9 (so the mapping between the two builders is itself checked; the area of a domed block at 1e-5, because FreeCAD's area of a spline face is a numerical integral it does not take to convergence: 6.7e-6 off at worst on the corpus, 9.5e-7 on the dome 2 × 1.5 × 2.5 where our quadrature and `mass_properties` agree, while its volume and centroid of the same solids are exact; the generator prints the worst deviation of a run), runs the three booleans and compares volume, area, centroid and shell count. The bound is 1e-7 of the result plus terms that are each an error the *reference* is measured or known to have (four times its identity residual; FreeCAD's tolerance times the area where an edge is a spline; the gap times the area where a `near` case is off by no more than the tolerance); the comment at `Bounds` derives them. Outcomes are `match`, `match~` (against an `approximate` reference), `empty`, `unsupported` with the kernel's reason, `unscored` (unreliable reference), and `MISMATCH` and `INVALID`, which fail the test. The count of agreeing outcomes may not drop below `AGREEING_FLOOR`; known mismatches would be listed in `KNOWN_MISMATCHES` (empty today). The table per category and kind pair goes to `target/evidence/booleans/corpus-score.txt`. `BOOLEAN_CORPUS_CASE=<part of an id>` (with `--nocapture`: every number) and `BOOLEAN_CORPUS_CATEGORY=<name>` narrow the run. `BOOLEAN_CORPUS_VERBOSE=1` prints every case of a run.

### Oracle 9: no body passes through itself

`topo::check` (oracle 2) looks at how a body hangs together, not at whether two of its faces pass through each other or two of its shells overlap: `topo::merge` of two overlapping blocks passes it. `tess::body_self_intersections` looks, on the mesh and without the kernel's help ([`architecture.md`](architecture.md) §5.2 and §6), and every body an operation returns must come out of it without a *certain* finding (`SelfCheck::is_clean`).

What "certain" means is stated, not tuned. The mesh of a face is within the chordal tolerance `c` of the face (0 for a plane bounded by straight edges, whose mesh is the face), and the face is within the modelling tolerance `t` of its geometry, so the meshes of two faces that only touch can go through each other by `c + c + 2t` at most. The depth of a crossing is how far either surface could be moved along its own normal without undoing it, measured on the mesh; deeper than that margin, the faces themselves cross. Two flat faces within `2t` of one plane that share area lie on each other, which is a finding however they face. What stays within the margin after two refinements of the mesh (four times finer each) is reported as marginal: contact, or an overlap too shallow to tell from it.

In place (`crates/testkit/tests/self_intersection.rs`, there because `kernel` and `tess` share a layer). Without any finding, certain or marginal: the fourteen reference solids and the pipe elbow, the primitives, extrusions with holes and tangent faces, moved, mirrored and merged bodies, every boolean of the scenarios of `crates/kernel/tests/boolean.rs` along the axes and turned (1098 bodies) and of a seeded random run with the generator of oracle 3 (1578 bodies in the test run; 39 834 in the long run, `cargo test --release -p craft3d-testkit --test self_intersection -- --ignored --nocapture random_booleans_long_run`, about two minutes). `SELF_PAIR="seed placement scale"` with the ignored test `one_pair` reproduces one pair and prints its faces. Seeded defects that must be caught, at scales 1e-3, 1 and 1e6, along the axes and tilted: a face pushed through the opposite face and through a neighbour, shells that overlap partly (block, cylinder, sphere, torus), a shell wholly inside another, a cavity outside every shell or inside another cavity, a body inside out, faces lying on each other facing the same way and facing each other, a crossing three tolerances deep where one tolerance deep is within the margin, and spheres overlapping by eight chords where a chord and a half is within it. The search itself (`crates/tess/tests/self_intersections.rs`) is held to a brute-force search with plain arithmetic on random triangles, to the same answer on any number of threads, and to the known crossings of the Utah teapot (handle and spout go into the body). The detector was checked by seeding breakages into it one at a time (a predicate sign, neighbours not recognised, a hierarchy that prunes too much, the margin ignored, the winding rule off by one, ...); when a new kind of mistake becomes possible, seed it and see that a test fails.

What it cannot see, so that a clean result is not read as more than it is:

- **Shallow overlaps of curved faces.** After the refinements the chordal tolerance is 1/16000 of the body's diagonal; an overlap of curved faces shallower than about six times that (four in most places) stays marginal.
- **Curved faces lying on each other.** A pin in a hole of its own size that is not united with it is caught when both happen to be meshed alike (their triangles are then in one plane exactly, which no approximation brings about) and is only marginal when the pin is turned about its axis.
- **Flat faces closer than twice the modelling tolerance** count as lying on each other: a wall thinner than that is reported as an overlap. The kernel refuses to make one.
- **Contact without overlap** (shells touching along an edge or in a point, a vertex on a face) is a marginal finding at most; `topo::check` and the boolean's own refusals cover results that are not manifolds, with one stated allowance: a solid whose skin is pinched in a single point (a profile standing on the axis of a full revolution with one corner) passes `topo::check`, because nothing in how the body hangs together shows it (`crates/topo/tests/genus.rs`).
- **Anything the tessellator cannot mesh** is an error, not a verdict; the check tries finer meshes before giving up. (Until 2026-10-13 a face narrower than the chordal tolerance was such a case: the polygon of a curved edge crossed its neighbour. The tessellator now samples the edge finer there, [`architecture.md`](architecture.md) §6, held to oracle 4 at forty tolerances in `crates/tess/tests/near_edges.rs`.)

A long test made of independent cases (every command with every adversarial value, seeded random pairs, every kind pair) runs them on every core through `craft3d_testkit::parallel::map_parallel` rather than one after the other: each case has its own seed or its own directory, the results come back in the order of the inputs, and a panic in one case fails the test with its own message. Keep a case independent of the others and of the order they run in, or it does not belong in such a test.

## The topological naming suite

Because stable references are the property most likely to rot silently, they get a dedicated suite (version 1 since M6: `crates/engine/tests/naming.rs`, with a sketch on a face and a boss extruded from it as the downstream feature; the scenario with a cut waits for booleans). Each scenario builds a model, attaches a downstream feature to a face or edge, edits something upstream, and asserts the downstream feature still refers to the entity a human would expect, or fails with `Missing` (never silently moves). Scenarios: change an extrude distance; add a sketch entity before the referenced one; reorder two independent features; split a referenced face with a cut; delete the feature that made the referenced edge. The face an extrusion ends on (`upTo`) is such a reference too, with its own scenarios in `crates/engine/tests/extrude_ends.rs`: the face moves and the end moves with it; the face sinks into a union and the extrusion fails with the name it lost while every other feature is built; the feature that makes the face is suppressed, deleted or moved after the extrusion; the reference is repaired by pointing it at a face that is there.

## Chamfers

The first blend (2026-10-14, M9) is held to four things that owe nothing to its own code.

- **Closed forms** (`crates/kernel/tests/chamfer.rs`, `crates/engine/tests/chamfer.rs`; scales 1e-3, 1 and 1e6, the kernel's also in tilted frames): a prism per straight edge (half the product of the two distances and the sine of the angle between the faces, times the length), Pappus for a rim (the triangle's area times the turn of its centroid), inclusion and exclusion where chamfers meet (two share ∫(d₁ - y)(d₂ - y) dy, three share d³/4, the corner face takes d³/12 more), and for a flat edge that ends in a spline wall an integral over the spline written out in the test.
- **A convex solid from its planes** (`convex_volume` in the kernel's test): the volume of what a list of half-spaces leaves, from the corners three planes share and a fan per face. It knows nothing of edges or tools, so it checks mitres with unequal distances, hexagonal prisms and corners through three points, and it is the oracle of the seeded random run: 120 blocks of random sizes with random sets of edges chamfered by a distance each, all built and all of the oracle's volume.
- **A reference kernel on the same operation.** OpenCascade's own chamfer (FreeCAD's `makeChamfer`) on a 4 × 3 × 2 block: all twelve edges, three at a corner and two give our volume, area and counts. That is where the corner rule comes from (observed behaviour, architecture §5.3).
- **A reference kernel on our result.** FreeCAD reads the STEP export of 18 chamfered bodies as valid solids of our volume, area and centre to 1e-15 (`crates/engine/tests/step_freecad/chamfers.rs`, part of `cargo xtask freecad`).

Every body is also run through `document.check` with `deep` in the engine's tests, and the chamfer's `edges` is a row of the failed-features table below.

## Fillets

The second blend (2026-10-14, M9) is held to the same four things as the chamfer, and to a fifth: tangency.

- **Closed forms** (`crates/kernel/tests/fillet.rs`, `crates/engine/tests/fillet.rs`; scales 1e-3, 1 and 1e6, the kernel's also in tilted frames; volume and area to 1e-9): per straight edge the kite between the two tangent lengths less the sector of the ball, r²·(cot(θ/2) − (π − θ)/2) for the angle θ between the faces (60°, 90° and 120°), times the length; Pappus for a rim (kite and sector each at its own centroid, for a square corner and for the base of a cone); two rounds that meet share ∫ w(y)² dy = (5/3 − π/2)·r³ with w the round's width at depth y; three leave an eighth of the ball in the corner's cube; a block or a prism with every edge rounded is the smaller solid grown by a ball (Steiner: V′ + A′·r + M′·r² + 4πr³/3, M′ half the sum of edge length times outer angle), which covers the corners that are not square.
- **The definition, by points** (`assert_matches_definition`): a point is in the rounded body when it is in the solid and no further than r from the solid's faces moved inwards by r (the union of the balls that fit). The distance is worked out in the test from the planes alone; the body is asked through `boolean::contains_points`, which owes nothing to the fillet or to `mass_properties`. 600 seeded points around a corner per case: the three edges of a block's corner, all twelve, the hexagonal prism's corner alone and with all eighteen edges. The eighth of a ball is also counted on a grid from that definition and held to its closed form.
- **Seeded random sets of edges** of 60 random blocks with one radius each: all built, all of the volume by strips and corners (162 corners with a ball and 129 pairs that run out into each other).
- **Tangency**, measured in the tests from the surfaces (nine points per seam, the outward normals of both faces at the point of each nearest it): the sine of the angle between them is at most 4e-15 over 1276 seams, held to 1e-9. The kernel holds its own result to the same (five points per seam) and returns an error otherwise.
- **A reference kernel on the same operation.** OpenCascade's own fillet (FreeCAD's `makeFillet`) on a 4 × 3 × 2 block: one edge, three at a corner and all twelve give our volume and area to 1e-16 and our faces and vertices; two that meet give our volume to 1e-11. Its edge counts are higher by one per sphere (a seam). The script and its output are in `target/scratch-fillet/` (`corner.py`, `freecad-makefillet.txt`); it is not part of `cargo xtask freecad`.
- **A reference kernel on our result.** FreeCAD reads the STEP export of 24 filleted bodies as valid solids of our volume, area and centre (1e-15 for cylinders and tori, 2e-9 where there are spheres), with our counts (`crates/engine/tests/step_freecad/fillets.rs`, part of `cargo xtask freecad`).

Every body is also run through `document.check` with `deep` in the engine's tests, and the fillet's `edges` is a row of the failed-features table below. The one configuration the boolean kernel refused on the way (a cylinder that goes on in a torus) is built since 2026-10-14 and held to closed forms at three scales (`a_cylinder_that_goes_on_in_a_torus_touches_it_along_their_border`; it was the ignored reproducer).

## Failed features

`crates/engine/tests/failed_features.rs` (2026-10-14, M8.5) holds every reference a feature can hold to one set of promises ([`architecture.md`](architecture.md) §4, *A feature that fails*). A table of 28 references (the edges of a chamfer since M9; a sketch on a face and on a datum plane; the sketch and the `upTo` face of an extrusion; the sketch and the datum axis of a revolution; the source of a transform, a mirror and a pattern; the datum plane of a mirror and the datum axis of a pattern; target and tool of a boolean; every way a datum plane, axis and point is placed) is run against four ways of breaking what is referred to (delete, suppress, move after, make it fail by deleting its variable), plus rolling back before it, redrawing the line a face was named after, and geometry that no longer fits. What is asserted:

- the reason starts with the parameter and names the feature and the names it lost; what is made from the failed feature fails naming it; `causedBy` is the feature to fix; `document.inspect` and `document.check` agree;
- **every feature that did not fail is what it is without the failed ones:** the failed features are deleted from a copy of the session and every remaining feature and body must be equal (status, parameters, volume, area, centroid, counts, names, who took which body). This is a second computation, not a reading of the first;
- **a repair gives the document built that way from the start:** the reference is pointed at another entity by a command and the document is compared with one in which the feature was added with that reference in the first place;
- **rolled back, the document is the one that ends at the marker** (the later features are deleted from a copy and the rest compared), for every position of the marker; **moved, the features that fail are those out of order** according to a dependency table written down in the test from the description of the part, for each of sixteen features in each position;
- undo and redo restore exactly; saved and opened in a new session the document is the same; and after every command incremental regeneration equals a full one.

A seeded random walk (16 seeds of 160 steps over a part of sixteen features: deletes, suppressions, moves, rollbacks, variables, dimensions, and every repair command pointed at random entities, some of which exist) asserts all of the above after every step. `WALK="seed steps"` with the ignored test `one_walk` reproduces one seed and prints its commands. Seeded breakages that the suite was seen to catch: a failed feature that still takes its source's body (7 tests fail), a cache that ignores that an input was rebuilt (9 tests fail). The wording of the reasons has no oracle but these tests: for the wording they are regression tests. The comparisons leave out `bbox`: `document.inspect` takes it from a mesh whose tolerance follows the size of the whole model, so the box of a curved body moves in its last digits when another body comes or goes.
**Edges and vertices (2026-10-14, `crates/engine/tests/naming_entities.rs`, 14 tests; `regen/src/entity.rs` and `regen/tests/merged_names.rs` for the parts below the commands).** The consumer is a datum point at a vertex, whose position says where a name ended up; edges are followed through `document.edges`. (a) *Complete and unique:* on the five primitives, eight sweeps (a bar, a plate with a hole, two arcs and two splines that share both ends, a ring, a quarter ring, a bowl on the axis, a post up to a tilted face), nine single booleans (flush and overlapping unions, a hole, a slot that cuts faces in two, a round notch across an edge, an intersection, a pocket with coincident faces, a cylinder cut in half lengthwise and a groove round, the two with numbered names), two and three booleans in a row, a transform, a mirror, patterns that stay apart and patterns that are joined (end to end, overlapping, round an axis): as many names as edges and vertices, no two entities answering to one name (aliases included), an edge named by its faces listing the faces on its sides, a datum point at every vertex name lying on that vertex, and every edge found by `document.edges` between its two faces. (b) *Stable:* nine edits of the sizes of a part with three booleans, at three scales, leave the record of every name (curve, faces, the names of the end vertices, the edges ending in a vertex, aliases) identical, and ten corners where a closed form says they must be. (c) *Removed:* exactly the references to what an edit removed fail, with the name, and are repaired by undoing the edit. (d) *Independent* of the scale (1e-3, 1, 1e6), of four threads building the same models at once (nothing in regeneration is parallel today, so this pins the absence of shared state, not a merge order), of unrelated features moved through the history, and (in `regen`) of the order of the entities in the body. (e) *Saved and reopened:* the same names, the same datum points, the same bytes when saved again. The limits are tests too: the numbered names that swap when the whole configuration is turned, the bare name a second edge between the same faces takes away, the two circles of a groove, and the numbered edges of a lens that still answer to the names the sweep gave them. Print the names of a body with `CRAFT3D_SHOW_NAMES=1` (or the name of one body) and `--nocapture`.

## Corpora

Real files are useful oracles but are large binaries, so they never go into this repository. When we adopt a corpus (for example public STEP test models for import, M10) it follows PhotoCraft's rules: fetched into `corpus/` (gitignored) at a pinned revision, verified against a committed sha256 manifest, tests behind a `corpus` cargo feature that fails loudly when the corpus is missing, and each file's licence checked and recorded before the pin is added.

## Evidence the developer can see

A test that renders writes its images under `target/evidence/<crate>/<test>/` (actual, expected, diff). Agents report the paths of the images worth looking at, and for a milestone demo leave a short script the developer can replay ([`development.md`](development.md) › Watching along).

## Performance tests

Benchmarks (criterion or simple timed examples) start with the first heavy algorithm: tessellation of a body with thousands of faces, a boolean between two such bodies, full and incremental regeneration of a 100-feature history. Numbers are recorded in the dev log with the machine and its load. Budgets and a generated scorecard follow PhotoCraft's model once there is a baseline (M4+).


## Geometry: intersections (`crates/geom/tests/`)

What holds `geom::intersect` to its contract, as built (2026-10-13):

- **On both surfaces.** Every returned curve is sampled at 241 places; each sample is within the curve's stated `deviation` of both surfaces by their own `project`, inside the box, and the `tangent` flag agrees with the angle between the normals (`common::check_meeting`).
- **Closed forms against independent formulas** at scales 1e-3, 1 and 1e6: radius and centre of plane/sphere and sphere/sphere circles (Pythagoras, Heron), eccentricity of plane/cone ellipses, the hyperbola's equation in the cone's frame, circles about a shared axis from the profiles, the semi-axes of the ellipses of equal crossing cylinders (`meet_exact.rs`).
- **Contact along a curve in closed form** (2026-10-14, `meet_exact.rs`): a cylinder that goes on in a torus (three sizes, three scales: the second curve held to `x² = 4 R y` and `y² + z² = r²` in the frame at the place of contact, the circle to its plane), cones tangent along a ruling (three pairs of half-angles, the axes to either side of the tangent plane and along the ruling either way: 144 pairs per scale, 36 of them with a conic and the ruling cut where it crosses) and cones with one apex (two rulings, one, the apex alone; from outside and from inside). Nothing is missing: the first surface is walked along a grid of circles, and every place where the second surface's own equation changes sign must lie on a returned curve; curves meet only at their ends.
- **A crossing the surfaces are a little apart at, wherever it lies** (2026-10-14, `meet_numeric.rs` › `a_crossing_a_little_apart_is_four_arms_wherever_it_lies`): 24 seeded places per scale, a tenth and three tenths of a tolerance apart either way: four arms, each with one end on the point, none drawn twice.
- **The marcher against the closed forms** (`meet_surfaces_numeric`, a test-only entry point that skips them): the same number of branches, along the exact curves, of the same length (`meet_numeric.rs`).
- **Known curves**: two closed quartics of unequal crossing cylinders, Viviani's curve, Villarceau circles, each against its parametrisation; Bézier and NURBS patches and the teapot's 32 patches against root finding along iso-lines (`meet_shapes.rs`, `meet_teapot.rs`).
- **Completeness on random pairs** of all 28 combinations of kinds (own SplitMix64, no dependency): one surface is sampled on a grid, the sign of the distance to the other is taken at every node from formulas in the test, and every change of sign must lie by a returned curve and every returned curve by changes of sign. The test prints, per pair, how many cases crossed, were apart and were refused (with the reason) and the slowest (`meet_random.rs`, `--nocapture`).
- **Curve/surface**: every hit list against a brute-force search for sign changes along the curve, for fixed cases and for random pairs of all 4 x 7 kinds (`curve_surface.rs`).
- **Determinism and symmetry**: the same call twice and with the surfaces swapped gives equal results (`==` on the values, so bit for bit). **Hostile input** (empty or unbounded box, bad tolerances, collapsed patches, surfaces tangent along a line, a line lying on a patch for a stretch) is an error or a plain answer within a time limit.

A curve near a point where the surfaces are tangent is well defined across both surfaces but not along them: a point within the tolerance of both can be much further from the exact curve there. Tests compare positions with the exact curve only as tightly as that allows.
