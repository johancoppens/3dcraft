# 3DCraft architecture

> **Last updated:** 2026-10-14 · **Status:** design plan v1; first crates built · **Change:** minor (chamfers: the first blend and the first consumer of edge references; revolved splines, closed splines and splines with corners in profiles)

## Current state (2026-10-12)

What exists on `main` today; where the code differs from the plan below, this summary wins.

- **Workspace:** 22 library crates (the 20 of the plan plus `zipstore` and `drawing`), all registered in `xtask/src/layers.rs`. With code: `math`, `geom`, `topo`, `expr`, `doc`, `ops`, `solve`, `kernel`, `tess`, `regen`, `render`, `zipstore`, `meshio`, `step`, `drawing`, `format`, `io`, `engine`, `automation`, `testkit`, `gpu`. `apps/craft3d-cli` is the headless CLI and `apps/craft3d` the desktop app. `xtask` has `layers` (layering and lint opt-in), `wasm`, `ci`, `stats` and `freecad`.
- **The one path works end to end** for primitive solids: command → document → regeneration → B-rep (checked) → tessellation → render or mesh file, and FreeCAD reads the result as a closed solid of the right volume.
- **Maths:** `math` has `Vec3`, `Bbox3`, `Frame` (placement of analytic geometry), `Transform` (affine, with inverse), `Tolerance` (linear and angular, as data) and Gauss–Legendre quadrature. Not built: robust orientation predicates (first needed by booleans, M7), intervals, root finding.
- **Geometry:** `geom` has the `Curve3` enum (line, circle, ellipse, NURBS) and the `Surface` enum (plane, cylinder, cone, sphere, torus, Bézier patch, NURBS), each with evaluation, first derivatives, parameter domain and periodicity, normals, and closest-point projection (closed form for the analytic kinds, sampled Newton / Gauss–Newton for ellipses and freeform). NURBS are de Boor on homogeneous points with hodograph derivatives. Not built: 2D parameter-space curves, trimmed and offset curves, extrusion/revolution/offset surfaces, second derivatives. `geom::intersect` intersects every pair of surface kinds (`meet_surfaces`, inside a box) and every curve kind with every surface kind (`intersect_curve_surface`): in closed form where one exists, numerically otherwise, within the tolerance or an error (§5.1 › Intersections as built).
- **Topology:** `topo` has the B-rep (`Body` with vertices, edges, loops of coedges, faces, shells), the validity checker `check` (references, finite numbers, vertices on edges, closed loops, edges on their faces' surfaces, each edge of a solid used once each way, Euler–Poincaré with genus) and `mass_properties` (area, volume, centroid by boundary integrals over the exact geometry). Fourteen reference solids (six primitives and hemisphere, and eight with trimmed faces: holes, half walls, a spherical cap, a frustum, an ellipse edge, Bézier and NURBS roofs) match their closed forms at three scales and in tilted frames. `mass_properties` also measures the faces a revolution makes: torus faces bounded around the tube, around the axis or both (the surface is closed both ways, so the boundary integral is right only up to a whole number of times the entire torus, which the area settles), and faces whose boundary passes through a pole of a sphere or the apex of a cone (the point stands for a stretch of the edge of the parameter range, which is added). It still refuses, rather than gets wrong, a boundary through a collapsed edge of a Bézier or NURBS surface, a boundary that winds around an axis more than once, torus loops that wind around the axis and the tube at once, and a boundary that turns back on itself at a pole. Deviations from the plan below: parameter-space curves are not stored (recovered by projection), no per-entity tolerances, no persistent names yet (M6), no inertia tensor, and the checker does not test self-intersection or that each face is bounded by its loops.
- **Expressions:** `expr` has dimensions (length and angle exponents) and units (`um mm cm m in ft`, `deg rad`), a parser and evaluator for formula text (`+ - * / ^`, functions, `pi`, variables, a unit after a number), and `VariableTable` (deterministic evaluation order, cycle detection, partial failure, rename that rewrites references). Source length, nesting depth and table size are capped. Not built: printing an expression back to text, storing the evaluation order (computed on demand; storing it is `doc`/`format`'s job).
- **Document:** `doc` has `Document` (units, tolerance, variables, ordered features, rollback marker, next feature id), features `Block`, `Cylinder`, `Sphere`, `Cone`, `Torus` whose parameters are expressions kept as source text, an `Orientation` (axis and angle) on all but the sphere, stable never-reused feature ids, and `validate()`. Sketches are features too (`doc::sketch`): a plane (a world plane with an offset), point, line, circle, arc and (2026-10-13) spline entities with ids that are never reused, sixteen kinds of constraint in the order they were added, and the last solution as the stored coordinates. Not built: the other feature kinds, references between features.
- **Sketch solver:** `solve` takes a sketch as plain numbers (points, lines, circles, arcs; constraints with evaluated values) and returns solved coordinates, the degrees of freedom left, and per constraint whether it is satisfied, redundant or conflicting (the later constraint is blamed). Newton-type with minimum-norm steps from the given start, so a solved sketch does not move and a free part moves as little as possible; every loop is capped. It knows nothing about the document: `regen` maps one onto the other.
- **Undo:** `ops::History` keeps snapshots (`Arc<Document>`) rather than reversible ops: an edit is applied to a copy and becomes one labelled step only if it succeeds and changes something.
- **Kernel:** `kernel::primitives` builds block, cylinder, cone, sphere and torus as B-rep. `kernel::profile` finds the closed regions of a set of 2D curves (loops of lines, arcs and, since 2026-10-13, splines joined end to end, circles; even-odd nesting gives holes and islands; open, branching, crossing or touching curves are errors that name them). `kernel::extrude` sweeps profiles along a plane's normal into one solid with a shell per profile, checked before it is returned, and reports for every face, edge and vertex where it came from (`Origins`). `kernel::extrude_to` (2026-10-13) ends an extrusion on the surface of a face instead (§4.1 › *Extrude ends*). `kernel::boolean` is the union, difference and intersection of two solids whose faces are planes and cylinders (edges: lines, circles, ellipses), with coincident faces and smooth edges handled, and a source for every face, edge and vertex of the result; everything else is `KernelError::Unsupported` with the faces and the reason (§5.3 › Booleans as built). It rests on `geom::intersect`: closed-form intersections of planes and cylinders with each other and with lines, circles and ellipses. `kernel::revolve` turns profiles about an axis in their plane through a full turn or part of one (a line sweeps a plane, a cylinder or a cone, an arc a sphere or a torus; a curve on the axis sweeps nothing) and reports origins in the same roles as an extrusion; a profile that crosses the axis and an arc that would sweep a spindle torus are errors that name the curves. `kernel::chamfer` (2026-10-14) replaces edges of a solid by faces: straight edges between planes and circular edges (whole or part) between a plane, a cylinder or a cone about the circle's axis, with one distance, two, or a distance and an angle, chains of tangent edges, mitres and flat corners where chamfers meet (§5.3 › *Chamfers as built*). Since 2026-10-14 a spline is revolved too (a rational B-spline surface of revolution, a full turn in two halves), a spline that closes on itself is a profile on its own and a spline with corners (a polyline) is one as well, each cut into pieces that sweep one face each (§4.1 › *Revolved splines, closed splines and corners*).
- **Regeneration:** `regen::regenerate` evaluates variables and builds each feature's body, with a status per feature (`Ok`, `Suppressed`, `RolledBack`, `Failed(reason)`); every body is run through `topo::check`. A bare number in a length parameter is taken in the document's unit. A sketch feature has no body: its result is the solved sketch (degrees of freedom, a state per constraint, solved coordinates, its frame in space), and `regen::settle_sketches` writes a solution back into the document, which the engine does at the end of every edit. No caching: a full rebuild per document revision, every sketch solved again.
- **Tessellation:** two entry points. `tessellate_patches` meshes untrimmed Bézier patches on one uniform grid (the teapot). `tessellate_body` meshes any B-rep body edges first: every edge (line, circle, ellipse, NURBS) becomes points once, within the chordal tolerance, and every face that uses it uses those points, so the welded mesh of a valid solid is a closed manifold. Each face is triangulated in its surface's parameter space by our own constrained Delaunay triangulation (holes by the even–odd rule), with interior points added until every triangle is within tolerance of the surface; loops that wind around an axis are cut along a seam whose two sides share their 3D points; poles, apexes and collapsed patch edges become one point. Faces are tessellated in parallel (`std::thread::scope`) and merged in face order: 1, 2 and 8 threads give byte-identical meshes. Planar faces get no interior points (a block is 12 triangles). A face around an axis whose other loops leave no room for a straight seam is cut along a seam in pieces, from loop to loop (§6). A face on a spline surface that closes on itself (a NURBS surface of revolution, with or without its seam as an edge) is followed across the seam like one on a cylinder, and every face's mesh is held against the chords of its edges before it is returned, so a mesh that is not closed is an error, never a result (2026-10-14, §6). Still `Unsupported`: a loop winding more than once, or around both the axis and the tube of a torus; refused as well: a face across the seam of a spline surface that closes on knots that are not clamped.
- **Mesh export:** `meshio` writes binary and ASCII STL, 3MF and OBJ; `io` welds a tessellated mesh, classifies it as solid or surface and encodes one or more objects. FreeCAD reads the box, the teapot and all fourteen tessellated reference solids (primitives, hemisphere, and the solids with trimmed faces) back as closed solids with the same counts, area and volume (`cargo xtask freecad`). No readers, no colours.
- **Native format:** `format` reads and writes `.3dcraft`: a stored ZIP (`zipstore`, with a reader hardened against hostile archives) holding a pretty-printed `manifest.json`, now at `format_version` 4 (version 1 to 3 files still open, through the migration chain). The file's types are separate from `doc`'s and converted by exhaustive destructuring, so a new document field does not compile until it is saved and loaded (verified by adding one). Saves are atomic and refuse an invalid document; loads validate. Not built: `thumb.png`, `blobs/`, the directory layout, autosave and crash recovery.
- **STEP export (2026-10-13):** `step` reads and writes ISO 10303-21 with its own model (records with parameters, simple and complex instances; nothing about CAD in it); `io::step` maps bodies to the AP214 B-rep entities (`MANIFOLD_SOLID_BREP`, `BREP_WITH_VOIDS`, `ADVANCED_FACE`, every curve and surface kind incl. rational B-splines, vertex loops for whole spheres and tori and for an apex inside a face) with the document's units, uncertainty and names, after checking each body; `file.export` and `craft3d-cli convert` write `.step`/`.stp`. For that `io` now depends on `geom`, `topo` and `kernel` (the latter only for `boolean::contains_points`, to tell which lump a cavity is in). FreeCAD reads 448 exported files as valid solids of our volume and area (`cargo xtask freecad`). No import yet, no assemblies, colours or names of faces. The conventions are in [`file-formats.md`](file-formats.md) and in the module documentation.
- **DXF and SVG export (2026-10-13):** `drawing` writes ASCII DXF (AutoCAD 2000) and SVG 1.1 from its own 2D model (chains of lines, circular and elliptic arcs and B-splines; whole circles and ellipses; a unit; layers); `io::drawing` maps a sketch (its curves joined into chains) and the loops of flat faces (seen from outside the body) onto it; `file.export` writes them for a `sketch` or a `face`. Every curve stays what it is. FreeCAD reads both formats back with the closed-form length and area ([`file-formats.md`](file-formats.md) › Flat outlines).
- **Engine:** `engine::Session` holds open documents and runs 56 commands (`file.*`, `recovery.*`, `edit.*`, `variable.*`, `feature.*`, `sketch.*`, `datum.*`, `history.rollback`, `document.inspect`, `document.check`, `document.measure`, `view.render`, `view.pick`) by id with JSON parameters. Edits are atomic undo steps; a failed command changes nothing; a panic inside a command is caught and reported. File access goes through explicit read and write roots. `tests/panic_hunt.rs` runs every command with adversarial parameters in four document states. Deviations from the plan: synchronous (no job pool, no events, no `arc-swap` snapshots), no parameter schemas beyond the documented params string, no `enabled` predicate beyond "needs a document". **Autosave and crash recovery** (2026-10-13, `engine/src/recovery.rs`, `recovery_store.rs`, `recovery_cmds.rs`; not in a browser): a session that its host gave a recovery directory notes after every command which documents changed (an `Arc` clone of the document, under a microsecond) and writes them with the `.3dcraft` writer on the one thread the engine starts, at most once per interval per document (30 s) and at once after a caught panic; a 300-feature document of 1.8 MB takes 40 to 90 ms there and nothing on the command's thread. The host ends it on a clean quit (`Session::end_recovery`), which removes the files; a killed process leaves them, and the next session's scan offers them through `recovery.list`, `recovery.open` and `recovery.discard`. The layout is in [`file-formats.md`](file-formats.md).
- **Desktop app and shell:** `ui-egui` is the shell as a library (serde state with the orbit camera, theme tokens, the viewport showing the renderer's image as a texture, a read-only feature tree, a status bar and a File menu); `apps/craft3d` puts it in an eframe window and adds the control listener (TCP on 127.0.0.1, token, the `serve` protocol plus `ui.*`), whose requests are answered on the UI thread between frames on the one `Session`. `engine::Session::scene_with` gives the shell meshes, the bodies' edges as polylines (`tess::tessellate_edges`: the points the mesh has along each edge) and sketch polylines per document revision, at the display quality (`SceneQuality::Display`, §6: finer than the export's automatic tolerance, within a triangle budget; `state.quality` in `ui.get`/`ui.set`), which `ui.screenshot` renders too; a change of quality is another mesh of the same revision, so the frame keys and the direct path's upload carry the scene's tolerance as well. Four things about the viewport: (1) the sharp image is made on the shell's render thread, and the UI thread only makes the quick preview; `frames::Scheduler`, a state machine without threads or clocks, decides what is made and drops every result that is not the image of what is wanted now (camera, document revision, size, selection). `Shell::new` renders where it draws (wasm, tests), `Shell::threaded_with` is what the window uses. (2) **Which renderer (2026-10-13, direct path the same day):** the window lends the shell its own wgpu device (eframe's `RenderState`: `Shell::threaded_with_gpu`), and with `--renderer auto` (the default) the viewport is drawn on it by `ui_egui::direct::Direct` over `craft3d_gpu::Onscreen` (§7.2): bodies and the lines over them, multisampled, every frame at the viewport's full size, directly into a texture registered with egui (`register_native_texture`) and shown as it is. Nothing is read back for display, there is no preview and no render thread on this path (the draw is submitted from the drawing thread and costs it about a millisecond; `RenderStats::milliseconds` is that thread's time, not the GPU's), and a frame is drawn only when something it depends on changed (camera, document revision, size, selection, theme). The mesh and the lines are uploaded once per scene revision (the lines again when the selection or the theme changes; the axes are rewritten in place when the zoom changes their length). When the direct path cannot be set up (no render state, no pipelines on that device), or fails for good while running (a lost device, a driver that falls over), the shell goes on as before with `ui_egui::backend::BodyRenderer`: the wgpu renderer on a device of its own per thread, read back as the same `Frame` the CPU renderer gives, with the quality rules below, or the CPU reference renderer when there is no adapter or it was asked for (`--renderer cpu`, `CRAFT3D_RENDERER=cpu`); the reason is in `ui.get` (`renderer.fallback`) and the terminal. A frame the device cannot take (a target or a mesh too large for it) is made that way too, and the next one directly again. `ui.get` reports `renderer {backend, adapter, fallback, direct, msaa}` and `render.msaa`; the status bar says `GPU 1440×900 ·…`. On the readback and CPU paths each thread has a renderer of its own with its own wgpu instance and device (wgpu's OpenGL backend ties a device to its thread), the sharp image is made on the render thread while a preview is on screen, and the budgets (`REST_SAMPLES`, `MOVING_SAMPLES` in samples for the CPU; `GPU_REST_PIXELS`, `GPU_MOVING_PIXELS` in pixels for the readback, which runs at a few hundred MB/s on this laptop's Intel driver) shrink the image while moving (`MOVING_DIVISOR`) and on a large window. `ui.screenshot` always renders on the CPU: it is the oracle. The tests: `crates/ui-egui/tests/gpu_viewport.rs` draws one scene through the direct path on a device made as eframe makes the window's (`direct::headless_render_state`) and through the readback path, and compares with the oracle under the tolerances of §7.2 (pictures in `target/evidence/ui/`); `tests/gpu_fallback.rs` takes the adapter away. In the browser the viewport is rendered on the CPU for now. Measurements (2026-10-13, `cargo run --release -p craft3d-ui-egui --example frame_time`, the development machine's Intel Meteor Lake iGPU over Vulkan, while other builds ran; the numbers are in `docs/development.md` › The live viewer). (3) Edges and sketches are lines over the image: on the direct path drawn by the GPU (§7.2), on the other paths drawn by egui in vector form, each cut against the renderer's depth buffer pixel by pixel; either way the part of an edge behind a body is left out, the part of a sketch behind a body is drawn dimmed, the world axes are always drawn. (4) Open and save: the shell only asks (`FileAction`); the application shows the system's dialog (`rfd`, on its own thread) and runs `file.open` or `file.save` with a grant for the chosen file's directory, which the control channel cannot reach ([`control-protocol.md`](control-protocol.md) › File access). `automation::bridge` is an MCP server that passes every message to that window (`mcp.message`).
- **Rendering:** `render` is the CPU reference renderer (perspective and orthographic, depth buffer, smooth two-sided shading, id buffer, supersampling, PNG), with cameras that frame a box in perspective, orthographically, or as a close-up from outside a larger model, and zoom. It draws no edges itself (the viewer draws them over its image, tested against its depth buffer; `view.render` has none yet), and has no near-plane clipping. `gpu` is the wgpu renderer for the same inputs and the same result (`Frame`: colour, face ids, view distance), offscreen (`Offscreen`) or on a device and queue someone else owns (`Renderer`), and, as `Onscreen`, the viewport's renderer on the window's own device: the picture multisampled, the lines over it drawn and depth-tested on the GPU, into a texture that is shown without any readback; it matches the CPU renderer within the tolerances derived in §7.2, see-through bodies included (two depth layers, since 2026-10-14), and the desktop app's viewport draws with it when there is an adapter, with the readback path and the CPU renderer as the fallbacks (see *Desktop app and shell*).
- **Pointing (2026-10-13, faces):** a position in a picture gives the persistent name of the face under it, and a name is shown highlighted. Three layers, one answer. (1) `render::pick` is the CPU renderer's own arithmetic for one sample (the same projection, edge functions, depth key and tie rule as `render`, and it skips the triangles `render` skips), so at a pixel centre it returns the face `Frame::ids` holds there, with the point of the triangle that projects onto the position; it walks the triangles once and allocates nothing. (2) The engine's `Scene` carries the names: `SceneBody::face_names` and `face_aliases` are `faceNames` and `faceAliases` of `document.inspect`, face `k` of a body having id `first_face_id + k` in `Scene::mesh`; `Scene::pick` turns a hit into feature, body, name and point, and `Scene::faces_named` turns a name (with the feature when several bodies have it) into face ids. The command `view.pick` (`engine/src/pick_cmds.rs`) asks it of the scene and camera `view.render` uses (the framing is shared: `commands::Framing`), or of a camera given. (3) The shell asks the same of the scene it draws with the viewport's camera: a click (`Shell::pick`, also `ui.pick`) sets `UiState::picked` and `UiState::highlight`, and `ui.highlight` sets the highlight by name. **How the GPU viewport gives the same answer:** it does not read the GPU's id target back. The pick is computed on the CPU from the scene the viewport draws and the camera it draws with, and the GPU's picture has the same face at that pixel because its face ids equal the CPU's outside the band of §7.2 (that is what the parity tests assert); on a silhouette pixel the answer is the CPU renderer's. **The highlight** is `render::Highlight` in `RenderParams`: up to eight runs of face ids and a base colour (`theme::Tokens::face_highlight`). Both renderers shade those faces from that colour instead of the body's, with more ambient light (`SHADE_HIGHLIGHT_AMBIENT` 0.6, `SHADE_HIGHLIGHT_DIFFUSE` 0.4, so a highlighted face in the shade still shows; fifths on purpose, because a colour byte times a fifth is never half-way between two levels, where the GPU rounds to even and the CPU away from zero: with 0.55 the whole shaded side of a face was a level apart). On the GPU the runs are four `vec4` of the scene's uniform block compared with the vertex's face id, so a change of highlight uploads no mesh; ids are compared as floats and a highlight at or above 2²⁴ is refused (`GpuError::OutOfRange`), which sends that frame to the CPU. The highlight is part of the frame key of every path (preview, sharp image on the render thread, the direct path, `ui.screenshot`). Tests: `crates/render` (pick against the id buffer, exactly), `crates/gpu/tests/parity.rs` (16 highlighted scenes per adapter under the tolerances of §7.2), `crates/engine/tests/pointing.rs` (the acceptance test: 13 generated views of five bodies, a primitive, a boolean and patterns among them, 691 picks compared with `faceNames`; every one of the 58 faces picked from some side), `crates/ui-egui/tests/pointing.rs` and `gpu_viewport.rs` (clicks, `ui.pick`, `ui.highlight`, the direct path against the oracle). Not there: several highlights at once, a highlight in `view.render`.
- **See-through bodies (2026-10-13).** `RenderParams::opacity` (1: opaque). The CPU renderer keeps, per sample, the front fragment and the nearest fragment strictly behind it (two depth keys and two colours; a fragment that is neither is not shaded), and blends them once all triangles are drawn: `opacity * front + (1 - opacity) * behind`, the background where nothing is behind, no blend where the front face is highlighted. Why this definition: it is exact and order-independent (two minima), it needs no sorting, and a GPU can do the same with two passes (the scene, then the scene again with a fragment discarded unless its depth is greater than the first pass's at that sample) and one blend in the resolve, so the two renderers can agree under the tolerances of §7.2. Blending every layer in depth order was rejected: it needs sorted fragments or many passes, and several layers of grey read worse than one. At opacity 1 none of this runs and the frame is bit-identical to before (asserted). **The GPU half (2026-10-14)** is depth peeling with two layers, in both renderers of `gpu` (§7.2, *See-through on the GPU*): the scene is drawn twice, the second time keeping only what is behind the front, and a last pass blends the two per sample with a table of the CPU renderer's own blend. The window's device draws see-through frames itself; a device that cannot says so (`GpuError::SeeThrough`, which both viewport paths treat as "this frame another way") and the picture on screen is then the oracle's own. The overlay draws the hidden stretches of body edges dimmed for such a frame (`viewport::overlay_see_through`; on the GPU the same segments flagged *dimmed*, uploaded when the bodies become see-through or opaque again). Tests: `crates/render` (the formula on stacked squares in all six triangle orders, opacity 1 and values that are not numbers, a highlight), `crates/ui-egui/tests/see_through.rs` (`ui.set`, the screenshot against the frame, hidden edges, picks unchanged, the slider, the GPU viewport drawing the frames itself, and a device that cannot falling back and coming back); the GPU's tests are listed in §7.2.
- **Pointing at edges (2026-10-13):** the same three layers. (1) `render::Viewpoint` projects a point the way the renderer projects a vertex, and `render::Neighbourhood` keeps the triangles that can be under a position within some pixels of another, so that many positions close together are looked up (`Neighbourhood::pick`, the arithmetic of `render::pick`, shared code) for one pass over the mesh. (2) `SceneBody::edge_names` and `edge_faces` are `name` and `faces` of `document.edges` for the polylines of `SceneBody::edges` (one per edge of the B-rep, in its order). `Scene::point_at` is the rule ([`control-protocol.md`](control-protocol.md), *Pointing*): the face under the position, and the nearest point in sight of any edge within the pick radius; a point is in sight when the surface the picture shows where the point lands is not nearer than the point (1e-7 of its distance plus the scene's size of slack: the points of an edge are points of the mesh, so this is rounding). `Scene::edges_named` turns an edge's own name, or two face names, into the edges of one body. (3) The shell's click and `ui.pick` call `point_at` with the viewport's camera; `UiState::picked` says which kind was hit and `UiState::highlight_edge` (an `EdgeRef`: own name, or the faces) is the edge shown. **The edge highlight is a line of the overlay**, not a shading: `viewport::Marks` holds the pieces of line of the highlighted edges, `viewport::overlay_marked` (CPU paths, `ui.screenshot`) and `direct::segments_marked` (the GPU's direct path) add them after everything else as `LineKind::Highlight`, depth-tested and dimmed where hidden, so the two paths agree on it exactly as they agree on every other line (§7.2). Cost: a pick is two passes over the mesh (the face, the neighbourhood) however many edges are near. Tests: `crates/engine/tests/pointing_edges.rs` (10 generated views of the five bodies: 1185 points of edges in sight picked and compared with `document.edges`, 776 points of hidden edges not picked through a face; a box alone against the closed form for a convex body; the radius measured; the nearest-edge rule on 2552 positions against a brute-force search; visibility there is a ray cast in space, another route than the pick's), `crates/ui-egui/tests/pointing_edges.rs` (37 edges clicked, `ui.pick`, `ui.highlight`, the screenshot, the direct path against the oracle along the highlighted lines).
- **Pointing at vertices (2026-10-13):** `SceneBody::vertices`, `vertex_names` and `vertex_faces` (the faces of the edges that end in a vertex) are what `document.edges` lists under `vertices`. `Scene::point_at` looks for the nearest vertex in sight within the radius before it settles for an edge (rule 4 of *Pointing* in [`control-protocol.md`](control-protocol.md)), `Scene::vertices_named` turns a vertex's own name, or the names of faces that all meet in it, into the vertices of one body, and `UiState::highlight_vertex` (a `VertexRef`) is drawn as a dot of `viewport::Marks::points`, by `overlay_marked` and `segments_marked` alike. Tests: `crates/engine/tests/pointing_edges.rs` (the same 10 views: 461 picks on vertices in sight give the vertex `document.edges` lists, 156 hidden ones are not picked; a box against the closed form, seven corners of eight; vertex against edge and face at measured distances), `crates/ui-egui/tests/pointing_edges.rs` (clicks, `ui.highlight {vertex | corner}`, the dot on the direct path against the oracle).
- **Demo:** `cargo run --release -p craft3d-render --example teapot` renders the Utah teapot (32 patches) to `target/evidence/teapot.png`.

## 1. Goals and principles

**Goals**
- A native, portable (Linux / macOS / Windows), fully open-source parametric 3D CAD modeller with its **own kernel and tessellator**, in pure Rust.
- **Built to be driven by AI.** Every action is a command with a stable id and serialisable parameters. An agent can build, inspect, render and export a model without a window.
- **Phase 1 has (almost) no UI:** load, save, view. The modelling surface is the command registry.
- **The design history is saved,** not just the result: sketches, constraints, formulas, variables, and the order in which they were applied.
- **Export** to STEP (exact B-rep) and to STL / 3MF / OBJ (meshes).
- **The UI can be swapped** without touching the core, and the core compiles to `wasm32`.

**Principles**

1. **Engine-first, headless-first.** Every feature is reachable without a GUI: from tests, the CLI, the control channel and MCP. The GUI is one client of the engine.
2. **Everything is a command.** Each action has a stable `CommandId` (such as `feature.extrude`) with typed, serialisable parameters. The UI, shortcuts, CLI, control channel, MCP and recorded scripts all dispatch the same commands.
3. **History is the source of truth; geometry is derived.** The document stores *how* the model is built. B-rep bodies and meshes are caches of that recipe.
4. **One algorithm, one implementation, one parameter struct.** Kernel and tessellator are CPU-only, deterministic Rust. Only *display* has a second (GPU) implementation, and it is checked against the CPU one.
5. **Immutable snapshots, structural sharing.** Documents and bodies are persistent data: `Arc`-shared, copy-on-write. Taking a snapshot is O(1); undo, background regeneration, autosave and UI reads are cheap and lock-free. (This is PhotoCraft's "copy-on-write tiles" applied to features and faces instead of pixels.)
6. **Determinism.** The same document gives bit-identical bodies and meshes across runs, thread counts and platforms.
7. **Pure Rust.** No C/C++ dependencies in the kernel, tessellator, formats or engine. System libraries appear only at the windowing/GPU edge (through winit and wgpu).
8. **Clean-room.** Public specs, textbooks, papers and observed behaviour only. No proprietary code, shaders or assets; no code from copyleft kernels.

### 1.1 Avoiding the usual CAD holes

PhotoCraft's plan starts from GIMP's lesson: properties baked into the core as assumptions (8-bit pixels, RGB only) cost years to undo. CAD systems have their own versions of that mistake. Each rule below is cheap on day one and a rewrite later.

| Property | The hole | Rule we adopt from day one | Where |
|---|---|---|---|
| **Topological naming** | Features that refer to "face 7" of the current body break or silently retarget when an upstream edit renumbers the faces. Open-source modellers have spent years retrofitting a fix | Every face, edge and vertex carries a **persistent name** derived from its origin (the feature that made it, the sketch entity it came from, the operation and operands that split or merged it). Features store names, never indices. A name that no longer resolves is a reported error on that feature, never a guess | `topo`, `kernel`, `regen`, `doc` |
| **Tolerance** | A global `EPSILON` works until a model is very small, very large, or imported from a system with another convention | Tolerance is **data**: a document-level linear and angular tolerance, plus per-entity tolerances on vertices and edges where an operation or import needed them. Every predicate takes a tolerance argument. No `const EPS` in public APIs | `math`, `topo`, `kernel` |
| **Units** | Unitless numbers that mean millimetres, until a file in inches arrives | The document has a length unit and an angle unit; expressions carry dimensions (`10 mm + 1 in` is valid, `10 mm + 30 deg` is an error). The kernel works in the document's unit; conversion happens at the format edges | `expr`, `doc`, `io` |
| **Geometry kinds** | Starting with planes and cylinders "for now" and discovering that every operation has to be reopened for freeform surfaces | `Curve` and `Surface` are enums that include NURBS from M1. An operation that does not yet handle a pair of kinds returns `Unsupported { op, kinds }`; it never assumes the case away. Analytic kinds stay analytic (a cylinder is not stored as a NURBS) so results stay exact where they can be | `geom`, `kernel` |
| **Precision** | `f32` in the modelling path, or mixing display and model precision | Kernel maths is `f64` throughout. `f32` exists only in vertex buffers handed to the GPU, converted relative to a per-view origin so large coordinates keep precision | `math`, `gpu` |
| **Result vs recipe** | Saving only the final solid, so a design cannot be edited | The native format stores the history. Cached bodies in a file are optional and verified by hash; a file with every cache removed opens to the same model | `doc`, `format` |
| **Single body, manifold only** | Assuming one solid per document, or that every result is a closed manifold | A document holds any number of bodies. A body is a list of shells and may be a solid, a sheet or a wire; validity is checked and reported, not assumed | `topo`, `doc` |
| **Regeneration order** | Implicit ordering by creation time or hash-map order, so reopening a file gives a different model | The feature list is an explicit ordered sequence; variables and formulas form an explicit dependency graph with a stored, deterministic evaluation order; the solver's constraint order is stored | `doc`, `regen`, `solve` |
| **File formats** | Format quirks leaking into core types | Formats live in standalone crates with their own format-level model; mapping to the document lives in `io`. Adding a format touches a leaf crate | `step`, `meshio`, `drawing`, `io` |
| **UI toolkit** | A core that calls into its toolkit | Nothing below L7 knows a toolkit exists | layering rule 2 |

The test is simple: **adding a surface kind, a feature type, or a file format should touch leaf crates, not the foundation.**

## 3. Dependency layering (enforced)

```text
 L8  apps/*                         (binaries: wire everything together)
 L7  ui-egui · automation
 L6  engine
 L5  io
 L4  regen · render · gpu · format
 L3  ops · solve · kernel · tess
 L2  doc
 L1  topo · expr
 L0  math · geom                    step, meshio, drawing (standalone, no workspace deps)
```

**Rules** (checked by `cargo xtask layers`, which parses `cargo metadata`):

1. A crate may depend only on crates in **lower** layers. No cycles. Sideways dependencies only where listed in `SAME_LAYER` in `xtask/src/layers.rs` (today: `geom` → `math`).
2. **Nothing below L7 may depend on any UI toolkit, winit, eframe or rfd.** Platform services (file dialogs, clipboard) reach the engine as injected functions or traits.
3. **`step`, `meshio` and `drawing` depend on no workspace crate.** The mapping between their models and ours lives in `io`. This keeps them publishable and fuzzable in isolation.
4. **`doc` contains no geometry algorithms.** It may use `topo` and `expr` *types* (names, expressions), nothing from L3.
5. **`kernel` and `tess` never depend on `gpu` or `render`.** Geometry has one implementation.
6. **wasm gate:** every crate in L0–L7 must build for `wasm32-unknown-unknown` (`cargo xtask wasm`).
7. `gpu` is optional for `engine`: the headless CLI and CI tests run `cpu-only`.

## 4. Document model (`craft3d-doc`)

A document is the recipe. Sketch of the types (final names are settled in M1/M2):

```rust
pub struct Document {
    pub id: DocId,
    pub units: Units,                    // length + angle unit
    pub tolerance: Tolerance,            // linear + angular modelling tolerance
    pub variables: VariableTable,        // name -> expression, in stored evaluation order
    pub features: Vec<Feature>,          // THE history: explicit order of application
    pub rollback: Option<FeatureId>,     // history marker: regenerate up to here
    pub metadata: Metadata,
}

pub struct Feature {
    pub id: FeatureId,                   // stable, never reused within a document
    pub name: String,
    pub suppressed: bool,
    pub kind: FeatureKind,
}

pub enum FeatureKind {
    DatumPlane(DatumPlane), DatumAxis(DatumAxis), DatumPoint(DatumPoint),
    Sketch(Sketch),
    Primitive(Primitive),                // box, cylinder, cone, sphere, torus
    Extrude(Extrude), Revolve(Revolve), Sweep(Sweep), Loft(Loft),
    Boolean(Boolean),                    // union / subtract / intersect between bodies
    Fillet(Fillet), Chamfer(Chamfer), Shell(Shell), Draft(Draft),
    Pattern(Pattern), Mirror(Mirror), Transform(TransformBody),
    Import(ImportedBody),                // a history-free body from STEP, stored as a blob
}

pub struct Sketch {                      // as built in M5: crates/doc/src/sketch.rs
    pub plane: SketchPlane,              // World { plane: Xy|Yz|Zx, offset }, Face { face: PersistentName, offset }, Datum { plane: FeatureId, offset }
    pub entities: Vec<Entity>,           // id, construction flag, geometry: Point {x, y}, Line, Circle, Arc, Spline on point ids
    pub constraints: Vec<Constraint>,    // id + kind, in the order they were applied
    pub next_entity_id: u64,             // ids are never reused within a sketch
    pub next_constraint_id: u64,
}                                        // the point coordinates and circle radii ARE the last solution

pub enum Constraint {
    Coincident(..), Horizontal(..), Vertical(..), Parallel(..), Perpendicular(..), Tangent(..),
    Equal(..), Concentric(..), Symmetric(..), Midpoint(..), Fixed(..),
    Distance { a: EntRef, b: EntRef, value: Expr }, Angle { .. , value: Expr },
    Radius { .. , value: Expr }, Diameter { .. , value: Expr },
}

pub struct Expr { pub source: String /* "width / 2 + 3 mm" */, /* parsed form cached, not serialised */ }

pub enum Ref {                           // how a feature points at geometry
    Feature(FeatureId),                  // a datum or a whole body
    Name(PersistentName),                // a face / edge / vertex
}
```

- **Every numeric parameter is an `Expr`,** not a number. `Extrude { distance: Expr }` may be `"25 mm"` or `"height - 2 * wall"`. The expression's source text is what is saved.
- **Order is explicit.** `features` is the order of application. `variables` keeps a stored topological order; `constraints` keeps the order in which they were added. Saving and reopening must reproduce the same model, so nothing that affects the result may depend on map iteration or solver start-up luck.
- **Solved sketch state is saved.** Constraint systems have several solutions (mirror branches). The last solution is stored and used as the solver's starting point, so a reopened sketch does not flip.
- **No bodies in the document.** Bodies live in the regeneration result, keyed by feature id.

### 4.1 Persistent names

A `PersistentName` identifies a topological entity by its origin, for example "the face made by extruding sketch entity `e12` of feature `F3`", "the cap face at the end of `F3`", "the edge between faces *A* and *B*", "the part of face *A* that survived boolean `F7`, on the side of operand 2". Names are produced by `kernel` operations (each operation reports, for every entity of its result, where it came from) and resolved by `regen` against the body at that point in the history.

Resolution outcomes are explicit: `One(entity)`, `Many(entities)` (the entity was split; the feature's policy decides whether that is acceptable) or `Missing`. A `Missing` or unexpected `Many` marks the feature as failed with a message naming the reference; the features before it remain valid.

The naming scheme is the hardest design problem in this plan and is prototyped in M6 before anything depends on it. Its rules and known limits get their own section in this document when that prototype lands.

**Splines in sketches (2026-10-13, the first step of M9's sweeps).** `Geometry::Spline { degree, control }` is a polynomial B-spline of degree 1 to 7 whose control points are point entities, in order, on clamped uniform knots that are derived from the degree and the count (`doc::clamped_uniform_knots`) and not stored. It starts at its first control point, ends at its last and leaves each along the leg to the next; with the first point also as the last it closes on itself. Why this form: the unknowns of the solver are the points, so the constraints that exist (coincident, fixed, distance, horizontal, ...) shape a spline without the solver knowing the kind at all, it adds no degrees of freedom, and it closes a loop with lines and arcs by sharing its end points. A later rational or non-uniform spline adds `weights` and `knots` as fields that default to what this one means. A spline *through* given points is not a second kind: `sketch.spline` with `through` works the control points out once (the curve takes point i at the Greville abscissa of control point i, a system that is well conditioned whatever the points) and stores an ordinary spline; the first and last points are shared as given, the ones in between become new control points. `regen` does not hand a spline to the solver: its points are there already. A `tangent` constraint between a spline and a line, an arc or another spline holds at an end point the two share (one point entity, or two tied by a coincident constraint) and becomes a condition on the spline's end leg: parallel to the line or to the other spline's leg, tangent to the arc's circle at that point; without a shared end the sketch fails with that reason. A point is held on a spline by `pointOn` (the next paragraph, 2026-10-14). The other constraints (parallel, equal, midpoint, a radius) refuse a spline as not supported yet.

**A point on a spline (2026-10-14).** `pointOn` takes a point and a spline. For the solver a spline is still not an entity and has no unknowns: `solve::Sketch::splines` lists the splines that points are put on (degree, knots, control points as point entities; `regen` adds one the first time a constraint needs it), and `Constraint::PointOnSpline` is **one equation without an extra unknown**. The curve's parameter is eliminated: the residual is the signed distance `g = (P − C(u)) · n(u)` at the *foot* of the point, the nearest point of the curve (the nearest of eight places per knot span, then a bisection on `(C − P) · C′`, every loop bounded). At the foot `P − C` is at right angles to the curve, so `g` does not change to first order with `u` or with the direction of `n`, and its gradient is exact with both held still: `n` for the point and `−N_i(u) n` for control point `i` (`crates/solve/src/spline.rs`; a unit test holds it against central differences of the distance itself, which finds its foot anew, for degrees 1 to 7). So the row has the point and `degree + 1` control points in it, which is why a gradient now has room for 18 unknowns instead of 8 (`dual::SLOTS`; the solver's timings did not move: 87 against 92 ms for 1602 unknowns). Degrees of freedom, redundancy and conflict come from the rank of the Jacobian like every other constraint's: one less per point on a spline; the same constraint twice, or an end control point on its own spline, is redundant; a point held elsewhere against a held spline is conflicting, with the distance as its residual. Two choices the developer may want different: beyond its ends a spline counts as going on straight along its first and last leg (as a point on a line is held on the whole line), and where the nearest point is a corner (a polyline's) the distance is the plain distance to that corner. A spline all on one spot has no direction: the constraint is reported undefined, the rest solves. Tests: `crates/solve/tests/splines.rs` (lands on the curve by an independent measure, 1e-3, 1 and 1e6, degrees 1 to 6; a spline pulled through a fixed point; dragged; redundant, conflicting, beyond the ends, bad input), `crates/engine/tests/sketch_spline.rs` › `a_point_is_held_on_a_spline` (through the commands, a control point moved by a variable, save and reopen).

**Profiles and extrusions with splines (2026-10-13).** `kernel::profile` takes `Curve2::Spline` (degree, knots, control points; `kernel::spline2` holds the arithmetic). A spline's ends join like those of a line; where it meets an arc its end control point is moved onto the arc's end. Area and centroid are exact (Green's theorem by Gauss–Legendre on each Bézier piece, whose integrands are polynomials). Whether a spline keeps clear of another curve, and of itself, is decided by subdivision: curves are compared as chords of pieces flat within an eighth of the tolerance, so curves that come within three quarters of the tolerance of each other away from a shared end are always refused, curves that stay more than one and a quarter of it apart never are; a spline with a cusp, or one that crosses or touches itself, is refused and named (`e7 crosses or touches itself`). A spline with a corner and a spline that closes on itself are cut into pieces (the next paragraph; both were refused until 2026-10-14). `kernel::extrude` sweeps a spline into a face on a polynomial B-spline surface (the spline's degree by 1) between B-spline edges; the caps are planes bounded by them; the wall is named `side(e7)` like any other, so moving a control point renames nothing. `kernel::revolve` sweeps it into a rational surface (the next paragraph). Such a solid is a boolean operand like any body with polynomial B-spline faces. Known limits, each an error and not a wrong result: the exact integrals (`mass_properties`) and the tessellator can decline the wall of a spline with a hairpin just short of a cusp (measured on random profiles: 4 of 88 meshes declined, 0 of 30 integrals), and the integrals take seconds on a wall that wiggles.

**Revolved splines, closed splines and corners (2026-10-14).** Three things a spline could not do in a profile, built on one idea: *no face lies on a spline surface that closes on itself*. `craft3d-geom` knows no period for a spline surface, so the tessellator, the exact measure and the booleans could not follow such a face across its seam; a surface that ends where its face does is an ordinary patch to all three. (The tessellator follows such a face since 2026-10-14, §6, for what a STEP file will bring; the measure and the booleans do not, so the kernel goes on making halves.) So where one curve would sweep a surface that closes, or one with a crease, it sweeps several faces instead.

- *A revolved spline* (`kernel::revolve`) sweeps a surface of revolution that is a NURBS surface exactly: around the axis (u) the standard rational quadratic arcs, in equal pieces of at most a quarter turn (weights 1 and the cosine of half the piece's angle, so never below cos 45°), along the spline (v) its own degree, knots and control points, each control point turned into the control polygon of its circle. u runs over 0 to 1 and is not the angle. A partial turn is one face between the spline's edge at the start and at the end (polynomial B-spline curves) and the arcs its ends sweep, as for a line or an arc. **A full turn of a loop with a spline in it is made in two halves:** each spline sweeps two faces (0 to 180° and 180° to 360°, each on its own surface), with the spline's edge in the sketch plane (`startEdge`) and half a turn on (`endEdge`) between them; the circles at a spline's ends are two arcs between a `startVertex` and an `endVertex`, and a line or an arc next to a spline has a face whose loop there is those two arcs. Loops without a spline are built as before (no seam, whole circles).
- *At the axis.* A spline may end on the axis: the border of its surface is then one point (as a cone has its apex), the body the kernel makes is valid and meshes watertight with the volume Pappus gives, but `topo::mass_properties` declines a boundary through a collapsed border of a spline surface, and so do booleans. A document could neither measure nor check such a body, so `feature.revolve` (`regen/src/revolve.rs`) refuses a spline that ends on the axis, with that reason and the way round (end it off the axis and close the profile with a line): work owed, with an ignored test as the reproducer (`crates/kernel/tests/spline_sweeps.rs`). A spline that reaches the axis *between* its ends is refused by name (`UnsupportedCurve`: the surface would pinch into a point); one that crosses it is `CrossesAxis`, judged on the curve (its true extremes, `Spline2::extent`), not on its control points.
- *A closed spline* (its last control point on its first) is a loop on its own. `kernel::profile` cuts it in two at the inner knot nearest the middle of its domain (knot insertion: the two pieces are the spline exactly) and hands on a loop of two segments with the same `source` and `piece` 0 and 1. Extruded it is two walls and two caps; revolved, two faces, or four for a full turn. Where it closes it has a corner in general, since the curve leaves along its first leg and arrives along its last.
- *Corners.* A spline with an inner knot as often as its degree (which is every inner knot of a spline of degree 1, a polyline) is cut there the same way, into one segment per smooth piece; a piece of degree 1 is a `Shape::Line`, so a polyline sweeps planes, cylinders and cones like the lines it is. A knot repeated more often than the degree tears the curve and stays refused.
- *Names.* An origin has a `piece` number beside its role and sources (`kernel::extrude::Origin`): 0 for the first or only entity those sources give in that role, counted up for the others (the pieces of a curve; in a full turn made in halves `2 k` and `2 k + 1` for piece `k`; for a vertex or a lateral edge, the number of the curve the loop leaves by). In a persistent name the first keeps the plain name and the others get the role `piece` in front, written like a copy: `F2:side(e7)`, `F2:piece(1)/F2:side(e7)`. Names stay unique within a body and a wall of a spline keeps its name when a control point moves; the numbers of the pieces after a corner change when a corner is added before them (they are counted along the curve).
- *Measured (2026-10-14).* `crates/kernel/tests/spline_sweeps.rs`: vases, rings, a hollow ring, closed splines of degree 2, 3 and 5, cornered cubics and polylines at 1e-3, 1, 1e3 and 1e6, on both sides of the axis, in two frames, through a full turn, 120°, 90°, a symmetric 120°, 270° and 342°: `topo::check` clean, volume, surface and centroid within 1e-9 of Pappus's theorems on an oracle that integrates the profile itself (de Boor and Gauss–Legendre, independent of the kernel's Bézier pieces), meshes watertight at two tolerances, the surface on the turned spline to 1e-12; a straight spline gives the cone's and the tube's closed forms to 1e-10; a polyline gives the solid its polygon gives to 1e-12. `crates/engine/tests/spline_sweeps.rs`: the same through the commands at 1e-3, 1 and 1e6 with `document.check {"deep": true}`, save and reopen, a control point moved by a variable against a full regeneration, and booleans with a block and a cylinder that keep `V(A ∪ B) + V(A ∩ B) = V(A) + V(B)` and `V(A − B) = V(A) − V(A ∩ B)` to 1e-7.

**Reference geometry (2026-10-13, M8.5).** Datum planes, axes and points are features of the history that make no body (`doc/src/datum.rs`: `FeatureKind::DatumPlane`, `DatumAxis`, `DatumPoint`). Their result is where they lie (`regen::Datum` in `FeatureResult::datum`: a frame, a point with a unit direction, a point), worked out in `regen/src/datum.rs` from the results of the features before them, cached and compared like every other result, and shown by `document.inspect` per feature under `datum`.

- *What a datum is placed by* is one of three small reference types, the same in the document, the file and the commands. A plane (`PlaneRef`): a base plane, a flat face by its persistent name (its frame as a sketch on that face has it, the normal out of the body), or a datum plane by feature id. A line (`AxisRef`): a world axis, a datum axis, or **the straight edge between two faces of one body, by the names of the two faces** (`regen::edges_between`; the pieces a boolean cut an edge into are one line, edges on different lines are refused). A point (`PointRef`): coordinates (three expressions), a datum point, a vertex by its persistent name, or the centre of the circular edge between two faces. No second naming scheme: faces by their names, edges by the faces they lie between, vertices by the names the features give them (primitives, sweeps and their copies by where they came from; after a boolean, and in a pattern whose instances are joined, by the faces that meet in them, `F7:corner[…]`, and by the name an operand gave them, as an alias: *Edges and vertices by their faces* below). `datum.references` lists, for one body, the vertices (with their aliases), the edges with their own names and their two faces, and the faces that have an axis, each with the name to use.
- *Planes* (`PlaneBy`): `Offset { from, distance }` keeps the origin and axes of `from`, moved along its normal; `Angle { from, about, angle }` is `from` turned about `about` counter-clockwise seen from the tip of the axis, **through the axis**, which has to be parallel to `from` (an edge of the face, or a line beside the plane; anything else is refused with the angle it makes); `ThreePoints` has its origin at the first point, x towards the second and the three counter-clockwise round the normal.
- *Axes* (`AxisBy`): `TwoPoints` (from the first to the second), `Edge { between }`, `Face` (the axis of a cylinder, cone or torus face, along the surface's own axis), `TwoPlanes` (along the cross product of the normals in the order given, through the point of the line nearest the first plane's origin; parallel planes are refused with how far apart they are). Which way the kernel runs an edge is not something a name says, so between two flat faces an edge axis points along the cross product of their outward normals in the order the faces are given; between other faces it has the direction of the edge's curve.
- *Where a datum is used.* A sketch lies on one (`SketchPlane::Datum { plane, offset }`: the datum's origin and axes); a mirror reflects in one (`Mirror::plane`); a revolution turns about one (`RevolveAxis::Datum`, which has to lie in the sketch's plane: off it or leaning out of it is refused with by how much); a circular pattern goes round one (`PatternLayout::Circular::about`); a datum plane is turned about one and a plane or axis goes through datum points. The commands take them by feature id or name in the parameter that was there (`plane` of `sketch.create`/`sketch.edit`/`feature.mirror`, `axis` of `feature.revolve`/`feature.pattern`), beside what they took before. A mirror and a pattern keep their own point, normal and axis unused, so that giving them again goes back.
- *Failure.* Every reference is found again at each regeneration. One that points at nothing fails the datum with the parameter, the feature and the name it lost (``from: `Base` no longer has a face F1:face(9); its faces are: …``); what is placed by a failed, suppressed, rolled back or later datum fails with the datum's name (``plane: `Shelf` failed; fix it first``); nothing else is touched. A datum is repaired by giving it another definition (`datum.plane` … with `replace`), which gives what building it that way from the start gives. Cycles cannot be built: a datum placed by a later feature fails as "comes after this feature".
- *Not built:* a datum at a vertex of a body a boolean made (vertices need names that survive a boolean, or a reference by the faces that meet there); an axis or centre from an elliptic or freeform edge; a plane tangent to a face, normal to a curve, or midway between two planes; a transform about a datum axis; drawing datums in the viewport.
- *Tests:* `crates/engine/tests/datums.rs` (boxes, discs and rings on offset, angled and three-point planes at 1e-3, 1 and 1e6 against closed forms, with their boxes and centres; mirrors, revolves and patterns about datums; upstream edits; lost references and repair; save and reopen; everything that is refused), `crates/regen/tests/datums.rs` (documents no command builds: cycles, datums of the wrong kind, the cache), `crates/format/tests/format.rs` (the file).

**A feature that fails (2026-10-14, M8.5).** Every reference a feature holds is found again at each regeneration: the sketch an extrusion or a revolution sweeps, the body a transform, a mirror, a pattern or a boolean is made from, the face a sketch lies on or an extrusion ends on, the datum a sketch, a mirror, a revolution or a pattern is placed by, what a datum is placed by, and the variables in every expression. What holds for all of them, and is held to it by `crates/engine/tests/failed_features.rs` (every reference of every feature kind, broken in every way a command can break it):

- *The reason* is the feature's status `Failed(reason)`. It starts with the parameter as `document.inspect` shows it under `params` (`source`, `upTo`, `plane`, `through.0` for the first of the points a datum goes through, `size.x` for an expression) and names the feature it referred to and the name it lost: ``target: `Plate` is suppressed``, ``plane: there is no feature F2 for the face F2:endCap(e5,e6,e7,e8) (was it deleted?)``, ``about: `Plate` no longer has a face F2:side(e5); its faces are: F2:side(e6), …`` (what is there instead, up to twelve names), ``sketch: `Disc` comes after this feature in the history; move it before (feature.move)``. A reference made of two names (an edge between two faces) names both. A cap is the exception that does not fail: a reference to `endCap` or `startCap` survives a change of the outline it was named after, because all caps of one role lie in one plane.
- *What is made from a failed feature* fails with ``… `X` failed; fix it first``, never with an error of its own, and so on down the chain. `regen::root_cause` walks such a chain to its start, the one feature that failed for a reason of its own; `document.inspect`, `document.check` and the result of every feature command give it as `causedBy`, so an agent reads the features to fix without following the chain.
- *Everything else is untouched.* A failed feature has no body, no names and takes no body: the body a failed boolean or transform would have taken is its source's again. The test's oracle is a second computation: the document with the failed features deleted has exactly the remaining features and bodies (status, parameters, volume, area, centroid, counts, names, who took which body).
- *A circle* (a datum placed on a face of a body that is sketched on that datum; a feature pointed at itself) can be built in no order. The reason says so (``… comes after this feature in the history and is itself made from this feature, directly or through others: the two cannot both be built; point one of them at something else``) instead of sending the user to `feature.move`, which would only turn the failure round. Regeneration ends on any circle: a feature is built from the results before it and from nothing else.
- *Repair* is pointing the reference at another entity with the command that edits the feature, which keeps its id, its place in the history and everything that refers to it: `feature.edit` (`sketch` of an extrusion or a revolution; `axis` of a revolution: `x`, `y`, a line of the sketch or a datum axis; `source` of a moved, mirrored or patterned body; `target`, `tool` and `op` of a boolean; `upTo`; `plane` of a mirror; `axis` of a circular pattern), `sketch.edit` (`face`, `plane`) and `datum.plane`, `datum.axis`, `datum.point` with `replace`. After it the document is the one built that way from the start: the same features, parameters, bodies and names, which the test compares for every reference after every way of breaking it. A variable that was deleted is defined again. `feature.edit` refuses a feature pointed at itself, a `sketch` that is no sketch and a boolean whose target is its tool; whether what it is pointed at can be used (it comes earlier, it has a body nothing else took) is for regeneration to say, as when the feature was added.
- *Reorder.* `feature.move` takes any position and never refuses an order: a feature that then comes before something it is made from fails as above, with the remedy in the reason, and what is made from it fails naming it. Refusing would forbid the steps in between when several features are moved one after the other, and deleting and suppressing do not refuse to break a reference either; undo restores exactly. Which features are built depends only on what comes before what: the test moves each of sixteen features to each position and compares the failed set with one computed from the part's description. A move to where the feature is already changes nothing and is no undo step.
- *Roll back.* `history.rollback` puts the marker on a feature; the features after it are `RolledBack`, have no reason and no body and take none. The document is then, for everything up to the marker and for every body, the document that ends there (the test deletes the later features from a copy and compares). A feature before the marker that needs one after it fails with "comes after". Deleting the feature the marker is on leaves the marker on the one before, so what was rolled back stays rolled back; only when it was the first feature is the marker cleared. A feature added while rolled back is appended at the end of the history and is rolled back itself (inserting at the marker is not built).
- *Saved and reopened,* failed, suppressed and rolled-back features have the same states, reasons and bodies: none of it is stored, all of it is regenerated from the same history.
- *Incremental regeneration* gives the same as a full one through all of this. What a reason quotes is part of what the cache compares: the name and kind of every feature it is made from, also one that comes later, who took its body, and whether a later one is made from the feature itself.

**Loft (2026-10-14, M9).** `doc::Loft { sections: Vec<LoftSection { sketch, start }>, ruled, closed }` is a solid through the closed profiles of a row of sketches, in order (`feature.loft`; `kernel::loft`, `regen/src/loft.rs`). Each sketch holds one closed loop without holes, on planes that follow each other (offset planes, datum planes; not necessarily parallel).
- *Matching.* Every loop is walked counter-clockwise as seen looking back along the loft, whichever way its sketch plane faces, and the curves are matched in that order, first with first. The first section starts at its curve with the smallest id; each later section is turned to lie nearest to the one before it (with as many curves: the turn for which the squared distances between matched corners, each seen from the centre of its section's area, add up to the least; otherwise the corner most nearly in the direction in which the section before starts; ties go to the smallest id). `start` names the curve a loop starts with instead: that is how a twist is given or taken out. A whole circle is walked as four quarter arcs from its point in that direction. Sections with different numbers of curves (a square to a circle, a triangle to a hexagon) are cut where the others have their corners, at the same fraction of the length of the loop from its start; corners within a thousandth of the loop of each other are one.
- *Sides.* One face per column of matched curves and per band. A band runs between two sections that follow each other when the loft is ruled, closed or has two sections, and through all sections otherwise. The surface is a plane where every control point lies in one (line to line in a plane: a box, the frustum of a pyramid), a cylinder or a cone for an arc to a coaxial arc over the same angles (whole circles about one axis, in straight bands, give one face without a seam, as an extrusion does), and otherwise a B-spline surface that contains every section curve exactly: the curves of a column are brought to one degree and one knot vector (`geom::refine`: knot insertion and degree elevation, which change the description of a curve and not the curve; arcs are exact rational quadratics), and each row of their control points, as homogeneous points, is joined by a straight line (ruled), by the spline of degree up to 3 that interpolates it at chord-length parameters (smooth), or by the closed cubic spline with continuous curvature (a smooth ring; one Bézier band per pair of sections). The parameters are the same for every column, so neighbouring faces share their edges exactly. The ends are planes on the first and the last sketch plane.
- *Soundness.* Refused in the kernel, with the sections named: planes that cross within the profiles (each profile lies wholly on one side of the plane of the next), sections in one place, a plane that lies along the loft, a side whose normal vanishes (it folds: half a turn of twist), and everything `topo::check` knows. What folds nowhere and still passes through itself (a bend that runs on into its own beginning) the kernel cannot see: regeneration runs `tess::body_self_intersections` on every loft with the parameters of `document.check {"deep": true}` and fails the feature with the two faces that cross and the advice to give a section another `start`. A loft that regenerates is one the deep check passes.
- *Names.* A side is `F9:side(e3,e7)`: the matched curves of its column, one per section, up to the section the face ends at (a face through all sections names all of them; in a ruled loft the face of the second band is `F9:side(e3,e7,e5)`; in a closed loft the face from the last section back to the first names all and the first again). The ends are `F9:startCap(…)` and `F9:endCap(…)` after the curves of the first and the last section. The parts a curve was cut in (a quartered circle, a side cut to match two) carry the curve's id, so their faces share a name: as after a boolean that cuts a face, the name then resolves to several faces. Edges and vertices are named by the faces they lie on (`F9:between[…]`, `F9:corner[…]`), as for a boolean. Names follow the matching: an edit that turns a section so far that another corner is nearest changes which curves are matched, and the old names then point at nothing rather than at another face.
- *Failures.* A section's sketch that is missing, suppressed, later in the history or failed fails the loft with `sections: section 2: …` and `causedBy`; so does a sketch with no closed profile, with several, or with a hole, and a `start` that is not a curve of the profile. `feature.edit` takes `sections`, `ruled` and `closed`.
- *Not built.* Guide curves, tangency at the ends, a section that is a single point (a tip), profiles with holes (loft the hole on its own and cut it out), and analytic recognition of a smooth loft that happens to be a surface of revolution (it is a B-spline surface).

**Extrude ends (2026-10-13, M8.5).** `doc::Extrude` has, besides `sketch`, `distance` and `symmetric`, an `end` (`ExtrudeEnd`: `Distance`, `ThroughAll`, `UpToFace { face: PersistentName }`) and `reversed` (against the sketch's normal; for a distance the same as negating it). `feature.extrude` takes one of `distance`, `throughAll` and `upTo`, with `symmetric` and `reversed`; `feature.edit` changes the end by giving the new one.

- *Symmetric:* `distance` is the whole length, half to each side of the sketch plane.
- *Through all* is decided in `regen` (`regen/src/extrude.rs`, `through_all`), from boxes, without a boolean. "All" is every body the features before this one have made that is still a body of the document at that point of the history (not taken by a boolean, a transform or a pattern before it) and that lies in the way: its box (`Body::bbox`, conservative), seen along the sketch's normal, overlaps the box of the profiles. The extrusion runs from the sketch plane to past the farthest such box by a margin (a hundredth of the way, at least a thousand tolerances), so that a cut never ends flush with the far side; `symmetric` runs from before the nearest box to past the farthest. With nothing in the way the feature fails and says so (`there is nothing to go through along the sketch's normal: none of the 2 bodies built before this feature lies in the way of the profile`). The length is not stored: it follows the bodies. The regeneration cache knows that such a feature depends on every feature before it (`FeatureKind::uses_all_earlier`).
- *Up to a face* is `kernel::extrude_to::extrude_up_to`. The profiles are extruded past the face's surface, a *tool* solid is built that has that surface as one of its faces (a block behind a plane; the solid cylinder, ball or ring of a cylinder, sphere or torus; for a polynomial Bézier or B-spline face the solid behind the whole patch, with a wall under each of its borders), and the kernel's boolean takes the tool away (or, from a sketch plane inside a ball or a cylinder, keeps what is inside it). What hangs on to the start caps is the result; what comes out on the other side of a cylinder is dropped. So the end lies on the face's *surface*: where the profile hangs over the face's edge it ends on the plane, cylinder, sphere or torus continued, and a freeform surface ends where its patch ends. The profile has to reach the face itself somewhere (looked at on nine points per edge of the end and of the face; the module documentation says what that cannot see). The reference is the face's persistent name, resolved against the body of the feature the name starts with, as it is at that point (a copy name such as `F3:copy(1)/F2:face(1)` against the boolean's body); pieces of one face count as the face, and a cap whose outline changed still names its surface, as for a sketch's plane. A name that points at nothing fails the feature with the name and the faces that are there (``upTo: `Part` no longer has a face F3:copy(1)/F2:face(1); its faces are: …``); it never lands on another face, and the features that do not depend on it are built. Pointing `upTo` at a face that is there repairs it.
- *Names.* The faces are named as a plain extrusion names them: `startCap` in the sketch plane, `side(e7)`, and `endCap` (with the outline of its profile) for the faces on the target surface, which need not be flat, and can be several faces with one name when the boolean left the end in pieces. Edges and vertices get their plain names too (`endEdge(e7)` where wall `e7` meets the surface) whenever each can be told; when one cannot, the body has no edge and vertex names, as after any boolean.
- *Refused, each with its reason:* a face parallel to the direction (or a freeform patch that turns away from it somewhere); a face behind the sketch plane (`reversed` turns the extrusion round; the direction is never guessed, so that an edit which moves the face to the other side fails instead of flipping the body); a surface that passes through the sketch plane inside the profile; a profile part of which passes beside the surface or beyond the patch; a profile that misses the face; `symmetric` with `upTo`. **Not built:** a cone face and a rational freeform face as the end (`Unsupported`); a second end on the other side (from a face up to a face); an offset from the face. Whatever the boolean refuses is the feature's failure, with the boolean's reason.

Measured (`crates/kernel/tests/extrude_to.rs`, `crates/engine/tests/extrude_ends.rs`, scales 1e-3, 1 and 1e6, world and tilted frames): a round profile up to an inclined plane has the volume of a cylinder of the mean height and an elliptic end of area πa²/cos θ; a rectangle up to a lying cylinder and a round profile up to a ball (from outside and from inside) have their closed forms to 1e-9; a rectangle up to a parabolic B-spline wall has the area under the parabola times its height, and the arc length in its area, to 1e-7.

**As built so far (M6, first slice).** An extrusion names what it makes by role and by the sketch entities involved, written `F2:side(e7)`: the caps are `startCap` and `endCap` with the entity ids of the profile's outer loop; a side face is `side(curve)`; the cap edges are `startEdge(curve)` and `endEdge(curve)`; the upright edge swept by a corner is `lateralEdge(incoming, outgoing)` in the direction the loop runs through that corner, and the corners are `startVertex` and `endVertex` with the same pair. The names do not depend on the order of the curves or on what else is in the sketch: drawing a hole afterwards adds names and changes none. Known limits: drawing a loop *around* an existing one turns it into a hole and reverses it, so its corner and upright-edge names get their pair the other way round (the old names go missing rather than land elsewhere), and the caps are renamed after the new outer loop. **Resolution (M6).** `doc::PersistentName` is the name as data (feature, role, sources; `F2:side(e7)` as text). `regen` resolves it against the features regenerated so far: the feature must exist, come earlier in the history, have succeeded, and have a face whose origin is exactly that name. Anything else fails the referring feature with a reason that says which of those it was and lists the names that do exist; a name never resolves to a different face. One looser match exists, for the *plane* of a sketch only: all caps of one role of one extrusion lie in one plane and share one frame, so a cap name whose outline is no longer there (`F2:endCap(e5,e6,e7,e8)` after the corners were rounded, or simply `F2:endCap()`) still gives the sketch its plane, that of any cap of that role of that feature. The stored name is not rewritten. A side face has no such fallback. The first consumer is a sketch on a face (`SketchPlane::Face`), and the suite in `crates/engine/tests/naming.rs` holds the scenarios.

**Bodies made from bodies (M6).** A transform, a mirror and a pattern make their body out of the body of an earlier feature. That feature's result stays in the regeneration (names are resolved against it) and is marked as taken by the later feature, so its body is no longer one of the document's bodies; `keep` leaves it its body. A body can be taken once. Every entity of the new body is named after the entity it is the image of, as a *copy*: `F5:copy(2)/F2:side(e7)` is the image, in instance 2 of F5, of the face F2 calls `side(e7)` (instance 0 for a transform or a mirror). The part after `/` is a name of its own, so copies of copies chain (`F9:copy(0)/F5:copy(2)/F2:side(e7)`, at most 32 deep). A copy resolves by walking the chain down to the face as it was first made, with the rules above (the looser match for caps included), and carrying its frame back up through the motion of each copy; a name whose instance no longer exists, or whose inner name is not of the body the feature was made from, points at nothing. After a mirror the frame is still seen from outside and right-handed: x is the image of x, and y points the other way than the image of y. Instances of a pattern that touch or overlap (their boxes come within the tolerance of each other) are joined by the kernel's union; the faces keep their copy names (a face merged from the faces of several instances is named after the first and answers to the others as aliases, see *Merged faces carry aliases* below), and edges are then referred to by the faces they lie between, as after any boolean.

**Booleans (M7).** A boolean feature combines the bodies of two earlier features (target and tool) and takes both, unless the tool is kept. Every face of the result is a face of one operand, or a piece of one, and is named as a copy of it: instance 0 is the target, 1 the tool (`F7:copy(0)/F2:endCap(e5,e6,e7,e8)`, `F7:copy(1)/F3:face(0)`). A face cut into pieces gives several faces with one name. That is resolution outcome `Many`; for the plane of a sketch it is accepted, because the pieces lie on one surface. A face the boolean removed is not among the result's names, and a reference to it fails and lists the faces that are there. **Edges are referred to by the faces they lie between** (`regen::edges_between`, `document.edges`): an edge of a solid is where two faces meet, and faces have names through every feature kind. "The edges between `F4:copy(0)/F2:endCap(...)` and `F4:copy(1)/F3:face(0)`" is the rim of a drilled hole, whatever the body's edge numbering is, and it is a list: two faces can meet in several edges, and pieces of one face share a name. Since 2026-10-14 an edge of a boolean also has a name of its own, made of exactly that pair (`F7:between[a,b]`, below); sweeps and primitives name their edges and vertices by where they came from. **Merged faces carry aliases (2026-10-13).** Faces that a boolean split needlessly, or that continue across both operands on one surface (the tops of two flush blocks united), are merged again by the kernel, so a union of flush bodies has no seam. The kernel lists every contributing face of such a face (`BooleanResult::merged`, the target's faces first, in order). `regen` names the face after the first contributor (`F3:copy(0)/F1:face(1)`) and gives it the names of the others as *aliases* (`F3:copy(1)/F2:face(1)`; `Names::aliases`, listed by `document.inspect` as `faceAliases`, per face, only when a body has any). A reference resolves by any of a face's names: a sketch on the merged top by the tool's cap name lands on it, with the frame of the tool's cap (the one plane), and `document.edges` finds the rim by either name. The stored name is not rewritten, and nothing is stored in the file: aliases are derived at regeneration, so a document written before this change resolves as it did, and a name that resolved without merging (a face of the tool that kept its own name) still does. Edits upstream: while the faces stay flush the alias follows the merged face; when they are no longer flush the name means the tool's own face, which is there, and the sketch goes with it (not a retarget: the same origin); when the tool's face is gone (sunk into the target) the name is `Missing`, listed or not. The pattern feature's union of touching instances does the same (`F2:copy(0)/F1:face(1)` with aliases `F2:copy(1)/…` and `F2:copy(2)/…`, in instance order). Known limit: nothing consumes an edge reference yet (fillets are M9).

**Edges and vertices by their faces (2026-10-14).** Every edge and every vertex of every body has a name of its own: within one body no two edges share a name and no two vertices do (`regen::Names::edges`, `vertices`; pinned by `crates/engine/tests/naming_entities.rs`). Where the name comes from depends on what made the body, and there is one rule per kind, not two schemes side by side:

- *A primitive and a sweep* name an edge and a vertex by where it came from, as before: `F1:vertex(6)`, `F2:lateralEdge(e5,e6)`, `F2:endVertex(e5,e6)`. Those names are complete and unique on every primitive and on every sweep the suite builds (profiles with holes, arcs, two arcs or two splines that share both ends, revolutions whole and partial and on the axis, an extrusion up to a face).
- *A transform, a mirror and a pattern whose instances stay apart* name an entity as the copy of the one it is the image of (`F5:copy(2)/F2:endVertex(e5,e6)`), as they do faces. What the source's entities answered to besides their own names (aliases, also those of faces) the copies answer to as copies; before 2026-10-14 the aliases of a merged face were lost in a copy and in a second boolean, which was a hole.
- *A boolean and a pattern whose instances are joined* name an edge by the faces it lies between and a vertex by the faces that meet in it, the faces by their names in that body, in the order names are compared in (by feature, role, sources, then what a copy is a copy of; a name typed or stored with its faces in another order is read as the same name): `F7:between[F7:copy(0)/F1:face(1),F7:copy(1)/F2:face(0)]` is the rim where the hole (the tool's wall) leaves the top of the target, `F7:corner[F7:copy(0)/F1:face(1),F7:copy(0)/F1:face(2),F7:copy(1)/F2:face(4)]` the corner where a slot's wall meets the top and the front. A seam, and the cut between two pieces of one face, has its face twice (`F7:between[a,a]`), the same pair `document.edges` takes. This is the decision that an edge is referred to by the faces it lies between ([`decisions.md`](decisions.md)), made into a name: it needs nothing from the kernel but the body and the names of its faces, so it is the same for a boolean and for the row of unions that joins a pattern, it does not depend on the order in which the kernel emitted the entities (`regen/src/entity.rs`, tested by naming a body and the same body with every list in another order), and it survives every edit that leaves the faces round the entity what they were.

*When several entities lie on the same faces* (the two halves of an edge a slot cut through, the two points where an edge enters and leaves a round notch, the edges on the two pieces a face was cut into, which share the face's name) none of them gets the bare name. Each then also lists, after `|`, the other faces near it: the faces at the vertices of the edge, or at the vertices one edge away from the vertex, and when that does not tell all of them apart the faces up to four edges further away, all of the group equally far, at the nearest distance that tells them all apart (`F7:between[top,front|left,slotWall]`). Why faces near it and not the vertices at its ends or its place along a loop: a vertex is itself named by faces, so that is the same information, and the order along a loop changes with every edge an edit adds. Why not always: the bare name stays valid through edits elsewhere on the body, and a name with more faces in it is lost by more edits. *When no face tells them apart* (the two circles in which a torus half sunk into a plate cuts its top; the two straight edges of a cylinder cut in half lengthwise, and the corners at their ends) they get a number after the list, `F7:between[a,b|c](0)` and `(1)`, in the order of where they lie in space: by x, then y, then z, of the vertex or of the middle of the edge, coordinates within the document's tolerance of each other (or joined by a row of such steps) counting as one, so rounding in the last digits cannot change the order and the scale does not.

*An entity an operand already had* (the kernel's `EdgeSource::Kept` and `VertexSource::Kept`) also answers to the name the primitive or sweep that first made it gave it, as a copy and as an *alias*: `F7:copy(0)/F1:vertex(6)`, and through three booleans `F9:copy(0)/F7:copy(0)/F5:copy(0)/F1:vertex(6)` (`Names::edge_aliases`, `vertex_aliases`; `aliases` in `datum.references` and `document.edges`). It is given only when exactly one entity of the result came from there: the two pieces of an edge a slot cut through are neither of them "the" edge, and both lose the alias. The name an entity had by its faces in a body in between is not carried along (it says nothing the faces here do not say, and the lists would grow with every boolean). A reference resolves by the own name or by an alias (`Names::edge_named`, `vertex_named`; a datum point at a vertex of a boolean or of a joined pattern, which failed before, is the first consumer).

*What an edit does to such a name* (each case is a test in the suite):

- Sizes change and the topology does not (a variable, a radius, a tool moved so that it cuts the same faces; three booleans in a row, at scales 1e-3, 1 and 1e6): every name stays on the same entity, checked by the faces on its sides, the names of the vertices at its ends and the edges that end in it, and for ten corners by the closed form of where the corner must be.
- An entity is removed (the slot no longer reaches the front): exactly the references to it fail, with the name (``at: `Part` no longer has a vertex F7:corner[…]; its vertices are: …``), the others stay where they were, and putting the entity back repairs them.
- A second entity appears on the same faces (the slot now cuts the top front edge in two): the bare name and the alias are gone and two longer names are there. A reference to "the edge between the top and the front" fails; it does not land on one of the halves. The reverse edit brings the name back.
- **Where stability cannot be had.** (1) *A numbered name.* The number is a place in space, not an origin. While the tied entities are all there and keep their order it stays; when one of them goes the others lose the number (the reference fails, which is right); but an edit that keeps them all and changes their order in space moves the number to another entity without any failure. The minimal example is in the suite: a cylinder cut in half lengthwise, both operands turned half a turn about the axis by one variable; the solid is the same solid turned, every name is still there, and `…(0)` and `…(1)` are each on the image of the other. Use the alias instead when there is one (the two edges where the walls of a lens meet are numbered as edges of a boolean, and answer to `…/F2:lateralEdge(e6,e4)` and `(e4,e6)`, which do not move). A feature that takes such a name should say so to the user; none does yet. (2) *An alias follows the kernel's choice where entities of both operands coincide.* The kernel reports one source per edge and vertex (where a vertex of the target lies on one of the tool, the target's; for an edge merged from two collinear ones, the least), so the other operand's name for it is not an alias, unlike the faces, which carry every contributor. (3) *A name with faces after `|` is lost by an edit to those faces*, also when the entity itself did not change: louder than needed, never wrong. (4) *Pieces of one face share its name* (unchanged), so "the corner where the top, the front and the slot meet" is two corners when the slot is cut by one face (a cylinder): that is the tie the faces near it, or the number, break.

Not built: a consumer of an edge's own name (datums, chamfers and `document.edges` take the pair of faces, which gives the list of edges between them; a chamfer takes them all, see *Chamfers* below), the names in `document.inspect` (it has `faceNames`; edges and vertices are listed by `document.edges` and `datum.references`), and a way for a feature to ask for "every piece of what was this edge".

**Chamfers (2026-10-14, M9: the first blend, and the first feature that consumes edges).** `doc::Chamfer` has `edges` (a list of references), `size` (`ChamferSize`: `Equal { distance }`, `TwoDistances { distance, second }`, `DistanceAngle { distance, angle }`, all expressions) and `chain`. It makes its body from the body of an earlier feature and takes it, like a transform.

- *What a chamfer holds of an edge* is **the names of the two faces the edge lies between, in order**: `[F1:face(1), F1:face(2)]`. Why the pair and not the edge's own name: (1) the order of the pair is what says which face the first distance is measured along and which face the angle is taken from, and a name of an edge has no first face; (2) after a boolean the edge's own name *is* that pair (`F7:between[a,b]`), so nothing is lost there, and on a sweep or a primitive `document.edges` lists the pair beside the name; (3) the pair survives what the own name does not: when a later edit cuts the edge in two (a slot through it), the own name is gone and two longer names are there, while "the edges between the top and the front" are both pieces, and both stay chamfered, which is what the user meant; (4) no numbered name is ever stored, so limit (1) of *Where stability cannot be had* cannot retarget a chamfer. The price: two faces that meet in several edges are chamfered along all of them, and one of several cannot be picked (not built: a reference by the edge's own name, for that case). Which body is chamfered is not stored apart: it is the body of the feature the first face is of, and every other face has to be of that feature too.
- *Resolution.* At every regeneration each pair is found again with `regen::edges_between`. A face that is gone fails the feature with the parameter, the feature and the name (``edges.0: `Notched` no longer has a face F3:copy(1)/F2:face(3); its faces are: …``); faces that no longer meet fail it with both names (``edges.1: the faces … and … of `Base` do not meet in an edge (any more)``); what is made from a failed chamfer fails naming it and carries `causedBy`, and the body the chamfer would have taken is its source's again, as for every feature (*A feature that fails*). Repair is `feature.edit` with `edges`, which gives the document built that way from the start. With `chain` each edge found stands for the edges that continue it smoothly as well (`kernel::chamfer::tangent_chain`: at each end the one other edge that leaves the vertex straight on, both ways, until none does or the chain closes); along the chain the "first" face is the one the edges share, or what continues the first face.
- *Which face gets which distance.* `distance` is measured along the first face of the pair, `second` along the second, each along the face and at right angles to the edge; `angle` is the angle between the first face and the chamfer face, inside the corner that is cut away or filled, so against a square corner the second face is cut `distance · tan(angle)` back and in general `distance · sin(angle) / sin(angle + θ)` with θ the angle between the two faces across the edge. Turning the pair round turns the distances round.
- *Names of what a chamfer makes.* A face of the body that is still there is a copy, instance 0, of the face it was (`F9:copy(0)/F2:side(e7)`), with the aliases it had, as in every feature that makes its body from another; a sketch on it lies where it lay. The face in the place of the edge of reference `k` is `F9:chamfer(k)` (role `chamfer`, the place of the reference in the chamfer's list). When that reference gave several edges (pieces between the same two faces, or a chain) their faces are `F9:chamfer(k,0)`, `F9:chamfer(k,1)`, … in the order of where the edges' middles lie in space (x, then y, then z, as numbered edge names are counted, with the same limit: an edit that changes that order moves the numbers). The flat face where three chamfers meet is `F9:chamferCorner(i,j,k)`, by the references of the three edges. Chamfer faces in one plane that became one face are named after the first and answer to the others as aliases. Why a number and not the two faces, as an edge of a boolean has them: the edges and vertices of the chamfered body are named by the faces they lie on, and a name in such a list lists no faces itself, so a face's name has to be flat. The number is the place in this feature's own list, which no upstream edit changes; taking an edge out of the list renumbers the ones after it. The edges and vertices of the result are named by their faces (`F9:between[F9:chamfer(0),F9:copy(0)/F1:face(1)]`), and one the body already had also answers to a copy of the name it had there, exactly as after a boolean (one implementation: `Names::name_entities`).
- *The frame of a flat chamfer face* (what a sketch on it gets): z out of the body; x along the edge, in the direction of the cross product of the directions into the first and the second face (each along its face, away from the edge); the origin where the cut line on the first face starts in that direction. It depends on the pair and the geometry, not on which way the kernel runs the edge.
- *Tests:* `crates/engine/tests/chamfer.rs` (closed forms at 1e-3, 1 and 1e6, `document.check` with `deep`, names, upstream edits that move and remove the edge, repair, a sketch on the chamfer face placed by its frame, a chamfer on an edge of a chamfer, save and reopen, everything refused), `crates/kernel/tests/chamfer.rs`, `crates/format/tests/format.rs`, and FreeCAD on the STEP export (`crates/engine/tests/step_freecad/chamfers.rs`).

**Primitives (M6).** A primitive is built in a fixed order, so the number of an entity says where it came from: its faces, edges and vertices are named `F3:face(1)`, `F3:edge(4)`, `F3:vertex(0)`. For a block the faces are 0 bottom, 1 top, 2 front (-y), 3 back (+y), 4 left (-x), 5 right (+x) in its own axes; for a cylinder 0 the wall, 1 the bottom, 2 the top; for a cone 0 the side, 1 the base. A sketch on such a face has the frame the kernel gave the face, seen from outside (on the top of a block: the block's own x and y at its height). The order is part of the kernel's contract and is pinned by `crates/engine/tests/naming.rs`.

**The frame of a sketch on a face** is the face's own, seen from outside the body (z is the outward normal, moved by the sketch's offset): on the end cap of an extrusion, the axes and origin of the extruded sketch, moved to the end; on the start cap the same origin and x axis with y reversed; on a side face made from a line, x runs along the line (in the direction the profile's loop runs) and y along the extruded sketch's normal, and the origin is the origin of the extruded sketch dropped straight onto the face. That point moves only when the face moves along its own normal: not with the line's end points (a corner radius), and not with the depth or direction of the extrusion. "Start" is the cap in the sketch plane and "end" the far one, whichever way the extrusion goes. Known limits: turning an extrusion round (a negative distance) puts its end cap on the other side facing the other way, so a sketch on it is mirrored in y, and a sketch on a side face stays on its side of the sketch plane rather than following the body; primitives do not name their faces yet; a curved face cannot carry a sketch.

## 5. Kernel

### 5.1 Geometry (`geom`)

```rust
pub enum Curve3 { Line(..), Circle(..), Ellipse(..), Nurbs(..), Trimmed(..), Offset(..), SurfaceIso(..), Intersection(..) }
pub enum Curve2 { Line(..), Circle(..), Ellipse(..), Nurbs(..) }           // parameter-space curves on a surface
pub enum Surface { Plane(..), Cylinder(..), Cone(..), Sphere(..), Torus(..), Extrusion(..), Revolution(..), Nurbs(..), Offset(..) }
```

Every kind implements evaluation with derivatives, parameter range and periodicity, bounding box, closest-point projection and inversion, and reversal. Projection as built (`Surface::project`): closed form for the analytic kinds; for Bézier and NURBS surfaces a search from the samples of a 16 × 16 grid that are nearer than their neighbours (and from a four times closer look around the nearest), each followed downhill by a damped Gauss–Newton iteration that puts the curving of the surface in when its steps fall short (Newton). It walks across the seam of a surface that closes on itself, half-steps towards a border that is a single point (a pole, a collapsed patch edge) and slides along a border of an open patch. The answer is a local nearest point, and the nearest one for a point closer to the surface than the surface curves, on a surface whose features are larger than a sixteenth of its domain (`crates/geom/tests/project.rs`). Intersections (curve/curve, curve/surface, surface/surface) are dispatched on the pair of kinds: closed-form where a formula exists (plane/plane, plane/cylinder, …), numeric marching with a tolerance otherwise. A pair that is not implemented returns `Unsupported`, and the test suite lists which pairs are covered.

#### Intersections as built (2026-10-13)

`geom::intersect::meet_surfaces(a, b, within, tolerance)` returns `None`, `Coincident { same_normal }` or `Meets(Meeting { curves, points })` for any two surfaces. Each `MeetingCurve` has the curve, the `range` of it that is meant, and the flags `closed`, `tangent` (the surfaces touch along it without crossing) and `exact`; an approximate curve carries a `deviation` that bounds its distance to both surfaces and is at most the linear tolerance. `points` are isolated touches. Curves are clipped to the box `within`, which is what makes a hyperbola or the curve of two crossing cylinders finite. The two surfaces are put in a fixed order first, so `meet(a, b)` and `meet(b, a)` are the same computation and the same result, bit for bit. **Curves never cross each other except at their ends:** where two branches cross (the surfaces are tangent there: two equal cylinders at right angles, a bitangent plane on a torus, Viviani's curve) every arm is a curve of its own that ends on the crossing point. `intersect_surfaces` (planes and cylinders, no box) is unchanged and still what `kernel::boolean` calls.

| Pair | Result |
|---|---|
| plane / plane, plane / cylinder, cylinders with parallel axes | exact: line, circle, ellipse, lines (the earlier closed forms) |
| plane / sphere, sphere / sphere | exact: circle, or a touch point |
| plane / cone | exact: circle, ellipse, parabola and one branch of a hyperbola (the last two as rational quadratic NURBS, the parabola polynomial), the apex alone, one ruling (tangent) or two; only the cone's own nappe |
| cylinder, cone, sphere, torus about one axis | exact: circles where their profiles meet (tangent ones flagged), the apex or a pole as a point |
| plane / torus, plane across or through the axis | exact: one or two circles about the axis, or the two sections of the tube |
| cylinders of equal radius whose axes cross | exact: two ellipses, as four half-ellipses that end on the two points where the cylinders touch |
| cones of equal half-angle with parallel axes | exact: the conic in the plane they meet in (not when that plane passes through the apexes: numeric) |
| equal spheres, cones, tori (cylinders, planes) | `Coincident` |
| every other pair, including anything with a Bézier or NURBS surface | numeric: C¹ cubic NURBS within the tolerance of both surfaces |

**The numeric method** (`intersect/march.rs`; the module comment has the argument in full). One surface is walked in its parameters, the other is a signed distance (closed form for the analytic kinds, closest point for freeform surfaces), and the intersection is the zero set of that distance over the first surface's parameter rectangle. A quadtree discards a cell when the distance at its centre exceeds what the surface can cover within the cell (a distance is 1-Lipschitz), and stops dividing when a bound on the second derivatives shows the distance to be monotonic along u or along v over the whole cell: such a cell holds no tangent point, and a branch through it is detected by the signs at its corners. Cells that reach the size of the tolerance without either holding are searched by Newton iteration for the point where the surfaces are tangent: a minimum or maximum of the distance is a touch point, a saddle is a crossing of two branches, anything flatter is refused. The same search runs earlier, as soon as cells keep failing both tests (around a point of tangency the gradient is small over an area that grows with the looseness of the bound, so thousands of cells per level fail there): where it finds the point and the gradient follows the Hessian's second-order model within a quarter on two rings around it, the disc inside the rings is settled without cells: it holds the touch, the two branches through the crossing (seeded along the directions in which the Hessian vanishes), or, around a critical point off the other surface with the distance of the sign its Hessian keeps, nothing. A touch is only recorded where the surfaces are within the tolerance and within a floor cell's reach of each other, which is where the cells alone would have found it. So no loop larger than a floor cell (twice the linear tolerance across) is missed, provided the derivative bounds and the rings hold: the bounds are proofs for analytic surfaces, Bézier patches and NURBS surfaces, rational ones included (since 2026-10-13: `RationalBezierPatch::derivative_bounds`, over the pieces of each span quartered twice), and estimates from samples for the curvature of freeform surfaces used as the distance (taken from how fast the normal turns on a grid near the point, doubled twice as margin); the rings are samples. Branches are marched with the step limited by the turn of the tangent, end where they close, leave the rectangle, run off the edge of the other surface or reach a crossing point or apex, and are fitted by a cubic Hermite spline that is refined until it is within half the tolerance of both surfaces and of the intersection itself at three places per span.

A contact where the Hessian of the distance is degenerate (the surfaces touch along a curve, or to more than second order) is a touch when the distance keeps one sign on three rings of samples around it: the surfaces do not cross there, so nothing is divided. **Refused, as errors:** such a contact where the sign changes on every ring (`Unsupported`); surfaces nearly tangent or coincident over an area, a curve that needs more points or evaluations than the caps allow, a fit that does not reach the tolerance, a tolerance finer than rounding allows at the size of the box (`NoConvergence` or `InvalidParameter`). Nothing partial is returned.

`intersect_curve_surface(curve, surface, tolerance)` covers every curve kind against every surface kind. Closed form: a line with a plane, cylinder, sphere or cone; a circle or ellipse with a plane and with a cylinder it is a section of a parallel cylinder to; a circle with a sphere, and with a surface of revolution about its own axis. Everything else is root finding on the signed distance along the curve with the same two certificates in one dimension (`intersect/curves.rs`); a hit where the curve stays within the tolerance of the surface without crossing by more is `tangent`, and a curve within the tolerance everywhere is `OnSurface`.

### 5.2 Topology (`topo`)

```text
Body ── Shell ── Face ── Loop ── Coedge ── Edge ── Vertex
                  │                 │        │        │
               Surface           Curve2    Curve3   Point     (+ orientation flags, tolerances, persistent names)
```

- A **body** is a set of shells: a *solid* (closed, oriented shells), a *sheet* (open faces) or a *wire* (edges only).
- A **face** is a surface trimmed by loops; a **coedge** is the use of an edge by a face, with a direction and a parameter-space curve.
- Storage is arena-based with typed ids, and persistent: an operation builds a new body that shares unchanged parts with its input.
- **Genus** (`topo::genus`): from Euler–Poincaré, `V − E + F − R − 2H = 2 (S − G)`. `R` is, per face, its loops beyond the first (−1 for a face without loops), which counts every face as a disc with holes. A face on a torus that still has the torus's handle (the whole torus, or the torus less the discs inside its loops) is not one and takes 2 off (`H`). A torus face with a loop around the axis or around the tube is a band, and one inside its loops is a patch: neither counts. The hole a drill leaves in a torus and the plug it takes out have the same loops walked the other way, so which of the two a face is, is read off the area its loops enclose in parameter space. A spline surface that closes on itself is not known to.
- **Validity checker** (`topo::check`): Euler–Poincaré, every edge of a solid used by exactly two coedges with opposite directions, loops closed, coedge curves on their surface within tolerance, vertices on their edges, consistent orientation, no self-intersection (the expensive checks behind a level flag). Every kernel operation is tested to return bodies that pass it.
- **Self-intersection, as built (2026-10-13):** `topo::check` does not test it. The test is `tess::body_self_intersections(&Body, &SelfCheckParams) -> SelfCheck`, in `tess` because it works on the mesh and so stays independent of the kernel it checks: it tessellates the body (chordal tolerance 1/1000 of its diagonal), finds the triangles that meet without being neighbours (§6), and reports crossings and overlaps between faces, each with a depth and with the margin `deviation(f) + deviation(g) + 2 × tolerance` that the approximation alone could explain (`deviation` is the chordal tolerance, or 0 for a plane bounded by straight edges, whose mesh is the face). A finding deeper than its margin is *certain*; one within it is reported as such and proves nothing (tangent faces, a ball resting on a plane). Findings within the margin between curved faces are looked at again with a mesh four times finer, twice by default. Flat faces within twice the modelling tolerance of one plane that share area are an overlap. Shells that do not cross are checked for where they lie, by the winding number of the other shells at a point of each: an outward shell must be in no material, a cavity in material. It is a test oracle today (`crates/testkit/tests/self_intersection.rs`, [`testing.md`](testing.md) oracle 9, which also lists what it cannot see), not yet a level of `check` or a step of the kernel operations.
- **Mass properties:** volume, surface area, centroid and inertia tensor, computed from the exact B-rep (surface integrals), independent of the tessellator. Volume and centroid are taken about the middle of the body, not the origin of the model (2026-10-13): a small body far from the origin is then measured as well as the same body at the origin. These are the backbone of the test oracles. As built (`topo::mass_properties`: area, volume, centroid): each face is a boundary integral in its surface's parameters, and the result does not depend on how the surface is parametrised. A sphere face is measured in a frame chosen for its boundary, not in the surface's own (one pole in the middle of the boundary, the other as far from it as it gets); on a cone the integral runs from the apex whenever the boundary comes near it. Every boundary integral is computed with half the panels its edges need, with all of them, and with twice as many until two sums in a row agree to 1e-12; a face for which they never do is an error (`Unsupported`), as is a face that lies outside its own loops (`UnboundedFace`). Only plane faces bounded by lines, circles and ellipses skip that check: their sums are exact. On a spline surface every panel, across the face and along its boundary, ends at the surface's knot lines (and an edge's panels at its own knots too), and the panels across the face are doubled along with the boundary's; a face that holds a pole of a spline surface of revolution is integrated from that pole. On a freeform surface the nodes along one piece of an edge are projected each from where the last one landed (`Surface::project_from`, a few evaluations instead of a search over the whole surface), and the search is run only where the short way does not land on a foot of the node: within 1e-5 of the body's size and square to the surface, which is the same point the search finds. A spline edge of eight knot spans or more (the curve in which two surfaces meet, as the kernel fits it) is summed first with the eight-node rule on one panel per span and then with the sixteen-node one, before its panels double.
- **Moving, mirroring, merging** (`topo::transform`): `Body::transformed` maps a body by an isometry exactly (no curve or surface changes kind; scaling and shear are errors) and keeps every entity id. Curves keep their parametrisation, so edges are untouched. A mirror turns right-handed things left-handed: frames become `(Tx, Ty, −Tz)`, every loop is walked the other way round, and faces on planes and freeform surfaces toggle `reversed`, while cylinders, cones (half-angle negated), spheres and tori keep their outward normal and get `v` negated. `Body::bbox` is a conservative box from the exact geometry (tight for planes, cylinders and cones with analytic edges; the whole surface for spheres and tori, the control net for freeform). `merge` puts the shells of several bodies into one and reports the id offsets; it does not check that they are disjoint. These are what the transform, mirror and pattern features build on.

### 5.3 Operations (`kernel`)

Each operation is a pure function: bodies and parameters in, `Result<OpResult, KernelError>` out, where `OpResult` holds the new body and the **origin map** (for every result entity: which input entities and which role produced it), which feeds persistent naming.

| Group | Operations | Milestone |
|---|---|---|
| Primitives | box, cylinder, cone, sphere, torus | M3 |
| From sketches | profile detection (closed regions from sketch entities), extrude, revolve | M6 |
| Loft | a solid through a row of closed profiles: ruled, smooth, closed into a ring (`kernel::loft`, ✅ 2026-10-14, see *Loft*) | M9 |
| Booleans | union, subtract, intersect on solids; imprint, split | M7 |
| Local | chamfer (✅ 2026-10-14, see *Chamfers as built*), fillet (constant radius first), shell, draft, offset face | M9 |
| Sweeps | sweep along a path | M9 |
| Arrangement | transform, mirror, linear and circular pattern | M6–M9 |

**Rules for every operation:**
- **Signature:** `fn(inputs, params: &P, tol: &Tolerance, cancel: &CancelToken) -> Result<OpResult, KernelError>`; `P: Serialize + Deserialize`.
- **Never an invalid body.** The result passes `topo::check` or the operation returns `Err`. Errors name the entities and the reason ("faces F3/cap and F5/side are tangent along a curve; tangent booleans are not supported yet").
- **Deterministic:** no dependence on thread count or hash order.
- **Not registered by itself:** `engine` registers commands; `kernel` stays engine-agnostic.

#### Chamfers as built (M9, 2026-10-14)

`kernel::chamfer::chamfer(body, edges, tolerance)` takes, per edge, the edge, which of its two faces is the first, and a size (two distances, or a distance and an angle), and returns the body with a source for every face (`Kept` faces of the body, `Chamfer` of which requested edges, `Corner` at which vertex), edge and vertex.

**Route: a tool solid per edge and the boolean, not a local operation.** Two routes were open. (a) A local operation: cut the two neighbours at the offset curves, put in the new face, sew. It is what fillets will need in the end, and it keeps every untouched entity as it is; but it needs its own handling of every way an edge can end (the neighbours' other edges, a vertex of any valence, a mix of convex and concave edges, seams, a chamfer that eats a whole neighbour), and each of those is a place to produce a body that is valid in its counts and wrong in space. (b) A tool whose cross-section is the triangle between the edge and the two cut lines, subtracted from the body at a convex edge and added at a concave one. It leaves all of that to a kernel that is measured against a reference kernel (11549 of 11988 corpus outcomes agree, none wrong), whose result is checked or refused, and that names every entity of its result. Its price is the contact it produces by design: two faces of every tool lie in the two neighbours (coincident faces, same normals in a subtraction and opposite in a union), tools of edges that meet overlap each other, a chain's tools end against each other, and a corner plane goes through three existing vertices. All of that is what the boolean kernel handles today (`Contact without overlap`, the coincident rows of its table, merging): of the cases built for this feature it refused none. (b) was taken for the first version, with what it cannot do stated below; (a) remains the route for fillets with a rolling ball and for chamfers on edges the boolean route cannot make a tool for.

**The tool.** *A straight edge between two planes:* a prism, `kernel::extrude` of the triangle (edge, edge + d₁ along the first face, edge + d₂ along the second) along the edge. *A circular edge between a plane, a cylinder or a cone about the circle's axis* (the end of a rod, the mouth of a hole, the foot of a boss, the base of a cone): the same triangle in the half-plane through the axis, turned by `kernel::revolve` through the whole circle or through the arc; the chamfer face is a cone. Convex or concave is read from the solid, never from the direction of the edge: with the faces to the left of their loops seen from outside, an edge is convex when the direction into one face points behind the other. Every tool is made from the body as it was given, so the order of the edges does not change the solid.

**Where an edge ends** (the part a local operation would have to do topologically). When every other edge at the end vertex is convex like the chamfered one (or every one concave), the body near the vertex is what its faces leave of space and the chamfer is one more such face: the tool is made longer than the edge (past where the chamfer plane cuts the other edges there, with a margin; by an angle for an arc), and what sticks out meets nothing, or only material when it is added. Otherwise the tool ends at the vertex, across the edge. That is right when the face the chamfer runs into lies in that plane (the top edge of a step that ends against a wall: the wall grows by the triangle and the boolean merges it into one face), and when the edge continues smoothly in another chamfered edge (a chain: the two tools end against each other and the cut between them leaves no trace). In every other case the end of the tool would stay in the result as a face nobody asked for, which the final check finds.

**Corners.** Two chamfered edges that meet: each chamfer is the whole half-space of its face near the vertex, so their faces meet in the line the two planes share (a mitre), for equal and unequal distances alike. Three chamfered edges of one kind (all convex or all concave) that meet in a vertex with nothing else: the corner is **the flat face through the three points in which the cut lines cross on the three faces**, a triangle; three points are always in a plane, so the rule is the same for unequal distances, as long as the three points are points of the chamfered body: when one chamfer is larger than the other two reach together (on a square corner: d₁ ≥ d₂ + d₃) it takes the corner whole, the other two never meet, and there is no corner face. It is what OpenCascade gives (measured through FreeCAD: all twelve edges of a 4 × 3 × 2 block by 0.25 have its volume, area and 26/48/24 counts to the last digits; three edges, and two, likewise), and what Fusion calls the corner type "chamfer"; the pointed corner where the three planes meet (a "mitre" corner) is not offered. It is made by one more boolean, with a block lying against that plane on the vertex's side. Where more than three edges meet, or convex and concave chamfers meet, there is no corner face: the chamfers are their half-spaces.

**Never a wrong solid.** (1) Before anything is built, a distance for which a cut line would leave its face is refused with the edge, the face and the largest distance that fits (`KernelError::ChamferTooLarge`): the measure is how far the rest of the face's boundary is from the edge along the face (for a straight edge the part of the boundary beside it; for a circle the part in its sector, and the axis), less the distance of another chamfer that cuts the face from the other side. (2) After the last boolean the result is held against what a chamfer is: every chamfer face is there, in one piece, borders both neighbours of its edge, and borders nothing but those, the faces at the ends of its edge, and the chamfers and corners of edges that end where it does; no other face of a tool is left; no chamfer face has become part of a face of the body. Anything else is `KernelError::Chamfer` with the edge (and the face), so a case the estimate in (1) lets through is still refused, with a less exact message. The boolean's own refusals come back as `KernelError::ChamferBoolean` with the edge.

**Supported and not** (tests: `crates/kernel/tests/chamfer.rs`, closed forms at three scales and in tilted frames):

| a circle or an arc between a plane, a cylinder and a cone about its axis, convex or concave (rod, hole, blind hole, boss, cone, half a rod) | built: the face is a cone |

**Cost.** One boolean of the body with a five-face tool per edge, and one per corner: the twelve edges and eight corners of a block take 20 booleans, a few milliseconds together in a debug build. On a body with thousands of faces each of those booleans looks at the whole body; a local operation would not. Not measured on a large body yet.

#### Booleans as built (M7, generalised 2026-10-13)

`kernel::boolean::boolean(a, b, op, tolerance)` returns a `BooleanResult`: the body and, per face, edge and vertex of it, a source (`FaceSource`, `EdgeSource`, `VertexSource`). `boolean_with` takes `BooleanOptions` (`merge`, on by default). `boolean::contains_points` classifies points against a solid with the same ray casting the booleans use; it does not go through `mass_properties`, so a count of sampled points measures a body independently of it.

**Method** (imprint, classify, select, sew, merge; one file per step in `crates/kernel/src/boolean/`):

1. *Section* (`section.rs`). For each face of A and face of B that can meet (their boxes meet and neither lies wholly to one side of the other's surface), the curves in which their surfaces meet are asked of `meet_surfaces`, with the box where both bodies are. A curve is cut where an edge of either face meets the other face's surface (`hits.rs`: the closed forms of `geom::intersect`, and where there is none the roots of the signed distance along the curve, isolated by the fact that the distance changes no faster than the curve moves), and where the curve itself ends. A stretch between two cuts is kept when its middle is in or on both faces. The boolean does not know which pair of surfaces a curve came from, nor whether it is exact: a vertex is always where an *edge's own curve* meets a surface, and is then found on the stretch within the tolerance.
2. *Imprint.* Edges are split at the vertices found on them. Edge pieces and stretches are registered as arcs; two arcs between the same vertices along the same curve are one arc. An edge of B that lies on a face of A, or along an edge of A, is shared from then on, and nothing is matched by position afterwards.
3. *Regions* (`regions.rs`). A face with arcs across it falls into regions: around each vertex the arcs are sorted by direction in the tangent plane (at the apex of a cone: seen along the axis), arcs that leave in one direction are told apart a little further along, and loops are followed keeping the region on the left. An arc with the same region on both sides divides nothing and is dropped. Loops are grouped in a chart of the surface: a loop that goes around a point just to its left is an outside, any other a hole of the innermost outside around it.
4. *Classify* (`classify.rs`, `chart.rs`). One point well inside a region decides for the region: on a face of the other solid with a coincident surface, or inside or outside the other solid by ray casting (a ray that meets an edge or grazes a face is abandoned for another, twelve at most; a point within twice the tolerance of the other body is no use, and the next of up to four is tried). **Inside or outside a face is a winding number in a chart of its surface**, computed from points in space, so no seam or pole is a special place: a plane is its own chart; a cylinder is mapped conformally (angle and `exp(height / radius)` as polar coordinates, evaluated without the exponential); a cone is dropped along its axis onto a plane, which makes the apex an ordinary point; a sphere is projected stereographically from a point chosen clear of the boundary; a torus is cut open along a circle that the boundary does not cross. A face on a sphere or a torus may contain the place its chart leaves out; the winding of its loops about a point just inside it says which. A face without loops is its whole surface.
5. *Select.* See the table below.
6. *Sew* (`sew.rs`). Faces connected through edges form a shell. Where more than two faces meet along an arc, faces and material alternate around it: each face that runs against the arc is paired with the next face counter-clockwise (faces tangent there are put in order a little way off the arc) and every pair gets its own copy of the edge. Where several fans of faces meet at a vertex, every fan gets its own copy of the vertex. The copies are in one place and share nothing, so every result is a manifold. A bounded face on a sphere gets a frame whose poles are clear of its boundary (a sphere is the same surface whichever way its poles point; what reads a face through its parameters is at its best that way).
7. *Merge* (`merge.rs`). Faces that share an edge and lie on one surface facing one way are one face when they are pieces of one face of an operand, or pieces of a face of A and a face of B that are coincident; every edge inside such a group goes and the loops are spliced where it was. A vertex left with two edges that continue each other along one curve goes too, unless its operand had it like that. The face that remains has the source of the lowest-numbered face of A in the group, else of B; a joined edge the lesser of its sources (an edge of A before an edge of B before an intersection). The result passes `topo::check` or the operation fails.

| Region of | Outside the other | Inside the other | Coincident, same normal | Coincident, opposite normals |
|---|---|---|---|---|
| A, union | kept | | kept (the source is A's face) | |
| A, intersection | | kept | kept (the source is A's face) | |
| A, difference | kept | | | kept |
| B, union | kept | | | |
| B, intersection | | kept | | |
| B, difference | | kept, turned inside out | | |

**Contact without overlap.** Bodies that only touch (face against face along a line, a circle or at a point; an edge against a face or an edge; a vertex against anything) have nothing in common: the union is both bodies as shells that share no entity, the intersection is `EmptyResult`, the difference is the first body with the entities it had. A curve along which two faces touch is imprinted like any other; where the result does not need it (it ends inside a face, or has one face on both sides) it leaves no trace, and where it does (a cylinder that touches all four sides of its block cuts it into four parts) it is an edge. A result whose parts hang together only by an edge or a vertex has that edge or vertex once per part.

**Supported and not** (tests: `crates/kernel/tests/boolean.rs`, `boolean_surfaces.rs`, `boolean_contact.rs`, `boolean_random.rs`, `boolean_corpus.rs`):

| Configuration | Result |
|---|---|
| faces on planes, cylinders, cones, spheres and tori; whole spheres and tori; edges on lines, circles, ellipses and splines | operands like any other |
| coincident faces (same or opposite normals; overlapping, touching or sharing edges), on any of those surfaces | handled by the table above, and merged |
| faces that touch along a curve or at a point; bodies that touch along an edge or at a vertex | handled: see *Contact without overlap* |
| curves that leave a vertex in one direction (a circle tangent to an edge it meets) | handled |

| a Bézier, B-spline or rational NURBS face in either body (a domed block against a block, a cylinder, a cone, a ball, a torus or another dome; a rational patch that is a piece of a cylinder, a cone, a sphere or a torus, or none of those, against the same) | operands like any other: see *Freeform faces* below; the curves in which its surface meets another are splines within the tolerance |

| a curve in which two faces cross, strictly inside both, that ends up dividing neither | `Unsupported` ("imprint lost"): a consistency check, zero on the corpus and the random runs |
| more than two faces along an edge where two of them are tangent to second order | `Unsupported` |

The curves come from `geom::intersect::meet_surfaces` (since 2026-10-13; the stand-in of the first version is gone): exact where there is a closed form, splines within the tolerance otherwise. What it cannot give (surfaces tangent or nearly coincident over an area, a touch along a curve without closed form) is refused with its reason. Curve/surface hits use geometry's closed forms for lines, circles and ellipses against planes and cylinders, and for every other analytic pair the bounded root isolation in `hits.rs`, which takes a piece as given (a hit at its end is a touch) and never samples. `BooleanResult::merged` lists, per face, every face of the operands it has a piece of; `BooleanOptions::trust_operands` skips the validity check of operands the kernel itself returned.

**Tolerances.** Points within half the linear tolerance are one vertex; between that and twice the tolerance the operation refuses. The same holds for faces: two faces on one surface, or on surfaces that never cross, are the same surface within half the tolerance of each other where one is over the other, apart at twice the tolerance or more, and refused in between. Joined faces are not moved onto each other: the volume of such a result is right to the area in contact times the gap. The counterpart for faces of different kinds (a ball that dips into a plate, a torus lying a hair too deep in a block): beside every curve in which two faces cross, `section::passage` walks one surface away from the curve both ways until it is twice the tolerance from the other. Where that happens on opposite sides of the other surface the faces cross, exactly as given. Where it happens on the same side, the surface went through the other and came back: a lens thinner than twice the tolerance, whose thickness is measured; up to half the tolerance the faces touch and nothing is imprinted, above it the operation refuses. A body ten tolerances thick is a body. No decision is taken on the sign of a number that could be rounding: membership is a winding number, a root is isolated by a bound and not by sampling, and what cannot be told is refused.

**Speed (2026-10-13).** Measured by stage on a cylinder through a plate with 1024 holes (1030 faces): classification 73 %, section 24 %, both from asking every boundary piece of a face with a thousand loops about every point. Now each outline keeps a box per boundary piece, sorted along x (`outline::Boxes`), and "is anything nearer than r" looks at the few pieces near the point; in a plane a loop is not followed around a point outside its box; edges are split only near a vertex; a region is classified by one point, the others being looked for only when it does not decide; a whole face away from the other solid's box is outside it. Bit-identical results (a digest of every result of the corpus and the random runs is printed by the tests). 100 holes one by one 371 → 134 ms, 1024 holes 82 → 9.9 s, the cylinder through the 1030-face plate 269 → 47 ms, two plates of 1030 faces each 0.64 to 0.85 s per operation.

**Freeform faces (2026-10-13, `boolean/freeform.rs`).** A Bézier or B-spline face is indexed by a `PatchTree`: the surface as Bézier pieces (`geom`: `NurbsSurface::bezier_spans` by knot insertion, `RationalBezierPatch` with de Casteljau splitting), each quartered five times, with the box of every piece's control net (the piece lies in it). The tree answers what the booleans ask of a surface: a bound below the distance from a point to the surface that never overestimates (the distance to the nearest box, split further on the spot to a quarter of the tolerance or of the distance), which is what calls a stretch of a curve provably clear of the surface in the root isolation of `hits.rs`; the nearest point, by Newton's iteration (second derivatives from differences of the first, steps held to the domain's sides) from the middle of the nearest piece and from every piece whose box is nearer than the best point found; the signed distance; and a bound on how fast the parameters change per length travelled on the surface (the smallest singular value of the Jacobian, from the Bézier nets of the derivatives and of the normal field), which the chart of the face needs: a freeform face's chart is its own parameter rectangle, reached through the nearest point. A `Sheet` (a surface with its index) is what the helpers of `outline`, `hits`, `section`, `classify`, `regions` and `chart` take; an `Outline` builds the tree for a freeform face once and shares it with the pieces of the face. The hull of a freeform face includes its control net. Where a freeform surface meets another, the surfaces count as crossing (no lens is looked for). A NURBS surface or curve evaluated beyond its domain continues the end span's polynomial, as a Bézier does, because the marcher of the surface intersections needs something to correct onto past a border. Since the evening of 2026-10-13 the root isolation (`hits.rs`, `numeric`) judges a whole stretch of a curve against a freeform face at once wherever the curve's bend is bounded (lines, circles, ellipses and splines, rational ones included, whose second derivative is bounded through the nets of their Bézier pieces: `NurbsCurve::derivative_bounds`): a stretch on the surface is proven to stay within the tolerance from the distances at its ends and a bound on the surface's second derivatives over its domain (from the Bézier nets: the difference between curve and surface along the parameter path between the feet stays within an eighth of the bend, `PatchTree::stretch_within`); a stretch beside it is proven clear by a lower bound on the distance from its chord to the surface (`segment_lower_bound`; the distance from a segment to a box is exact, one convex quadratic per side crossing) less how far the curve can leave the chord. The tree bounds its pieces by boxes in the piece's own frame (as thick as the piece bends, not as it tilts: a tilted piece's axis-aligned box is as thick as the piece is wide, which left a curve at 1.06 tolerances from a face unprovable), takes a threshold above which nothing matters, and the point bound is only asked where it can prove something. The slowest corpus case (a contact of two spline-roofed blocks, 200 s per boolean) takes 0.19 s.

**Rational faces (2026-10-13, late).** A face on a rational Bézier or NURBS surface (weights that are not all one) is an operand like a polynomial one. A rational patch lies in the hull of its control points just the same, so the boxes of the tree, the bound below the distance, the nearest point and the signed distance needed nothing. What was polynomial-only were the three bounds that came from derivative nets, and each now has a proven counterpart in `geom` (`nurbs.rs`; the arguments are in the doc comments):

- *First and second derivatives* (`RationalBezierPatch::derivative_bounds`, `NurbsCurve::derivative_bounds`). With `S = A / w` (weighted points over weight, both in Bernstein form), `S_u = (A_u − S w_u) / w` and `S_uu = (A_uu − 2 w_u S_u − w_uu S) / w`. `A_u − S w_u` is a Bernstein form whose coefficients are `m (w₁ (P₁ − P₀) + (w₁ − w₀) (P₀ − S))` over neighbours, and `S` lies in the hull, so `|P₀ − S|` is at most the reach of `P₀` across the box of the net; `w` is at least the lightest weight; the second derivatives likewise from second differences of `w (P − S)`. For weights that are all one these are the hull bounds of a polynomial patch, to the last bit. They loosen as the weights of a piece differ and tighten as the piece shrinks, so they are taken from small pieces: the leaves of the tree for the bound that `stretch_within` uses, the pieces of a span quartered twice for the marcher's field (which used estimates from samples for a rational surface before), a span halved three times for a curve.
- *The normal* (`RationalBezierPatch::weighted_normal_net`). `w³ (S_u × S_v) = w (A_u × A_v) + w_v (A × A_u) + w_u (A_v × A)` is a polynomial where the normal is not; its Bézier net (degrees `3m − 1` by `3n − 1`, products of Bernstein forms) holds it in its hull, so the normal is at least as long as the distance from the origin to the box of that net over the cube of the heaviest weight. With the bound on the first derivatives that gives the smallest singular value of the Jacobian, and so the parameter speed the chart needs.
- *The bend of a rational edge* (`hits.rs`, `turn_bound`) comes from the curve bound above, so a rational spline is judged a whole stretch at once like any other curve.

Measured on a NURBS cylinder the parameter speed bound is within 20 % of the true value and the second-derivative bound within 50 %; on a bicubic roof with the weights 1, 2, 0.5 and 3 within 36 % and 24 %. The parameter speed is now taken in the surface's own parameters, with the width of the piece: before, it was the piece's own, which is right only for a span one wide, and a B-spline face over a wider knot span got a bound that was too small by that width (found here, fixed for polynomial faces too; `the_parameter_speed_is_in_the_parameters_of_the_surface`).

The oracle (`crates/kernel/tests/boolean_rational.rs`): a rational surface can *be* a piece of a quadric or a torus, so each test solid exists twice, with its curved faces on the analytic surfaces and on the rational patches that equal them (a quarter rod, a quarter ball zone, a quarter frustum, a quarter slice of a ring with an outer and an inner face; patches that end on the trims and patches a fifth larger; circular edges as circles and as rational arcs). The twins pass `check`, measure as the closed forms to 1e-9 and mesh watertight; their three booleans against a block, a cylinder, a ball, a cone and a torus through the rational face agree with the same booleans of the analytic solid within 5.1e-8 in volume and area (360 booleans; held to 1e-6) at the scales 1e-3, 1 and 1e6, in the world's frame and tilted; tangent contact with a plane and a ball and an edge of a block on the face come out as for the analytic twin. A roof that is no quadric (the weights above) is held to a quadrature of its own and to the identities of sets, against a block, a ball, a block over a corner (which cuts the rational roof edges) and a cylinder.

*Refused:* a rational face on the surface it equals (see the table above); a patch with a collapsed border (the pole of a sphere octant: its parametrisation stalls there, as a polynomial patch's does; a border that is collapsed only up to rounding counts as collapsed, because a normal shorter than 1e-9 of the product of the derivatives is rounding and not a bound); weights more than a factor of a thousand apart within a span. *Cost* (the optimized test profile, four at a time on a quiet machine): a boolean with a rational quadric face takes 35 to 420 ms (medians per pair of solids 45 to 250 ms, a block the slowest tool) where the analytic twin takes 0.4 to 14 ms (closed forms against marched splines and nearest-point searches, as for any freeform face); the weighted roof against a block takes 1.5 s where the polynomial roof takes 0.2 s, because its parameters really move four times as fast and its second derivatives really are twelve times as large, and the chart (one speed for the whole face) and the proofs pay for both. The polynomial roof itself got 15 to 30 % faster by the parameter speed taken in the surface's parameters (0.28 s before).

**Not done:** freeform faces whose parametrisation stalls; a freeform face on the surface of another face (coincident freeform faces); a lens between a freeform surface and another; speed (a boolean of a domed block and a block takes about 0.1 s, most of it nearest-point searches); a spatial index over the faces of a body (every face pair is still tested by box and by side); an untouched operand does not come back with its entities in their old order.

### 5.4 Sketch solver (`solve`)

A 2D geometric constraint solver: entities become unknowns, constraints become equations, solved numerically (Newton-type with a rank-revealing step) from the stored previous solution. It reports degrees of freedom, which constraints are redundant or conflicting, and never loops forever (iteration cap → `DidNotConverge`). Dragging (later, with the UI) is the same solve with a soft target. Decomposition into small sub-problems is an optimisation for later; correctness and diagnostics come first.

As built (M5): the unknowns are point coordinates and circle radii; gradients are exact (forward-mode dual numbers); the Jacobian is factorised row by row in the order the constraints were added, so a row that depends on earlier ones marks its constraint as redundant (it holds) or conflicting (it does not). When the whole system does not converge, constraints are added one at a time from the solution of the earlier ones, and one that cannot be added is blamed. That diagnosis is this solver's verdict, not a proof. A constraint that has no value where the others put the sketch (an angle on a line that shrank to a point) is conflicting too, with the reason. `solve` repeats its pass from its own result until nothing changes, so `Ok` means that solving again gives the same coordinates, bit for bit, and the same verdict. `regen::settle_sketches` still does not store a solution with a conflict in it: a collapsed line no longer says which way it pointed, and the stored shape is what brings the sketch back on the same side. Steps are minimum-norm with a line search, so free geometry moves as little as possible and mirror choices (which side of a line, inside or outside a circle) follow the starting point. An angle is signed: counter-clockwise from the first line's direction to the second's.

### 5.5 Regeneration (`regen`)

`regen` walks `Document::features` in order and produces, per feature, a status (`Ok`, `Suppressed`, `Failed { reason }`, `Skipped` because an input failed) and the bodies that exist after it.

- **Incremental.** Each feature's result is cached under a key made of its own parameters (after expression evaluation) and the keys of its inputs. Editing feature *k* reuses 0..k-1 untouched and recomputes only the features that depend on what changed. *As built (M6, `regen/src/cache.rs`):* the key is the feature's definition, the values of its expressions, the document's units and tolerance, and for every feature it is made from (directly or through others) the stamp of that feature's result and who had taken its body. A rebuilt result that equals the old one keeps its stamp, so a change that makes no difference stops there. Sketch solves are cached on their own (a sketch solves the same wherever it lies), which also spares the solve that stores a sketch's solution after an edit. The cache lives with the open document; `regenerate_cached` returns exactly what `regenerate` returns, and the test suites hold it to that after every command.
- **Variables first.** The variable table is evaluated in its stored order; a cycle or a dimension error fails only the features that use the affected variables.
- **Partial success is normal.** A failed feature does not discard the model: bodies up to the failure stay available and renderable, and the failure is data an agent can read (`document.inspect`). *As built (2026-10-14):* there is no `Skipped` status; a feature whose input failed is `Failed` with a reason that names the input, and `regen::root_cause` gives the feature to fix (§4, *A feature that fails*).
- **Background jobs.** Regeneration runs on the job pool from a snapshot and commits its result if the document has not changed in a conflicting way.

## 6. Tessellator (`tess`)

`tessellate(&Body, &TessParams, cancel) -> Result<Mesh, TessError>` with `TessParams { chordal_tolerance, angular_tolerance, max_edge_length }`.

- **Edges first, then faces.** Each edge is discretised once; both faces sharing it use the same points, so the mesh of a solid is **watertight by construction**: no cracks, no T-junctions.
- **An edge is as fine as its faces need** (as built 2026-10-13). The points of an edge are first chosen for its curve alone, within the chordal tolerance. A face may need more: where another of its edges comes nearer than the tolerance, the chords of a curved edge cross it and no longer bound the face (a hole close to a rim, a notch that stops just short of an arc); and close to a pole of a sphere a chord is far from the straight segment the triangulation takes it for in parameter space. And a face may be narrower than the tolerance altogether: between a line and a flat arc from the same vertex to the same vertex the arc is one chord and the loop a line there and back, which encloses nothing; such a face asks for every chord of its curved edges. Before it is triangulated, each face names the chords it cannot do with; they are cut in two on the curve, for every face that uses the edge, and the faces concerned are done again. At most 12 rounds, an edge growing to at most four times its points and 32 more; each round is the same for any number of threads. What is left after that is the error it always was (edges that really cross). `tessellate_edges` goes through the same rounds, so its polylines are the borders of the mesh; `tessellate_body_and_edges` gives both for the work of one.
- **No size of its own** (2026-10-13). Nothing in the tessellator is a length: every threshold is a ratio (of the chordal tolerance, of an edge's parameter range, of a face's own extent). A body and its tolerance made *k* times as large give the same mesh *k* times as large: bit for bit when *k* is a power of two, where scaling does not round (`crates/tess/tests/scale.rs`, and for boolean results `crates/testkit/tests/self_intersection.rs`). For other *k* the edges get the same points to rounding; the triangles between them may differ where two triangulations are equally good (four points of a grid on a cylinder lie on one circle, and the last bit chooses the diagonal), so those meshes are the same surface, not the same triangles. A knot of a spline edge is a point of the edge only when it is inside the edge's range by more than 1e-9 of that range: an edge cut from a spline at a knot may start a rounding error before it.
- **Closed, and checked** (2026-10-14). That the mesh of a closed solid is closed is not left to the construction alone: it is checked on every face before its mesh is returned (`body.rs`, `closes_along_edges`). The sides of the face's triangles that lie on the boundary of its region are compared with what the face's loops say must be there: every chord of every edge, once for each use of the edge by a loop and in that direction, point for point and bit for bit; what the mesh has beyond its edges (the two sides of a seam the tessellator cut itself) must be there once each way. A face that fails is a `TessError::Face` that names the edge, the chord and the face on the other side. Faces that pass and share an edge use its chords in opposite directions, so the mesh of a body whose every edge is used once each way is closed without being welded: the sides inside a face are shared by two triangles by the making of the triangulation. The cost is that of sorting the boundary of each face, not its triangles: on the timing fixtures (`crates/tess/tests/timing.rs`, up to 396,270 triangles, best of three rounds on a machine busy with other work) it is not to be told from the noise between runs, where welding the mesh to check the same thing (`Mesh::weld` and `Welded::is_closed`, the table's last column) takes as long as making it: 190 ms for a sphere of 246,512 triangles that takes 150 to 180 ms to tessellate. A sheet is checked the same way: its border is the edges that are used once.
- **A manifold, where the body is thinner than the tolerance** (2026-10-14). The check above finds a mesh that is open; a mesh can also be closed and still no manifold. A rung is a side of a triangle that joins two points of a face's boundary across the face. Two faces that share an edge can both have the rung between the same two points of it: across a neck of a face between two stretches of one edge, with the neighbouring face just behind it, both take the same chord for their surface, and four triangles meet in it (a ball's face and a torus's around the curve they meet in; found on boolean results cut around a pole). `Welded::is_closed` and every program that reads the mesh call that open. Every face reports its rungs; where two faces have the same one, the curved face of the two (of two curved ones the first in face order) gets a point of its own surface in the middle of it and is done again, which takes its mesh off the chord by less than the tolerance. Three rounds, each the same for any number of threads; a rung still shared then is an error at the face. Two plane faces with a side in common overlap in one plane, which is the body's to answer for, and are left.
- **Poles of spline surfaces** (2026-10-14). A face may run into a row of control points that is one point, with an edge that ends there or passes through. Two things are different from a sphere's pole, whose parameters are in closed form. The parameter around the pole of a boundary point *near* the pole is found by the search that projects it, to rounding over how slowly the surface moves with it there, which a few millionths of the surface's size from the pole is no digits at all (and the curves in which a boolean cuts such a face have points that near); a boundary that zigzags in that parameter bounds triangles that stand inside out. So a boundary point where the surface moves a thousand times slower with a parameter than it does elsewhere along the loop is projected again by descent from its neighbour along the loop, on the side away from the pole (`Surface::project_from`), which moves the parameter only as far as the point asks. And between such points lie triangles whose area is within the rounding of their own corners: they face no way that can be told, were cut in two for facing the wrong way until the triangulation gave up (the error read "needs about 2050 segments"), and are now left alone on spline surfaces. Held to by `crates/kernel/tests/boolean_poles.rs`: an octant's patch and a dome cut through and around their poles, eight results that were refused or meshed wrongly before.
- **Closed surfaces** (as built 2026-10-13). A face is to the left of its loops. On a sphere, loops that all run clockwise bound everything outside them: the face is the whole sphere with those loops as holes (a ball with a hole drilled across the sphere's axis), cut open along a meridian that no hole lies on. The same on a torus is not handled yet. A whole closed surface may also be given with its seam as an edge from pole to pole that the one loop walks there and back, as a STEP file has a sphere (2026-10-14): a loop that comes back from a pole the way it went there turns all the way around the pole, and the face is everything about it.
- **The seam of a face that goes around its surface** (as built 2026-10-13). Such a face (a wall between two circles, a zone of a sphere, a cap up to a pole, a band of a torus around its axis or around its tube) is cut open in parameter space along a seam from its lower winding loop, or the lower end of the surface, to the upper one; the two sides of the cut are the same curve in space and get the same points. A straight seam is tried first, at sixteen places, and is what an ordinary face gets. When the other loops are in the way of every one of them (seven blade roots that together cover the circumference of a turbine hub; two rows of holes, the second row half a pitch further), the seam is made of straight pieces from loop to loop: it enters a hole at one of its vertices and goes on from another, and the two stretches of the hole between those vertices become part of the two sides of the cut, one a period further than the other. The pieces are found by triangulating the loops, laid out three times side by side, with our own constrained Delaunay triangulation: no edge of it crosses a loop, so every edge between two different loops is a piece a seam can use, and the edges join the lower side to the upper because the face is connected. The seam is the chain with the fewest pieces (breadth first, short edges first); every piece is tested once more against all loops and against the pieces before it and their copies a period away. It costs nothing where a straight seam exists. Covered: cylinder, cone (also from its apex), sphere (zone, cap to a pole, whole sphere with holes), torus bands both ways, as the surface has them and reversed (`crates/tess/tests/winding_seam.rs`, closed-form areas at three sizes; `crates/testkit/tests/winding_seam_solids.rs`, a pipe drilled by the boolean kernel). A face for which no seam is found asks for finer chords first (chords too coarse can close the way between two loops) and is `Unsupported` after that.
- **Spline surfaces that close on themselves** (2026-10-14). `craft3d-geom` reports a period for a cylinder, a cone, a sphere and a torus, and none for a Bézier or NURBS surface. The tessellator finds it: a spline surface closes in u (or in v, or in both, as a torus does) when its control net ends there on the row it starts with (the same points to 10⁻⁹ of the net's size, weights in one proportion, so that the two rows are one curve) and its knots are clamped; the period is the width of its domain. From there on such a face is a face on a closed surface like any other: its boundary is followed across the seam, a face that goes around is cut open along a seam whose two sides share their points, a face may reach a row of control points that is one point (a pole), and the seam may be an edge of the body that the loop walks there and back (then the face is an ordinary patch one period wide) or no edge at all. The surface itself is defined over one period only, so parameters beyond it are brought back into it wherever the surface is evaluated. Covered (`crates/tess/tests/closed_freeform.rs`, against closed forms, at three sizes): a full turn of a spline with a seam edge and between two circles, with the surface's seam anywhere and the turn in either parameter, a window across the seam and the wall around it, a NURBS torus with and without its two seams as edges, and a surface that closes to a point at both ends. **Not recognised, and refused:** a surface that closes on knots that are not clamped (the control net does not show it). Its seam is not followed, the boundary jumps from one end of the parameter range to the other, and that is what the face is refused for: a chord of an edge whose straight segment in parameter space strays further from the chord than the chord is long (and than twice the tolerance) is a boundary that is not closed in parameter space, an error at the face (`mesh_face`), on every kind of surface. (The first face on a closed spline surface, on 2026-10-13, came back as a mesh that was not closed, without an error: the points of its seam edge were projected now to one end of the range and now to the other.) A boundary whose extent on a spline surface is less than 10⁻⁹ of the surface's range is rounding of the projection and bounds no region.
- **Interior points keep their distance from the boundary** (2026-10-13). A grid point is left out when it is nearer than 0.3 of a grid step to any constraint, also one that is not an edge of the triangle the point falls in (the fan around a corner of a hole; found by walking the triangles within that distance, 64 at most). A point just above a chord of a hole, between the chord and its arc, makes a triangle that stands inside out, which refinement then never gets right.
- **Faces** are triangulated in parameter space (constrained Delaunay over the trimmed domain) with refinement until the surface deviation is within the chordal tolerance, then mapped to 3D. Planar faces need no refinement.
- **The grid a curved face is seeded with** is sized so that a cell of it, cut in two triangles, is within the tolerance of the surface: by the arc for the analytic kinds, and for freeform surfaces by bounds on the second derivatives (Filip, Magedson & Markot 1986: over a right triangle with legs `hu` and `hv` along the parameters the deviation is at most `(Muu hu² + 2 Muv hu hv + Mvv hv²) / 8`). For a Bézier patch the bounds are those of its control net. **For a NURBS surface they are proven too since 2026-10-14** (until then: second differences on a lattice of 8 by 8 samples, times 1.5, which promised nothing): the surface is a rational Bézier patch on each knot span, each patch the face's box reaches is cut down to the part the box covers (across the seam too, for a surface that closes), and that part is bounded by `RationalBezierPatch::derivative_bounds` after four cuts in halves, each across the parameter that brings the bound down most. A spline face also gets a step of its own per parameter, `(Muu + Muv) hu² = (Mvv + Muv) hv² = 4 × tolerance`, which keeps the same bound and never has more cells than one step for both: the wall of an extruded spline, straight along the sweep, is one cell that way. Where one parameter would need more cells than the limit (`TessParams::max_segments`) and the other has room, it is held at the limit and the other made finer. The grid's promise is for its own cells; the triangles along the boundary are not cells of it and grid points too near the boundary are left out, so every triangle is measured afterwards all the same, and the measure at a triangle's centroid and the middles of its free sides remains a sample. *Measured* (2026-10-14, `crates/testkit/tests/mesh_hashes.rs`, 441 meshes: the reference solids straight and askew, boolean results, extruded, lofted and revolved splines, at three sizes and three tolerances): the 333 meshes of bodies without NURBS faces are what they were, bit for bit; the 108 of the twelve bodies with NURBS faces changed. Triangles at a tolerance of 10⁻³ of the size, before and after: a domed block with a NURBS roof 9,750 and 8,416 (now the mesh of its Bézier twin); an extruded leaf of two splines 10,966 and 324; a loft through three leaves 62,672 and 49,580; revolved vases 245,112 and 247,916 (degree 2), 269,380 and 318,048 (degree 3), 227,524 and 279,348 (degree 5), and up to a third more for three quarters of a turn: on rational surfaces the proven bounds are looser than 1.5 times what was sampled. The largest distance from the meshes to their surfaces, on seven points per triangle, is 0.889 of the tolerance before and after (8/9: a third along a boundary chord that sags by the whole tolerance); the sampled grid broke no promise that was measured, it made none. One body of the set is refused as too fine at 10⁻⁵ of its size where it was meshed before (a three-quarter turn of a cubic spline, 1.8 million triangles in one face): the proven grid needs 1,097 cells a side there against a limit of 1,024. The showcase documents: the six with splines changed (the housing from 5,244 to 1,868 triangles at the automatic tolerance, the vase from 17,300 to 20,980), the six without did not, bit for bit.
- **Output** keeps, per triangle, the face it came from (and per polyline, the edge), so the renderers can colour, select and pick by entity, and exporters can group.
- **Parallel per face** (rayon), merged in face order, so the result is identical for any thread count.
- **Our own triangulator.** No external triangulation or meshing library; this is part of "custom tessellator".
- **What a viewer draws: the display quality** (2026-10-13). The engine's scene (`Session::scene_with(SceneQuality)`, §8.5) is sampled at one of three qualities: `Automatic`, the chordal tolerance `view.render`, previews and `file.export` use when none is given (1e-3 of the model's size, the side of a square with the bodies' total area; without bodies, the diagonal of the sketches); `Tolerance(t)`, a tolerance in document units; and `Display { relative, max_triangles }`, what a viewport shows: `relative` times the model's size (3e-5 by default: on a model that fills a 1020-pixel viewport a chord error of a thirtieth of a pixel, so a circle stays round when the developer zooms in on a detail), coarsened until the scene has at most `max_triangles` (a million) triangles and every body is within the tessellator's reach, but never beyond the automatic tolerance, so the display is never coarser than the export. The coarsening is a ladder: a build with a budget stops at the first body after which the budget is exceeded, or that is too fine for the tessellator (`TessError::TooFine`), and the next tolerance is coarser by the ratio of the estimated total (the count so far over the share of the model's faces done) to the budget, at least twice and at most 64 times, six attempts at most; the scene says whether it was coarsened. The budget is the scene's, and it stops a body inside the tessellator (2026-10-13): the bodies are tessellated in feature order and each is given what the ones before it left (`TessParams::max_triangles`); the tessellator ends a body with `TessError::OverBudget` at the end of the first round of its faces in which they have more triangles than that, and ends that round as soon as the faces done show it (faces are done in parallel, each adds its triangles to a count, the ones not started are skipped). What it reports, and what the ladder's estimate takes, is the shortest run of faces from the first, in face order, whose triangles exceed the budget, as a single thread finds them: a function of the body and the parameters, not of the number of threads or of which finished first. So a scene within the budget is the scene built without one, bit for bit, and a scene over it is discarded; nothing in between. The granularity is a face: one face that alone exceeds the budget (a fine sphere) is still tessellated in full. Export, `view.render` and previews pass no budget. Measured on the plate with 1024 holes, asked for at 1e-6 of its size (647,180 triangles in full; processor time on a machine busy with other builds, relative to that full tessellation in the same run): a budget of 100,000 triangles took 0.79 of it before and takes 0.43 now, one of 30,000 took 0.78 and takes 0.24 (2.0 s against 6.7 s on the clock); the ladder ends at the same tolerance in 9 of 13 budgets on the part of `crates/engine/tests/scene.rs` and at a neighbouring one in the others (finer in 3, coarser in 1), because the estimate is now taken at the face that crossed the budget, not at the end of its body. Measured (release, 2026-10-13, `crates/engine/tests/scene_bench.rs`): a flange with six bolt holes, 820 triangles at the automatic tolerance and 4328 at the display quality, about 10 ms either way; a plate with 1024 holes (1030 faces), 24,588 triangles in 666 ms and 122,892 in 776 ms; the tessellator's cost beyond about 0.6 ms per face is about 1.5 µs per triangle, which is what the budget bounds.

- **Self-intersections of a mesh** (`tess::self_intersections(&Mesh, tolerance, limit)`, as built 2026-10-13): the pairs of triangles that cross or overlap although they are not neighbours. *Whether* two triangles meet is decided exactly: orientation predicates evaluated in `f64` with an error bound and, where that cannot tell, again without rounding as sums of non-overlapping `f64` (`exact.rs`, after Shewchuk 1997; our own code, no dependency), because the triangles of a planar face are coplanar to the last bit or a rounding error from it. Neighbours (bit-identical corners) meet only beyond what they share. *How deep* is a measure in `f64`: how far the surface around one triangle reaches on both sides of the other inside the column over it, the smaller of the two directions, so that contact has depth zero and a tip that pricks a surface has the depth of the prick (the column is a hair wider than its triangle only across an edge beyond which the surface goes on, so that what stands exactly on a seam of the triangulation passes through; where the surface turns away square, as around an edge along which two parts of a body meet, what stands on the edge touches); for triangles in one plane, the width of their common area. Candidates come from a bounding-volume hierarchy, searched on several threads (`std::thread::scope`, as the tessellator does) and merged in triangle order.

Mesh invariants are tested, not hoped for: closed 2-manifold for a solid, consistent outward orientation, no degenerate triangles, deviation from the surface within tolerance, mesh volume converging to the B-rep volume as the tolerance shrinks.

## 7. Rendering

Display is the one place with two implementations.

### 7.1 Draw list

`render` and `gpu` consume the same data: meshes and edge polylines from `tess` with entity ids, a camera (orthographic or perspective), lights, a display mode (shaded, shaded with edges, wireframe, hidden-line later) and per-entity colours and selection state. Nothing about display leaks into `kernel` or `tess`.

### 7.2 Backends

- **CPU (`render`).** The reference implementation: a software rasteriser with a depth buffer, flat/smooth shading, edge overlay, and an **id buffer** (which face or edge is under each pixel). Used by tests, the CLI (`craft3d-cli render`), MCP previews, `ui.screenshot`, and as the fallback in the viewport when no GPU is available or asked for (`--renderer cpu`). It favours exactness and readability over speed.
- **GPU (`gpu`).** wgpu (Vulkan, Metal, DX12, OpenGL, WebGPU) pipelines for the same draw list; picking reads the id buffer. The scene pass draws one sample per pixel into targets `ssaa` times larger per axis (an `Rgba8Unorm` colour target, an `Rg32Uint` target with the face id and the bits of the view distance, a `Depth32Float` buffer with near and far fitted to the mesh per frame); a resolve pass takes the rounded integer mean of the colour samples and the first sample's id and distance, exactly as the CPU renderer ends. Positions go to the GPU in `f32` relative to the centre of the mesh; the camera is computed in `f64` and narrowed last. That is the crate's `Offscreen` and `Renderer`, which read the frame back. **The viewport of the desktop app draws with the crate's `Onscreen`** (2026-10-13) on the window's own wgpu device, into a texture egui shows as it is: nothing is read back for display. Its scene pass draws the same shader into a colour target and depth buffer with 4 samples per pixel (MSAA; 1 where the adapter has no multisampling for the formats, and on wgpu's OpenGL backend, which resolved nothing out of a multisampled attachment on the development machine), shading once per pixel at its centre, exactly where the CPU renderer samples for `ssaa = 1`; a second pass draws the lines over the picture (the edges of the bodies, the world axes, the sketches, the sketch points) as screen-space quads inked by the distance of the pixel's centre to the segment (the CPU viewport's `draw_line`), each tested in the fragment shader against the depth buffer with the CPU viewport's rule (a point is behind a body only when the surface under its pixel and the eight around it is nearer, with the slack the GPU frame gets; a hidden edge is left out, a hidden sketch drawn dimmed), and resolves the samples into the shown texture. The GPU tests against the true depth where the CPU viewport tests against its frame's screen-interpolated distance, so the GPU allows a line the depth spread of the nine pixels as well: that keeps the edge in the hollow where two surfaces meet visible, as the CPU's interpolation happens to. A third pass, only when asked, draws face ids and distances at one sample per pixel (for the tests, and for picking later). Three differences are known and documented in the crate: a triangle that crosses the eye plane is clipped where the CPU renderer drops it whole, a triangle with a corner that does not fit in `f32` is not drawn, and a sample exactly on an edge follows the GPU's top-left rule.
- **Parity tests** (`crates/gpu/tests/parity.rs`; the derivations are in `crates/gpu/tests/common/mod.rs`). 75 scenes (the Utah teapot, the sixteen reference solids of the test kit tilted at scales 1e-3, 1 and 1e6 and once ten million units from the origin, and hand-made awkward meshes), in perspective and orthographic, at supersampling 1 to 4, on every adapter of the machine. **The documented tolerance** is:
  - *The band.* The GPU's rasteriser snaps projected vertices to a grid of 2⁻⁸ pixel, so the renderers can disagree about a sample only within 2⁻⁸ pixel of a triangle's edge, and that shows only where the surface under the sample changes. The band is every pixel within one pixel of a projected *feature edge* (a face's border, an edge with one triangle, a silhouette edge) or of a change of face id in the CPU frame. It is computed from the mesh, the camera and the CPU frame, never from the GPU frame, and must leave more than half of the picture.
  - *Face ids:* equal outside the band. Inside it at most 1/128 of the band's pixels may differ (the probability that an edge passes within 2⁻⁸ pixel of a pixel's centre).
  - *Distance* outside the band: within `2⁻²⁰ · reach + 2⁻⁷ · G`, where `reach` is the eye's distance to the mesh centre plus the mesh diagonal (sixteen `f32` roundings of 2⁻²⁴ on numbers that large) and `G` is the largest difference to the eight neighbouring pixels in the CPU frame (the gradient, times one grid step, doubled).
  - *Colour* outside the band: at most 1/255 per channel, with no exceptions (both renderers round per sample; a value within the `f32` error of a half-integer rounds the other way), plus `2⁻⁷ · Gc` levels where the CPU picture itself changes by `Gc` between neighbours, which is a second level only next to a jump of 128 or more. The number of pixels that differ by that one level is bounded too, by the sum over the pixels of `2 · (2⁻⁷ · Gc + 0.004)`: a systematic error such as a truncated mean exceeds it. Inside the band at most 1/128 of the pixels may differ by more than a level.

  Measured on the three adapters of the development machine (Intel Vulkan, lavapipe, Intel OpenGL): no id differs outside the band, at most 0.07 % of a scene's pixels outside the band differ by one level and none by two, the largest distance error is 39 % of its tolerance, and at most 0.14 % of a band's pixels differ. The tests **fail** when no adapter is found, with the way to get one (`mesa-vulkan-drivers` gives lavapipe); they do not skip.
  - *The multisampled picture* (`crates/gpu/tests/onscreen.rs`, `compare_msaa` in the same `common/mod.rs`) is compared with the CPU frame at `ssaa = 1`, with the ids and distances of the capture pass, under the same tolerance with two exceptions that follow from multisampling: inside the band the colour is not compared at all (the samples lie on both sides of a feature edge and the resolved colour is their blend: the anti-aliasing; the number of such pixels is measured and must be more than a twentieth of the band), and on a *seam* (within a pixel of an interior triangle edge of one face) a pixel may mix two fragments, each shaded at the pixel centre from its own triangle's interpolated normal, so it is allowed `1 + Gc` levels, a pixel of the CPU picture's own gradient. Measured on the development machine: away from every edge not one pixel of the teapot or the block differs by a level, at most 6 seam pixels of a scene differ by more than a level, and about a tenth of the band is blended. The lines are checked on a block with lines behind, before, on and beside it (dimmed, left out, whole), and `crates/ui-egui/tests/gpu_viewport.rs` draws the viewport's own scene through the shell on a device made as eframe makes the window's and compares the shown picture with the CPU picture (bodies and inked lines) the same way, sampling every line of the overlay to check that the GPU hid, dimmed and drew what the CPU decided: 1812 of 1812 samples agree.
- **See-through on the GPU** (2026-10-14; `crates/gpu/src/peel.rs`, `peel.wgsl`, `peel_samples.wgsl`, `blend.wgsl`). `RenderParams::opacity` below 1 is drawn with two depth layers, as the CPU renderer defines it (*Current state*, *See-through bodies*): the front surface blended over the nearest surface strictly behind it. At opacity 1 (and at an opacity that is not a number) none of it runs: the passes, pipelines and targets are the ones of the opaque picture, and the frame is that picture bit for bit (asserted on every adapter).
  - *The passes.* (1) The front: the opaque scene pass with another fragment entry, whose alpha says whether the sample is seen through (1 for a body's face, 0 for a highlighted face; the target is cleared to alpha 0, so the background is not blended either), and whose depth buffer is kept. (2) The one behind: the same triangles into a colour target and a depth buffer of their own (`Less`), each fragment dropped unless it is behind the front. (3) The blend: one triangle over the picture that reads both layers per sample, blends them and writes the mean of the samples (the supersamples of the readback renderer, in place of its resolve pass; the multisamples of the viewport, in place of the hardware resolve), with the frame's ids and distances taken from the front as ever. Then, in the viewport, the lines: straight onto the shown texture at one sample (they are inked by distance, not by coverage), tested against the front's depth buffer as over an opaque picture. Per frame that is one more pass over the triangles and one more over the pixels; the extra targets (a colour layer and a depth buffer behind, and in the viewport a front layer and its keys, all with the samples of the renderer) are made for the first see-through frame of a size.
  - *The comparison of the layers, and its bias: strict, and none.* The front is the nearest fragment at its sample, so every other fragment that covers the sample is at or behind it: all that has to be told apart is the front itself (and what ties with it) from the rest. With one sample per pixel (the readback renderer; the viewport on OpenGL) the second pass reads the front's depth buffer as a texture and keeps a fragment when its own depth is greater. Both passes rasterise the same triangles with the same vertex stage on the same device, so a triangle's depth at a sample is the same number in both and a surface is never its own "behind"; a bias would only hide a surface that is really there. Two surfaces closer together than `Depth32Float` resolves over the frame's depth range (about 10⁻⁷ of it) have equal depths and then nothing is behind the front, where the CPU renderer in `f64` still sees the second: measured on a wall 10⁻⁹ of its width thick, every pixel sees past both sheets on all adapters, and a wall 10⁻⁴ of its width thick shows its other side as on the CPU.
  - *With several samples per pixel* a fragment is shaded once per pixel and the depth test runs per sample on depths the shader does not see, so that comparison is not available: the fragment's own depth is the triangle's depth at the pixel centre. Making the pass run per sample does not help: **measured on Intel's Vulkan driver (Mesa 25.3.6), a per-sample fragment's depth differs from the depth buffer by far more than rounding** (every body pixel showed its own front as "behind"; lavapipe agreed with its depth buffer). The viewport therefore stores, next to the front's colour, a *key* of the triangle in front at each sample: the bits of its depth at the pixel centre, as the four bytes of an `Rgba8Unorm` target (the one format a multisampled viewport needs anyway; a byte goes in and comes out exactly). The second pass computes the same key for its own triangle (same triangle, same pixel, same arithmetic) and drops, through the fragment's sample mask, the samples whose front has that key; the depth test then keeps the nearest of what is left, per sample and exactly. Two triangles with the same corners have the same key, so a face that coincides with the front is not behind it, as on the CPU (asserted). No multisampled depth texture is read by the peeling, only by the lines as before, so the OpenGL limitation of the decisions document changes nothing here: on OpenGL the viewport has one sample and takes the first path.
  - *The blend is the CPU's own.* `opacity · front + (1 − opacity) · behind`, rounded, is a function of two bytes; the renderer tabulates it in `f64` with the CPU renderer's expression (a 256 × 256 `R8Unorm` texture, written when the opacity changes) and the blend pass looks it up per channel. So a sample whose two layers equal the CPU's has the CPU's colour exactly, also where the exact blend lies half-way between two levels (at opacity 0.1 that is a tenth of all pairs of levels) and `f32` would round the other way.
  - *The tolerance for a see-through picture*, derived in `crates/gpu/tests/common/mod.rs`, is the one above with two layers in place of one. Both layers are known from the CPU renderer alone: the front picture is its frame at opacity 1, the picture behind its frame at opacity 0. *The band* also holds every pixel within one pixel of a change of the face behind the front (where two surfaces behind the front pass through each other, which no mesh edge and no id of the front shows; the test finds that face from the definition with a small rasteriser of its own, for the band only). *Colour* outside the band: each layer is within its own `1 + ⌊2⁻⁷ · G⌋`, the exact blends therefore within the larger of the two, and rounding is monotone and commutes with adding an integer, so the blended levels differ by at most `1 + ⌊2⁻⁷ · max(G_front, G_behind)⌋`. *How many* differ at all: the probabilities of the two layers add. Ids and distances are the front's and keep their tolerances. Nothing was loosened: the same per-pixel limit, the same counted bound.
  - *Measured* (three adapters: Intel Vulkan, lavapipe, Intel OpenGL; `parity.rs`, 114 see-through scenes per adapter: the sixteen reference solids at opacities 0.1, 0.5 and 0.9, their three other rounds of scale and distance at one opacity each, the teapot, a plate with a hole and a body inside a hollow body at all three, a third of them with highlighted faces): no id differs outside the band, no colour by two levels, at most 0.11 % of a scene's pixels outside the band by one level (never more than 92 pixels), the largest distance error 23 % of its tolerance, at most 0.15 % of a band's pixels differ. The viewport's picture (`onscreen.rs`, nine scenes per adapter, four samples on Vulkan): not one pixel away from every edge differs by a level, at most one seam pixel by more than a level. `crates/gpu/tests/see_through.rs` holds the scenes where the comparison of the layers bites, for both renderers: one sheet in four views (nowhere its own "behind"), a wall of two sheets 10⁻² and 10⁻⁴ of its width apart, two sheets 10⁻⁹ apart, a face corner for corner on the front, a box seen 2° above its top face, lines over a see-through picture (hidden and dimmed, hidden and left out, in front), hostile opacities and a renderer told it cannot. `crates/ui-egui/tests/gpu_viewport.rs` draws the window's own scene see-through on a device made as eframe makes the window's: 0 of 408 223 pixels away from edges and lines differ, and 1769 of 1769 samples along the lines agree (a hidden, dimmed edge lies on a feature edge of what is behind the front, where a multisampled pixel mixes the faces that meet there: such a sample is compared with the dimmed ink over the range of the CPU picture's 3 × 3 pixels around it).
  - *A finding about the oracle, not changed here.* The CPU renderer counts a sample that lies exactly on an edge shared by two triangles in both (its edge function is inclusive on both sides), and their depth keys there agree only up to rounding; where the second comes out a hair greater, the surface is its own "behind" and the sample is drawn opaque. A square of two triangles seen head-on at 240 × 180, with pixel centres on its diagonal, has 8 such pixels in the CPU's see-through picture and none in the GPU's (whose rasteriser gives such a sample to one triangle); `a_surface_is_never_behind_itself` pins the GPU's side and prints the CPU's count. A rule for shared edges in `render` (or keys compared with the rounding of their interpolation as slack) would remove it.
  - *What is refused.* A device on which the pipelines of the layers cannot be made keeps drawing opaque pictures and answers a see-through one with `GpuError::SeeThrough` and the reason; the viewport then draws that frame with its other renderer (`ui.get` › `render.renderer` says which). `Onscreen::without_see_through` and `Renderer::without_see_through` put a renderer in that state for the tests of the fallback. None of the adapters this was built on is in it.
  - *Cost* (release, Intel integrated graphics, the frame until the GPU is done, `examples/viewport_cost.rs`): at 1020 × 777 with four samples 1.7 ms opaque and 4.7 ms see-through for 12 800 triangles, 12.5 ms and 19.0 ms for 665 000; at 2560 × 1400, 5.0 and 9.1 ms, 15.8 and 25.7 ms. The CPU renderer takes 176 to 227 ms for the same see-through frames at 1020 × 777.

### 7.3 What the oracle is for

In PhotoCraft the CPU compositor defines what the image *is*. Here the model's truth is the B-rep and its mass properties, not the picture. The CPU renderer is the oracle for **display** only: it lets agents and the developer see a model without a GPU, and it catches GPU regressions. Geometric correctness is tested geometrically ([`testing.md`](testing.md)).

## 8. Engine (`craft3d-engine`)

### 8.1 `Session`: commands in, events out

```rust
pub struct Session { /* docs, registry, job pool, prefs, services */ }

impl Session {
    pub fn new(services: Services) -> Self;                         // platform functions injected
    pub fn dispatch(&self, doc: Option<DocId>, cmd: CommandInvocation) -> Result<JobHandle, CommandError>;
    pub fn registry(&self) -> &CommandRegistry;
    pub fn snapshot(&self, doc: DocId) -> Arc<DocSnapshot>;         // lock-free read: document + regeneration result
    pub fn events(&self) -> EventReceiver;                          // DocChanged, RegenProgress, FeatureFailed, …
}

pub struct CommandInvocation { pub id: CommandId, pub params: serde_json::Value /* validated against the schema */ }
```

### 8.2 `CommandRegistry`

Each command registers `id` (`"feature.extrude"`), `label`, an optional `menu_path` and shortcut (unused in phase 1), a parameter schema with a one-line params doc agents can read, `enabled(&DocSnapshot) -> bool` with a reason when disabled, and `run`. `run` returns a JSON result and records exactly **one** history step.

Command families (ids are settled when each is implemented, and are stable afterwards):

| Family | Examples |
|---|---|
| `file.*` | `file.new`, `file.open`, `file.save`, `file.close`, `file.export` (the format from the file name or `format`: STEP or a mesh format for every body, DXF or SVG for the outline of a `sketch` or of a flat `face`) |
| `edit.*` | `edit.undo`, `edit.redo` |
| `variable.*` | `variable.set`, `variable.delete`, `variable.rename` |
| `sketch.*` | `sketch.create`, `sketch.addLine`, `sketch.addArc`, `sketch.addCircle`, `sketch.constrain`, `sketch.solve` |
| `datum.*` | `datum.plane`, `datum.axis`, `datum.point` (reference geometry, §4.1 › *Reference geometry*), `datum.references` (what a body offers a datum, with the names) |
| `feature.*` | `feature.primitive.box`, `feature.extrude`, `feature.revolve`, `feature.boolean`, `feature.chamfer` (built 2026-10-14, `engine/src/blend_cmds.rs`), `feature.fillet`, `feature.edit`, `feature.suppress`, `feature.delete`, `feature.reorder` |
| `history.*` | `history.rollback`, `history.regenerate` |
| `document.*` | `document.inspect`, `document.measure` (volume, area, centroid, bounding box, distances), `document.check` (validity report) |
| `view.*` | `view.render` (PNG from a named or explicit camera, CPU or GPU) |

**Inspection is a first-class command.** `document.inspect` returns the feature tree with per-feature status, variables with values, sketches with their degrees of freedom, and bodies with face/edge counts, persistent names and mass properties. An agent must be able to verify what it did from JSON alone, and use `view.render` when it needs to look.

### 8.3 Operations and history (`ops`)

Every mutation of a document is an `Op` (`SetVariable`, `AddFeature`, `EditFeature`, `ReorderFeature`, `AddConstraint`, …). A command produces a labelled `Transaction` of ops. Undo history stores transactions; because documents are persistent data, a "before" state costs only what changed. Undo history (session-only, what the user did) is distinct from the **design history** (the feature list, saved in the file).

### 8.4 Runtime model

```text
 Client (UI / CLI / control / MCP) ──dispatch()──► Engine thread (owns mutable docs, applies ops, publishes snapshots)
        ▲                                               │ spawns
        │ events (changed, progress, failed)            ▼
        │                                   Job pool (rayon): regeneration, tessellation, export, autosave
        │                                   read snapshots, return results
 Viewport: render(snapshot) on GPU or CPU
```

Every job takes a `CancelToken`. Services injected into `Session`: file system (native fs / in-memory for tests / browser later), clock, notifier.

### 8.5 The UI-swap seam

A frontend needs four things from the core: `Session` (commands in, events out), the `CommandRegistry` (metadata), snapshots with view-models (feature tree, variable table, inspector as plain structs), and a renderer it can host (`gpu::Onscreen` on the host's own device into a texture it shows, or `render` into an RGBA buffer; the egui shell today hosts the first as `ui_egui::direct::Direct` when the window lends it the device, and otherwise `ui_egui::backend::BodyRenderer`, which gives it a `Frame` from the GPU read back or from the CPU). Interactive tools (sketching with the mouse, dragging a face) come after phase 1 and follow PhotoCraft's pattern: pointer events in, ops and overlay primitives out, so the control channel can replay them.

**Litmus test:** `craft3d-cli` and the automation server can do everything the GUI does.

## 9. Files

Detail in [`file-formats.md`](file-formats.md).

- **Native `.3dcraft`** (`format`): a bundle (ZIP of STORE entries, or a directory with the same layout) with a versioned `manifest.json` holding the document, and content-addressed blobs for imported bodies and optional regeneration caches. Atomic saves, autosave and crash recovery through the same writer.
- **STEP** (`step` + `io`): export of exact B-rep (AP214 geometry and topology) is built; import later. STEP carries the result, not the history.
- **Meshes** (`meshio` + `io`): STL, 3MF and OBJ export from `tess` output at a caller-chosen tolerance.
- **Flat outlines** (`drawing` + `io`, 2026-10-13): DXF and SVG export of a sketch or of a flat face, as true curves at true size, for laser cutting.

## 10. Automation

Detail in [`control-protocol.md`](control-protocol.md).

- **CLI** (`craft3d-cli`): `convert`, `info`, `run` (a list of commands against a document), `commands` (the registry), `render`, `serve` (JSON lines on stdio or loopback TCP) and `mcp`.
- **Control channel:** the desktop app listens on loopback with a token; agents send `engine.execute`, `ui.inspect`, `ui.screenshot`. This is also how the developer watches an agent work in a live window.
- **MCP** (`automation`): `doc_*`, `command_list`, `command_run`, `command_batch`, `doc_render_preview`, generated from the registry; file access limited to explicit read and write roots.
- **Scripts:** a recorded session is `Vec<CommandInvocation>`; replaying it rebuilds the model. This is the natural format for agent-written test scenarios.

## 11. Testing and quality

Detail in [`testing.md`](testing.md).

| Layer | What |
|---|---|
| Unit / property | per crate; geometry against closed-form values; proptest for predicates, expression evaluation, persistent structures |
| Kernel invariants | every operation result passes `topo::check`; mass properties against analytic values; boolean identities |
| Tessellation | watertightness, orientation, deviation, volume convergence |
| Regeneration | determinism, incremental = full, save → load → regenerate equality, replay |
| Formats | round trips, malformed-input sweeps, fuzz targets, external validators |
| Renderers | CPU golden images; GPU vs CPU parity |
| Engine | command-level tests; `panic_hunt` fuzzing every command |
| Portability | CI: Linux x64, macOS arm64, Windows x64, wasm32 build check |
