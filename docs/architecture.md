# 3DCraft architecture

> **Last updated:** 2026-10-13 · **Status:** design plan v1; first crates built · **Change:** minor (extrude ends: symmetric, through all, up to a face)

## Current state (2026-10-12)

What exists on `main` today; where the code differs from the plan below, this summary wins.

- **Workspace:** 22 library crates (the 20 of the plan plus `zipstore` and `drawing`), all registered in `xtask/src/layers.rs`. With code: `math`, `geom`, `topo`, `expr`, `doc`, `ops`, `solve`, `kernel`, `tess`, `regen`, `render`, `zipstore`, `meshio`, `step`, `drawing`, `format`, `io`, `engine`, `automation`, `testkit`, `gpu`. `apps/craft3d-cli` is the headless CLI and `apps/craft3d` the desktop app. `xtask` has `layers` (layering and lint opt-in), `wasm`, `ci`, `stats` and `freecad`.
- **The one path works end to end** for primitive solids: command → document → regeneration → B-rep (checked) → tessellation → render or mesh file, and FreeCAD reads the result as a closed solid of the right volume.
- **Maths:** `math` has `Vec3`, `Bbox3`, `Frame` (placement of analytic geometry), `Transform` (affine, with inverse), `Tolerance` (linear and angular, as data) and Gauss–Legendre quadrature. Not built: robust orientation predicates (first needed by booleans, M7), intervals, root finding.
- **Geometry:** `geom` has the `Curve3` enum (line, circle, ellipse, NURBS) and the `Surface` enum (plane, cylinder, cone, sphere, torus, Bézier patch, NURBS), each with evaluation, first derivatives, parameter domain and periodicity, normals, and closest-point projection (closed form for the analytic kinds, sampled Newton / Gauss–Newton for ellipses and freeform). NURBS are de Boor on homogeneous points with hodograph derivatives. Not built: 2D parameter-space curves, trimmed and offset curves, extrusion/revolution/offset surfaces, second derivatives. `geom::intersect` intersects every pair of surface kinds (`meet_surfaces`, inside a box) and every curve kind with every surface kind (`intersect_curve_surface`): in closed form where one exists, numerically otherwise, within the tolerance or an error (§5.1 › Intersections as built).
- **Topology:** `topo` has the B-rep (`Body` with vertices, edges, loops of coedges, faces, shells), the validity checker `check` (references, finite numbers, vertices on edges, closed loops, edges on their faces' surfaces, each edge of a solid used once each way, Euler–Poincaré with genus) and `mass_properties` (area, volume, centroid by boundary integrals over the exact geometry). Fourteen reference solids (six primitives and hemisphere, and eight with trimmed faces: holes, half walls, a spherical cap, a frustum, an ellipse edge, Bézier and NURBS roofs) match their closed forms at three scales and in tilted frames. `mass_properties` also measures the faces a revolution makes: torus faces bounded around the tube, around the axis or both (the surface is closed both ways, so the boundary integral is right only up to a whole number of times the entire torus, which the area settles), and faces whose boundary passes through a pole of a sphere or the apex of a cone (the point stands for a stretch of the edge of the parameter range, which is added). It still refuses, rather than gets wrong, a boundary through a collapsed edge of a Bézier or NURBS surface, a boundary that winds around an axis more than once, torus loops that wind around the axis and the tube at once, and a boundary that turns back on itself at a pole. Deviations from the plan below: parameter-space curves are not stored (recovered by projection), no per-entity tolerances, no persistent names yet (M6), no inertia tensor, and the checker does not test self-intersection or that each face is bounded by its loops.
- **Expressions:** `expr` has dimensions (length and angle exponents) and units (`um mm cm m in ft`, `deg rad`), a parser and evaluator for formula text (`+ - * / ^`, functions, `pi`, variables, a unit after a number), and `VariableTable` (deterministic evaluation order, cycle detection, partial failure, rename that rewrites references). Source length, nesting depth and table size are capped. Not built: printing an expression back to text, storing the evaluation order (computed on demand; storing it is `doc`/`format`'s job).
- **Document:** `doc` has `Document` (units, tolerance, variables, ordered features, rollback marker, next feature id), features `Block`, `Cylinder`, `Sphere`, `Cone`, `Torus` whose parameters are expressions kept as source text, an `Orientation` (axis and angle) on all but the sphere, stable never-reused feature ids, and `validate()`. Sketches are features too (`doc::sketch`): a plane (a world plane with an offset), point, line, circle, arc and (2026-10-13) spline entities with ids that are never reused, sixteen kinds of constraint in the order they were added, and the last solution as the stored coordinates. Not built: the other feature kinds, references between features.
- **Sketch solver:** `solve` takes a sketch as plain numbers (points, lines, circles, arcs; constraints with evaluated values) and returns solved coordinates, the degrees of freedom left, and per constraint whether it is satisfied, redundant or conflicting (the later constraint is blamed). Newton-type with minimum-norm steps from the given start, so a solved sketch does not move and a free part moves as little as possible; every loop is capped. It knows nothing about the document: `regen` maps one onto the other.
- **Undo:** `ops::History` keeps snapshots (`Arc<Document>`) rather than reversible ops: an edit is applied to a copy and becomes one labelled step only if it succeeds and changes something.
- **Kernel:** `kernel::primitives` builds block, cylinder, cone, sphere and torus as B-rep. `kernel::profile` finds the closed regions of a set of 2D curves (loops of lines, arcs and, since 2026-10-13, splines joined end to end, circles; even-odd nesting gives holes and islands; open, branching, crossing or touching curves are errors that name them). `kernel::extrude` sweeps profiles along a plane's normal into one solid with a shell per profile, checked before it is returned, and reports for every face, edge and vertex where it came from (`Origins`). `kernel::extrude_to` (2026-10-13) ends an extrusion on the surface of a face instead (§4.1 › *Extrude ends*). `kernel::boolean` is the union, difference and intersection of two solids whose faces are planes and cylinders (edges: lines, circles, ellipses), with coincident faces and smooth edges handled, and a source for every face, edge and vertex of the result; everything else is `KernelError::Unsupported` with the faces and the reason (§5.3 › Booleans as built). It rests on `geom::intersect`: closed-form intersections of planes and cylinders with each other and with lines, circles and ellipses. `kernel::revolve` turns profiles about an axis in their plane through a full turn or part of one (a line sweeps a plane, a cylinder or a cone, an arc a sphere or a torus; a curve on the axis sweeps nothing) and reports origins in the same roles as an extrusion; a profile that crosses the axis and an arc that would sweep a spindle torus are errors that name the curves.
- **Regeneration:** `regen::regenerate` evaluates variables and builds each feature's body, with a status per feature (`Ok`, `Suppressed`, `RolledBack`, `Failed(reason)`); every body is run through `topo::check`. A bare number in a length parameter is taken in the document's unit. A sketch feature has no body: its result is the solved sketch (degrees of freedom, a state per constraint, solved coordinates, its frame in space), and `regen::settle_sketches` writes a solution back into the document, which the engine does at the end of every edit. No caching: a full rebuild per document revision, every sketch solved again.
- **Tessellation:** two entry points. `tessellate_patches` meshes untrimmed Bézier patches on one uniform grid (the teapot). `tessellate_body` meshes any B-rep body edges first: every edge (line, circle, ellipse, NURBS) becomes points once, within the chordal tolerance, and every face that uses it uses those points, so the welded mesh of a valid solid is a closed manifold. Each face is triangulated in its surface's parameter space by our own constrained Delaunay triangulation (holes by the even–odd rule), with interior points added until every triangle is within tolerance of the surface; loops that wind around an axis are cut along a seam whose two sides share their 3D points; poles, apexes and collapsed patch edges become one point. Faces are tessellated in parallel (`std::thread::scope`) and merged in face order: 1, 2 and 8 threads give byte-identical meshes. Planar faces get no interior points (a block is 12 triangles). A face around an axis whose other loops leave no room for a straight seam is cut along a seam in pieces, from loop to loop (§6). Still `Unsupported`: a loop winding more than once, or around both the axis and the tube of a torus.
- **Mesh export:** `meshio` writes binary and ASCII STL, 3MF and OBJ; `io` welds a tessellated mesh, classifies it as solid or surface and encodes one or more objects. FreeCAD reads the box, the teapot and all fourteen tessellated reference solids (primitives, hemisphere, and the solids with trimmed faces) back as closed solids with the same counts, area and volume (`cargo xtask freecad`). No readers, no colours.
- **Native format:** `format` reads and writes `.3dcraft`: a stored ZIP (`zipstore`, with a reader hardened against hostile archives) holding a pretty-printed `manifest.json`, now at `format_version` 4 (version 1 to 3 files still open, through the migration chain). The file's types are separate from `doc`'s and converted by exhaustive destructuring, so a new document field does not compile until it is saved and loaded (verified by adding one). Saves are atomic and refuse an invalid document; loads validate. Not built: `thumb.png`, `blobs/`, the directory layout, autosave and crash recovery.
- **STEP export (2026-10-13):** `step` reads and writes ISO 10303-21 with its own model (records with parameters, simple and complex instances; nothing about CAD in it); `io::step` maps bodies to the AP214 B-rep entities (`MANIFOLD_SOLID_BREP`, `BREP_WITH_VOIDS`, `ADVANCED_FACE`, every curve and surface kind incl. rational B-splines, vertex loops for whole spheres and tori and for an apex inside a face) with the document's units, uncertainty and names, after checking each body; `file.export` and `craft3d-cli convert` write `.step`/`.stp`. For that `io` now depends on `geom`, `topo` and `kernel` (the latter only for `boolean::contains_points`, to tell which lump a cavity is in). FreeCAD reads 448 exported files as valid solids of our volume and area (`cargo xtask freecad`). No import yet, no assemblies, colours or names of faces. The conventions are in [`file-formats.md`](file-formats.md) and in the module documentation.
- **DXF and SVG export (2026-10-13):** `drawing` writes ASCII DXF (AutoCAD 2000) and SVG 1.1 from its own 2D model (chains of lines, circular and elliptic arcs and B-splines; whole circles and ellipses; a unit; layers); `io::drawing` maps a sketch (its curves joined into chains) and the loops of flat faces (seen from outside the body) onto it; `file.export` writes them for a `sketch` or a `face`. Every curve stays what it is. FreeCAD reads both formats back with the closed-form length and area ([`file-formats.md`](file-formats.md) › Flat outlines).
- **Engine:** `engine::Session` holds open documents and runs 50 commands (`file.*`, `recovery.*`, `edit.*`, `variable.*`, `feature.*`, `sketch.*`, `history.rollback`, `document.inspect`, `document.check`, `document.measure`, `view.render`, `view.pick`) by id with JSON parameters. Edits are atomic undo steps; a failed command changes nothing; a panic inside a command is caught and reported. File access goes through explicit read and write roots. `tests/panic_hunt.rs` runs every command with adversarial parameters in four document states. Deviations from the plan: synchronous (no job pool, no events, no `arc-swap` snapshots), no parameter schemas beyond the documented params string, no `enabled` predicate beyond "needs a document". **Autosave and crash recovery** (2026-10-13, `engine/src/recovery.rs`, `recovery_store.rs`, `recovery_cmds.rs`; not in a browser): a session that its host gave a recovery directory notes after every command which documents changed (an `Arc` clone of the document, under a microsecond) and writes them with the `.3dcraft` writer on the one thread the engine starts, at most once per interval per document (30 s) and at once after a caught panic; a 300-feature document of 1.8 MB takes 40 to 90 ms there and nothing on the command's thread. The host ends it on a clean quit (`Session::end_recovery`), which removes the files; a killed process leaves them, and the next session's scan offers them through `recovery.list`, `recovery.open` and `recovery.discard`. The layout is in [`file-formats.md`](file-formats.md).
- **Desktop app and shell:** `ui-egui` is the shell as a library (serde state with the orbit camera, theme tokens, the viewport showing the renderer's image as a texture, a read-only feature tree, a status bar and a File menu); `apps/craft3d` puts it in an eframe window and adds the control listener (TCP on 127.0.0.1, token, the `serve` protocol plus `ui.*`), whose requests are answered on the UI thread between frames on the one `Session`. `engine::Session::scene_with` gives the shell meshes, the bodies' edges as polylines (`tess::tessellate_edges`: the points the mesh has along each edge) and sketch polylines per document revision, at the display quality (`SceneQuality::Display`, §6: finer than the export's automatic tolerance, within a triangle budget; `state.quality` in `ui.get`/`ui.set`), which `ui.screenshot` renders too; a change of quality is another mesh of the same revision, so the frame keys and the direct path's upload carry the scene's tolerance as well. Four things about the viewport: (1) the sharp image is made on the shell's render thread, and the UI thread only makes the quick preview; `frames::Scheduler`, a state machine without threads or clocks, decides what is made and drops every result that is not the image of what is wanted now (camera, document revision, size, selection). `Shell::new` renders where it draws (wasm, tests), `Shell::threaded_with` is what the window uses. (2) **Which renderer (2026-10-13, direct path the same day):** the window lends the shell its own wgpu device (eframe's `RenderState`: `Shell::threaded_with_gpu`), and with `--renderer auto` (the default) the viewport is drawn on it by `ui_egui::direct::Direct` over `craft3d_gpu::Onscreen` (§7.2): bodies and the lines over them, multisampled, every frame at the viewport's full size, directly into a texture registered with egui (`register_native_texture`) and shown as it is. Nothing is read back for display, there is no preview and no render thread on this path (the draw is submitted from the drawing thread and costs it about a millisecond; `RenderStats::milliseconds` is that thread's time, not the GPU's), and a frame is drawn only when something it depends on changed (camera, document revision, size, selection, theme). The mesh and the lines are uploaded once per scene revision (the lines again when the selection or the theme changes; the axes are rewritten in place when the zoom changes their length). When the direct path cannot be set up (no render state, no pipelines on that device), or fails for good while running (a lost device, a driver that falls over), the shell goes on as before with `ui_egui::backend::BodyRenderer`: the wgpu renderer on a device of its own per thread, read back as the same `Frame` the CPU renderer gives, with the quality rules below, or the CPU reference renderer when there is no adapter or it was asked for (`--renderer cpu`, `CRAFT3D_RENDERER=cpu`); the reason is in `ui.get` (`renderer.fallback`) and the terminal. A frame the device cannot take (a target or a mesh too large for it) is made that way too, and the next one directly again. `ui.get` reports `renderer {backend, adapter, fallback, direct, msaa}` and `render.msaa`; the status bar says `GPU 1440×900 ·…`. On the readback and CPU paths each thread has a renderer of its own with its own wgpu instance and device (wgpu's OpenGL backend ties a device to its thread), the sharp image is made on the render thread while a preview is on screen, and the budgets (`REST_SAMPLES`, `MOVING_SAMPLES` in samples for the CPU; `GPU_REST_PIXELS`, `GPU_MOVING_PIXELS` in pixels for the readback, which runs at a few hundred MB/s on this laptop's Intel driver) shrink the image while moving (`MOVING_DIVISOR`) and on a large window. `ui.screenshot` always renders on the CPU: it is the oracle. The tests: `crates/ui-egui/tests/gpu_viewport.rs` draws one scene through the direct path on a device made as eframe makes the window's (`direct::headless_render_state`) and through the readback path, and compares with the oracle under the tolerances of §7.2 (pictures in `target/evidence/ui/`); `tests/gpu_fallback.rs` takes the adapter away. In the browser the viewport is rendered on the CPU for now. Measurements (2026-10-13, `cargo run --release -p craft3d-ui-egui --example frame_time`, the development machine's Intel Meteor Lake iGPU over Vulkan, while other builds ran; the numbers are in `docs/development.md` › The live viewer). (3) Edges and sketches are lines over the image: on the direct path drawn by the GPU (§7.2), on the other paths drawn by egui in vector form, each cut against the renderer's depth buffer pixel by pixel; either way the part of an edge behind a body is left out, the part of a sketch behind a body is drawn dimmed, the world axes are always drawn. (4) Open and save: the shell only asks (`FileAction`); the application shows the system's dialog (`rfd`, on its own thread) and runs `file.open` or `file.save` with a grant for the chosen file's directory, which the control channel cannot reach ([`control-protocol.md`](control-protocol.md) › File access). `automation::bridge` is an MCP server that passes every message to that window (`mcp.message`).
- **Rendering:** `render` is the CPU reference renderer (perspective and orthographic, depth buffer, smooth two-sided shading, id buffer, supersampling, PNG), with cameras that frame a box in perspective, orthographically, or as a close-up from outside a larger model, and zoom. It draws no edges itself (the viewer draws them over its image, tested against its depth buffer; `view.render` has none yet), and has no near-plane clipping. `gpu` is the wgpu renderer for the same inputs and the same result (`Frame`: colour, face ids, view distance), offscreen (`Offscreen`) or on a device and queue someone else owns (`Renderer`), and, as `Onscreen`, the viewport's renderer on the window's own device: the picture multisampled, the lines over it drawn and depth-tested on the GPU, into a texture that is shown without any readback; it matches the CPU renderer within the tolerances derived in §7.2, and the desktop app's viewport draws with it when there is an adapter, with the readback path and the CPU renderer as the fallbacks (see *Desktop app and shell*).
- **Pointing (2026-10-13, faces):** a position in a picture gives the persistent name of the face under it, and a name is shown highlighted. Three layers, one answer. (1) `render::pick` is the CPU renderer's own arithmetic for one sample (the same projection, edge functions, depth key and tie rule as `render`, and it skips the triangles `render` skips), so at a pixel centre it returns the face `Frame::ids` holds there, with the point of the triangle that projects onto the position; it walks the triangles once and allocates nothing. (2) The engine's `Scene` carries the names: `SceneBody::face_names` and `face_aliases` are `faceNames` and `faceAliases` of `document.inspect`, face `k` of a body having id `first_face_id + k` in `Scene::mesh`; `Scene::pick` turns a hit into feature, body, name and point, and `Scene::faces_named` turns a name (with the feature when several bodies have it) into face ids. The command `view.pick` (`engine/src/pick_cmds.rs`) asks it of the scene and camera `view.render` uses (the framing is shared: `commands::Framing`), or of a camera given. (3) The shell asks the same of the scene it draws with the viewport's camera: a click (`Shell::pick`, also `ui.pick`) sets `UiState::picked` and `UiState::highlight`, and `ui.highlight` sets the highlight by name. **How the GPU viewport gives the same answer:** it does not read the GPU's id target back. The pick is computed on the CPU from the scene the viewport draws and the camera it draws with, and the GPU's picture has the same face at that pixel because its face ids equal the CPU's outside the band of §7.2 (that is what the parity tests assert); on a silhouette pixel the answer is the CPU renderer's. **The highlight** is `render::Highlight` in `RenderParams`: up to eight runs of face ids and a base colour (`theme::Tokens::face_highlight`). Both renderers shade those faces from that colour instead of the body's, with more ambient light (`SHADE_HIGHLIGHT_AMBIENT` 0.6, `SHADE_HIGHLIGHT_DIFFUSE` 0.4, so a highlighted face in the shade still shows; fifths on purpose, because a colour byte times a fifth is never half-way between two levels, where the GPU rounds to even and the CPU away from zero: with 0.55 the whole shaded side of a face was a level apart). On the GPU the runs are four `vec4` of the scene's uniform block compared with the vertex's face id, so a change of highlight uploads no mesh; ids are compared as floats and a highlight at or above 2²⁴ is refused (`GpuError::OutOfRange`), which sends that frame to the CPU. The highlight is part of the frame key of every path (preview, sharp image on the render thread, the direct path, `ui.screenshot`). Tests: `crates/render` (pick against the id buffer, exactly), `crates/gpu/tests/parity.rs` (16 highlighted scenes per adapter under the tolerances of §7.2), `crates/engine/tests/pointing.rs` (the acceptance test: 13 generated views of five bodies, a primitive, a boolean and patterns among them, 691 picks compared with `faceNames`; every one of the 58 faces picked from some side), `crates/ui-egui/tests/pointing.rs` and `gpu_viewport.rs` (clicks, `ui.pick`, `ui.highlight`, the direct path against the oracle). Not there: several highlights at once, a highlight in `view.render`.
- **See-through bodies (2026-10-13).** `RenderParams::opacity` (1: opaque). The CPU renderer keeps, per sample, the front fragment and the nearest fragment strictly behind it (two depth keys and two colours; a fragment that is neither is not shaded), and blends them once all triangles are drawn: `opacity * front + (1 - opacity) * behind`, the background where nothing is behind, no blend where the front face is highlighted. Why this definition: it is exact and order-independent (two minima), it needs no sorting, and a GPU can do the same with two passes (the scene, then the scene again with a fragment discarded unless its depth is greater than the first pass's at that sample) and one blend in the resolve, so the two renderers can agree under the tolerances of §7.2. Blending every layer in depth order was rejected: it needs sorted fragments or many passes, and several layers of grey read worse than one. At opacity 1 none of this runs and the frame is bit-identical to before (asserted). **The GPU half is not built:** `gpu::check_params` refuses an opacity below 1 (`GpuError::OutOfRange`, which both viewport paths treat as "this frame another way"), so the shell's `BodyRenderer` and the direct path hand a see-through frame to the CPU renderer and the picture on screen is the oracle's own; the cost is the CPU renderer's frame time while the bodies are see-through. The overlay draws the hidden stretches of body edges dimmed for such a frame (`viewport::overlay_see_through`). Tests: `crates/render` (the formula on stacked squares in all six triangle orders, opacity 1 and values that are not numbers, a highlight), `crates/ui-egui/tests/see_through.rs` (`ui.set`, the screenshot against the frame, hidden edges, picks unchanged, the slider, the GPU viewport falling back and coming back).
- **Pointing at edges (2026-10-13):** the same three layers. (1) `render::Viewpoint` projects a point the way the renderer projects a vertex, and `render::Neighbourhood` keeps the triangles that can be under a position within some pixels of another, so that many positions close together are looked up (`Neighbourhood::pick`, the arithmetic of `render::pick`, shared code) for one pass over the mesh. (2) `SceneBody::edge_names` and `edge_faces` are `name` and `faces` of `document.edges` for the polylines of `SceneBody::edges` (one per edge of the B-rep, in its order). `Scene::point_at` is the rule ([`control-protocol.md`](control-protocol.md), *Pointing*): the face under the position, and the nearest point in sight of any edge within the pick radius; a point is in sight when the surface the picture shows where the point lands is not nearer than the point (1e-7 of its distance plus the scene's size of slack: the points of an edge are points of the mesh, so this is rounding). `Scene::edges_named` turns an edge's own name, or two face names, into the edges of one body. (3) The shell's click and `ui.pick` call `point_at` with the viewport's camera; `UiState::picked` says which kind was hit and `UiState::highlight_edge` (an `EdgeRef`: own name, or the faces) is the edge shown. **The edge highlight is a line of the overlay**, not a shading: `viewport::Marks` holds the pieces of line of the highlighted edges, `viewport::overlay_marked` (CPU paths, `ui.screenshot`) and `direct::segments_marked` (the GPU's direct path) add them after everything else as `LineKind::Highlight`, depth-tested and dimmed where hidden, so the two paths agree on it exactly as they agree on every other line (§7.2). Cost: a pick is two passes over the mesh (the face, the neighbourhood) however many edges are near. Tests: `crates/engine/tests/pointing_edges.rs` (10 generated views of the five bodies: 1185 points of edges in sight picked and compared with `document.edges`, 776 points of hidden edges not picked through a face; a box alone against the closed form for a convex body; the radius measured; the nearest-edge rule on 2552 positions against a brute-force search; visibility there is a ray cast in space, another route than the pick's), `crates/ui-egui/tests/pointing_edges.rs` (37 edges clicked, `ui.pick`, `ui.highlight`, the screenshot, the direct path against the oracle along the highlighted lines).
- **Pointing at vertices (2026-10-13):** `SceneBody::vertices`, `vertex_names` and `vertex_faces` (the faces of the edges that end in a vertex) are what `document.edges` lists under `vertices`. `Scene::point_at` looks for the nearest vertex in sight within the radius before it settles for an edge (rule 4 of *Pointing* in [`control-protocol.md`](control-protocol.md)), `Scene::vertices_named` turns a vertex's own name, or the names of faces that all meet in it, into the vertices of one body, and `UiState::highlight_vertex` (a `VertexRef`) is drawn as a dot of `viewport::Marks::points`, by `overlay_marked` and `segments_marked` alike. Tests: `crates/engine/tests/pointing_edges.rs` (the same 10 views: 461 picks on vertices in sight give the vertex `document.edges` lists, 156 hidden ones are not picked; a box against the closed form, seven corners of eight; vertex against edge and face at measured distances), `crates/ui-egui/tests/pointing_edges.rs` (clicks, `ui.highlight {vertex | corner}`, the dot on the direct path against the oracle).
- **Demo:** `cargo run --release -p craft3d-render --example teapot` renders the Utah teapot (32 patches) to `target/evidence/teapot.png`.

## 1. Goals and principles

**Goals**
- A native, portable (Linux / macOS / Windows), fully open-source parametric 3D CAD modeller with its **own kernel and tessellator**, in pure Rust.
- **Built to be driven by AI.** Every action is a command with a stable id and serialisable parameters. An agent can build, inspect, render and export a model without a window.
- **Phase 1 has (almost) no UI:** load, save, view. The modelling surface is the command registry.
- **The design history is saved,** not just the result: sketches, constraints, formulas, variables, and the order in which they were applied.
- **Export** to STEP (exact B-rep) and to STL / 3MF / OBJ (meshes).
- **The UI can be swapped** without touching the core, and the core compiles to `wasm32`.

**Principles**

1. **Engine-first, headless-first.** Every feature is reachable without a GUI: from tests, the CLI, the control channel and MCP. The GUI is one client of the engine.
2. **Everything is a command.** Each action has a stable `CommandId` (such as `feature.extrude`) with typed, serialisable parameters. The UI, shortcuts, CLI, control channel, MCP and recorded scripts all dispatch the same commands.
3. **History is the source of truth; geometry is derived.** The document stores *how* the model is built. B-rep bodies and meshes are caches of that recipe.
4. **One algorithm, one implementation, one parameter struct.** Kernel and tessellator are CPU-only, deterministic Rust. Only *display* has a second (GPU) implementation, and it is checked against the CPU one.
5. **Immutable snapshots, structural sharing.** Documents and bodies are persistent data: `Arc`-shared, copy-on-write. Taking a snapshot is O(1); undo, background regeneration, autosave and UI reads are cheap and lock-free. (This is PhotoCraft's "copy-on-write tiles" applied to features and faces instead of pixels.)
6. **Determinism.** The same document gives bit-identical bodies and meshes across runs, thread counts and platforms.
7. **Pure Rust.** No C/C++ dependencies in the kernel, tessellator, formats or engine. System libraries appear only at the windowing/GPU edge (through winit and wgpu).
8. **Clean-room.** Public specs, textbooks, papers and observed behaviour only. No proprietary code, shaders or assets; no code from copyleft kernels.

### 1.1 Avoiding the usual CAD holes

PhotoCraft's plan starts from GIMP's lesson: properties baked into the core as assumptions (8-bit pixels, RGB only) cost years to undo. CAD systems have their own versions of that mistake. Each rule below is cheap on day one and a rewrite later.

| Property | The hole | Rule we adopt from day one | Where |
|---|---|---|---|
| **Topological naming** | Features that refer to "face 7" of the current body break or silently retarget when an upstream edit renumbers the faces. Open-source modellers have spent years retrofitting a fix | Every face, edge and vertex carries a **persistent name** derived from its origin (the feature that made it, the sketch entity it came from, the operation and operands that split or merged it). Features store names, never indices. A name that no longer resolves is a reported error on that feature, never a guess | `topo`, `kernel`, `regen`, `doc` |
| **Tolerance** | A global `EPSILON` works until a model is very small, very large, or imported from a system with another convention | Tolerance is **data**: a document-level linear and angular tolerance, plus per-entity tolerances on vertices and edges where an operation or import needed them. Every predicate takes a tolerance argument. No `const EPS` in public APIs | `math`, `topo`, `kernel` |
| **Units** | Unitless numbers that mean millimetres, until a file in inches arrives | The document has a length unit and an angle unit; expressions carry dimensions (`10 mm + 1 in` is valid, `10 mm + 30 deg` is an error). The kernel works in the document's unit; conversion happens at the format edges | `expr`, `doc`, `io` |
| **Geometry kinds** | Starting with planes and cylinders "for now" and discovering that every operation has to be reopened for freeform surfaces | `Curve` and `Surface` are enums that include NURBS from M1. An operation that does not yet handle a pair of kinds returns `Unsupported { op, kinds }`; it never assumes the case away. Analytic kinds stay analytic (a cylinder is not stored as a NURBS) so results stay exact where they can be | `geom`, `kernel` |
| **Precision** | `f32` in the modelling path, or mixing display and model precision | Kernel maths is `f64` throughout. `f32` exists only in vertex buffers handed to the GPU, converted relative to a per-view origin so large coordinates keep precision | `math`, `gpu` |
| **Result vs recipe** | Saving only the final solid, so a design cannot be edited | The native format stores the history. Cached bodies in a file are optional and verified by hash; a file with every cache removed opens to the same model | `doc`, `format` |
| **Single body, manifold only** | Assuming one solid per document, or that every result is a closed manifold | A document holds any number of bodies. A body is a list of shells and may be a solid, a sheet or a wire; validity is checked and reported, not assumed | `topo`, `doc` |
| **Regeneration order** | Implicit ordering by creation time or hash-map order, so reopening a file gives a different model | The feature list is an explicit ordered sequence; variables and formulas form an explicit dependency graph with a stored, deterministic evaluation order; the solver's constraint order is stored | `doc`, `regen`, `solve` |
| **File formats** | Format quirks leaking into core types | Formats live in standalone crates with their own format-level model; mapping to the document lives in `io`. Adding a format touches a leaf crate | `step`, `meshio`, `drawing`, `io` |
| **UI toolkit** | A core that calls into its toolkit | Nothing below L7 knows a toolkit exists | layering rule 2 |

The test is simple: **adding a surface kind, a feature type, or a file format should touch leaf crates, not the foundation.**

## 3. Dependency layering (enforced)

```text
 L8  apps/*                         (binaries: wire everything together)
 L7  ui-egui · automation
 L6  engine
 L5  io
 L4  regen · render · gpu · format
 L3  ops · solve · kernel · tess
 L2  doc
 L1  topo · expr
 L0  math · geom                    step, meshio, drawing (standalone, no workspace deps)
```

**Rules** (checked by `cargo xtask layers`, which parses `cargo metadata`):

1. A crate may depend only on crates in **lower** layers. No cycles. Sideways dependencies only where listed in `SAME_LAYER` in `xtask/src/layers.rs` (today: `geom` → `math`).
2. **Nothing below L7 may depend on any UI toolkit, winit, eframe or rfd.** Platform services (file dialogs, clipboard) reach the engine as injected functions or traits.
3. **`step`, `meshio` and `drawing` depend on no workspace crate.** The mapping between their models and ours lives in `io`. This keeps them publishable and fuzzable in isolation.
4. **`doc` contains no geometry algorithms.** It may use `topo` and `expr` *types* (names, expressions), nothing from L3.
5. **`kernel` and `tess` never depend on `gpu` or `render`.** Geometry has one implementation.
6. **wasm gate:** every crate in L0–L7 must build for `wasm32-unknown-unknown` (`cargo xtask wasm`).
7. `gpu` is optional for `engine`: the headless CLI and CI tests run `cpu-only`.

## 4. Document model (`craft3d-doc`)

A document is the recipe. Sketch of the types (final names are settled in M1/M2):

```rust
pub struct Document {
    pub id: DocId,
    pub units: Units,                    // length + angle unit
    pub tolerance: Tolerance,            // linear + angular modelling tolerance
    pub variables: VariableTable,        // name -> expression, in stored evaluation order
    pub features: Vec<Feature>,          // THE history: explicit order of application
    pub rollback: Option<FeatureId>,     // history marker: regenerate up to here
    pub metadata: Metadata,
}

pub struct Feature {
    pub id: FeatureId,                   // stable, never reused within a document
    pub name: String,
    pub suppressed: bool,
    pub kind: FeatureKind,
}

pub enum FeatureKind {
    DatumPlane(DatumPlane), DatumAxis(DatumAxis), DatumPoint(DatumPoint),
    Sketch(Sketch),
    Primitive(Primitive),                // box, cylinder, cone, sphere, torus
    Extrude(Extrude), Revolve(Revolve), Sweep(Sweep), Loft(Loft),
    Boolean(Boolean),                    // union / subtract / intersect between bodies
    Fillet(Fillet), Chamfer(Chamfer), Shell(Shell), Draft(Draft),
    Pattern(Pattern), Mirror(Mirror), Transform(TransformBody),
    Import(ImportedBody),                // a history-free body from STEP, stored as a blob
}

pub struct Sketch {                      // as built in M5: crates/doc/src/sketch.rs
    pub plane: SketchPlane,              // World { plane: Xy|Yz|Zx, offset: Expr }; datum planes and faces join in M6
    pub entities: Vec<Entity>,           // id, construction flag, geometry: Point {x, y}, Line, Circle, Arc, Spline on point ids
    pub constraints: Vec<Constraint>,    // id + kind, in the order they were applied
    pub next_entity_id: u64,             // ids are never reused within a sketch
    pub next_constraint_id: u64,
}                                        // the point coordinates and circle radii ARE the last solution

pub enum Constraint {
    Coincident(..), Horizontal(..), Vertical(..), Parallel(..), Perpendicular(..), Tangent(..),
    Equal(..), Concentric(..), Symmetric(..), Midpoint(..), Fixed(..),
    Distance { a: EntRef, b: EntRef, value: Expr }, Angle { .. , value: Expr },
    Radius { .. , value: Expr }, Diameter { .. , value: Expr },
}

pub struct Expr { pub source: String /* "width / 2 + 3 mm" */, /* parsed form cached, not serialised */ }

pub enum Ref {                           // how a feature points at geometry
    Feature(FeatureId),                  // a datum or a whole body
    Name(PersistentName),                // a face / edge / vertex
}
```

- **Every numeric parameter is an `Expr`,** not a number. `Extrude { distance: Expr }` may be `"25 mm"` or `"height - 2 * wall"`. The expression's source text is what is saved.
- **Order is explicit.** `features` is the order of application. `variables` keeps a stored topological order; `constraints` keeps the order in which they were added. Saving and reopening must reproduce the same model, so nothing that affects the result may depend on map iteration or solver start-up luck.
- **Solved sketch state is saved.** Constraint systems have several solutions (mirror branches). The last solution is stored and used as the solver's starting point, so a reopened sketch does not flip.
- **No bodies in the document.** Bodies live in the regeneration result, keyed by feature id.

### 4.1 Persistent names

A `PersistentName` identifies a topological entity by its origin, for example "the face made by extruding sketch entity `e12` of feature `F3`", "the cap face at the end of `F3`", "the edge between faces *A* and *B*", "the part of face *A* that survived boolean `F7`, on the side of operand 2". Names are produced by `kernel` operations (each operation reports, for every entity of its result, where it came from) and resolved by `regen` against the body at that point in the history.

Resolution outcomes are explicit: `One(entity)`, `Many(entities)` (the entity was split; the feature's policy decides whether that is acceptable) or `Missing`. A `Missing` or unexpected `Many` marks the feature as failed with a message naming the reference; the features before it remain valid.

The naming scheme is the hardest design problem in this plan and is prototyped in M6 before anything depends on it. Its rules and known limits get their own section in this document when that prototype lands.

**Splines in sketches (2026-10-13, the first step of M9's sweeps).** `Geometry::Spline { degree, control }` is a polynomial B-spline of degree 1 to 7 whose control points are point entities, in order, on clamped uniform knots that are derived from the degree and the count (`doc::clamped_uniform_knots`) and not stored. It starts at its first control point, ends at its last and leaves each along the leg to the next; with the first point also as the last it closes on itself. Why this form: the unknowns of the solver are the points, so the constraints that exist (coincident, fixed, distance, horizontal, ...) shape a spline without the solver knowing the kind at all, it adds no degrees of freedom, and it closes a loop with lines and arcs by sharing its end points. A later rational or non-uniform spline adds `weights` and `knots` as fields that default to what this one means. A spline *through* given points is not a second kind: `sketch.spline` with `through` works the control points out once (the curve takes point i at the Greville abscissa of control point i, a system that is well conditioned whatever the points) and stores an ordinary spline; the first and last points are shared as given, the ones in between become new control points. `regen` does not hand a spline to the solver: its points are there already. A `tangent` constraint between a spline and a line, an arc or another spline holds at an end point the two share (one point entity, or two tied by a coincident constraint) and becomes a condition on the spline's end leg: parallel to the line or to the other spline's leg, tangent to the arc's circle at that point; without a shared end the sketch fails with that reason. The other constraints refuse a spline (`pointOn` a spline included) as not supported yet.

**Profiles and extrusions with splines (2026-10-13).** `kernel::profile` takes `Curve2::Spline` (degree, knots, control points; `kernel::spline2` holds the arithmetic). A spline's ends join like those of a line; where it meets an arc its end control point is moved onto the arc's end. Area and centroid are exact (Green's theorem by Gauss–Legendre on each Bézier piece, whose integrands are polynomials). Whether a spline keeps clear of another curve, and of itself, is decided by subdivision: curves are compared as chords of pieces flat within an eighth of the tolerance, so curves that come within three quarters of the tolerance of each other away from a shared end are always refused, curves that stay more than one and a quarter of it apart never are; a spline with a cusp, or one that crosses or touches itself, is refused and named (`e7 crosses or touches itself`). Refused as well, each with its reason: a spline with a corner (an inner knot as often as its degree, which is every inner knot of a degree-1 spline: its wall would be a creased surface), and a loop of one spline that closes on itself (its wall would be a freeform surface that closes on itself, which the tessellator does not follow; two splines that share both ends are a loop). `kernel::extrude` sweeps a spline into a face on a polynomial B-spline surface (the spline's degree by 1) between B-spline edges; the caps are planes bounded by them; the wall is named `side(e7)` like any other, so moving a control point renames nothing. `kernel::revolve` refuses a spline (`UnsupportedCurve`): the surface would be rational. Such a solid is a boolean operand like any body with polynomial B-spline faces. Known limits, each an error and not a wrong result: the exact integrals (`mass_properties`) and the tessellator can decline the wall of a spline with a hairpin just short of a cusp (measured on random profiles: 4 of 88 meshes declined, 0 of 30 integrals), and the integrals take seconds on a wall that wiggles.

**Extrude ends (2026-10-13, M8.5).** `doc::Extrude` has, besides `sketch`, `distance` and `symmetric`, an `end` (`ExtrudeEnd`: `Distance`, `ThroughAll`, `UpToFace { face: PersistentName }`) and `reversed` (against the sketch's normal; for a distance the same as negating it). `feature.extrude` takes one of `distance`, `throughAll` and `upTo`, with `symmetric` and `reversed`; `feature.edit` changes the end by giving the new one.

- *Symmetric:* `distance` is the whole length, half to each side of the sketch plane.
- *Through all* is decided in `regen` (`regen/src/extrude.rs`, `through_all`), from boxes, without a boolean. "All" is every body the features before this one have made that is still a body of the document at that point of the history (not taken by a boolean, a transform or a pattern before it) and that lies in the way: its box (`Body::bbox`, conservative), seen along the sketch's normal, overlaps the box of the profiles. The extrusion runs from the sketch plane to past the farthest such box by a margin (a hundredth of the way, at least a thousand tolerances), so that a cut never ends flush with the far side; `symmetric` runs from before the nearest box to past the farthest. With nothing in the way the feature fails and says so (`there is nothing to go through along the sketch's normal: none of the 2 bodies built before this feature lies in the way of the profile`). The length is not stored: it follows the bodies. The regeneration cache knows that such a feature depends on every feature before it (`FeatureKind::uses_all_earlier`).
- *Up to a face* is `kernel::extrude_to::extrude_up_to`. The profiles are extruded past the face's surface, a *tool* solid is built that has that surface as one of its faces (a block behind a plane; the solid cylinder, ball or ring of a cylinder, sphere or torus; for a polynomial Bézier or B-spline face the solid behind the whole patch, with a wall under each of its borders), and the kernel's boolean takes the tool away (or, from a sketch plane inside a ball or a cylinder, keeps what is inside it). What hangs on to the start caps is the result; what comes out on the other side of a cylinder is dropped. So the end lies on the face's *surface*: where the profile hangs over the face's edge it ends on the plane, cylinder, sphere or torus continued, and a freeform surface ends where its patch ends. The profile has to reach the face itself somewhere (looked at on nine points per edge of the end and of the face; the module documentation says what that cannot see). The reference is the face's persistent name, resolved against the body of the feature the name starts with, as it is at that point (a copy name such as `F3:copy(1)/F2:face(1)` against the boolean's body); pieces of one face count as the face, and a cap whose outline changed still names its surface, as for a sketch's plane. A name that points at nothing fails the feature with the name and the faces that are there (``upTo: `Part` no longer has a face F3:copy(1)/F2:face(1); its faces are: …``); it never lands on another face, and the features that do not depend on it are built. Pointing `upTo` at a face that is there repairs it.
- *Names.* The faces are named as a plain extrusion names them: `startCap` in the sketch plane, `side(e7)`, and `endCap` (with the outline of its profile) for the faces on the target surface, which need not be flat, and can be several faces with one name when the boolean left the end in pieces. Edges and vertices get their plain names too (`endEdge(e7)` where wall `e7` meets the surface) whenever each can be told; when one cannot, the body has no edge and vertex names, as after any boolean.
- *Refused, each with its reason:* a face parallel to the direction (or a freeform patch that turns away from it somewhere); a face behind the sketch plane (`reversed` turns the extrusion round; the direction is never guessed, so that an edit which moves the face to the other side fails instead of flipping the body); a surface that passes through the sketch plane inside the profile; a profile part of which passes beside the surface or beyond the patch; a profile that misses the face; `symmetric` with `upTo`. **Not built:** a cone face and a rational freeform face as the end (`Unsupported`); a second end on the other side (from a face up to a face); an offset from the face. Whatever the boolean refuses is the feature's failure, with the boolean's reason.

Measured (`crates/kernel/tests/extrude_to.rs`, `crates/engine/tests/extrude_ends.rs`, scales 1e-3, 1 and 1e6, world and tilted frames): a round profile up to an inclined plane has the volume of a cylinder of the mean height and an elliptic end of area πa²/cos θ; a rectangle up to a lying cylinder and a round profile up to a ball (from outside and from inside) have their closed forms to 1e-9; a rectangle up to a parabolic B-spline wall has the area under the parabola times its height, and the arc length in its area, to 1e-7.

**As built so far (M6, first slice).** An extrusion names what it makes by role and by the sketch entities involved, written `F2:side(e7)`: the caps are `startCap` and `endCap` with the entity ids of the profile's outer loop; a side face is `side(curve)`; the cap edges are `startEdge(curve)` and `endEdge(curve)`; the upright edge swept by a corner is `lateralEdge(incoming, outgoing)` in the direction the loop runs through that corner, and the corners are `startVertex` and `endVertex` with the same pair. The names do not depend on the order of the curves or on what else is in the sketch: drawing a hole afterwards adds names and changes none. Known limits: drawing a loop *around* an existing one turns it into a hole and reverses it, so its corner and upright-edge names get their pair the other way round (the old names go missing rather than land elsewhere), and the caps are renamed after the new outer loop. **Resolution (M6).** `doc::PersistentName` is the name as data (feature, role, sources; `F2:side(e7)` as text). `regen` resolves it against the features regenerated so far: the feature must exist, come earlier in the history, have succeeded, and have a face whose origin is exactly that name. Anything else fails the referring feature with a reason that says which of those it was and lists the names that do exist; a name never resolves to a different face. One looser match exists, for the *plane* of a sketch only: all caps of one role of one extrusion lie in one plane and share one frame, so a cap name whose outline is no longer there (`F2:endCap(e5,e6,e7,e8)` after the corners were rounded, or simply `F2:endCap()`) still gives the sketch its plane, that of any cap of that role of that feature. The stored name is not rewritten. A side face has no such fallback. The first consumer is a sketch on a face (`SketchPlane::Face`), and the suite in `crates/engine/tests/naming.rs` holds the scenarios.

**Bodies made from bodies (M6).** A transform, a mirror and a pattern make their body out of the body of an earlier feature. That feature's result stays in the regeneration (names are resolved against it) and is marked as taken by the later feature, so its body is no longer one of the document's bodies; `keep` leaves it its body. A body can be taken once. Every entity of the new body is named after the entity it is the image of, as a *copy*: `F5:copy(2)/F2:side(e7)` is the image, in instance 2 of F5, of the face F2 calls `side(e7)` (instance 0 for a transform or a mirror). The part after `/` is a name of its own, so copies of copies chain (`F9:copy(0)/F5:copy(2)/F2:side(e7)`, at most 32 deep). A copy resolves by walking the chain down to the face as it was first made, with the rules above (the looser match for caps included), and carrying its frame back up through the motion of each copy; a name whose instance no longer exists, or whose inner name is not of the body the feature was made from, points at nothing. After a mirror the frame is still seen from outside and right-handed: x is the image of x, and y points the other way than the image of y. Instances of a pattern that touch or overlap (their boxes come within the tolerance of each other) are joined by the kernel's union; the faces keep their copy names (a face merged from the faces of several instances is named after the first and answers to the others as aliases, see *Merged faces carry aliases* below), and edges are then referred to by the faces they lie between, as after any boolean.

**Booleans (M7).** A boolean feature combines the bodies of two earlier features (target and tool) and takes both, unless the tool is kept. Every face of the result is a face of one operand, or a piece of one, and is named as a copy of it: instance 0 is the target, 1 the tool (`F7:copy(0)/F2:endCap(e5,e6,e7,e8)`, `F7:copy(1)/F3:face(0)`). A face cut into pieces gives several faces with one name. That is resolution outcome `Many`; for the plane of a sketch it is accepted, because the pieces lie on one surface. A face the boolean removed is not among the result's names, and a reference to it fails and lists the faces that are there. **Edges are referred to by the faces they lie between** (`regen::edges_between`, `document.edges`): an edge of a solid is where two faces meet, and faces have names through every feature kind. "The edges between `F4:copy(0)/F2:endCap(...)` and `F4:copy(1)/F3:face(0)`" is the rim of a drilled hole, whatever the body's edge numbering is, and it is a list: two faces can meet in several edges, and pieces of one face share a name. So edges made by a boolean need no names of their own (a name would need two parents). Sweeps still name their edges and vertices directly as well. **Merged faces carry aliases (2026-10-13).** Faces that a boolean split needlessly, or that continue across both operands on one surface (the tops of two flush blocks united), are merged again by the kernel, so a union of flush bodies has no seam. The kernel lists every contributing face of such a face (`BooleanResult::merged`, the target's faces first, in order). `regen` names the face after the first contributor (`F3:copy(0)/F1:face(1)`) and gives it the names of the others as *aliases* (`F3:copy(1)/F2:face(1)`; `Names::aliases`, listed by `document.inspect` as `faceAliases`, per face, only when a body has any). A reference resolves by any of a face's names: a sketch on the merged top by the tool's cap name lands on it, with the frame of the tool's cap (the one plane), and `document.edges` finds the rim by either name. The stored name is not rewritten, and nothing is stored in the file: aliases are derived at regeneration, so a document written before this change resolves as it did, and a name that resolved without merging (a face of the tool that kept its own name) still does. Edits upstream: while the faces stay flush the alias follows the merged face; when they are no longer flush the name means the tool's own face, which is there, and the sketch goes with it (not a retarget: the same origin); when the tool's face is gone (sunk into the target) the name is `Missing`, listed or not. The pattern feature's union of touching instances does the same (`F2:copy(0)/F1:face(1)` with aliases `F2:copy(1)/…` and `F2:copy(2)/…`, in instance order). Known limits: nothing consumes an edge reference yet (fillets are M9); vertices have no such reference yet (three faces).

**Primitives (M6).** A primitive is built in a fixed order, so the number of an entity says where it came from: its faces, edges and vertices are named `F3:face(1)`, `F3:edge(4)`, `F3:vertex(0)`. For a block the faces are 0 bottom, 1 top, 2 front (-y), 3 back (+y), 4 left (-x), 5 right (+x) in its own axes; for a cylinder 0 the wall, 1 the bottom, 2 the top; for a cone 0 the side, 1 the base. A sketch on such a face has the frame the kernel gave the face, seen from outside (on the top of a block: the block's own x and y at its height). The order is part of the kernel's contract and is pinned by `crates/engine/tests/naming.rs`.

**The frame of a sketch on a face** is the face's own, seen from outside the body (z is the outward normal, moved by the sketch's offset): on the end cap of an extrusion, the axes and origin of the extruded sketch, moved to the end; on the start cap the same origin and x axis with y reversed; on a side face made from a line, x runs along the line (in the direction the profile's loop runs) and y along the extruded sketch's normal, and the origin is the origin of the extruded sketch dropped straight onto the face. That point moves only when the face moves along its own normal: not with the line's end points (a corner radius), and not with the depth or direction of the extrusion. "Start" is the cap in the sketch plane and "end" the far one, whichever way the extrusion goes. Known limits: turning an extrusion round (a negative distance) puts its end cap on the other side facing the other way, so a sketch on it is mirrored in y, and a sketch on a side face stays on its side of the sketch plane rather than following the body; primitives do not name their faces yet; a curved face cannot carry a sketch.

## 5. Kernel

### 5.1 Geometry (`geom`)

```rust
pub enum Curve3 { Line(..), Circle(..), Ellipse(..), Nurbs(..), Trimmed(..), Offset(..), SurfaceIso(..), Intersection(..) }
pub enum Curve2 { Line(..), Circle(..), Ellipse(..), Nurbs(..) }           // parameter-space curves on a surface
pub enum Surface { Plane(..), Cylinder(..), Cone(..), Sphere(..), Torus(..), Extrusion(..), Revolution(..), Nurbs(..), Offset(..) }
```

Every kind implements evaluation with derivatives, parameter range and periodicity, bounding box, closest-point projection and inversion, and reversal. Projection as built (`Surface::project`): closed form for the analytic kinds; for Bézier and NURBS surfaces a search from the samples of a 16 × 16 grid that are nearer than their neighbours (and from a four times closer look around the nearest), each followed downhill by a damped Gauss–Newton iteration that puts the curving of the surface in when its steps fall short (Newton). It walks across the seam of a surface that closes on itself, half-steps towards a border that is a single point (a pole, a collapsed patch edge) and slides along a border of an open patch. The answer is a local nearest point, and the nearest one for a point closer to the surface than the surface curves, on a surface whose features are larger than a sixteenth of its domain (`crates/geom/tests/project.rs`). Intersections (curve/curve, curve/surface, surface/surface) are dispatched on the pair of kinds: closed-form where a formula exists (plane/plane, plane/cylinder, …), numeric marching with a tolerance otherwise. A pair that is not implemented returns `Unsupported`, and the test suite lists which pairs are covered.

#### Intersections as built (2026-10-13)

`geom::intersect::meet_surfaces(a, b, within, tolerance)` returns `None`, `Coincident { same_normal }` or `Meets(Meeting { curves, points })` for any two surfaces. Each `MeetingCurve` has the curve, the `range` of it that is meant, and the flags `closed`, `tangent` (the surfaces touch along it without crossing) and `exact`; an approximate curve carries a `deviation` that bounds its distance to both surfaces and is at most the linear tolerance. `points` are isolated touches. Curves are clipped to the box `within`, which is what makes a hyperbola or the curve of two crossing cylinders finite. The two surfaces are put in a fixed order first, so `meet(a, b)` and `meet(b, a)` are the same computation and the same result, bit for bit. **Curves never cross each other except at their ends:** where two branches cross (the surfaces are tangent there: two equal cylinders at right angles, a bitangent plane on a torus, Viviani's curve) every arm is a curve of its own that ends on the crossing point. `intersect_surfaces` (planes and cylinders, no box) is unchanged and still what `kernel::boolean` calls.

| Pair | Result |
|---|---|
| plane / plane, plane / cylinder, cylinders with parallel axes | exact: line, circle, ellipse, lines (the earlier closed forms) |
| plane / sphere, sphere / sphere | exact: circle, or a touch point |
| plane / cone | exact: circle, ellipse, parabola and one branch of a hyperbola (the last two as rational quadratic NURBS, the parabola polynomial), the apex alone, one ruling (tangent) or two; only the cone's own nappe |
| cylinder, cone, sphere, torus about one axis | exact: circles where their profiles meet (tangent ones flagged), the apex or a pole as a point |
| plane / torus, plane across or through the axis | exact: one or two circles about the axis, or the two sections of the tube |
| cylinders of equal radius whose axes cross | exact: two ellipses, as four half-ellipses that end on the two points where the cylinders touch |
| cones of equal half-angle with parallel axes | exact: the conic in the plane they meet in (not when that plane passes through the apexes: numeric) |
| equal spheres, cones, tori (cylinders, planes) | `Coincident` |
| every other pair, including anything with a Bézier or NURBS surface | numeric: C¹ cubic NURBS within the tolerance of both surfaces |

**The numeric method** (`intersect/march.rs`; the module comment has the argument in full). One surface is walked in its parameters, the other is a signed distance (closed form for the analytic kinds, closest point for freeform surfaces), and the intersection is the zero set of that distance over the first surface's parameter rectangle. A quadtree discards a cell when the distance at its centre exceeds what the surface can cover within the cell (a distance is 1-Lipschitz), and stops dividing when a bound on the second derivatives shows the distance to be monotonic along u or along v over the whole cell: such a cell holds no tangent point, and a branch through it is detected by the signs at its corners. Cells that reach the size of the tolerance without either holding are searched by Newton iteration for the point where the surfaces are tangent: a minimum or maximum of the distance is a touch point, a saddle is a crossing of two branches, anything flatter is refused. The same search runs earlier, as soon as cells keep failing both tests (around a point of tangency the gradient is small over an area that grows with the looseness of the bound, so thousands of cells per level fail there): where it finds the point and the gradient follows the Hessian's second-order model within a quarter on two rings around it, the disc inside the rings is settled without cells: it holds the touch, the two branches through the crossing (seeded along the directions in which the Hessian vanishes), or, around a critical point off the other surface with the distance of the sign its Hessian keeps, nothing. A touch is only recorded where the surfaces are within the tolerance and within a floor cell's reach of each other, which is where the cells alone would have found it. So no loop larger than a floor cell (twice the linear tolerance across) is missed, provided the derivative bounds and the rings hold: the bounds are proofs for analytic surfaces and polynomial Bézier patches, and estimates from samples for rational NURBS and for the curvature of freeform surfaces used as the distance (taken from how fast the normal turns on a grid near the point, doubled twice as margin); the rings are samples. Branches are marched with the step limited by the turn of the tangent, end where they close, leave the rectangle, run off the edge of the other surface or reach a crossing point or apex, and are fitted by a cubic Hermite spline that is refined until it is within half the tolerance of both surfaces and of the intersection itself at three places per span.

A contact where the Hessian of the distance is degenerate (the surfaces touch along a curve, or to more than second order) is a touch when the distance keeps one sign on three rings of samples around it: the surfaces do not cross there, so nothing is divided. **Refused, as errors:** such a contact where the sign changes on every ring (`Unsupported`); surfaces nearly tangent or coincident over an area, a curve that needs more points or evaluations than the caps allow, a fit that does not reach the tolerance, a tolerance finer than rounding allows at the size of the box (`NoConvergence` or `InvalidParameter`). Nothing partial is returned.

`intersect_curve_surface(curve, surface, tolerance)` covers every curve kind against every surface kind. Closed form: a line with a plane, cylinder, sphere or cone; a circle or ellipse with a plane and with a cylinder it is a section of a parallel cylinder to; a circle with a sphere, and with a surface of revolution about its own axis. Everything else is root finding on the signed distance along the curve with the same two certificates in one dimension (`intersect/curves.rs`); a hit where the curve stays within the tolerance of the surface without crossing by more is `tangent`, and a curve within the tolerance everywhere is `OnSurface`.

### 5.2 Topology (`topo`)

```text
Body ── Shell ── Face ── Loop ── Coedge ── Edge ── Vertex
                  │                 │        │        │
               Surface           Curve2    Curve3   Point     (+ orientation flags, tolerances, persistent names)
```

- A **body** is a set of shells: a *solid* (closed, oriented shells), a *sheet* (open faces) or a *wire* (edges only).
- A **face** is a surface trimmed by loops; a **coedge** is the use of an edge by a face, with a direction and a parameter-space curve.
- Storage is arena-based with typed ids, and persistent: an operation builds a new body that shares unchanged parts with its input.
- **Genus** (`topo::genus`): from Euler–Poincaré, `V − E + F − R − 2H = 2 (S − G)`. `R` is, per face, its loops beyond the first (−1 for a face without loops), which counts every face as a disc with holes. A face on a torus that still has the torus's handle (the whole torus, or the torus less the discs inside its loops) is not one and takes 2 off (`H`). A torus face with a loop around the axis or around the tube is a band, and one inside its loops is a patch: neither counts. The hole a drill leaves in a torus and the plug it takes out have the same loops walked the other way, so which of the two a face is, is read off the area its loops enclose in parameter space. A spline surface that closes on itself is not known to.
- **Validity checker** (`topo::check`): Euler–Poincaré, every edge of a solid used by exactly two coedges with opposite directions, loops closed, coedge curves on their surface within tolerance, vertices on their edges, consistent orientation, no self-intersection (the expensive checks behind a level flag). Every kernel operation is tested to return bodies that pass it.
- **Self-intersection, as built (2026-10-13):** `topo::check` does not test it. The test is `tess::body_self_intersections(&Body, &SelfCheckParams) -> SelfCheck`, in `tess` because it works on the mesh and so stays independent of the kernel it checks: it tessellates the body (chordal tolerance 1/1000 of its diagonal), finds the triangles that meet without being neighbours (§6), and reports crossings and overlaps between faces, each with a depth and with the margin `deviation(f) + deviation(g) + 2 × tolerance` that the approximation alone could explain (`deviation` is the chordal tolerance, or 0 for a plane bounded by straight edges, whose mesh is the face). A finding deeper than its margin is *certain*; one within it is reported as such and proves nothing (tangent faces, a ball resting on a plane). Findings within the margin between curved faces are looked at again with a mesh four times finer, twice by default. Flat faces within twice the modelling tolerance of one plane that share area are an overlap. Shells that do not cross are checked for where they lie, by the winding number of the other shells at a point of each: an outward shell must be in no material, a cavity in material. It is a test oracle today (`crates/testkit/tests/self_intersection.rs`, [`testing.md`](testing.md) oracle 9, which also lists what it cannot see), not yet a level of `check` or a step of the kernel operations.
- **Mass properties:** volume, surface area, centroid and inertia tensor, computed from the exact B-rep (surface integrals), independent of the tessellator. Volume and centroid are taken about the middle of the body, not the origin of the model (2026-10-13): a small body far from the origin is then measured as well as the same body at the origin. These are the backbone of the test oracles. As built (`topo::mass_properties`: area, volume, centroid): each face is a boundary integral in its surface's parameters, and the result does not depend on how the surface is parametrised. A sphere face is measured in a frame chosen for its boundary, not in the surface's own (one pole in the middle of the boundary, the other as far from it as it gets); on a cone the integral runs from the apex whenever the boundary comes near it. Every boundary integral is computed with half the panels its edges need, with all of them, and with twice as many until two sums in a row agree to 1e-12; a face for which they never do is an error (`Unsupported`), as is a face that lies outside its own loops (`UnboundedFace`). Only plane faces bounded by lines, circles and ellipses skip that check: their sums are exact. On a spline surface every panel, across the face and along its boundary, ends at the surface's knot lines (and an edge's panels at its own knots too), and the panels across the face are doubled along with the boundary's; a face that holds a pole of a spline surface of revolution is integrated from that pole. On a freeform surface the nodes along one piece of an edge are projected each from where the last one landed (`Surface::project_from`, a few evaluations instead of a search over the whole surface), and the search is run only where the short way does not land on a foot of the node: within 1e-5 of the body's size and square to the surface, which is the same point the search finds. A spline edge of eight knot spans or more (the curve in which two surfaces meet, as the kernel fits it) is summed first with the eight-node rule on one panel per span and then with the sixteen-node one, before its panels double.
- **Moving, mirroring, merging** (`topo::transform`): `Body::transformed` maps a body by an isometry exactly (no curve or surface changes kind; scaling and shear are errors) and keeps every entity id. Curves keep their parametrisation, so edges are untouched. A mirror turns right-handed things left-handed: frames become `(Tx, Ty, −Tz)`, every loop is walked the other way round, and faces on planes and freeform surfaces toggle `reversed`, while cylinders, cones (half-angle negated), spheres and tori keep their outward normal and get `v` negated. `Body::bbox` is a conservative box from the exact geometry (tight for planes, cylinders and cones with analytic edges; the whole surface for spheres and tori, the control net for freeform). `merge` puts the shells of several bodies into one and reports the id offsets; it does not check that they are disjoint. These are what the transform, mirror and pattern features build on.

### 5.3 Operations (`kernel`)

Each operation is a pure function: bodies and parameters in, `Result<OpResult, KernelError>` out, where `OpResult` holds the new body and the **origin map** (for every result entity: which input entities and which role produced it), which feeds persistent naming.

| Group | Operations | Milestone |
|---|---|---|
| Primitives | box, cylinder, cone, sphere, torus | M3 |
| From sketches | profile detection (closed regions from sketch entities), extrude, revolve | M6 |
| Booleans | union, subtract, intersect on solids; imprint, split | M7 |
| Local | fillet, chamfer (constant radius first), shell, draft, offset face | M9 |
| Sweeps | sweep along a path, loft between profiles | M9 |
| Arrangement | transform, mirror, linear and circular pattern | M6–M9 |

**Rules for every operation:**
- **Signature:** `fn(inputs, params: &P, tol: &Tolerance, cancel: &CancelToken) -> Result<OpResult, KernelError>`; `P: Serialize + Deserialize`.
- **Never an invalid body.** The result passes `topo::check` or the operation returns `Err`. Errors name the entities and the reason ("faces F3/cap and F5/side are tangent along a curve; tangent booleans are not supported yet").
- **Deterministic:** no dependence on thread count or hash order.
- **Not registered by itself:** `engine` registers commands; `kernel` stays engine-agnostic.

#### Booleans as built (M7, generalised 2026-10-13)

`kernel::boolean::boolean(a, b, op, tolerance)` returns a `BooleanResult`: the body and, per face, edge and vertex of it, a source (`FaceSource`, `EdgeSource`, `VertexSource`). `boolean_with` takes `BooleanOptions` (`merge`, on by default). `boolean::contains_points` classifies points against a solid with the same ray casting the booleans use; it does not go through `mass_properties`, so a count of sampled points measures a body independently of it.

**Method** (imprint, classify, select, sew, merge; one file per step in `crates/kernel/src/boolean/`):

1. *Section* (`section.rs`). For each face of A and face of B that can meet (their boxes meet and neither lies wholly to one side of the other's surface), the curves in which their surfaces meet are asked of `meet_surfaces`, with the box where both bodies are. A curve is cut where an edge of either face meets the other face's surface (`hits.rs`: the closed forms of `geom::intersect`, and where there is none the roots of the signed distance along the curve, isolated by the fact that the distance changes no faster than the curve moves), and where the curve itself ends. A stretch between two cuts is kept when its middle is in or on both faces. The boolean does not know which pair of surfaces a curve came from, nor whether it is exact: a vertex is always where an *edge's own curve* meets a surface, and is then found on the stretch within the tolerance.
2. *Imprint.* Edges are split at the vertices found on them. Edge pieces and stretches are registered as arcs; two arcs between the same vertices along the same curve are one arc. An edge of B that lies on a face of A, or along an edge of A, is shared from then on, and nothing is matched by position afterwards.
3. *Regions* (`regions.rs`). A face with arcs across it falls into regions: around each vertex the arcs are sorted by direction in the tangent plane (at the apex of a cone: seen along the axis), arcs that leave in one direction are told apart a little further along, and loops are followed keeping the region on the left. An arc with the same region on both sides divides nothing and is dropped. Loops are grouped in a chart of the surface: a loop that goes around a point just to its left is an outside, any other a hole of the innermost outside around it.
4. *Classify* (`classify.rs`, `chart.rs`). One point well inside a region decides for the region: on a face of the other solid with a coincident surface, or inside or outside the other solid by ray casting (a ray that meets an edge or grazes a face is abandoned for another, twelve at most; a point within twice the tolerance of the other body is no use, and the next of up to four is tried). **Inside or outside a face is a winding number in a chart of its surface**, computed from points in space, so no seam or pole is a special place: a plane is its own chart; a cylinder is mapped conformally (angle and `exp(height / radius)` as polar coordinates, evaluated without the exponential); a cone is dropped along its axis onto a plane, which makes the apex an ordinary point; a sphere is projected stereographically from a point chosen clear of the boundary; a torus is cut open along a circle that the boundary does not cross. A face on a sphere or a torus may contain the place its chart leaves out; the winding of its loops about a point just inside it says which. A face without loops is its whole surface.
5. *Select.* See the table below.
6. *Sew* (`sew.rs`). Faces connected through edges form a shell. Where more than two faces meet along an arc, faces and material alternate around it: each face that runs against the arc is paired with the next face counter-clockwise (faces tangent there are put in order a little way off the arc) and every pair gets its own copy of the edge. Where several fans of faces meet at a vertex, every fan gets its own copy of the vertex. The copies are in one place and share nothing, so every result is a manifold. A bounded face on a sphere gets a frame whose poles are clear of its boundary (a sphere is the same surface whichever way its poles point; what reads a face through its parameters is at its best that way).
7. *Merge* (`merge.rs`). Faces that share an edge and lie on one surface facing one way are one face when they are pieces of one face of an operand, or pieces of a face of A and a face of B that are coincident; every edge inside such a group goes and the loops are spliced where it was. A vertex left with two edges that continue each other along one curve goes too, unless its operand had it like that. The face that remains has the source of the lowest-numbered face of A in the group, else of B; a joined edge the lesser of its sources (an edge of A before an edge of B before an intersection). The result passes `topo::check` or the operation fails.

| Region of | Outside the other | Inside the other | Coincident, same normal | Coincident, opposite normals |
|---|---|---|---|---|
| A, union | kept | | kept (the source is A's face) | |
| A, intersection | | kept | kept (the source is A's face) | |
| A, difference | kept | | | kept |
| B, union | kept | | | |
| B, intersection | | kept | | |
| B, difference | | kept, turned inside out | | |

**Contact without overlap.** Bodies that only touch (face against face along a line, a circle or at a point; an edge against a face or an edge; a vertex against anything) have nothing in common: the union is both bodies as shells that share no entity, the intersection is `EmptyResult`, the difference is the first body with the entities it had. A curve along which two faces touch is imprinted like any other; where the result does not need it (it ends inside a face, or has one face on both sides) it leaves no trace, and where it does (a cylinder that touches all four sides of its block cuts it into four parts) it is an edge. A result whose parts hang together only by an edge or a vertex has that edge or vertex once per part.

**Supported and not** (tests: `crates/kernel/tests/boolean.rs`, `boolean_surfaces.rs`, `boolean_contact.rs`, `boolean_random.rs`, `boolean_corpus.rs`):

| Configuration | Result |
|---|---|
| faces on planes, cylinders, cones, spheres and tori; whole spheres and tori; edges on lines, circles, ellipses and splines | operands like any other |
| coincident faces (same or opposite normals; overlapping, touching or sharing edges), on any of those surfaces | handled by the table above, and merged |
| faces that touch along a curve or at a point; bodies that touch along an edge or at a vertex | handled: see *Contact without overlap* |
| curves that leave a vertex in one direction (a circle tangent to an edge it meets) | handled |
| a boundary through the apex of a cone or a pole of a sphere | handled |
| intersection curves that are approximations (splines within a deviation of both surfaces) | handled: tolerant edges |
| a pair of surfaces whose intersection `meet_surfaces` does not give | `Unsupported`, with its reason |
| a polynomial Bézier or B-spline face in either body (a domed block against a block, a cylinder, a cone, a ball, a torus or another dome) | operands like any other: see *Freeform faces* below; the curves in which its surface meets another are splines within the tolerance |
| a rational freeform face (weights not all one), or one whose parametrisation may stall or fold | `Unsupported`, with its reason |
| two faces between half and twice the tolerance apart where one is over the other; two faces of different kinds that go through each other by that much; two points likewise; a piece of a face thinner than about eight tolerances | `Unsupported` ("at the edge of tolerance") |
| two faces of different kinds that go through each other by less than half the tolerance | touching: nothing is imprinted |
| a curve in which two faces cross, strictly inside both, that ends up dividing neither | `Unsupported` ("imprint lost"): a consistency check, zero on the corpus and the random runs |
| more than two faces along an edge where two of them are tangent to second order | `Unsupported` |

The curves come from `geom::intersect::meet_surfaces` (since 2026-10-13; the stand-in of the first version is gone): exact where there is a closed form, splines within the tolerance otherwise. What it cannot give (surfaces tangent or nearly coincident over an area, a touch along a curve without closed form) is refused with its reason. Curve/surface hits use geometry's closed forms for lines, circles and ellipses against planes and cylinders, and for every other analytic pair the bounded root isolation in `hits.rs`, which takes a piece as given (a hit at its end is a touch) and never samples. `BooleanResult::merged` lists, per face, every face of the operands it has a piece of; `BooleanOptions::trust_operands` skips the validity check of operands the kernel itself returned.

**Tolerances.** Points within half the linear tolerance are one vertex; between that and twice the tolerance the operation refuses. The same holds for faces: two faces on one surface, or on surfaces that never cross, are the same surface within half the tolerance of each other where one is over the other, apart at twice the tolerance or more, and refused in between. Joined faces are not moved onto each other: the volume of such a result is right to the area in contact times the gap. The counterpart for faces of different kinds (a ball that dips into a plate, a torus lying a hair too deep in a block): beside every curve in which two faces cross, `section::passage` walks one surface away from the curve both ways until it is twice the tolerance from the other. Where that happens on opposite sides of the other surface the faces cross, exactly as given. Where it happens on the same side, the surface went through the other and came back: a lens thinner than twice the tolerance, whose thickness is measured; up to half the tolerance the faces touch and nothing is imprinted, above it the operation refuses. A body ten tolerances thick is a body. No decision is taken on the sign of a number that could be rounding: membership is a winding number, a root is isolated by a bound and not by sampling, and what cannot be told is refused.

**Speed (2026-10-13).** Measured by stage on a cylinder through a plate with 1024 holes (1030 faces): classification 73 %, section 24 %, both from asking every boundary piece of a face with a thousand loops about every point. Now each outline keeps a box per boundary piece, sorted along x (`outline::Boxes`), and "is anything nearer than r" looks at the few pieces near the point; in a plane a loop is not followed around a point outside its box; edges are split only near a vertex; a region is classified by one point, the others being looked for only when it does not decide; a whole face away from the other solid's box is outside it. Bit-identical results (a digest of every result of the corpus and the random runs is printed by the tests). 100 holes one by one 371 → 134 ms, 1024 holes 82 → 9.9 s, the cylinder through the 1030-face plate 269 → 47 ms, two plates of 1030 faces each 0.64 to 0.85 s per operation.

**Freeform faces (2026-10-13, `boolean/freeform.rs`).** A Bézier or B-spline face is indexed by a `PatchTree`: the surface as Bézier pieces (`geom`: `NurbsSurface::bezier_spans` by knot insertion, `RationalBezierPatch` with de Casteljau splitting), each quartered five times, with the box of every piece's control net (the piece lies in it). The tree answers what the booleans ask of a surface: a bound below the distance from a point to the surface that never overestimates (the distance to the nearest box, split further on the spot to a quarter of the tolerance or of the distance), which is what calls a stretch of a curve provably clear of the surface in the root isolation of `hits.rs`; the nearest point, by Newton's iteration (second derivatives from differences of the first, steps held to the domain's sides) from the middle of the nearest piece and from every piece whose box is nearer than the best point found; the signed distance; and a bound on how fast the parameters change per length travelled on the surface (the smallest singular value of the Jacobian, from the Bézier nets of the derivatives and of the normal field), which the chart of the face needs: a freeform face's chart is its own parameter rectangle, reached through the nearest point. A `Sheet` (a surface with its index) is what the helpers of `outline`, `hits`, `section`, `classify`, `regions` and `chart` take; an `Outline` builds the tree for a freeform face once and shares it with the pieces of the face. The hull of a freeform face includes its control net. Where a freeform surface meets another, the surfaces count as crossing (no lens is looked for). A NURBS surface or curve evaluated beyond its domain continues the end span's polynomial, as a Bézier does, because the marcher of the surface intersections needs something to correct onto past a border. Since the evening of 2026-10-13 the root isolation (`hits.rs`, `numeric`) judges a whole stretch of a curve against a freeform face at once wherever the curve's bend is bounded (lines, circles, ellipses, polynomial splines; a rational spline falls back to the piecewise judgement): a stretch on the surface is proven to stay within the tolerance from the distances at its ends and a bound on the surface's second derivatives over its domain (from the Bézier nets: the difference between curve and surface along the parameter path between the feet stays within an eighth of the bend, `PatchTree::stretch_within`); a stretch beside it is proven clear by a lower bound on the distance from its chord to the surface (`segment_lower_bound`; the distance from a segment to a box is exact, one convex quadratic per side crossing) less how far the curve can leave the chord. The tree bounds its pieces by boxes in the piece's own frame (as thick as the piece bends, not as it tilts: a tilted piece's axis-aligned box is as thick as the piece is wide, which left a curve at 1.06 tolerances from a face unprovable), takes a threshold above which nothing matters, and the point bound is only asked where it can prove something. The slowest corpus case (a contact of two spline-roofed blocks, 200 s per boolean) takes 0.19 s.

**Not done:** rational freeform faces and freeform faces whose parametrisation stalls; a lens between a freeform surface and another; speed (a boolean of a domed block and a block takes about 0.1 s, most of it nearest-point searches); a spatial index over the faces of a body (every face pair is still tested by box and by side); an untouched operand does not come back with its entities in their old order.

### 5.4 Sketch solver (`solve`)

A 2D geometric constraint solver: entities become unknowns, constraints become equations, solved numerically (Newton-type with a rank-revealing step) from the stored previous solution. It reports degrees of freedom, which constraints are redundant or conflicting, and never loops forever (iteration cap → `DidNotConverge`). Dragging (later, with the UI) is the same solve with a soft target. Decomposition into small sub-problems is an optimisation for later; correctness and diagnostics come first.

As built (M5): the unknowns are point coordinates and circle radii; gradients are exact (forward-mode dual numbers); the Jacobian is factorised row by row in the order the constraints were added, so a row that depends on earlier ones marks its constraint as redundant (it holds) or conflicting (it does not). When the whole system does not converge, constraints are added one at a time from the solution of the earlier ones, and one that cannot be added is blamed. That diagnosis is this solver's verdict, not a proof. A constraint that has no value where the others put the sketch (an angle on a line that shrank to a point) is conflicting too, with the reason. `solve` repeats its pass from its own result until nothing changes, so `Ok` means that solving again gives the same coordinates, bit for bit, and the same verdict. `regen::settle_sketches` still does not store a solution with a conflict in it: a collapsed line no longer says which way it pointed, and the stored shape is what brings the sketch back on the same side. Steps are minimum-norm with a line search, so free geometry moves as little as possible and mirror choices (which side of a line, inside or outside a circle) follow the starting point. An angle is signed: counter-clockwise from the first line's direction to the second's.

### 5.5 Regeneration (`regen`)

`regen` walks `Document::features` in order and produces, per feature, a status (`Ok`, `Suppressed`, `Failed { reason }`, `Skipped` because an input failed) and the bodies that exist after it.

- **Incremental.** Each feature's result is cached under a key made of its own parameters (after expression evaluation) and the keys of its inputs. Editing feature *k* reuses 0..k-1 untouched and recomputes only the features that depend on what changed. *As built (M6, `regen/src/cache.rs`):* the key is the feature's definition, the values of its expressions, the document's units and tolerance, and for every feature it is made from (directly or through others) the stamp of that feature's result and who had taken its body. A rebuilt result that equals the old one keeps its stamp, so a change that makes no difference stops there. Sketch solves are cached on their own (a sketch solves the same wherever it lies), which also spares the solve that stores a sketch's solution after an edit. The cache lives with the open document; `regenerate_cached` returns exactly what `regenerate` returns, and the test suites hold it to that after every command.
- **Variables first.** The variable table is evaluated in its stored order; a cycle or a dimension error fails only the features that use the affected variables.
- **Partial success is normal.** A failed feature does not discard the model: bodies up to the failure stay available and renderable, and the failure is data an agent can read (`document.inspect`).
- **Background jobs.** Regeneration runs on the job pool from a snapshot and commits its result if the document has not changed in a conflicting way.

## 6. Tessellator (`tess`)

`tessellate(&Body, &TessParams, cancel) -> Result<Mesh, TessError>` with `TessParams { chordal_tolerance, angular_tolerance, max_edge_length }`.

- **Edges first, then faces.** Each edge is discretised once; both faces sharing it use the same points, so the mesh of a solid is **watertight by construction**: no cracks, no T-junctions.
- **An edge is as fine as its faces need** (as built 2026-10-13). The points of an edge are first chosen for its curve alone, within the chordal tolerance. A face may need more: where another of its edges comes nearer than the tolerance, the chords of a curved edge cross it and no longer bound the face (a hole close to a rim, a notch that stops just short of an arc); and close to a pole of a sphere a chord is far from the straight segment the triangulation takes it for in parameter space. And a face may be narrower than the tolerance altogether: between a line and a flat arc from the same vertex to the same vertex the arc is one chord and the loop a line there and back, which encloses nothing; such a face asks for every chord of its curved edges. Before it is triangulated, each face names the chords it cannot do with; they are cut in two on the curve, for every face that uses the edge, and the faces concerned are done again. At most 12 rounds, an edge growing to at most four times its points and 32 more; each round is the same for any number of threads. What is left after that is the error it always was (edges that really cross). `tessellate_edges` goes through the same rounds, so its polylines are the borders of the mesh; `tessellate_body_and_edges` gives both for the work of one.
- **No size of its own** (2026-10-13). Nothing in the tessellator is a length: every threshold is a ratio (of the chordal tolerance, of an edge's parameter range, of a face's own extent). A body and its tolerance made *k* times as large give the same mesh *k* times as large: bit for bit when *k* is a power of two, where scaling does not round (`crates/tess/tests/scale.rs`, and for boolean results `crates/testkit/tests/self_intersection.rs`). For other *k* the edges get the same points to rounding; the triangles between them may differ where two triangulations are equally good (four points of a grid on a cylinder lie on one circle, and the last bit chooses the diagonal), so those meshes are the same surface, not the same triangles. A knot of a spline edge is a point of the edge only when it is inside the edge's range by more than 1e-9 of that range: an edge cut from a spline at a knot may start a rounding error before it.
- **Closed surfaces** (as built 2026-10-13). A face is to the left of its loops. On a sphere, loops that all run clockwise bound everything outside them: the face is the whole sphere with those loops as holes (a ball with a hole drilled across the sphere's axis), cut open along a meridian that no hole lies on. The same on a torus is not handled yet.
- **The seam of a face that goes around its surface** (as built 2026-10-13). Such a face (a wall between two circles, a zone of a sphere, a cap up to a pole, a band of a torus around its axis or around its tube) is cut open in parameter space along a seam from its lower winding loop, or the lower end of the surface, to the upper one; the two sides of the cut are the same curve in space and get the same points. A straight seam is tried first, at sixteen places, and is what an ordinary face gets. When the other loops are in the way of every one of them (seven blade roots that together cover the circumference of a turbine hub; two rows of holes, the second row half a pitch further), the seam is made of straight pieces from loop to loop: it enters a hole at one of its vertices and goes on from another, and the two stretches of the hole between those vertices become part of the two sides of the cut, one a period further than the other. The pieces are found by triangulating the loops, laid out three times side by side, with our own constrained Delaunay triangulation: no edge of it crosses a loop, so every edge between two different loops is a piece a seam can use, and the edges join the lower side to the upper because the face is connected. The seam is the chain with the fewest pieces (breadth first, short edges first); every piece is tested once more against all loops and against the pieces before it and their copies a period away. It costs nothing where a straight seam exists. Covered: cylinder, cone (also from its apex), sphere (zone, cap to a pole, whole sphere with holes), torus bands both ways, as the surface has them and reversed (`crates/tess/tests/winding_seam.rs`, closed-form areas at three sizes; `crates/testkit/tests/winding_seam_solids.rs`, a pipe drilled by the boolean kernel). A face for which no seam is found asks for finer chords first (chords too coarse can close the way between two loops) and is `Unsupported` after that.
- **Interior points keep their distance from the boundary** (2026-10-13). A grid point is left out when it is nearer than 0.3 of a grid step to any constraint, also one that is not an edge of the triangle the point falls in (the fan around a corner of a hole; found by walking the triangles within that distance, 64 at most). A point just above a chord of a hole, between the chord and its arc, makes a triangle that stands inside out, which refinement then never gets right.
- **Faces** are triangulated in parameter space (constrained Delaunay over the trimmed domain) with refinement until the surface deviation is within the chordal tolerance, then mapped to 3D. Planar faces need no refinement.
- **Output** keeps, per triangle, the face it came from (and per polyline, the edge), so the renderers can colour, select and pick by entity, and exporters can group.
- **Parallel per face** (rayon), merged in face order, so the result is identical for any thread count.
- **Our own triangulator.** No external triangulation or meshing library; this is part of "custom tessellator".
- **What a viewer draws: the display quality** (2026-10-13). The engine's scene (`Session::scene_with(SceneQuality)`, §8.5) is sampled at one of three qualities: `Automatic`, the chordal tolerance `view.render`, previews and `file.export` use when none is given (1e-3 of the model's size, the side of a square with the bodies' total area; without bodies, the diagonal of the sketches); `Tolerance(t)`, a tolerance in document units; and `Display { relative, max_triangles }`, what a viewport shows: `relative` times the model's size (3e-5 by default: on a model that fills a 1020-pixel viewport a chord error of a thirtieth of a pixel, so a circle stays round when the developer zooms in on a detail), coarsened until the scene has at most `max_triangles` (a million) triangles and every body is within the tessellator's reach, but never beyond the automatic tolerance, so the display is never coarser than the export. The coarsening is a ladder: a build with a budget stops at the first body after which the budget is exceeded, or that is too fine for the tessellator (`TessError::TooFine`), and the next tolerance is coarser by the ratio of the estimated total (the count so far over the share of the model's faces done) to the budget, at least twice and at most 64 times, six attempts at most; the scene says whether it was coarsened. The budget is the scene's, and it stops a body inside the tessellator (2026-10-13): the bodies are tessellated in feature order and each is given what the ones before it left (`TessParams::max_triangles`); the tessellator ends a body with `TessError::OverBudget` at the end of the first round of its faces in which they have more triangles than that, and ends that round as soon as the faces done show it (faces are done in parallel, each adds its triangles to a count, the ones not started are skipped). What it reports, and what the ladder's estimate takes, is the shortest run of faces from the first, in face order, whose triangles exceed the budget, as a single thread finds them: a function of the body and the parameters, not of the number of threads or of which finished first. So a scene within the budget is the scene built without one, bit for bit, and a scene over it is discarded; nothing in between. The granularity is a face: one face that alone exceeds the budget (a fine sphere) is still tessellated in full. Export, `view.render` and previews pass no budget. Measured on the plate with 1024 holes, asked for at 1e-6 of its size (647,180 triangles in full; processor time on a machine busy with other builds, relative to that full tessellation in the same run): a budget of 100,000 triangles took 0.79 of it before and takes 0.43 now, one of 30,000 took 0.78 and takes 0.24 (2.0 s against 6.7 s on the clock); the ladder ends at the same tolerance in 9 of 13 budgets on the part of `crates/engine/tests/scene.rs` and at a neighbouring one in the others (finer in 3, coarser in 1), because the estimate is now taken at the face that crossed the budget, not at the end of its body. Measured (release, 2026-10-13, `crates/engine/tests/scene_bench.rs`): a flange with six bolt holes, 820 triangles at the automatic tolerance and 4328 at the display quality, about 10 ms either way; a plate with 1024 holes (1030 faces), 24,588 triangles in 666 ms and 122,892 in 776 ms; the tessellator's cost beyond about 0.6 ms per face is about 1.5 µs per triangle, which is what the budget bounds.

- **Self-intersections of a mesh** (`tess::self_intersections(&Mesh, tolerance, limit)`, as built 2026-10-13): the pairs of triangles that cross or overlap although they are not neighbours. *Whether* two triangles meet is decided exactly: orientation predicates evaluated in `f64` with an error bound and, where that cannot tell, again without rounding as sums of non-overlapping `f64` (`exact.rs`, after Shewchuk 1997; our own code, no dependency), because the triangles of a planar face are coplanar to the last bit or a rounding error from it. Neighbours (bit-identical corners) meet only beyond what they share. *How deep* is a measure in `f64`: how far the surface around one triangle reaches on both sides of the other inside the column over it, the smaller of the two directions, so that contact has depth zero and a tip that pricks a surface has the depth of the prick (the column is a hair wider than its triangle only across an edge beyond which the surface goes on, so that what stands exactly on a seam of the triangulation passes through; where the surface turns away square, as around an edge along which two parts of a body meet, what stands on the edge touches); for triangles in one plane, the width of their common area. Candidates come from a bounding-volume hierarchy, searched on several threads (`std::thread::scope`, as the tessellator does) and merged in triangle order.

Mesh invariants are tested, not hoped for: closed 2-manifold for a solid, consistent outward orientation, no degenerate triangles, deviation from the surface within tolerance, mesh volume converging to the B-rep volume as the tolerance shrinks.

## 7. Rendering

Display is the one place with two implementations.

### 7.1 Draw list

`render` and `gpu` consume the same data: meshes and edge polylines from `tess` with entity ids, a camera (orthographic or perspective), lights, a display mode (shaded, shaded with edges, wireframe, hidden-line later) and per-entity colours and selection state. Nothing about display leaks into `kernel` or `tess`.

### 7.2 Backends

- **CPU (`render`).** The reference implementation: a software rasteriser with a depth buffer, flat/smooth shading, edge overlay, and an **id buffer** (which face or edge is under each pixel). Used by tests, the CLI (`craft3d-cli render`), MCP previews, `ui.screenshot`, and as the fallback in the viewport when no GPU is available or asked for (`--renderer cpu`). It favours exactness and readability over speed.
- **GPU (`gpu`).** wgpu (Vulkan, Metal, DX12, OpenGL, WebGPU) pipelines for the same draw list; picking reads the id buffer. The scene pass draws one sample per pixel into targets `ssaa` times larger per axis (an `Rgba8Unorm` colour target, an `Rg32Uint` target with the face id and the bits of the view distance, a `Depth32Float` buffer with near and far fitted to the mesh per frame); a resolve pass takes the rounded integer mean of the colour samples and the first sample's id and distance, exactly as the CPU renderer ends. Positions go to the GPU in `f32` relative to the centre of the mesh; the camera is computed in `f64` and narrowed last. That is the crate's `Offscreen` and `Renderer`, which read the frame back. **The viewport of the desktop app draws with the crate's `Onscreen`** (2026-10-13) on the window's own wgpu device, into a texture egui shows as it is: nothing is read back for display. Its scene pass draws the same shader into a colour target and depth buffer with 4 samples per pixel (MSAA; 1 where the adapter has no multisampling for the formats, and on wgpu's OpenGL backend, which resolved nothing out of a multisampled attachment on the development machine), shading once per pixel at its centre, exactly where the CPU renderer samples for `ssaa = 1`; a second pass draws the lines over the picture (the edges of the bodies, the world axes, the sketches, the sketch points) as screen-space quads inked by the distance of the pixel's centre to the segment (the CPU viewport's `draw_line`), each tested in the fragment shader against the depth buffer with the CPU viewport's rule (a point is behind a body only when the surface under its pixel and the eight around it is nearer, with the slack the GPU frame gets; a hidden edge is left out, a hidden sketch drawn dimmed), and resolves the samples into the shown texture. The GPU tests against the true depth where the CPU viewport tests against its frame's screen-interpolated distance, so the GPU allows a line the depth spread of the nine pixels as well: that keeps the edge in the hollow where two surfaces meet visible, as the CPU's interpolation happens to. A third pass, only when asked, draws face ids and distances at one sample per pixel (for the tests, and for picking later). Three differences are known and documented in the crate: a triangle that crosses the eye plane is clipped where the CPU renderer drops it whole, a triangle with a corner that does not fit in `f32` is not drawn, and a sample exactly on an edge follows the GPU's top-left rule.
- **Parity tests** (`crates/gpu/tests/parity.rs`; the derivations are in `crates/gpu/tests/common/mod.rs`). 75 scenes (the Utah teapot, the sixteen reference solids of the test kit tilted at scales 1e-3, 1 and 1e6 and once ten million units from the origin, and hand-made awkward meshes), in perspective and orthographic, at supersampling 1 to 4, on every adapter of the machine. **The documented tolerance** is:
  - *The band.* The GPU's rasteriser snaps projected vertices to a grid of 2⁻⁸ pixel, so the renderers can disagree about a sample only within 2⁻⁸ pixel of a triangle's edge, and that shows only where the surface under the sample changes. The band is every pixel within one pixel of a projected *feature edge* (a face's border, an edge with one triangle, a silhouette edge) or of a change of face id in the CPU frame. It is computed from the mesh, the camera and the CPU frame, never from the GPU frame, and must leave more than half of the picture.
  - *Face ids:* equal outside the band. Inside it at most 1/128 of the band's pixels may differ (the probability that an edge passes within 2⁻⁸ pixel of a pixel's centre).
  - *Distance* outside the band: within `2⁻²⁰ · reach + 2⁻⁷ · G`, where `reach` is the eye's distance to the mesh centre plus the mesh diagonal (sixteen `f32` roundings of 2⁻²⁴ on numbers that large) and `G` is the largest difference to the eight neighbouring pixels in the CPU frame (the gradient, times one grid step, doubled).
  - *Colour* outside the band: at most 1/255 per channel, with no exceptions (both renderers round per sample; a value within the `f32` error of a half-integer rounds the other way), plus `2⁻⁷ · Gc` levels where the CPU picture itself changes by `Gc` between neighbours, which is a second level only next to a jump of 128 or more. The number of pixels that differ by that one level is bounded too, by the sum over the pixels of `2 · (2⁻⁷ · Gc + 0.004)`: a systematic error such as a truncated mean exceeds it. Inside the band at most 1/128 of the pixels may differ by more than a level.

  Measured on the three adapters of the development machine (Intel Vulkan, lavapipe, Intel OpenGL): no id differs outside the band, at most 0.07 % of a scene's pixels outside the band differ by one level and none by two, the largest distance error is 39 % of its tolerance, and at most 0.14 % of a band's pixels differ. The tests **fail** when no adapter is found, with the way to get one (`mesa-vulkan-drivers` gives lavapipe); they do not skip.
  - *The multisampled picture* (`crates/gpu/tests/onscreen.rs`, `compare_msaa` in the same `common/mod.rs`) is compared with the CPU frame at `ssaa = 1`, with the ids and distances of the capture pass, under the same tolerance with two exceptions that follow from multisampling: inside the band the colour is not compared at all (the samples lie on both sides of a feature edge and the resolved colour is their blend: the anti-aliasing; the number of such pixels is measured and must be more than a twentieth of the band), and on a *seam* (within a pixel of an interior triangle edge of one face) a pixel may mix two fragments, each shaded at the pixel centre from its own triangle's interpolated normal, so it is allowed `1 + Gc` levels, a pixel of the CPU picture's own gradient. Measured on the development machine: away from every edge not one pixel of the teapot or the block differs by a level, at most 6 seam pixels of a scene differ by more than a level, and about a tenth of the band is blended. The lines are checked on a block with lines behind, before, on and beside it (dimmed, left out, whole), and `crates/ui-egui/tests/gpu_viewport.rs` draws the viewport's own scene through the shell on a device made as eframe makes the window's and compares the shown picture with the CPU picture (bodies and inked lines) the same way, sampling every line of the overlay to check that the GPU hid, dimmed and drew what the CPU decided: 1812 of 1812 samples agree.

### 7.3 What the oracle is for

In PhotoCraft the CPU compositor defines what the image *is*. Here the model's truth is the B-rep and its mass properties, not the picture. The CPU renderer is the oracle for **display** only: it lets agents and the developer see a model without a GPU, and it catches GPU regressions. Geometric correctness is tested geometrically ([`testing.md`](testing.md)).

## 8. Engine (`craft3d-engine`)

### 8.1 `Session`: commands in, events out

```rust
pub struct Session { /* docs, registry, job pool, prefs, services */ }

impl Session {
    pub fn new(services: Services) -> Self;                         // platform functions injected
    pub fn dispatch(&self, doc: Option<DocId>, cmd: CommandInvocation) -> Result<JobHandle, CommandError>;
    pub fn registry(&self) -> &CommandRegistry;
    pub fn snapshot(&self, doc: DocId) -> Arc<DocSnapshot>;         // lock-free read: document + regeneration result
    pub fn events(&self) -> EventReceiver;                          // DocChanged, RegenProgress, FeatureFailed, …
}

pub struct CommandInvocation { pub id: CommandId, pub params: serde_json::Value /* validated against the schema */ }
```

### 8.2 `CommandRegistry`

Each command registers `id` (`"feature.extrude"`), `label`, an optional `menu_path` and shortcut (unused in phase 1), a parameter schema with a one-line params doc agents can read, `enabled(&DocSnapshot) -> bool` with a reason when disabled, and `run`. `run` returns a JSON result and records exactly **one** history step.

Command families (ids are settled when each is implemented, and are stable afterwards):

| Family | Examples |
|---|---|
| `file.*` | `file.new`, `file.open`, `file.save`, `file.close`, `file.export` (the format from the file name or `format`: STEP or a mesh format for every body, DXF or SVG for the outline of a `sketch` or of a flat `face`) |
| `edit.*` | `edit.undo`, `edit.redo` |
| `variable.*` | `variable.set`, `variable.delete`, `variable.rename` |
| `sketch.*` | `sketch.create`, `sketch.addLine`, `sketch.addArc`, `sketch.addCircle`, `sketch.constrain`, `sketch.solve` |
| `feature.*` | `feature.primitive.box`, `feature.extrude`, `feature.revolve`, `feature.boolean`, `feature.fillet`, `feature.edit`, `feature.suppress`, `feature.delete`, `feature.reorder` |
| `history.*` | `history.rollback`, `history.regenerate` |
| `document.*` | `document.inspect`, `document.measure` (volume, area, centroid, bounding box, distances), `document.check` (validity report) |
| `view.*` | `view.render` (PNG from a named or explicit camera, CPU or GPU) |

**Inspection is a first-class command.** `document.inspect` returns the feature tree with per-feature status, variables with values, sketches with their degrees of freedom, and bodies with face/edge counts, persistent names and mass properties. An agent must be able to verify what it did from JSON alone, and use `view.render` when it needs to look.

### 8.3 Operations and history (`ops`)

Every mutation of a document is an `Op` (`SetVariable`, `AddFeature`, `EditFeature`, `ReorderFeature`, `AddConstraint`, …). A command produces a labelled `Transaction` of ops. Undo history stores transactions; because documents are persistent data, a "before" state costs only what changed. Undo history (session-only, what the user did) is distinct from the **design history** (the feature list, saved in the file).

### 8.4 Runtime model

```text
 Client (UI / CLI / control / MCP) ──dispatch()──► Engine thread (owns mutable docs, applies ops, publishes snapshots)
        ▲                                               │ spawns
        │ events (changed, progress, failed)            ▼
        │                                   Job pool (rayon): regeneration, tessellation, export, autosave
        │                                   read snapshots, return results
 Viewport: render(snapshot) on GPU or CPU
```

Every job takes a `CancelToken`. Services injected into `Session`: file system (native fs / in-memory for tests / browser later), clock, notifier.

### 8.5 The UI-swap seam

A frontend needs four things from the core: `Session` (commands in, events out), the `CommandRegistry` (metadata), snapshots with view-models (feature tree, variable table, inspector as plain structs), and a renderer it can host (`gpu::Onscreen` on the host's own device into a texture it shows, or `render` into an RGBA buffer; the egui shell today hosts the first as `ui_egui::direct::Direct` when the window lends it the device, and otherwise `ui_egui::backend::BodyRenderer`, which gives it a `Frame` from the GPU read back or from the CPU). Interactive tools (sketching with the mouse, dragging a face) come after phase 1 and follow PhotoCraft's pattern: pointer events in, ops and overlay primitives out, so the control channel can replay them.

**Litmus test:** `craft3d-cli` and the automation server can do everything the GUI does.
